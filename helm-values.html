Values

O site da Ana subiu em produção com uma linha de comando de quatrocentos caracteres: doze --set, um -f e um --namespace. Funcionou. Três semanas depois, ao refazer o deploy num cluster novo, ninguém conseguiu repetir a linha — ela estava no histórico do terminal de alguém que saiu de férias. O values é a parte do Helm que resolve isso: os valores de cada ambiente em arquivo, versionados junto com o chart, e a linha de comando voltando a ter vinte caracteres.

Você vai aprender
  • Como os values chegam ao template, em cascata.
  • A precedência: defaults do chart, arquivos -f e --set.
  • Como organizar um arquivo de valores por ambiente.
  • O que os values viram no cluster: réplicas, imagem e configuração.
  • As formas de passar valor e em que cada uma é melhor.
  • Por que o --set para tudo vira dívida técnica — e o que fazer no lugar.

1. A cena: a linha de comando que ninguém sabe refazer

O comando original era mais ou menos assim: helm install cardapio ./cardapio --set replicaCount=4 --set image.tag=2.0 --set resources.limits.memory=512Mi --set service.targetPort=8080 --set ingress.host=cardapio.loja.test ... e continuava por mais sete flags. Cada uma foi acrescentada num dia diferente, resolvendo um problema real.

O problema aparece quando alguém precisa repetir aquilo: um ambiente novo, um cluster de recuperação, uma revisão de auditoria. O comando não está em lugar nenhum além do histórico de um terminal, e quem o digitou não lembra por que memory é 512Mi (e não 256Mi) nem se aquele targetPort ainda é necessário.

A solução do Helm é simples e é a mesma do resto do guia: o que é configuração sai da linha de comando e vai para um arquivo versionado. O comando volta a ser helm upgrade cardapio ./cardapio -f values-producao.yaml, e a diferença entre os ambientes fica visível num diff.

2. Como os values chegam ao template

Dentro do template, tudo o que o chart recebe aparece em .Values. O que chega ali é o resultado de uma cascata, e entender a ordem é o que evita a frase “mas eu passei o valor e ele não pegou”.

values.yaml
O arquivo de padrões dentro do chart. É o primeiro da cascata e o que serve de documentação.
-f / --values
Um arquivo extra de valores. Pode ser repetido; o último da linha vence quando os dois definem a mesma chave.
--set
Um valor solto na linha de comando, em notação de pontos: image.tag=2.0. Tem a maior precedência.
--set-string
Igual ao --set, mas força o valor a ser texto. Serve para tags como 1.0.
precedência
A ordem em que as fontes se sobrepõem: padrões, depois arquivos, depois linha de comando.
revisão
Cada upgrade guarda os values usados, e eles podem ser lidos depois com helm get values.

Uma consequência que vale destacar: a cascata é por chave, não por bloco. Se o values.yaml do chart define resources.limits.memory: 256Mi e o seu arquivo de produção define resources.limits.memory: 512Mi, o resto do bloco resources continua vindo do padrão. Você não precisa repetir o que não muda — e é por isso que um arquivo de ambiente costuma ser curto.

3. O values.yaml do chart

O arquivo de padrões é a interface do chart com quem instala. Um bom values.yaml tem os valores que fazem sentido em qualquer ambiente e um comentário em cada bloco explicando o que ele controla.

replicaCount: 1
image:
  repository: cardapio
  tag: "1.0"
  pullPolicy: IfNotPresent
service:
  port: 80
  targetPort: 8080
ambiente: teste
config:
  porta: "8080"
  log: "info"

Note a escolha de ambiente: teste como padrão. Poderia ser producao, mas o padrão seguro é o ambiente menos perigoso: quem instala em produção precisa dizer isso explicitamente, e quem esquece não derruba nada importante. O mesmo raciocínio vale para replicaCount: 1 e para tags conservadoras.

Note também as aspas em tag: "1.0" e porta: "8080". Sem elas, o YAML lê 1.0 como número e 8080 como inteiro. Em campos que o Kubernetes espera como texto — como o conteúdo de um ConfigMap — isso gera erro de tipo na hora de aplicar. A regra prática: número que não vai ser usado em conta vai entre aspas.

4. Um arquivo por ambiente

Com o padrão no chart, cada ambiente ganha o seu arquivo, com só o que muda. O de produção da padaria tem quatro linhas de conteúdo:

replicaCount: 3
image:
  tag: "2.0"
ambiente: producao
config:
  log: "warn"

Quatro linhas contra as doze --set do começo da aula, e agora elas estão num arquivo que aparece no diff, que tem autor e que pode ser revisado. O de teste pode ser ainda menor — às vezes vazio, porque os padrões já são de teste.

Onde guardar esses arquivos é decisão de time. Duas opções comuns: dentro do chart, numa pasta values/ (útil quando o chart é do próprio time), ou num repositório separado, ao lado dos manifestos de cada ambiente (útil quando o chart é de terceiro e você só guarda as sobrescritas). A regra é uma só: os arquivos entram no controle de versão junto com o que os usa.

Uma armadilha de organização: não crie values-producao.yaml com o arquivo inteiro copiado. A cópia inteira funciona hoje e cria um problema amanhã — quando o chart ganhar uma chave nova com padrão seguro, o arquivo copiado não terá essa chave e a instalação ficará com comportamento diferente do resto. Sobrescreva só o que muda.

5. A precedência, na prática

Quando duas fontes definem a mesma chave, uma vence. A ordem é fixa e vale a pena decorar, porque é ela que explica a maioria dos “não pegou”.

OrdemFonteVence quando
1º (mais fraco)values.yaml do chartnada mais define a chave
2º-f arquivo1.yaml -f arquivo2.yamlo último arquivo que define a chave ganha
3º (mais forte)--set e --set-stringsempre, para a chave que ele define

Dois detalhes que só aparecem na prática. O primeiro: a ordem dos -f importa, e é comum ver um arquivo comum seguido do arquivo do ambiente — -f values.yaml -f values-producao.yaml — para que o segundo refine o primeiro. O segundo: --set ganha de todos, inclusive do -f que veio depois dele na linha. Não é ordem de leitura; é força.

Existe um jeito de conferir tudo isso sem instalar: helm template renderiza com os values da linha de comando e mostra o manifesto final. Se o valor não apareceu onde você esperava, o problema está na cascata ou no nome da chave — e não no cluster.

6. O que os values viram: réplicas

O caso mais simples é o número de réplicas, porque ele vai direto do values para o campo do Deployment. O manifesto abaixo é o que o chart renderiza quando replicaCount vale 3. Ele está com uma réplica: ajuste e rode.

O values de produção diz replicaCount: 3. Ponha três réplicas no Deployment e confira na tabela.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080
deployment.apps/cardapio created

NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   1/1     1            1           2m

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 3
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080

Depois de aplicar, o painel mostra três pods e o Deployment com 3/3 prontos. É a mudança mais comum de um upgrade e a mais barata: o controlador cria as réplicas que faltam sem recriar as existentes.

O detalhe que pega iniciante: --set replicaCount=3 na linha de comando também funciona, e é para lá que a maioria corre. Só que esse três não fica registrado em lugar nenhum revisável — fica no histórico da release, que é uma tabela difícil de comparar. O arquivo de valores é lido, revisado e discutido; o --set é esquecido.

7. O que os values viram: imagem e tag

A segunda mudança clássica é a imagem. Aqui o Helm não faz nada especial: ele só troca o texto que o template renderiza. O efeito no cluster é o de sempre — imagem nova significa ReplicaSet novo e rollout. Vale dizer que o Helm não faz rollout progressivo próprio: quem faz é o Deployment, com as regras que já vimos.

O values de produção usa a tag 2.0. Troque a imagem para cardapio:2.0 e mantenha duas réplicas.

kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080
deployment.apps/cardapio created

NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   2/2     2            2           2m

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 2

    matchLabels:
      app: cardapio

        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:2.0
          ports:
            - containerPort: 8080

Essa é a mudança que mais aparece em produção e a que mais precisa de disciplina: a tag precisa ser única por build (nada de latest), e o values precisa dizer exatamente qual tag está no ar. Com latest, dois ambientes podem estar rodando imagens diferentes com o mesmo values — e o diagnóstico vira especulação.

Um cuidado com --set image.tag=2.0: o Helm interpreta 2.0 como número e tenta converter. Em muitos casos ele avisa e usa 2, e o resultado é a imagem cardapio:2. Para tags assim, use --set-string image.tag=2.0 ou, melhor ainda, o arquivo de valores, onde as aspas resolvem o problema na origem.

8. O que os values viram: configuração

A terceira mudança típica é a configuração do programa: uma porta, um nível de log, um endereço. Nos charts bem feitos, isso vira um ConfigMap — e aí o values precisa de um cuidado extra, porque o conteúdo de ConfigMap é sempre texto.

O values de produção define as chaves PORTA (8080) e AMBIENTE (producao). Renomeie as chaves no ConfigMap — o programa lê exatamente esses dois nomes.

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio-config
  labels:
    app: cardapio
data:
  port: "8080"
  env: "producao"
configmap/cardapio-config created

NAME              DATA   AGE
cardapio-config   2      2m

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio-config
  labels:
    app: cardapio
data:
  PORTA: "8080"
  AMBIENTE: "producao"

Repare que os valores continuam entre aspas. Num ConfigMap, o valor precisa ser texto; se o template renderizar PORTA: 8080 sem aspas, o cluster recusa com uma mensagem do tipo cannot unmarshal number into Go struct field ConfigMap.data of type string. É o erro que mais aparece em chart novo, e a causa quase sempre é o values.yaml sem aspas.

Quando a configuração cresce, o padrão do Helm é o oposto do que se vê por aí: em vez de uma chave por valor, um bloco inteiro de texto. O template usa {{ toYaml .Values.config | nindent 2 }} e o values guarda o bloco como uma árvore. Assim, acrescentar uma linha de configuração não exige mexer no template.

9. A dívida do --set

Agora a parte que dá título à aula. O --set não é proibido: para um teste rápido, para sobrescrever uma chave só num experimento, ele é a ferramenta certa. O problema é quando ele vira o jeito padrão de operar.

FormaServe bem paraCuidado
-f arquivo.yamlo que é do ambiente: réplicas, imagem, configuraçãoé o que se revisa e se versiona
--set chave=valorteste rápido, uma chave sónão fica no repositório; some com o terminal
--set-stringtag numérica como 1.0, conteúdo de ConfigMapforça texto e evita o número
--set-fileconteúdo de arquivo (ex.: um script, um certificado)o conteúdo inteiro vai parar no Secret da release

Listas são o caso em que o --set mais sofre. Para definir dois hosts de Ingress, a sintaxe é --set ingress.hosts[0]=cardapio.loja.test --set ingress.hosts[1]=pedidos.loja.test — e basta uma vírgula ou um colchete fora do lugar para o Helm interpretar outra coisa. Em arquivo, a mesma informação é uma lista YAML comum, com um item por linha, do jeito que você já escreve manifesto.

Outro limite: o --set sobrescreve, mas não remove. Se o padrão do chart traz ingress.enabled: true e você quer desligar, --set ingress.enabled=false funciona; agora, para apagar uma chave que veio de um -f, é --set chave=null, o que ninguém lembra na hora. Arquivo resolvido com um diff de duas linhas é mais claro do que qualquer malabarismo na linha de comando.

Três motivos concretos para preferir arquivo. O primeiro é a repetibilidade: o arquivo está no repositório, então qualquer pessoa refaz o deploy com o mesmo comando. O segundo é a legibilidade: vinte --set numa linha não são lidos por ninguém, e um diff de arquivo mostra exatamente o que mudou entre dois deploys.

O terceiro é o mais sério e quase ninguém pensa nele: os values passados por --set ficam gravados no Secret de histórico da release, em texto legível. Se alguém passar uma senha por ali, ela vira permanente e visível para quem lê Secrets no namespace. Senha vai em Secret criado à parte; o chart só referencia o nome.

Para saber o que foi passado numa release, existe helm get values, que mostra exatamente o que veio da linha de comando e dos arquivos (transcrição):

$ helm get values cardapio -n padaria-prod
USER-SUPPLIED VALUES:
ambiente: producao
config:
  log: warn
image:
  tag: 2.0
replicaCount: 3

É esse bloco que você compara com o do ambiente de teste para saber o que difere. E é esse bloco que deveria vir de um arquivo — porque ali ele está revisado, e no Secret ele é só consequência.

Um erro clássico de quem muda values é trocar algo que o Kubernetes não permite alterar depois. Mudar o selectors de um Deployment existente, por exemplo, é recusado pelo cluster, e a mensagem sai pelo Helm (transcrição):

$ helm upgrade cardapio ./cardapio -f values-producao.yaml
Error: UPGRADE FAILED: cannot patch "cardapio" with kind Deployment:
Deployment.apps "cardapio" is invalid: spec.selector: Invalid value:
v1.LabelSelector{MatchLabels:map[string]string{"app":"cardapio-novo"}}:
field is immutable

Nesse caso não é o values que está errado — é o tipo de mudança. Campo imutável exige apagar e recriar o objeto (o que, em produção, é um deploy com downtime planejado, não um ajuste de values).

10. Cenários do dia a dia

Cenário 1: o --set esquecido no deploy seguinte

Um --set resources.limits.memory=512Mi foi passado uma vez, num dia de pico. Meses depois, um upgrade com o arquivo de valores (que não tinha esse campo) devolveu o limite para o padrão do chart, e o pod passou a ser morto por memória. O valor estava no histórico da release, mas ninguém olhou.

Cenário 2: dois ambientes, um arquivo copiado

O values-homologacao.yaml foi criado copiando o de produção inteiro. Quando produção ganhou uma chave nova, homologação ficou com o comportamento antigo e o bug só apareceu lá. A correção foi reduzir cada arquivo ao que realmente difere — quatro ou cinco linhas — e deixar o resto no padrão do chart.

Cenário 3: a senha no Secret da release

Alguém passou --set postgresql.password=... num chart de banco. A release subiu, e a senha ficou gravada no Secret de histórico, legível por qualquer pessoa com permissão de leitura no namespace. A auditoria encontrou três meses depois. O conserto foi criar o Secret à parte e apontar o chart para ele.

Exercício: o arquivo de produção

Complete o comando para instalar o chart usando o arquivo de valores de produção, e o trecho do arquivo que define três réplicas.

helm upgrade cardapio ./cardapio values-producao.yaml # values-producao.yaml : 3

Dica: a flag que carrega arquivo de valores tem forma curta e longa; a chave do arquivo é a mesma que o template lê em .Values. Um --set depois dela ganharia desse valor.

12. Resumo

Values é a configuração do chart: o values.yaml traz os padrões, cada ambiente tem o seu arquivo com o que muda, e a linha de comando serve para ajustes pontuais. A cascata é values.yaml → arquivos -f (o último vence) → --set, e a sobreposição é por chave, não por bloco inteiro.

O que o values faz no cluster é sempre a mesma história: vira texto no template renderizado. Réplicas mudam sem recriar pods; imagem nova provoca rollout; configuração precisa de aspas, porque ConfigMap é texto. Campo imutável, como o selector, não se resolve com values.

E a dívida: --set para tudo é um comando que ninguém reconstrói, um diff que ninguém lê e um valor que fica gravado no Secret da release. Use arquivo para o que é do ambiente, --set só para o experimento do minuto. Na aula de Kustomize, a alternativa sem template para quem só quer sobrepor YAML: o Kustomize.

Para lembrar
  • Precedência: padrões do chart → -f (último vence) → --set.
  • Sobrescreva só o que muda; arquivo de ambiente copiado inteiro vira armadilha.
  • --set-string para tags numéricas e para conteúdo de ConfigMap.
  • Texto que vai para ConfigMap precisa estar entre aspas no values.
  • --set fica gravado no Secret da release: nada de senha por ali.
  • helm get values mostra o que foi sobrescrito; compare ambientes com ele.
