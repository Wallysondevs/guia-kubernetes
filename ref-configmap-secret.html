ConfigMap e Secret

A Ana abre esta página com pressa, no meio de um manifesto, procurando o nome exato de um campo. Ela já sabe o que é um ConfigMap e já criou um Secret no terminal; o que ela precisa agora é da consulta: qual é o campo, qual é o comando, o que o cluster aceita e o que ele recusa. É isso que está aqui — em tabelas, com o nome do campo na primeira coluna, para achar com Ctrl+F.

1. Para que serve esta página (e o que ela não cobre)

ConfigMap e Secret são os dois objetos que guardam configuração fora da imagem. A diferença de intenção é simples: o ConfigMap guarda o que pode ser lido em voz alta — preço, horário, endereço, nome da loja. O Secret guarda o que não pode aparecer num print de tela — senha, token, certificado.

Esta página é a consulta: os campos dos dois objetos, as formas de criar, a decisão entre env e volume, e o que o API server valida. Ela não reensina o assunto do zero e não substitui as aulas. Quando o texto disser “a aula X mostra o passo a passo”, é lá que está a história contada com a padaria.

O que fica de fora, de propósito: rotação de credencial, configuração imutável, envFrom com prefixo, montagem de arquivo único com subPath e os tipos de Secret um por um. Cada um tem a sua página, e no fim desta há o link de todas elas.

Uma coisa vale dizer antes da primeira tabela, porque é a confusão número um de quem começa: Secret não é criptografia. O valor em data é base64, que é codificação — qualquer pessoa decodifica em um comando. O que protege um Secret de verdade é RBAC, e disso trata a página de RBAC.

2. O essencial em 10 linhas

Se você só tem dois minutos, leia esta lista. Ela cabe numa tela e resolve a maior parte das dúvidas de consulta.

  1. ConfigMap guarda texto; Secret guarda segredo. Os dois são namespaced: só servem para pods do mesmo namespace.
  2. O campo principal dos dois é data, um mapa de chave e valor.
  3. No ConfigMap, o valor de data é texto puro. No Secret, é base64.
  4. ConfigMap tem binaryData para bytes; Secret tem stringData para texto puro que o cluster converte sozinho.
  5. Secret tem type (Opaque é o padrão); ConfigMap não tem.
  6. Chave válida: letras, números, hífen, sublinhado e ponto. Nada de espaço, barra ou acento.
  7. Os dois têm limite de 1 MiB por objeto e aceitam immutable: true.
  8. Para criar: kubectl create ... (rápido) ou kubectl apply -f (guardável).
  9. Para entregar ao pod: env/envFrom (variável) ou volume (arquivo).
  10. Variável é lida no start; volume é reescrito quando o objeto muda — e nunca nos dois casos com immutable.

O resto da página detalha cada linha. As duas últimas são as que mais causam dúvida na prática, então voltam em tabela própria na seção 5.

3. Anatomia: os campos dos dois objetos

Os dois objetos têm a mesma espinha: apiVersion, kind, metadata e os campos de conteúdo. O que muda é o que existe dentro do conteúdo. O dl abaixo é o mapa dos campos, na ordem em que eles aparecem num manifesto típico.

metadata.name
o nome do objeto, usado em toda referência. Minúsculas, números e hífen; até 253 caracteres. Precisa ser único dentro do namespace.
data
o mapa principal. No ConfigMap, valores de texto UTF-8; no Secret, valores em base64. É daqui que saem as chaves lidas por envFrom, configMapKeyRef e pelos volumes.
binaryData
só no ConfigMap: um segundo mapa, com valores em base64, para conteúdo binário (uma imagem pequena, um arquivo comprimido). Não serve para variável de ambiente, só para volume.
stringData
só no Secret: texto puro que o API server converte para base64 ao gravar. É o campo certo para escrever senha no manifesto sem calcular base64 na mão.
type
só no Secret: Opaque (padrão), kubernetes.io/tls, kubernetes.io/dockerconfigjson, kubernetes.io/basic-auth, entre outros. Muda as chaves obrigatórias e o que o cluster faz com o conteúdo.
immutable
booleano nos dois. true na criação significa que data e binaryData nunca mais mudam: qualquer edição é recusada com field is immutable.

Repare no que não existe: não há campo para “tipo” no ConfigMap, nem para “ambiente” (dev, prod) em nenhum dos dois. O ambiente se resolve com namespace e com o nome do objeto — cardapio-prod, cardapio-dev —, não com um campo mágico.

Também não há validação de conteúdo: o cluster não sabe se preco deveria ser número. Ele confere a forma (chave válida, base64 válido, tamanho), não o significado. Um ConfigMap com preco: "quatro e cinquenta" é aceito sem reclamar.

4. Os campos e as formas de criar

Há dois caminhos para criar: pelo terminal, com kubectl create, e pelo arquivo, com kubectl apply -f. O primeiro é bom para teste e para gerar o YAML a partir de um arquivo; o segundo é o que se guarda no repositório e se revisa em pull request.

ComandoO que criaQuando usar
kubectl create configmap cardapio --from-literal=preco=4.50ConfigMap com uma chave por --from-literalteste rápido, uma ou duas chaves
kubectl create configmap cardapio --from-file=cardapio.jsonConfigMap com uma chave igual ao nome do arquivoconfiguração que já vive num arquivo
kubectl create secret generic senhas --from-literal=senha=s3nh4Secret Opaque com o valor já em base64credencial de teste, sem passar pelo YAML
kubectl create secret tls loja-tls --cert=tls.crt --key=tls.keySecret do tipo kubernetes.io/tlscertificado para o Ingress

Nos dois casos, o comando só monta o objeto: o que ele grava no cluster é exatamente o que você veria no YAML. Por isso o hábito útil é --dry-run=client -o yaml, que imprime o manifesto sem aplicar — e aí você guarda o arquivo e passa a usar apply.

Na criação pelo arquivo, o campo metadata.name é a chave de tudo: é por ele que o apply decide se cria ou atualiza. Mudou o nome, mudou o objeto — o antigo continua lá, com o valor antigo, e o pod antigo continua lendo dele. É a origem do clássico “criei a configuração nova e o site não mudou”: o objeto é outro, e a referência no pod continua sendo o velho.

O namespace entra na mesma conta. Dois ConfigMaps com o mesmo nome, um em padaria e outro em default, são objetos diferentes e não se enxergam. Um pod no namespace default que aponta para cardapio nunca vai achar o ConfigMap de padaria, por mais que o nome esteja certo — é o erro de referência mais comum de todos, e ele não aparece no apply.

As duas linhas que mais confundem são stringData e binaryData. O primeiro é uma comodidade de escrita: você põe texto, o cluster guarda em base64, e na leitura o campo aparece dentro de data — stringData nunca é devolvido pelo get. O segundo é o contrário: um campo que já nasce em base64 e serve para bytes que não são texto.

Nos dois objetos, a chave tem as mesmas regras: começa e termina com letra ou número, e no meio aceita letra, número, hífen, sublinhado e ponto. preco, preco-promocao, db.host e LIMITE_PEDIDO são válidos. preço com cedilha, preco promo com espaço e preco/promo com barra não são.

5. Os campos que mais confundem

A decisão que aparece em todo manifesto de pod é variável ou arquivo. Os dois caminhos funcionam com ConfigMap e com Secret, e a escolha muda o que acontece quando o valor é editado. A tabela é curta porque a diferença é curta; o efeito, não.

Critérioenv / envFromvolume
forma no containervariável de ambienteum arquivo por chave, dentro de uma pasta
atualiza sem reiniciarnão: o valor é lido no start do containersim, com atraso de segundos a minutos
nome da variávelo da chave, ou o que você escolher com configMapKeyRefo da chave vira nome do arquivo; items renomeia e filtra
tamanho confortávelvalores curtosJSON, YAML, certificado, arquivo grande
erro se o objeto não existepod fica em CreateContainerConfigErrorpod fica em ContainerCreating, com evento de falha de montagem
melhor parapoucas chaves, lidas uma vezconfiguração que precisa de releitura

Um detalhe que vale para os dois caminhos: items só existe em volume. Com ele você escolhe quais chaves entram e com que nome de arquivo, o que resolve dois problemas de uma vez — não montar o ConfigMap inteiro e renomear a chave sem tocar no objeto.

Sobre base64, a frase que resolve a dúvida: é uma codificação reversível, não uma senha. O comando echo czNuaDQ= | base64 -d devolve s3nh4 em qualquer máquina. O que impede alguém de ler um Secret é a permissão (RBAC) e o cuidado de não versionar o valor em texto puro.

E sobre stringData: ele é mesclado em data na hora de gravar. Se a mesma chave aparecer nos dois campos, o valor de stringData é o que fica. Não é um lugar para guardar coisa diferente; é só uma forma mais legível de escrever a mesma coisa.

$ kubectl get secret senhas -o yaml
apiVersion: v1
kind: Secret
metadata:
  name: senhas
  namespace: padaria
type: Opaque
data:
  senha: czNuaDQ=
  usuario: YW5h

Essa é a saída de um cluster real, e ela mostra o que o get devolve: senha em base64, sem stringData em lugar nenhum. Se o YAML tivesse stringData, o valor apareceria aqui já convertido, dentro de data.

6. Erros e mensagens

O API server valida a forma do objeto antes de gravar. Quando recusa, a mensagem diz qual campo e por quê, no formato The ConfigMap "nome" is invalid: campo: motivo. As quatro mensagens abaixo cobrem quase tudo o que acontece na prática.

MensagemCausaO que fazer
a valid config key must consist of alphanumeric characters, '-' or '_'chave com espaço, barra, acento ou outro caractere proibidorenomear a chave; hífen, ponto e sublinhado são aceitos
illegal base64 data at input byte 4valor em data do Secret que não é base64codificar o valor ou escrever em stringData
cannot unmarshal number into Go struct fieldvalor sem aspas: preco: 4.50 vira número, não textopôr o valor entre aspas: "4.50"
Forbidden: field is immutabletentativa de editar um objeto com immutable: truecriar um objeto novo com outro nome e trocar a referência
configmap "cardapio" not foundo pod aponta para um objeto que não existe ou está em outro namespacecriar o objeto no mesmo namespace ou corrigir o name

Estas são duas recusas reais, na ordem em que um cluster de teste respondeu — a primeira de chave inválida, a segunda de base64 inválido:

$ kubectl apply -f cardapio.yaml
The ConfigMap "cardapio" is invalid: data[preco promo]: Invalid value: "preco promo": a valid config key must consist of alphanumeric characters, '-' or '_' (e.g. "key.name", "KEY_NAME", "key-name")

$ kubectl apply -f senhas.yaml
The Secret "senhas" is invalid: data[senha]: Invalid value: "s3nh4": illegal base64 data at input byte 4

Repare que a mensagem não fala de segurança nem de conteúdo: fala da forma. “A chave tem de ser alfanumérica com hífen ou sublinhado” e “o dado não é base64”. Consertar é literal — renomear a chave, codificar o valor — e não envolve reiniciar nada, porque o objeto nem chegou a ser gravado.

Quando o problema é de referência, o lugar de olhar é o evento. O comando filtra os eventos pelo nome do pod e mostra a mensagem exata do kubelet, que costuma ser mais específica do que o status:

$ kubectl get events --field-selector involvedObject.name=web
LAST SEEN   TYPE      REASON        OBJECT   MESSAGE
12s         Warning   FailedMount   pod/web  MountVolume.SetUp failed for volume "config" : configmap "cardapio" not found

Essa linha diz três coisas de uma vez: o volume que falhou (config), o tipo do objeto (configmap) e o nome que ele procurou (cardapio). Com isso em mãos, a conferência é kubectl get configmap no namespace certo — e não adivinhar no escuro.

O caso da última linha da tabela é o mais traiçoeiro, porque o apply passa: o objeto do pod é válido, e o erro só aparece depois, no status. Um pod que aponta para ConfigMap inexistente fica em CreateContainerConfigError, e o describe mostra a frase configmap "cardapio" not found nos eventos. É a diferença entre “o cluster recusou o meu manifesto” e “o cluster aceitou e o container não conseguiu montar”.

7. Duas coisas para praticar agora

A primeira caixa é o mínimo que funciona para entregar um ConfigMap como arquivo. A segunda é o conserto que você vai precisar no dia em que quiser um arquivo só, com outro nome.

O pod lê o ConfigMap por variável. Monte o mesmo ConfigMap como volume em /etc/cardapio: acrescente volumes e volumeMounts.

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio
data:
  preco: "4.50"
  horario: 6h as 19h
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: cardapio:1.0
      env:
        - name: PRECO
          valueFrom:
            configMapKeyRef:
              name: cardapio
              key: preco
configmap/cardapio created
pod/web created

NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          9m

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio
data:
  preco: "4.50"
  horario: 6h as 19h
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  volumes:
    - name: config
      configMap:
        name: cardapio
  containers:
    - name: web
      image: cardapio:1.0
      volumeMounts:
        - name: config
          mountPath: /etc/cardapio

O volume aparece em dois lugares e é a mesma coisa duas vezes: em spec.volumes ele declara o que montar; em volumeMounts, onde montar dentro do container. O name é o elo entre os dois — e não é o nome do ConfigMap, é um apelido do volume.

O site precisa de um arquivo só, chamado preco.txt, e não da pasta com as duas chaves. Use items para montar apenas preco com esse nome.

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio
data:
  preco: "4.50"
  horario: 6h as 19h
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  volumes:
    - name: config
      configMap:
        name: cardapio
  containers:
    - name: web
      image: cardapio:1.0
      volumeMounts:
        - name: config
          mountPath: /etc/cardapio
configmap/cardapio created
pod/web created

NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          9m

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio
data:
  preco: "4.50"
  horario: 6h as 19h
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  volumes:
    - name: config
      configMap:
        name: cardapio
        items:
          - key: preco
            path: preco.txt
  containers:
    - name: web
      image: cardapio:1.0
      volumeMounts:
        - name: config
          mountPath: /etc/cardapio

Com items, o container passa a ver um arquivo só: /etc/cardapio/preco.txt. A chave horario continua no ConfigMap, mas não entra no volume. É a diferença entre “monte tudo” e “monte isto, com este nome” — e ela aparece muito quando o programa espera um caminho fixo e você não quer mudar o código.

8. Para ir além

As páginas abaixo contam a história por trás de cada campo desta referência. Se você chegou aqui só para lembrar o nome de um campo, pode parar; se quer o passo a passo, comece pela primeira.

  • ConfigMap — a criação, as chaves, os tropeços e o que o objeto não resolve.
  • Secret — base64, tipos de Secret e as regras para o segredo não vazar.
  • Secret na prática — qual credencial mora onde e a rotação no dia da mudança.
  • ConfigMap como volume — arquivos, items, permissões e o que é sobrescrito.
  • envFrom — todas as chaves de uma vez, com prefixo e precedência.
  • ConfigMap imutável — immutable: true e o padrão versionado.
  • Recarregar configuração — o que muda sem reiniciar e o que exige rollout.
  • Variáveis de ambiente — env com valor fixo e com valueFrom.
  • Montando a configuração — juntar ConfigMap, Secret e volume no mesmo pod.

Para praticar a criação sem escrever YAML, o caminho é o kubectl create com --dry-run=client -o yaml: você vê o manifesto que o cluster geraria e usa como base. É mais rápido do que decorar a indentação, e o resultado é sempre válido.

Resumo

ConfigMap e Secret guardam configuração fora da imagem. Os dois têm metadata.name, data, immutable, limite de 1 MiB e as mesmas regras de chave. O ConfigMap tem binaryData e texto puro; o Secret tem stringData, type e valores em base64.

Para criar, kubectl create resolve no teste e kubectl apply -f é o que se guarda. Para entregar, env/envFrom dá variável lida no start; volume dá arquivo, com items escolhendo chave e nome. Base64 não é criptografia: quem protege é o RBAC.

O API server valida a forma — chave, base64, aspas, tamanho — e não o conteúdo. Erro de forma vem na hora do apply, com o campo e o motivo na mensagem; erro de referência só aparece no status do pod, em CreateContainerConfigError. Saber qual dos dois você está vendo economiza metade do tempo de diagnóstico.

Para lembrar
  • data é texto no ConfigMap e base64 no Secret; stringData aceita texto no Secret.
  • Chave válida: letras, números, -, _ e . — sem espaço nem acento.
  • env não atualiza; volume atualiza com atraso; immutable não atualiza nunca.
  • items monta uma chave só, com o nome de arquivo que você escolher.
  • CreateContainerConfigError é referência errada, não manifesto inválido.
  • Base64 decodifica em um comando: o segredo de verdade é permissão.
