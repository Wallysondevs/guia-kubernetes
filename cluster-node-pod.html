Cluster, node e pod

Na aula passada a Ana entregou o primeiro pedido ao Kubernetes e viu um pod nascer. Mas onde esse pod nasceu, exatamente? Dentro de qual computador? Quem escolheu? Essas perguntas têm três respostas encaixadas uma na outra: o pod mora num nó, e os nós formam o cluster. Nesta aula a Ana abre cada caixa: vê as máquinas que compõem o cluster, descobre em qual delas o pod caiu, olha o endereço de rede que o pod ganhou e põe dois containers no mesmo pacote para entender o que é — e o que não é — um pod.

Você vai aprender
  • O que é um cluster e o que significa “estar conectado” a um.
  • O que é um nó, quais papéis ele pode ter e o que roda dentro dele.
  • O que é um pod, na prática: rede própria, IP próprio, um ou mais containers.
  • Como ver os nós, o nó do pod e o IP do pod com o kubectl.
  • Por que READY 2/2 quer dizer dois containers, não dois pods.
  • Onde o painel deste guia é simplificado, para você não se enganar.

1. A cena: a padaria virou três máquinas

No começo era um notebook. O site rodava ali, e o Kubernetes também podia rodar ali, num cluster de estudo. Depois a padaria cresceu: entrou o sistema de encomendas, entrou o painel do fornecedor, entrou o cronômetro do forno. Rodar tudo num computador só passou a ser arriscado — se ele cai, cai tudo. A solução natural é espalhar: uma máquina para o site, outra para as encomendas, outra de reserva.

Só que espalhar traz o problema de sempre: quem decide o que vai onde? Quem percebe que uma máquina morreu? Quem recoloca o que estava nela? O Kubernetes resolve isso juntando as máquinas num conjunto único, com um endereço só, e tratando o conjunto como se fosse uma coisa. Esse conjunto é o cluster. Para o seu kubectl, não existem “três servidores”: existe um cluster, e você pede para ele.

Dentro do cluster, cada máquina é um nó. E o que o cluster coloca em cima de um nó nunca é “um programa solto”: é um pod. Três palavras, três escalas. Pense no cluster como a padaria inteira, no nó como uma das cozinhas e no pod como a bandeja que sai do forno para um pedido — a cozinha pode ter várias bandejas, e a bandeja não escolhe em qual cozinha vai.

2. Cluster: um endereço, um contexto

Do lado de fora, um cluster é basicamente um endereço de API e uma credencial. O kubectl guarda isso num arquivo de configuração, o ~/.kube/config, e organiza em contextos: cada contexto diz “para este endereço, com esta credencial, neste namespace”. Quando você tem mais de um cluster — o de estudo e o da empresa, por exemplo —, trocar de um para o outro é trocar de contexto.

ana@notebook:~$ kubectl config get-contexts
CURRENT   NAME        CLUSTER     AUTHINFO    NAMESPACE
*         kind-guia   kind-guia   kind-guia   default
ana@notebook:~$ kubectl config current-context
kind-guia

O asterisco marca o contexto em uso. kind-guia é o nome que o kind deu ao cluster de estudo — “kind” mais o nome que você escolheu na criação. É esse mesmo nome que aparece na coluna CLUSTER e no AUTHINFO, porque num cluster de estudo o acesso é local e simples: o kind escreve a configuração no seu notebook e você já está autenticado.

Uma confusão comum: o cluster não é “o programa kubectl”. O kubectl é o telefone; o cluster é quem atende. Você pode desligar o notebook, reinstalar o kubectl, trocar de terminal — o cluster continua lá, com os objetos que você criou. E o contrário também: se o cluster sumir, o kubectl continua no seu PATH, respondendo “connection refused” a tudo.

3. Nó: a máquina que faz o trabalho

Um nó é uma máquina — física ou virtual — que participa do cluster. Cada nó tem nome, endereço IP, sistema operacional, versão do runtime de containers e uma etiqueta padrão com o próprio nome (kubernetes.io/hostname). Você quase nunca precisa saber disso tudo; precisa saber quantos nós existem, se estão Ready e quanto de CPU e memória cada um oferece.

Os nós têm papéis. O control plane é o nó do cérebro: nele rodam o API server, o etcd, o scheduler e os controladores. Os workers são os nós de trabalho, onde os seus pods rodam. Num cluster de estudo com kind, é comum existir um nó de controle e um ou dois workers — e o nó de controle também aceita pods, o que confunde quem espera que ele fique “reservado”. Em cluster de produção, o nó de controle costuma ficar isolado por segurança.

Cada nó carrega etiquetas, e a mais importante no começo é kubernetes.io/hostname, com o nome do nó como valor. Elas não são enfeite: o agendador usa etiquetas para decidir onde um pod cabe, e você também pode usar (nas aulas de labels e selectors) para dizer “este pod só roda em nó com disco”. Por isso vale a pena saber que nó tem nome, e que o nome é o identificador usado em toda parte.

cluster
O conjunto de nós, com um endereço de API e um estado guardado. É a unidade que o seu kubectl enxerga.
nó (node)
Uma máquina do cluster. Tem nome, IP e capacidade de CPU e memória.
control plane
O nó (ou nós) que rodam o cérebro: API server, etcd, scheduler e controladores.
kubelet
O agente que roda em cada nó e cuida dos containers daquela máquina, obedecendo ao cluster.
pod
A menor unidade que o cluster agenda: um ou mais containers com o mesmo IP e o mesmo ciclo de vida.
container
O processo empacotado que de fato executa o seu programa. Vive dentro do pod.

4. Pod: o pacote com rede própria

Um pod é um envelope. Dentro dele vai pelo menos um container — o seu programa — e, opcionalmente, outros containers que precisam ficar lado a lado. Todos os containers de um pod compartilham o mesmo endereço de rede e o mesmo volume de arquivos, e é isso que faz o pod ser mais do que “um container com outro nome”: dentro do pod, os containers conversam por localhost, como programas na mesma máquina.

Cada pod ganha um IP próprio no momento em que nasce. Esse IP é interno ao cluster: ninguém na internet chega nele, e ele muda quando o pod é recriado. Quem quiser falar com o site de fora precisa de um Service, que é assunto do Nível 2 — por enquanto, guarde a ideia de que o IP do pod é descartável e o nome do pod também.

E o pod tem um ciclo de vida curto por natureza. Ele nasce, roda e morre; quem cuida de manter a quantidade certa é o controlador (o Deployment, na aula 1). Não existe “consertar um pod”: existe apagar e deixar o controlador criar outro. Você vai ver isso na prática em toda a carreira.

Antes de seguir, uma promessa útil para o resto do guia: nenhum desses três nomes é decorativo. Cluster aparece em todo comando que você roda; nó aparece quando algo não cabe ou não sobe; pod aparece em praticamente toda tabela. Se você conseguir dizer, em qualquer momento, “este pod está neste nó deste cluster”, já entendeu a estrutura que o Kubernetes usa para organizar tudo.

5. Vendo os nós

A primeira coisa a fazer em qualquer cluster novo é perguntar quem são as máquinas. O comando básico é kubectl get nodes. A caixa abaixo começa com ele; a missão é usar a variação que mostra os detalhes de rede e de sistema de cada nó.

A tabela só mostra nome, papel e versão. Acrescente -o wide ao comando dos nós para ver também o IP interno e o runtime de containers.

kubectl get nodes
ana@notebook:~$ kubectl get nodes
NAME                 STATUS   ROLES           AGE   VERSION
guia-control-plane   Ready    control-plane   8m    v1.37.3
guia-worker          Ready    <none>          4m    v1.37.3
guia-worker2         Ready    <none>          4m    v1.37.3

kubectl get nodes -o wide

Com -o wide entram três colunas novas: INTERNAL-IP (o endereço do nó dentro da rede do cluster), OS-IMAGE e KERNEL-VERSION mais o CONTAINER-RUNTIME, que aqui é containerd://1.7.24. O containerd é quem efetivamente baixa a imagem e liga o container; o Kubernetes manda, ele executa.

Coluna do get nodesO que significaQuando importa
NAMEnome do nó, único no clusterpara descrever o problema a alguém
STATUSReady ou NotReadyNotReady: o kubelet do nó parou de responder
ROLEScontrol-plane ou <none>saber quem é cérebro e quem é trabalho

Se o get nodes responde Ready em todos, o cluster está saudável por baixo. Se algum aparece NotReady, comece por ali: os pods daquele nó serão marcados como perdidos e recriados em outro lugar. O cluster prefere recriar a insistir num nó que não responde.

6. Onde o meu pod caiu?

A tabela do get pods não mostra o nó. Para descobrir onde um pod está e qual IP ele ganhou, o caminho mais direto é o describe: ele abre o objeto inteiro e, nas primeiras linhas, diz o nó e o endereço. A caixa abaixo cria um pod e precisa descrevê-lo.

O pod foi criado, mas ninguém viu onde ele caiu. Acrescente a linha kubectl describe pod forno e rode.

kubectl run forno --image=forno:1.0
ana@notebook:~$ kubectl run forno --image=forno:1.0
pod/forno created

kubectl run forno --image=forno:1.0
kubectl describe pod forno

As primeiras linhas do describe são um resumo de identidade: Name, Namespace, Service Account e as duas que interessam aqui. Node: mostra o nó e o IP dele, separados por barra. IP: é o endereço do pod dentro da rede do cluster. Mais abaixo vêm os containers, o estado de cada um, e no fim os eventos.

Se você preferir a informação em tabela, existe o atalho: kubectl get pods -o wide acrescenta IP e NODE ao get pods. A transcrição abaixo é de um cluster local com dois pods:

ana@notebook:~$ kubectl get pods -o wide
NAME       READY   STATUS    RESTARTS   AGE   IP               NODE                 NOMINATED NODE   READINESS GATES
cardapio   1/1     Running   0          2m    10.244.3.71      guia-control-plane   <none>           <none>
forno      1/1     Running   0          5m    10.244.145.245   guia-control-plane   <none>           <none>

Repare que os dois pods estão no mesmo nó e têm IPs diferentes. Isso é o normal: o nó hospeda vários pods, e cada pod tem o seu endereço. Em cluster com mais nós, você veria pods espalhados — e é justamente esse espalhamento que protege o serviço quando uma máquina cai.

Uma última leitura da tabela: o AGE de cada pod conta desde que ele nasceu. Se você olhar duas vezes e o pod mais novo estiver sempre com poucos minutos, é sinal de que algo está recriando pods — o controlador trabalha, mas o pod não fica de pé. Quem conta essa história direito é o RESTARTS, junto com o describe: reinício é container morrendo dentro do mesmo pod; nome novo é pod inteiro sendo recriado.

7. Dois containers, um pod

Um pod pode ter mais de um container, e isso não é exceção esquisita: é o padrão quando dois programas precisam estar sempre juntos. Um exemplo clássico é o do programa que exporta métricas: ele lê o que o programa principal está fazendo, e faz sentido que os dois estejam no mesmo pacote, no mesmo nó, no mesmo IP.

Acrescente um segundo container ao pod, com nome metricas e imagem metricas:1.0, na mesma lista de containers. A coluna READY tem de passar a mostrar 2/2.

apiVersion: v1
kind: Pod
metadata:
  name: forno
spec:
  containers:
    - name: forno
      image: forno:1.0
pod/forno created

NAME    READY   STATUS    RESTARTS   AGE
forno   1/1     Running   0          5m

apiVersion: v1
kind: Pod
metadata:
  name: forno
spec:
  containers:
    - name: forno
      image: forno:1.0
    - name: metricas
      image: metricas:1.0

O READY 2/2 é a prova visual: são dois containers prontos de dois pedidos, num pod só. O número à esquerda da barra é quantos estão prontos; o da direita é quantos foram declarados. Se um dos dois não ficar pronto, a fração cai para 1/2 e o pod inteiro é considerado não pronto — o que faz sentido, porque o pacote é uma unidade só.

Essa característica tem consequência: container extra no mesmo pod é casamento. Se o exportador de métricas morre, o pod inteiro é reiniciado, inclusive o programa principal. Por isso a decisão de juntar containers num pod deve ser tomada só quando os dois realmente dependem um do outro — a aula de sidecar volta nisso com calma.

8. O que a caixa faz (e o que ela simplifica)

Vale ser honesto sobre o painel deste guia, porque ele é o seu laboratório até você ter um cluster. Ele guarda um cluster simulado em memória, com nós, um agendador, controladores e objetos, e responde com as mesmas mensagens do kubectl de verdade. Mas o agendador é simplificado: no painel, os pods caem sempre no nó guia-control-plane. Num cluster real, o scheduler escolhe entre os nós olhando capacidade e etiquetas, e você veria pods espalhados.

Também não há kubelet de verdade no painel: o container não é executado. Por isso você não verá CrashLoopBackOff, ImagePullBackOff ou logs do programa dentro das caixas — essas cenas aparecem no guia como transcrição de um cluster real, sempre identificadas. O que o painel faz bem é o que é cálculo: validar manifesto, criar objetos, agendar, casar etiquetas, calcular endpoints.

9. Cenários do dia a dia

Cenário 1: o pod que mudou de nó sozinho

A Ana anotou o nó de um pod para investigar e, no dia seguinte, o pod estava em outro nó com outro nome. Não foi mágica nem bug: o pod morreu, o controlador criou outro, e o scheduler achou lugar em outro nó. Pod é descartável; o que é estável é o nome do Deployment. Anotar o nome do pod num caderno é sempre uma foto tirada hoje de algo que muda amanhã.

Cenário 2: dois containers, um IP

Ela colocou o exportador de métricas num pod separado e depois não conseguia fazer o programa principal conversar com ele por localhost. Claro: localhost só funciona dentro do mesmo pod. Entre pods, a conversa é por IP ou por nome de Service, e cada pod tem o seu. A decisão de juntar ou separar containers é, antes de tudo, uma decisão sobre rede e ciclo de vida.

Cenário 3: o nó NotReady e os pods órfãos

Um dos nós do cluster ficou NotReady porque o kubelet parou de responder. Os pods daquele nó foram marcados como perdidos depois de alguns minutos, e os controladores criaram substitutos nos nós que estavam saudáveis. Por isso o cluster com vários nós aguenta a queda de um: não é o pod que é imortal, é o conjunto que se reorganiza.

11. Resumo

Cluster é o conjunto de máquinas que o Kubernetes gerencia com um endereço só; nó é cada máquina, com papel de control plane ou de trabalho; pod é o envelope que o cluster agenda, com IP próprio e um ou mais containers. Container é o que executa o seu programa.

Para ver as máquinas, kubectl get nodes (e -o wide para IP e runtime). Para saber onde um pod caiu, kubectl describe pod e leia Node e IP — ou use kubectl get pods -o wide. E se o pod tem dois containers, o READY 2/2 mostra isso: dois prontos de dois declarados.

Guarde a ideia que sustenta o resto do guia: nada disso é permanente. Pod nasce e morre, IP muda, nó pode ficar NotReady. O que permanece é o que você descreveu. Na próxima aula a Ana olha para o outro lado da moeda: por que tudo isso vale a pena, com as três dores que o Kubernetes resolve e as duas que ele não resolve.

Para lembrar
  • Cluster = conjunto; nó = máquina; pod = pacote que roda num nó.
  • O pod tem IP próprio; o IP muda quando o pod é recriado.
  • Containers do mesmo pod conversam por localhost.
  • kubectl get nodes -o wide mostra IP interno e runtime.
  • kubectl describe pod mostra Node e IP.
  • READY 2/2 é container, não pod.
  • No painel do guia, todo pod cai no mesmo nó: o agendador é simplificado.
