Instalar kubectl e kind

A Ana decidiu que vale a pena: o site da padaria vai rodar em Kubernetes. Agora falta o passo menos glamouroso e mais decisivo — instalar as ferramentas. Ela abre o terminal, digita kubectl e recebe command not found. Nesta aula ela instala o kubectl (o controle remoto) e o kind (o cluster de mentira dentro da sua máquina), confere cada um com um comando, aprende onde as configurações ficam e vê os tropeços clássicos com o conserto de cada um. Tudo com comandos reais, do jeito que se faz no Linux, no macOS e no Windows.

Você vai aprender
  • Para que serve cada ferramenta e por que são duas.
  • O pré-requisito que ninguém conta: o Docker.
  • Instalar o kubectl e o kind em Linux, macOS e Windows.
  • Conferir a instalação sem precisar de cluster.
  • Onde ficam o binário (PATH) e a configuração (~/.kube/config).
  • Os cinco erros de instalação mais comuns e o conserto de cada um.

1. A cena: command not found

“Instale o kubectl e o kind” — era o que dizia o tutorial que a Ana achou. Ela copiou a linha do curl, colou no terminal, viu um monte de números passando e depois nada. Abriu o terminal de novo e digitou só kubectl, para ver o que acontecia. A resposta foi seca:

ana@notebook:~$ kubectl
bash: kubectl: command not found

Aquele command not found é a primeira parede de todo mundo. Ele não quer dizer “quebrou”: quer dizer “o shell procurou um programa chamado kubectl nas pastas onde ele sabe procurar e não achou nada”. Ou o arquivo não foi baixado, ou foi baixado no lugar errado, ou não tem permissão de execução, ou a pasta onde ele está não entra na busca do shell.

São quatro causas diferentes para o mesmo aviso, e é justamente por isso que instalar é uma etapa que assusta. A boa notícia: instalar é a única parte do Kubernetes que se faz uma vez e esquece. E cada passo pode ser conferido com um comando que responde sim ou não. É o que vamos fazer aqui, na ordem em que a Ana fez.

2. Duas ferramentas, dois papéis

Antes de baixar nada, entenda o que cada peça faz — porque a confusão entre elas gera metade dos erros. O kubectl é um programa que conversa com um cluster. Ele não roda nada, não guarda nada, não é um servidor: ele monta um pedido, manda para a API do cluster e imprime a resposta. Se o cluster não existe ou não está no ar, o kubectl existe do mesmo jeito, e você pode até perguntar a versão dele sem rede nenhuma.

O kind é o contrário: ele cria um cluster inteiro dentro da sua máquina, usando containers Docker como se fossem máquinas. É ferramenta de estudo e de teste. O nome é uma sigla de Kubernetes in Docker. Com ele você sobe um cluster em um ou dois minutos, apaga quando quiser e não paga nuvem nenhuma.

E o Docker é o motor que o kind usa. Sem Docker (ou outro runtime equivalente) rodando, o kind não tem onde montar o cluster e falha com uma mensagem sobre o daemon. Por isso a ordem de instalação é Docker, depois kubectl, depois kind — e não a ordem alfabética do tutorial.

kubectl
Cliente de linha de comando: conversa com a API do cluster e imprime a resposta.
kind
Cria clusters Kubernetes locais usando containers Docker como nós.
Docker
Motor de containers. O kind depende dele para existir.
kubeconfig
Arquivo ~/.kube/config com endereços de clusters, credenciais e o contexto atual.
contexto
Combinação “cluster + usuário + namespace” que o kubectl usa por padrão.
PATH
Lista de pastas onde o shell procura programas. Se o binário não está numa delas, é “command not found”.

3. O pré-requisito que ninguém avisa: o Docker

O kind precisa de um runtime de containers. No Linux, Docker Engine; no macOS e no Windows, o Docker Desktop, que já traz uma máquina virtual com o motor dentro. Sem isso, o comando mais importante do kind termina com uma mensagem sobre não conseguir falar com o daemon.

A conferência é simples e vale fazer antes de qualquer download:

ana@notebook:~$ docker --version
Docker version 27.4.1, build 0b9d7b4f

ana@notebook:~$ docker run --rm hello-world
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
...
Hello from Docker!
This message shows that your installation appears to be working correctly.

Repare que são duas perguntas diferentes. A primeira (docker --version) diz que o programa está instalado. A segunda (docker run) diz que o motor está funcionando — e é essa que importa. Dá para ter o programa instalado e o motor parado, o que produz o erro clássico Cannot connect to the Docker daemon. No Linux, o conserto costuma ser sudo systemctl start docker e, para não precisar de sudo a cada comando, colocar o seu usuário no grupo docker. No macOS e no Windows, é abrir o Docker Desktop e esperar o ícone parar de girar.

Um detalhe de segurança que vale saber desde já: entrar no grupo docker equivale a ter poder de administrador na máquina, porque dá para montar pastas do sistema dentro de um container. Em máquina de estudo, tudo bem. Em servidor de produção, prefira outras saídas.

4. Instalando o kubectl

O kubectl é um único arquivo executável. Não tem instalador, não tem dependência, não tem “próximo, próximo, concluir”: você baixa o arquivo da versão certa, dá permissão de execução e coloca numa pasta que esteja no PATH. No Linux, com a arquitetura x86-64 (a mais comum), é isto:

ana@notebook:~$ curl -LO "https://dl.k8s.io/release/v1.37.3/bin/linux/amd64/kubectl"
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
100 55.9M  100 55.9M    0     0  18.4M      0  0:00:03  0:00:03 --:--:-- 18.4M

ana@notebook:~$ chmod +x kubectl
ana@notebook:~$ sudo mv kubectl /usr/local/bin/kubectl
ana@notebook:~$ kubectl version --client
Client Version: v1.37.3
Kustomize Version: v5.8.1

Três linhas, três ideias. O curl -LO baixa o arquivo com o nome original (o -O maiúsculo é o que preserva o nome). O chmod +x marca o arquivo como executável — sem isso o shell responde Permission denied. E o sudo mv leva o arquivo para /usr/local/bin, que é uma pasta de programas do sistema e já está no PATH de praticamente toda distribuição.

Quer outra versão? Troque o número no caminho. Quer a última estável sem pensar? Use a composição que a documentação oficial sugere, com $(curl -L -s https://dl.k8s.io/release/stable.txt) no lugar de v1.37.3. Em máquina ARM (Apple Silicon, Raspberry Pi, alguns notebooks), troque amd64 por arm64 — e esse é o erro de download mais comum: baixar a arquitetura errada e receber exec format error ao rodar.

No macOS, o caminho mais curto é o Homebrew, que já cuida de arquitetura e PATH:

ana@notebook:~$ brew install kubectl
==> Downloading https://formulae.brew.sh/api/formula/kubectl.json
==> Fetching kubectl--1.37.3.bottle.tar.gz
==> Pouring kubectl--1.37.3.bottle.tar.gz
==> Caveats
The kubernetes-cli formula is keg-only, which means it was not symlinked into /opt/homebrew.
==> Summary
/opt/homebrew/Cellar/kubectl/1.37.3: 3 files, 57.2MB

ana@notebook:~$ kubectl version --client
Client Version: v1.37.3
Kustomize Version: v5.8.1

No Windows, o caminho natural é winget install -e --id Kubernetes.kubectl ou o Chocolatey com choco install kubernetes-cli. Em qualquer sistema, o teste final é o mesmo: kubectl version --client precisa imprimir Client Version e a versão. Se imprimiu, o binário está instalado e executável.

5. Instalando o kind

O kind também é um único executável, e a lógica é idêntica: baixar, dar permissão, mover para o PATH. A diferença é que o kind não é um cliente de cluster — ele é um programa que conversa com o Docker para criar nós. A instalação no Linux:

ana@notebook:~$ curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.30.0/kind-linux-amd64
100  9.4M  100  9.4M    0     0  12.1M      0  0:00:00  0:00:00 --:--:-- 12.1M

ana@notebook:~$ chmod +x ./kind
ana@notebook:~$ sudo mv ./kind /usr/local/bin/kind
ana@notebook:~$ kind --version
kind version 0.30.0

Aquele kind version 0.30.0 é a prova de que o binário está no PATH e roda. Se a sua máquina for ARM, o arquivo é kind-linux-arm64. No macOS, brew install kind resolve; no Windows, winget install Kubernetes.kind ou choco install kind.

Uma alternativa para quem já programa em Go é go install sigs.k8s.io/kind@latest, que compila e coloca o binário em ~/go/bin — pasta que, em algumas instalações, não está no PATH. É a causa número um de “instalei e continua dando command not found”.

6. Conferindo se o cliente responde

Com o binário no lugar, a primeira pergunta a fazer é se ele responde. E existe um detalhe importante: o kubectl mostra a versão do cliente mesmo sem cluster nenhum. Isso separa dois problemas que costumam se misturar na cabeça do iniciante — “minha instalação está quebrada?” e “meu cluster está quebrado?”.

As duas primeiras linhas são os erros de quem trata o kubectl como programa comum: bandeira antes do verbo e um verbo install que não existe. Rode para ver as mensagens e depois escreva a forma certa: kubectl version --client.

kubectl --version
kubectl install --client
kubectl get nodes
ana@notebook:~$ kubectl --version
error: unknown command "--version" for "kubectl"

ana@notebook:~$ kubectl install --client
error: unknown command "install" for "kubectl"

ana@notebook:~$ kubectl get nodes
NAME                 STATUS   ROLES           AGE   VERSION
guia-control-plane   Ready    control-plane   8m    v1.37.3
guia-worker          Ready    <none>          4m    v1.37.3
guia-worker2         Ready    <none>          4m    v1.37.3

kubectl version --client
kubectl get nodes

A primeira mensagem, error: unknown command "--version" for "kubectl", é a mesma que a Ana levou meia hora para entender: no kubectl, o primeiro pedaço depois do nome é um verbo (version, get, delete, create). Bandeira vem depois do verbo, nunca antes. A segunda, unknown command "install", lembra que o kubectl não instala nada nele mesmo: instalação de ferramenta é trabalho do sistema operacional.

Depois do conserto, a saída tem duas linhas: Client Version: v1.37.3 e Kustomize Version: v5.8.1. A segunda existe porque o kubectl embute o kustomize (ferramenta de montagem de manifestos, Nível 3). Não é erro; é só o pacote que vem junto.

Se você rodar kubectl version sem --client num cluster de verdade, aparece também uma linha Server Version: v1.37.3 — a versão de quem está do outro lado. O painel deste guia mostra a versão do cliente, porque ele não tem um servidor de API real na outra ponta; na sua máquina, com o cluster da próxima aula no ar, a linha do servidor aparece.

7. Onde as coisas ficam: PATH e kubeconfig

Duas pastas explicam quase todos os mistérios de instalação. A primeira é o PATH, a lista de pastas onde o shell procura programas. echo $PATH mostra a sua. Se você baixou o binário na pasta de downloads e rodou ./kubectl, funcionou porque o ./ mandou o shell olhar na pasta atual; sem o ./, o shell procura no PATH e não acha.

A segunda pasta é a de configuração. Quando o kubectl precisa saber com qual cluster falar, ele lê o arquivo ~/.kube/config. Esse arquivo guarda endereços, certificados e uma lista de contextos — combinações de cluster, usuário e namespace — com uma marcada como atual. O kind escreve nesse arquivo quando cria um cluster, e é por isso que, depois do kind, o kubectl “já sabe” onde está o cluster.

A primeira linha tem o verbo no singular e o kubectl não reconhece. Corrija para get-contexts e veja a lista de contextos, o contexto atual e o arquivo que o kubectl lê.

kubectl config get-context
kubectl config current-context
kubectl config view
ana@notebook:~$ kubectl config get-context
kubectl config: use current-context, get-contexts ou view

ana@notebook:~$ kubectl config current-context
kind-guia

ana@notebook:~$ kubectl config view
apiVersion: v1
kind: Config
clusters:
- cluster:
    server: https://127.0.0.1:6443
  name: kind-guia
contexts:
- context:
    cluster: kind-guia
    user: kind-guia
    namespace: default
  name: kind-guia
current-context: kind-guia

kubectl config get-contexts
kubectl config current-context
kubectl config view

A lista tem uma coluna CURRENT com um asterisco: é o contexto em uso. O nome kind-guia não é escolha nossa — o kind batiza o contexto com o prefixo kind- mais o nome do cluster. Já o config view imprime o arquivo inteiro: o server (https://127.0.0.1:6443) é o endereço da API do cluster, e current-context diz qual bloco o kubectl usa quando você não passa --context.

Esse arquivo é a peça que você vai copiar de um lado para outro na vida real: com ele, um pipeline de integração consegue falar com um cluster remoto sem ninguém digitar senha. E é também um arquivo sensível: quem tem o kubeconfig de produção tem acesso a produção. Nunca comite esse arquivo, nunca cole o conteúdo em chat, nunca deixe em pasta compartilhada.

8. As duas ferramentas se encontram

Instalar as duas e não provar que conversam é como comprar telefone e nunca discar. O teste final é curto: o kind lista os clusters que existem na máquina, e o kubectl fala com um deles. Se os dois responderem, a instalação está completa.

O painel já tem um cluster criado (na sua máquina, a próxima aula ensina a criar). Acrescente a linha do kubectl para ver os nós desse cluster respondendo.

kind get clusters
ana@notebook:~$ kind get clusters
guia

kind get clusters
kubectl get nodes

O kind get clusters imprime guia: o nome do cluster na visão do kind. O kubectl get nodes imprime três linhas com STATUS Ready — os nós do cluster. Nomes diferentes, papéis diferentes: o kind administra a “caixa” (o cluster), o kubectl olha o que existe dentro dela.

Se o kind get clusters responde e o kubectl get nodes reclama de conexão, o problema não é instalação: é contexto. Basta olhar o current-context e confirmar que ele aponta para o cluster certo. Esse diagnóstico em dois passos — “o binário responde?” e “o contexto aponta para onde?” — resolve a maior parte dos chamados de suporte de quem está começando.

9. Os tropeços clássicos (e o conserto)

Instalação dá errado por poucos motivos, sempre os mesmos. Vale conhecer os cinco antes de se deparar com eles, porque todos têm conserto simples e todos já custaram uma tarde de alguém.

MensagemCausaConserto
bash: kubectl: command not foundbinário fora do PATH ou não baixado mover para /usr/local/bin ou acrescentar a pasta ao PATH
Permission deniedfalta permissão de execuçãochmod +x kubectl
exec format errorarquitetura errada (amd64 em ARM, ou o contrário) baixar de novo com arm64
Cannot connect to the Docker daemonDocker instalado, motor parado iniciar o Docker Desktop ou sudo systemctl start docker
sudo: kubectl: command not foundo sudo reseta o PATH usar caminho absoluto: sudo /usr/local/bin/kubectl

O último é o mais traiçoeiro, porque contradiz a experiência: funciona sem sudo, falha com ele. O motivo é que o sudo monta um ambiente novo, com o PATH do administrador, e a sua pasta pessoal de binários some. A solução é caminho absoluto — ou, melhor ainda, não usar sudo para comandos do dia a dia.

Cenário 1: a versão do tutorial

A Ana seguiu um vídeo de dois anos atrás e instalou o kubectl 1.29 num cluster 1.37. Funcionou para quase tudo, mas um comando novo reclamou de versão. Regra prática: o kubectl pode ser até uma versão menor ou maior que o cluster; mais que isso começa a dar diferença de recurso. Quando o cluster é local e criado por você, simplesmente instale a mesma versão — e atualize com um download, sem drama.

Cenário 2: o kind que funcionava até fechar o notebook

Na segunda-feira, o kind get clusters respondeu No kind clusters found e ela achou que tinha perdido tudo. Não perdeu: os nós de um cluster kind são containers Docker, e containers param quando a máquina reinicia (ou quando o Docker Desktop fecha). O cluster continua registrado no kind e volta a subir quando o motor está no ar; se não voltar, é recriar — leva um minuto, e a receita está no manifesto.

Cenário 3: o PATH que só existia na aba aberta

Ela acrescentou a pasta ao PATH com export PATH=$PATH:~/bin, funcionou, e no dia seguinte o comando sumiu de novo. O export vale só para aquela sessão do terminal. Para valer sempre, a linha precisa entrar no arquivo de inicialização do shell (~/.bashrc ou ~/.zshrc) — e, honestamente, mover o binário para /usr/local/bin é mais simples e não depende de arquivo nenhum.

Exercício: a bandeira que dispensa o cluster

Você quer ver a versão do kubectl numa máquina sem cluster nenhum. Complete o comando com a bandeira que manda o kubectl não procurar o servidor:

kubectl version

Dica: em inglês, “cliente” se escreve client, e a bandeira tem dois hífens.

11. Resumo

São duas ferramentas com papéis opostos: o kubectl é o controle remoto que conversa com um cluster; o kind é quem cria o cluster local, usando Docker como base. Por isso a ordem é Docker, kubectl, kind — e por isso o Docker precisa estar com o motor no ar, não só instalado.

Instalar é sempre o mesmo ritual: baixar o executável certo para a sua arquitetura, dar permissão com chmod +x e colocar numa pasta do PATH, normalmente /usr/local/bin. O teste é duplo: kubectl version --client prova o binário, sem precisar de cluster; kind get clusters prova que o kind fala com o Docker; kubectl get nodes prova que os dois se encontraram. As configurações ficam em ~/.kube/config, que é útil e sensível ao mesmo tempo.

Com as ferramentas instaladas, falta a parte boa: criar o primeiro cluster de verdade, ver as mensagens aparecendo uma a uma e descobrir o que já vem instalado dentro dele. É a próxima aula.

Para lembrar
  • kubectl conversa; kind cria; Docker é o motor embaixo.
  • Comando do kubectl é verbo primeiro: kubectl version --client, nunca kubectl --version.
  • Binário precisa estar no PATH e ter chmod +x.
  • command not found é PATH; Permission denied é permissão.
  • Arquitetura errada dá exec format error: baixe arm64 ou amd64 conforme a máquina.
  • Contextos ficam em ~/.kube/config; o kind escreve nele sozinho.
