Operators e CRDs

A Ana quer um banco de dados dentro do cluster que faça backup sozinho, troque de versão sem perder dado e saiba promover a réplica quando a principal cair. Um Deployment não sabe nada disso: ele só mantém pods de pé. Quem sabe é um operador — um programa que mora no cluster e cuida de um tipo de recurso que o Kubernetes não tinha antes. Nesta aula a Ana entende as duas peças que andam juntas: a CRD, que ensina a API a aceitar um tipo novo, e o operador, que é o loop que faz esse tipo acontecer de verdade.

Você vai aprender
  • O que é uma CRD e por que ela muda o que o kubectl conhece.
  • O que é um operador, na prática: um pod com permissão que compara desejo e realidade.
  • Como descobrir os campos de um recurso com kubectl explain.
  • O que o operador cria por você e o que continua sendo responsabilidade sua.
  • Por que instalar a CRD sem o operador é ter o cardápio sem o cozinheiro.
  • Quando um operador vale a complexidade — e quando um StatefulSet já resolve.

1. A cena: o banco que precisa se cuidar sozinho

O banco de preços da padaria roda hoje numa máquina alugada, com um script de backup que a Ana roda quando lembra. Ela quer trazê-lo para o cluster. O caminho óbvio é um StatefulSet com um volume por réplica: o Kubernetes mantém os pods de pé e o disco montado. Só que StatefulSet não sabe promover réplica, não sabe fazer backup consistente, não sabe trocar de versão esperando a réplica nova ficar saudável.

É aí que aparece a palavra que todo mundo repete sem explicar: operator. Um operador é um programa que roda como pod, olha para um tipo de objeto do cluster e age para que a realidade combine com o que está escrito ali. Se o objeto diz “três réplicas, versão 16, backup diário”, o operador cria o StatefulSet, os Services, o volume, o cronograma de backup — e continua vigiando.

Para que esse objeto exista, o cluster precisa aprender um tipo novo. Pod, Deployment e Service são tipos embutidos na API. Um tipo inventado — Cardapio, BancoPadaria, Cluster — precisa ser registrado. Quem registra é a CRD, e é por ela que começamos.

2. A CRD: ensinando um tipo novo à API

O Kubernetes é uma API HTTP com recursos. Cada recurso tem um grupo, uma versão e um nome: pod é v1, Deployment é apps/v1, Ingress é networking.k8s.io/v1. Uma CustomResourceDefinition é um objeto que diz ao servidor: “existe um tipo chamado Cardapio, no grupo padaria.test, versão v1, com escopo de namespace”. A partir do instante em que ela é aceita, o kubectl passa a tratar esse tipo como qualquer outro: get, apply, describe, delete.

Instalar uma CRD é uma mudança de plataforma, não de aplicação. Ela não cria nada sozinha: só abre o balcão para um tipo novo. Um objeto daquele tipo — a custom resource, ou CR — é o pedido que você escreve: kind: Cardapio, com os campos que a CRD declarou. Sem operador, esse objeto fica guardado no etcd como texto: existe, aparece no get, e nada acontece no mundo real.

A última linha é a que mais surpreende. Uma CRD instalada sem operador não quebra nada — ela só fica inerte. O sintoma é sutil: o apply responde created, o get mostra o objeto, e nenhum pod nasce. Quem vem de Deployment espera que “criar” signifique “acontecer”, e aqui não significa.

CRD
A definição que registra um tipo novo na API: grupo, versão, nome, escopo e o schema dos campos.
custom resource (CR)
Um objeto daquele tipo. É o pedido: “quero um cardápio com 12 pratos e backup diário”.
operador
Programa que roda no cluster, vigia um tipo e age para que o mundo real combine com o pedido.
controlador
O laço de código que observa, compara e age. Um operador costuma ter vários controladores.
loop de reconciliação
O ciclo “veja o estado atual, compare com o desejado, corrija a diferença”. Roda para sempre.
finalizer
Marca que impede o objeto de sumir antes de o operador limpar o que criou (backup, disco, DNS).
ownerReference
Campo que diz quem é o dono de um objeto. É o que faz o Kubernetes apagar os filhos junto com o pai.
ServiceAccount
A identidade com que o pod do operador fala com a API. Sem permissão, o operador não vê nada.

Repare na dupla CRD + operador: a CRD é o contrato, o operador é o trabalhador. Um projeto de operador publica os dois juntos, quase sempre com um Helm chart ou um único YAML com vários documentos separados por ---.

3. O operador por dentro: observar, comparar, agir

O operador é um programa comum, escrito em Go na maioria dos casos, empacotado em imagem e rodado como Deployment de uma réplica. O que ele tem de especial é o laço. Ele abre uma conexão com o servidor da API e pede para ser avisado quando um objeto do seu tipo mudar. A cada aviso — e também a cada poucos minutos, por segurança — ele faz três perguntas.

A primeira: o que o objeto pede? É o spec da custom resource. A segunda: o que existe hoje? Ele lista os StatefulSets, Services, Secrets e volumes que carregam a etiqueta de dono daquele objeto. A terceira: qual é a diferença? Se falta uma réplica, ele cria; se sobra, apaga; se a versão está diferente, ele faz o upgrade na ordem certa, esperando cada passo ficar saudável.

Por rodar dentro do cluster, o operador precisa de permissão para ler e escrever nos tipos que manipula. Isso é RBAC: uma identidade (ServiceAccount), um conjunto de regras (Role ou ClusterRole) e uma ligação entre os dois (RoleBinding). O assunto tem aula própria mais adiante; aqui basta saber que um operador é um pod com poderes de administrador sobre uma parte do cluster, e que isso é tanto a graça quanto o risco.

Dois detalhes de operação que ninguém conta. O primeiro é que o operador também quebra: se o pod dele cai e não volta, a reconciliação para. Nada do que já existe desaparece — os pods do banco continuam rodando —, mas mudanças param de ser aplicadas. O segundo é que a versão do operador importa: atualizar o operador sem ler as notas de versão pode migrar dados de um jeito irreversível.

4. A caixa: descobrir o que o cluster conhece

O comando que responde “este cluster conhece quais tipos?” é kubectl api-resources. Ele lista cada recurso com nome plural, apelidos, grupo/versão, se é de namespace e qual é o kind. Depois de instalar uma CRD, o tipo novo aparece nessa lista — é assim que você confirma que a instalação pegou.

O comando está no singular e o kubectl não o reconhece. Corrija para kubectl api-resources e rode: a sessão tem de mostrar a tabela de recursos.

kubectl api-resource
ana@notebook:~$ kubectl api-resource
error: unknown command "api-resource" for "kubectl"

kubectl api-resources

Antes da correção a resposta é error: unknown command "api-resource" for "kubectl" — o kubectl não tenta adivinhar o comando que você quis digitar. Depois, a tabela mostra os tipos embutidos: pods, deployments, services, horizontalpodautoscalers, namespaces e o resto.

Vale guardar duas colunas dessa tabela. APIVERSION é o que vai no topo do manifesto — é ela que você erra quando copia um exemplo antigo. E NAMESPACED diz se o objeto vive dentro de um namespace ou é global, como namespaces e nodes. Errar isso gera aquele NotFound que parece mentira, porque você acabou de criar o objeto.

Sobre o painel desta aula, uma nota honesta: o cluster simulado conhece apenas os tipos embutidos. As CRDs aparecem nas transcrições, com o formato real, mas não podem ser instaladas aqui. É de propósito — instalar uma CRD no editor não provaria nada, porque quem faz o tipo acontecer é o operador, e o painel não roda containers.

5. A caixa: perguntar quais campos existem

Ninguém decora o schema de um recurso. O comando para perguntar é kubectl explain: você passa o caminho do campo e ele devolve descrição, tipo e subcampos. Funciona igual para recurso embutido e para recurso de CRD — desde que a CRD esteja instalada, porque a documentação vem do schema dela.

O explain exige o nome completo do recurso: deploy não serve. Troque por deployment.spec.strategy e rode.

kubectl explain deploy.spec.strategy
ana@notebook:~$ kubectl explain deploy.spec.strategy
error: field "deploy.spec.strategy" does not exist

kubectl explain deployment.spec.strategy

Com o apelido, a resposta é error: field "deploy.spec.strategy" does not exist. Com o nome completo, aparece o bloco FIELD: strategy <DeploymentStrategy>, a descrição e os subcampos type e rollingUpdate — inclusive o valor RollingUpdate, que é o padrão. É a documentação da versão que está rodando no seu cluster, não a da internet.

Aprender esse comando muda o dia a dia por um motivo simples: ele responde “esse campo existe mesmo?” antes de você perder meia hora num manifesto que o servidor aceita e ignora. Foi assim que descobrimos, numa aula anterior, que livenessProb sem o “e” final não é erro: é campo desconhecido, descartado em silêncio.

6. A caixa: o operador desligado

O operador é um pod. Se ele não está rodando, o laço não gira. Esta caixa mostra o operador do cardápio com replicas: 0 — alguém desligou “para economizar” durante a Black Friday e esqueceu de voltar. Os objetos do banco continuam lá, mas nenhuma mudança nova é aplicada.

O operador tem de ficar com uma réplica pronta. Corrija o replicas para 1 e rode.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio-operator
  labels:
    managed-by: cardapio-operator
spec:
  replicas: 0
  selector:
    matchLabels:
      app: cardapio-operator
  template:
    metadata:
      labels:
        app: cardapio-operator
    spec:
      serviceAccountName: cardapio-operator
      containers:
        - name: manager
          image: cardapio-operator:0.4
          args:
            - --watch-namespace=default
deployment.apps/cardapio-operator created

NAME                READY   UP-TO-DATE   AVAILABLE   AGE
cardapio-operator   0/0     0            0           9m

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio-operator
  labels:
    managed-by: cardapio-operator
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cardapio-operator
  template:
    metadata:
      labels:
        app: cardapio-operator
    spec:
      serviceAccountName: cardapio-operator
      containers:
        - name: manager
          image: cardapio-operator:0.4
          args:
            - --watch-namespace=default

Com zero réplicas, o painel mostra o Deployment sem nenhum pod pronto e a tabela com READY 0/1. Com uma, o pod sobe e o laço começa a girar. Em cluster de verdade, o efeito é o que interessa: os objetos que o operador criou continuam existindo e funcionando, mas o operador não percebe mudanças — uma alteração no spec da custom resource fica sem efeito, um pod do banco que morre pode não ser reposto na ordem certa.

Essa diferença é a chave para entender operadores: eles não são o banco, são o gerente do banco. Tirar o gerente não fecha a loja; só deixa a loja sem ninguém para repor estoque, ajustar preço e chamar o conserto.

7. O que o operador cria por você

Quando o operador do banco recebe um pedido de três réplicas, ele escreve no cluster um conjunto de objetos. Um StatefulSet com três pods e três volumes; um Service sem IP fixo para os pods se acharem pelo nome; um Secret com a senha do usuário de aplicação; talvez um CronJob de backup. Cada objeto criado leva uma etiqueta dizendo de quem é filho, e o Kubernetes usa isso para apagar tudo junto se a custom resource for removida.

Esta é uma transcrição de cluster real, de um cluster com uma CRD de banco instalada e um objeto criado havia três minutos. Repare no bloco Status: é o operador que o preenche, não o servidor da API.

ana@notebook:~$ kubectl get bancos
NAME       ENGINE    VERSION   READY   AGE
precos     postgres  16        3/3     3m

ana@notebook:~$ kubectl describe banco precos
Name:         precos
Namespace:    default

Kind:         Banco
Spec:
  Engine:     postgres
  Replicas:   3
  Version:    16
  Backup:
    Schedule:  0 3 * * *
    Retention: 7d

  Phase:      Ready
  Ready:      3
  Endpoint:   precos-0.precossvc.default.svc.cluster.local:5432
  Conditions:
    Type                Status  Reason
    Consistent          True    AllReplicasReady
    BackupScheduled     True    CronJobCreated

  Type    Reason        Age   From              Message
  ----    ------        ----  ----              -------
  Normal  StatefulSetSet 3m   banco-controller  created StatefulSet precos
  Normal  ServiceCreated 3m   banco-controller  created Service precossvc
  Normal  SecretCreated  3m   banco-controller  created Secret precos-app

Três coisas nesse texto explicam o padrão. O Status é escrito pelo operador, com campos que ele inventou — Phase, Ready, Endpoint. Os Events têm como origem o banco-controller, e não o default-scheduler: é o operador contando o que fez. E o Endpoint mostra que o operador não só criou objetos como também sabe o nome DNS que o cliente deve usar.

Do lado de quem usa, a vantagem é enorme: um apply de quinze linhas substitui um StatefulSet, dois Services, um Secret, três volumes e um CronJob. Do lado de quem opera, o custo também é real: agora você depende de um programa de terceiros, com versão própria, bugs próprios e permissões amplas.

8. Depois de instalar: como conferir

Instalar um operador tem uma ordem e uma conferência. A ordem é: CRD, depois RBAC, depois o Deployment do operador, depois a custom resource. Inverter — criar o objeto antes da CRD — resulta no erro que você já viu nesta trilha: no matches for kind .... E a conferência é sempre a mesma tríade.

ana@notebook:~$ kubectl get crd
NAME                     CREATED AT
bancos.padaria.test      2026-11-20T18:12:33Z

ana@notebook:~$ kubectl api-resources --api-group=padaria.test
NAME      SHORTNAMES   APIVERSION         NAMESPACED   KIND
bancos                 padaria.test/v1    true         Banco

ana@notebook:~$ kubectl explain banco.spec.backup
GROUP:      padaria.test
KIND:       Banco
VERSION:    v1

FIELD: backup <BackupSpec>

DESCRIPTION:
     Backup schedule and retention for the database cluster.

FIELDS:
   schedule   <string>
     Cron expression in UTC.

   retention  <string>
     How long to keep each backup, for example 7d.

A tríade confirma três coisas diferentes. get crd diz que o tipo está registrado. O api-resources filtrado pelo grupo mostra o nome plural, o apelido e o escopo — é o que você usa no kubectl get. E o explain prova que o schema veio junto: os campos schedule e retention existem, com descrição escrita por quem fez o operador.

Se o explain disser field does not exist para um campo que a documentação do projeto menciona, quase sempre é versão: a CRD instalada é mais antiga que o operador, ou o contrário. Vale comparar a versão do chart com a do spec.versions da CRD antes de culpar o manifesto.

E o que continua sendo sua responsabilidade mesmo com operador? Capacidade — o operador cria pods, não compra nó, e um banco de três réplicas que não cabe no cluster vira Pending igual a qualquer outro. Backup testado — o operador agenda, mas restaurar é seu. Credenciais e rotação de senha. Monitoramento e alerta. E a decisão de atualizar: operador antigo com CRD nova costuma ser a receita de incidente silencioso.

9. Cenários do dia a dia

Cenário 1: a CRD instalada sem o operador

O time aplicou o YAML da CRD e criou um Cardapio “para testar”. O get mostrou o objeto, e nada aconteceu — nenhum pod, nenhum Service. Faltava o Deployment do operador, que estava no mesmo arquivo, três documentos abaixo. A lição: instalar CRD sem operador é abrir a porta sem ter a cozinha.

Cenário 2: o operador com permissão de menos

Depois de um upgrade do chart, o operador passou a logar forbidden: cannot list resource "bancos" a cada poucos segundos. A CRD e o Deployment estavam certos; o ClusterRole tinha ficado para trás e não incluía o novo recurso. O sintoma no get era um objeto eternamente em Reconciling.

Cenário 3: o operador que valia menos que um StatefulSet

A Ana quase instalou um operador de cache para economizar trabalho. Comparando, o “operador” só criava um StatefulSet de uma réplica e um Service: nada que ela não escrevesse em vinte linhas. Ela ficou com o StatefulSet e economizou um programa de terceiros para atualizar. Operador é para lógica que você não quer escrever — não para empacotar YAML.

11. Resumo

CRD é contrato, operador é trabalhador. A CRD ensina a API a aceitar um tipo novo, com grupo, versão e schema; a partir dali o kubectl trata o recurso como qualquer outro. O operador é um pod com permissão que gira um laço: observa o objeto, compara com o que existe e corrige a diferença — criando StatefulSets, Services, Secrets e CronJobs por você.

A dupla tem ordem de instalação e conferência própria: CRD, RBAC, operador, custom resource; depois get crd, api-resources e explain. E tem um preço: mais um programa para atualizar, com permissões amplas e ciclo de vida separado do cluster.

Na próxima aula a Ana volta ao agendador, agora com as ferramentas que só fazem sentido em cluster grande: afinidade entre pods, espalhamento por topologia e o Pending que nenhum evento explica de primeira.

Para lembrar
  • CRD registra o tipo; a custom resource é o pedido; o operador faz acontecer.
  • Sem operador, a CR existe e nada acontece.
  • kubectl api-resources mostra o que o cluster conhece; explain mostra os campos.
  • Operador é um pod: caiu, o laço para; os objetos existentes continuam.
  • O status de uma CR costuma ser escrito pelo operador, não pelo servidor.
  • Nem todo problema precisa de operador: StatefulSet + Service resolve muita coisa.
