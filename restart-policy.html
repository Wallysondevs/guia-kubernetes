restartPolicy

A migração do banco da Ana rodou de madrugada, terminou com sucesso e... rodou de novo. E de novo. Quando ela abriu o painel de manhã, o pod estava com RESTARTS em 47. Nada estava quebrado no script: o Kubernetes só estava fazendo o que mandaram — reiniciar o container sempre que ele termina. Quem manda nisso é uma linha do manifesto chamada restartPolicy, e ela é a diferença entre um site que nunca cai e uma migração que roda sem parar.

Você vai aprender
  • Onde vive o restartPolicy e por que ele é do pod, não do container.
  • Os três valores: Always (o padrão), OnFailure e Never.
  • O que é CrashLoopBackOff e de onde vêm os segundos de espera.
  • A diferença entre reiniciar container e recriar pod.
  • As regras de cada objeto: Deployment só aceita Always, Job só aceita OnFailure ou Never.
  • Como escolher a política certa para cada tarefa da padaria.

1. A cena: a migração que rodava em loop

O script migrar.js da Ana arruma as tabelas do banco: cria as colunas que faltam, copia os dados antigos e termina. É uma tarefa com começo, meio e fim — exatamente o oposto de um servidor que fica esperando conexões.

Ela criou um pod com command: ["node", "migrar.js"] e foi dormir. O script rodou em dois segundos e saiu com código 0, o que quer dizer "terminei bem". O kubelet viu o container terminado e, como não havia nenhuma instrução dizendo o contrário, reiniciou. O script rodou de novo, com os dados já migrados, e terminou de novo. A cada reinício, o contador subia.

Nenhum erro, nenhum alerta: o pod estava Running praticamente o tempo todo, porque o container era reiniciado assim que saía. O sintoma só apareceu quando o banco começou a ficar estranho, com a migração aplicada quarenta e sete vezes.

O problema não estava no script nem na imagem. Estava na política de reinício padrão, que existe para serviços e atrapalha tarefas. Entender essa política é o que separa "o Kubernetes está maluco" de "eu pedi isso sem saber".

2. A política do pod: uma linha, três valores

O restartPolicy é um campo do spec do pod — irmão de containers e volumes, não filho deles. Isso significa que a decisão vale para o pod inteiro: se ele tem dois containers, a política é uma só para os dois. O container declara imagem, comando e recursos; o pod declara o que fazer quando o container termina.

Quem executa a política é o kubelet, o agente que roda em cada nó. Ele observa o estado do container, e quando o processo termina ele decide: reinicia, ou deixa como está? Essa decisão acontece sem passar pelo API server, no próprio nó — o que explica por que o reinício é quase instantâneo.

restartPolicy
Campo de spec no pod: o que fazer quando um container termina. Vale para todos os containers do pod.
Always
O padrão. Reinicia o container sempre que ele termina, com código zero ou não.
OnFailure
Reinicia só quando o container termina com código diferente de zero.
Never
Não reinicia nunca. O container termina e fica registrado com o código de saída.
CrashLoopBackOff
O estado em que o container falha, é reiniciado, falha de novo — e o kubelet passa a esperar cada vez mais entre tentativas.
backoffLimit
No Job: quantas tentativas antes de desistir de vez. O padrão é 6.

O valor padrão, quando você não escreve nada, é Always. É uma escolha razoável para o caso mais comum — um servidor que deve estar sempre no ar —, e é a origem de 90% das surpresas com tarefas curtas. Quando o seu programa tem fim, escreva a política de propósito.

3. Always: o reinício sem fim

Com Always, todo término é um recomeço. O site da Ana cai e volta; o processo que estoura memória volta; o script que termina bem volta também. Não há distinção entre sucesso e falha, e é por isso que esse valor é o certo para serviços e o errado para tarefas.

Quando o container falha repetidamente, o kubelet não reinicia em loop apertado — ele espera. Os atrasos dobram: dez segundos, vinte, quarenta, oitenta, cento e sessenta, e o teto de cinco minutos. Se o container conseguir rodar dez minutos seguidos, o contador zera. Durante a espera, o pod aparece como CrashLoopBackOff no get pods.

$ kubectl get pods
NAME       READY   STATUS             RESTARTS      AGE
cardapio   0/1     CrashLoopBackOff   6 (44s ago)   8m12s

$ kubectl describe pod cardapio | tail -n 6
Events:
  Type     Reason     Age                 From      Message
  ----     ------     ----                ----      -------
  Warning  BackOff     44s (x14 over 8m)   kubelet   Back-off restarting failed container web in pod cardapio_default
  Normal   Pulled      30s (x15 over 8m)   kubelet   Container image "cardapio:1.0" already present on machine
  Normal   Created     30s (x15 over 8m)   kubelet   Created container: web
  Normal   Started     29s (x15 over 8m)   kubelet   Started container web

Essa é a transcrição de um cluster local com um pod em laço de falha. A leitura certa: o RESTARTS alto mostra que o cluster já desistiu de tentar rápido e agora espera; o x15 over 8m mostra quantas vezes tentou em oito minutos; e o BackOff é o motivo do estado atual. O problema nunca é o backoff — ele é o cluster protegendo você de um loop que consumiria o nó. O problema é o exit code que está causando a falha, e esse está no describe, em Last State.

4. OnFailure: só quando dá errado

O valor OnFailure é o meio do caminho e resolve a migração da Ana com elegância: se o script sai com 0, o container fica Completed e ninguém mexe nele; se sai com erro, o kubelet tenta de novo, com o mesmo backoff do Always. É a política de quem aceita uma segunda chance, mas não uma repetição infinita de sucesso.

A caixa abaixo tem o pod da migração com um erro de digitação no valor — Alwayss, com dois "e-sse" — e o cluster recusa o objeto inteiro. Conserte para OnFailure e rode.

Troque Alwayss por OnFailure: a migração deve ser tentada de novo apenas quando falhar.

apiVersion: v1
kind: Pod
metadata:
  name: forno
spec:
  restartPolicy: Alwayss
  containers:
    - name: forno
      image: cardapio:1.0
      command: ["node", "migrar.js"]
The Pod "forno" is invalid: spec.restartPolicy: Unsupported value: "Alwayss": supported values: "Always", "Never", "OnFailure"

apiVersion: v1
kind: Pod
metadata:
  name: forno
spec:
  restartPolicy: OnFailure
  containers:
    - name: forno
      image: cardapio:1.0
      command: ["node", "migrar.js"]

A resposta do cluster é específica e didática: Unsupported value: "Alwayss": supported values: "Always", "Never", "OnFailure". Repare que ela lista os três valores aceitos — quase todo erro de enum no Kubernetes faz isso, e é uma das razões de valer a pena ler a mensagem até o fim em vez de olhar só a primeira linha.

5. Never: uma vez, e o resultado fica

Never é a política de quem não quer repetição nenhuma: o container roda uma vez e, termine bem ou mal, o kubelet não toca mais nele. O pod fica com fase Succeeded (se o código foi 0) ou Failed, e você decide o que fazer com o resultado. É o que se usa em script de auditoria, em exportação de dados e em qualquer tarefa em que rodar duas vezes seria pior do que não rodar.

Na prática, você quase nunca cria um Pod solto com Never. Cria um Job, que é o objeto feito para tarefas: ele cria o pod, aplica a política, conta as tentativas (backoffLimit) e registra a conclusão. O Job exige que a política seja OnFailure ou Never — e recusa Always, porque um Job que reinicia eternamente nunca terminaria.

$ kubectl get jobs
NAME      COMPLETIONS   DURATION   AGE
limpeza   1/1           12s        46s

$ kubectl get pods
NAME            READY   STATUS      RESTARTS   AGE
limpeza-7k2pd   0/1     Completed   0          46s

Transcrição de um Job que terminou: 1/1 conclusões, e o pod com Completed e READY 0/1. O 0/1 aqui não é problema — container terminado não está pronto para receber tráfego, e não precisa. O nome do pod ganhou um sufixo (7k2pd) porque foi o Job que o criou; pod de Job nunca tem nome fixo.

6. Os três valores lado a lado

A tabela que vale colar no monitor: ela responde "e se o meu programa terminar com zero?" e "e se terminar com erro?" para cada política.

PolíticaSaiu com 0Saiu com erroServe para
Alwaysreiniciareinicia, com backoffserviços que devem estar sempre no ar
OnFailurefica Completedreinicia, com backofftarefas que podem ser tentadas de novo
Neverfica Completedfica Failedtarefas em que repetir é perigoso

Duas leituras úteis. A primeira: Always é o único valor que ignora o código de saída — para ele, todo fim é fim. A segunda: a diferença entre OnFailure e Never não está no sucesso, está na falha; é ali que você escolhe entre "tenta de novo" e "me mostra o erro e para".

Um aviso sobre a política Always num pod que termina bem: o container reinicia e o pod nunca chega a Succeeded. Se você estiver esperando um pod de migração "concluir", isso não vai acontecer — ele vai ficar reiniciando para sempre, como o da Ana. Quem precisa de conclusão registrada é o Job.

7. Quem reinicia o quê: kubelet e controlador

Aqui está a confusão que a palavra "reinício" esconde. Existem dois níveis, com donos diferentes, e eles não se substituem.

NívelQuem ageO que aconteceNome muda?
containerkubelet, no nóreinicia o processo dentro do mesmo pod, conforme a políticanão
podReplicaSet do Deploymentcria um pod novo quando o pod somesim, sempre
podJobcria um pod novo a cada tentativa, até o backoffLimitsim
pod soltoninguémapagou, acabou: nenhum controlador olha por ele—

É por isso que a caixa da seção 4 funciona como exemplo e não como solução: um Pod solto com OnFailure reinicia o container, mas se o pod inteiro for apagado (ou o nó morrer), ninguém o recria. Quem cuida disso é o Deployment, no caso de serviço, e o Job, no caso de tarefa.

Cada objeto tem a sua regra de política, e o cluster valida na hora de aplicar. Deployment, ReplicaSet, StatefulSet e DaemonSet trabalham com Always — eles existem para manter processos vivos, e um container que termina seria recriado de qualquer forma. Job e CronJob trabalham com OnFailure ou Never. A caixa abaixo tem o Job com a política errada: conserte e veja o objeto nascer.

O Job está com Always no template, e o cluster recusa. Troque por Never: a limpeza roda uma vez e o resultado fica registrado.

apiVersion: batch/v1
kind: Job
metadata:
  name: limpeza
spec:
  template:
    spec:
      restartPolicy: Always
      containers:
        - name: limpeza
          image: busybox
          command: ["sh", "-c", "echo limpando"]
The Job "limpeza" is invalid: spec.template.spec.restartPolicy: Unsupported value: "Always": supported values: "OnFailure", "Never"

apiVersion: batch/v1
kind: Job
metadata:
  name: limpeza
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: limpeza
          image: busybox
          command: ["sh", "-c", "echo limpando"]

A mensagem aponta para spec.template.spec.restartPolicy e lista os dois valores válidos. Note o caminho: a política de um Job não fica no spec dele, fica no spec.template.spec — dentro do molde do pod que ele vai criar. Essa é a mesma estrutura de Deployment, e é a razão de tanta gente errar a indentação na primeira vez.

8. backoffLimit: até quando o Job insiste

Se a política do Job é OnFailure ou Never, alguém precisa decidir quando parar de tentar — senão o Job vira o mesmo loop do pod solto da Ana, só que com nome de tarefa. Esse alguém é o campo backoffLimit, cujo padrão é 6: depois da sexta falha, o Job marca o pod como Failed e para. A partir daí, o estado é definitivo até alguém apagar e recriar.

As duas políticas contam diferente, e a diferença aparece no que você olha no cluster. Com OnFailure, o kubelet reinicia o container dentro do mesmo pod: o nome do pod não muda, o RESTARTS sobe, e é o mesmo pod por todas as tentativas. Com Never, cada tentativa é um pod novo: você vê vários pods com o sufixo diferente, cada um com RESTARTS zero e um exit code registrado.

apiVersion: batch/v1
kind: Job
metadata:
  name: limpeza
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: limpeza
          image: busybox
          command: ["sh", "-c", "echo limpando"]

Com Never e backoffLimit: 3, o Job cria até quatro pods (a tentativa inicial mais três repetições). Cada falha deixa um pod em Failed no histórico, e esse histórico é o que torna o diagnóstico simples: você vê as mensagens de cada tentativa em kubectl logs do pod correspondente, sem que uma tentativa apague a anterior.

Para tarefas de dados, a recomendação da Ana é Never — um script de migração que roda duas vezes no mesmo container pode deixar o banco em estado meio migrado, e o pod novo a cada tentativa dá rastro. Para tarefas de rede, que falham por instabilidade e funcionam na segunda, OnFailure é mais econômico.

9. Escolhendo com o kubectl run

Quando você cria um pod rápido com kubectl run, a flag --restart decide o objeto. E a decisão é maior do que parece: com Always (o padrão), o comando não cria um pod — cria um Deployment. Com Never, cria um pod solto. Com OnFailure, cria um Job.

O comando está criando um Deployment sem querer. Use a flag que cria um pod solto, que não reinicia nunca.

kubectl run forno --image=cardapio:1.0 --restart=Always
kubectl get pods
ana@notebook:~$ kubectl run forno --image=cardapio:1.0 --restart=Always
deployment.apps/forno created

ana@notebook:~$ kubectl get pods
NAME                     READY   STATUS    RESTARTS   AGE
forno-8swgvz7wkh-kpgh5   1/1     Running   0          5m

kubectl run forno --image=cardapio:1.0 --restart=Never
kubectl get pods

As respostas são diferentes já na primeira linha: deployment.apps/forno created contra pod/forno created. No primeiro caso o pod existe, mas com nome comprido, dono e a promessa de voltar sempre; no segundo é um pod só, com nome fixo e sem ninguém olhando por ele.

O painel do guia simplifica um dos casos: --restart=OnFailure cria um Job no cluster de verdade, e aqui aparece como pod. Use a caixa para fixar a diferença entre Always e Never, que é o que ela simula fielmente.

10. Cenários do dia a dia

Cenário 1: o relatório que repetia a cada dez minutos

O relatório diário foi criado como pod solto com a política padrão. Ele gerava o arquivo, saía com zero e reiniciava, gerando de novo — e mandando o e-mail de novo. A Ana trocou por um CronJob, que cria um Job por dia, com restartPolicy: OnFailure: uma execução por dia, e nova tentativa só se falhar.

Cenário 2: o pod que ficou "pronto" sem estar

Um pod com Never e um servidor dentro: o programa terminou por causa de um arquivo de configuração ausente, e o pod ficou Failed, parado, sem ninguém reiniciar. O time estranhou a "falta de resiliência". Não era falta de resiliência: era política errada para um serviço. Servidor pede Always; tarefa pede Job.

Cenário 3: o CrashLoopBackOff que não era do cluster

O pod do site entrava em CrashLoopBackOff de hora em hora. O cluster estava tentando, com espera crescente, e o exit code 1 no Last State apontava para uma variável de ambiente faltando. A política estava certíssima; o programa é que não tinha o que precisava. Sem o describe, a tentação é culpar o Kubernetes — e ele só estava reiniciando.

12. Resumo

O restartPolicy é um campo do spec do pod e vale para todos os containers dele. São três valores: Always (o padrão) reinicia sempre, ignorando o código de saída; OnFailure reinicia só quando o programa falha; Never deixa o container terminar e não mexe mais. Quem executa é o kubelet, no nó, e é por isso que o reinício é rápido.

Falhas repetidas entram em backoff: dez, vinte, quarenta segundos, dobrando até o teto de cinco minutos. Durante essa espera o pod aparece como CrashLoopBackOff, e o RESTARTS alto indica que o cluster já está esperando. O backoff é proteção, não a causa — a causa está no exit code do describe.

Reiniciar container (kubelet) e recriar pod (ReplicaSet, Job) são coisas diferentes, e pod solto não tem quem o recrie. Cada objeto tem sua regra: Deployment só aceita Always; Job e CronJob só aceitam OnFailure ou Never, no spec.template.spec. Para a padaria, a regra prática é: site e API sempre Always; migração e relatório em Job. Na próxima aula a Ana coloca um passo antes do container principal — os init containers.

Para lembrar
  • restartPolicy fica em spec e vale para o pod inteiro; o padrão é Always.
  • OnFailure só reinicia quando o código de saída é diferente de zero.
  • CrashLoopBackOff é espera crescente: 10s, 20s, 40s… até 5 minutos.
  • Deployment exige Always; Job exige OnFailure ou Never.
  • No Job, a política fica em spec.template.spec.restartPolicy.
  • kubectl run --restart=Always cria Deployment; --restart=Never cria Pod.
