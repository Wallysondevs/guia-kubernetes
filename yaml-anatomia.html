A anatomia do YAML

A Ana já criou pod, já leu a tabela do kubectl get e já sabe que o manifesto é o jeito de guardar a receita. Aí ela copia um manifesto de um blog, roda o kubectl apply e recebe um erro que não fala de pod, de imagem nem de cluster: fala de indentação. Nesta aula ela aprende a linguagem do arquivo — chave e valor, listas com hífen, dois espaços de recuo, comentários e separadores — e a ler os cinco erros de YAML que aparecem antes de qualquer erro de Kubernetes. É a aula que economiza mais tempo de todas: quase todo manifesto que “não funciona” está apenas mal escrito.

Você vai aprender
  • Por que o Kubernetes escolheu YAML e o que o arquivo representa.
  • Chave e valor: os dois-pontos, o espaço depois deles e o que é um mapa.
  • Os tipos que você escreve sem perceber: texto, número, booleano, nulo e lista.
  • O hífen das listas e por que ele muda tudo no spec.containers.
  • Indentação com dois espaços, o tab proibido e a mensagem de erro de cada tropeço.
  • Comentários, --- e arquivos com vários objetos.
  • Distinguir erro de YAML de erro do Kubernetes pelo texto da mensagem.

1. A cena: o manifesto que não abre

O site da padaria já roda em um pod com o manifesto escrito à mão pela Ana, e funciona. Animada, ela resolve copiar de um blog um manifesto mais completo, com etiquetas, portas e limites de memória, para “deixar profissional”. Salva como cardapio.yaml, roda kubectl apply -f cardapio.yaml e recebe:

error: error parsing cardapio.yaml: error converting YAML to JSON: yaml: line 1: bad indentation of a sequence entry

A primeira reação é achar que o cluster quebrou. Não quebrou: o arquivo nem chegou ao cluster. O kubectl lê o YAML no seu computador, transforma em JSON e só então envia. Se o YAML não fecha, o envio nem começa — e o erro é do tradutor, não do Kubernetes. É por isso que ele fala de “sequência” e “indentação”, palavras que não existem no vocabulário de pods.

O manifesto copiado tinha uma linha com um espaço a menos. Um espaço. A Ana levou quarenta minutos para achar, porque o erro não aponta a linha (no cluster de verdade aponta; no painel deste guia a mensagem vem com um número fixo) e porque ela estava procurando problema no lugar errado — na imagem, no nome, na memória. O problema estava na forma do arquivo.

Esta aula é sobre essa forma. YAML é pequeno: cinco ou seis regras resolvem 95% dos casos. O resto é reconhecer a mensagem e saber onde olhar. No fim, você vai ler um manifesto de dez linhas e enxergar a estrutura — o que é mapa, o que é lista, o que é texto e o que é número — sem pensar.

2. YAML é só um formato de dados

YAML é uma maneira de escrever dados em texto, como o JSON, só que feita para olho humano. O JSON usa chaves, colchetes e vírgulas; o YAML usa recuo e hífen. O conteúdo é o mesmo: um objeto com campos dentro de campos. O nome é brincadeira — “YAML Ain't Markup Language”, “YAML não é linguagem de marcação”. Não é linguagem de programação também: não tem if, não tem laço, não executa nada. É uma lista de dados com aparência de texto.

O Kubernetes adotou YAML porque manifesto é coisa que gente lê, revisa e guarda em repositório. Um arquivo com replicas: 3 é compreensível por qualquer pessoa da equipe; o mesmo dado em JSON é uma linha comprida com três níveis de chaves. E o cluster guarda tudo em JSON no fim das contas — o YAML é só a roupa com que você entrega e recebe.

Três ideias resolvem o começo. Primeira: tudo é chave e valor. Segunda: o recuo diz a quem a chave pertence. Terceira: o hífen diz que aquilo é um item de lista. Se você entender essas três, entende qualquer manifesto deste guia.

Uma coisa que confunde quem vem de HTML: no YAML, espaço não é estilo, é estrutura. Em HTML, você pode indentar como quiser e a página não muda. Em YAML, mover uma linha dois espaços para a direita muda o significado do arquivo: a chave passa a pertencer a outro pai. É a diferença entre “a imagem do container web” e “uma chave solta que ninguém reconhece”.

3. Chave e valor: o mapa

A peça básica é o par. À esquerda, o nome do campo; à direita, o valor. Entre os dois, dois-pontos e um espaço. Sem o espaço, o YAML não reconhece o par — name:web é lido como um texto solto, e o erro que aparece depois não tem nada a ver com o que você escreveu.

Quando o valor é simples, ele fica na mesma linha. Quando o valor é um conjunto de outros campos, ele fica nas linhas de baixo, com dois espaços a mais, e os dois-pontos ficam sozinhos no fim:

metadata:
  name: cardapio
  labels:
    app: cardapio

Leia em voz alta: “metadata tem name igual a cardapio, e tem labels, e labels tem app igual a cardapio”. O recuo de name e labels é o mesmo (dois espaços), então os dois são filhos de metadata. O recuo de app é maior (quatro espaços), então app é filho de labels. Essa é a hierarquia inteira. Não há chave de fechamento, não há ponto final: quem fecha o bloco é a próxima linha com recuo menor, ou o fim do arquivo.

Dá para escrever mapa na forma curta, entre chaves, como JSON: labels: {app: cardapio}. O YAML aceita, e o Kubernetes entende. Só que ninguém escreve manifesto assim, e ler fica pior. Use a forma de linhas.

E o mais importante: dois espaços por nível, sempre. O YAML aceita qualquer número de espaços, desde que o mesmo nível use o mesmo número — um espaço também funciona. A comunidade escolheu dois porque cabe muito nível na tela e porque é o que o kubectl usa quando devolve um arquivo. Escolha dois e não invente: quando você cola um trecho de outro arquivo com quatro, o desalinhamento é questão de tempo.

4. Os tipos que você digita sem perceber

YAML não pergunta o tipo: ele adivinha pelo formato. 8080 vira número; "8080" vira texto; true vira booleano; cardapio vira texto. Adivinhar é prático para escrever e perigoso para errar, porque o Kubernetes valida tipos com rigor: um campo que espera inteiro recusa texto, e um campo que espera texto recusa número. É o assunto do primeiro erro da sua vida com manifesto.

chave
O nome do campo, antes dos dois-pontos: name, image, containerPort. Tem de ser exatamente o nome que o Kubernetes conhece — containerPorts no plural não existe.
valor
O que vem depois dos dois-pontos e do espaço. Pode ser um dado simples na mesma linha ou um bloco nas linhas seguintes, mais indentado.
hífen
Marca um item de lista. Aparece no começo do item e conta como recuo: tudo o que pertence àquele item fica alinhado depois dele.
comentário
Começa com # e vai até o fim da linha. O kubectl ignora. Serve para explicar por que aquele valor está ali — e é a única parte do arquivo que não vira dado.
documento
Um arquivo YAML pode ter vários objetos, separados por uma linha com ---. Cada pedaço desses é um documento.

As regras de aspas são poucas e valem a pena. Texto comum não precisa de aspas: name: cardapio. Use aspas quando o valor tiver dois-pontos seguido de espaço, começar com caractere especial, tiver # ou puder ser confundido com número. E, quando usar, saiba a diferença: aspas duplas interpretam escapes (\n vira quebra de linha de verdade); aspas simples não, são literais.

O caso clássico é a porta. containerPort: 8080 é inteiro, e é o que o campo quer. containerPort: "8080" é texto — parece a mesma coisa na tela, e o cluster recusa. A caixa abaixo tem esse erro de propósito. Rode, leia a mensagem e conserte.

O campo containerPort está entre aspas, e por isso chega como texto. Tire as aspas, rode de novo e veja o pod nascer.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
      ports:
        - containerPort: "8080"
The Pod "cardapio" is invalid: spec.containers[0].ports[0].containerPort: Invalid value: must be an integer

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
      ports:
        - containerPort: 8080

A mensagem é The Pod "cardapio" is invalid: spec.containers[0].ports[0].containerPort: Invalid value: must be an integer. Traduzindo: “o pod cardapio é inválido: o campo da porta do primeiro container, na primeira porta, tem valor inválido: precisa ser um inteiro”. Repare que ela dá o caminho completo, com índices — [0] é o primeiro item da lista. Aprender a ler esse caminho é metade do trabalho: ele diz exatamente onde olhar.

Booleanos seguem a mesma lógica: true e false, em minúsculas, sem aspas. Escreva assim e não invente. As formas yes, no, on e off existem em versões antigas do padrão e são interpretadas de formas diferentes por ferramentas diferentes — uma delas vira true, outra deixa como texto. Nenhum manifesto do Kubernetes precisa disso. Quando o valor é vazio, use null ou deixe a chave sem nada depois dos dois-pontos.

5. A lista e o hífen

Lista é a segunda estrutura do YAML, e é onde o recuo engana. Um item de lista começa com hífen e espaço. Uma lista de textos é a forma mais simples:

args:
  - --porta
  - "8080"

Aqui args vale dois textos: --porta e 8080. Cada hífen é um item. Note que 8080 está entre aspas porque, como argumento de programa, é texto — sem aspas, viraria número e a validação reclamaria.

Agora a lista que importa: lista de mapas. Um container é um mapa com nome, imagem, portas. Vários containers são uma lista desses mapas. O hífen marca onde cada mapa começa, e todas as chaves daquele mapa ficam alinhadas com a primeira:

spec:
  containers:
    - name: web
      image: cardapio:1.0
      ports:
        - containerPort: 8080

Conte os espaços: containers está em dois; o hífen, em quatro; name vem depois do hífen mais um espaço; image e ports estão na mesma coluna de name — ou seja, pertencem ao mesmo mapa. E ports é outra lista, com um item só, que começa com hífen em oito e tem containerPort em dez.

Existe uma variação que confunde: o hífen pode ficar na mesma coluna da chave pai, e o conteúdo deslocado dois espaços. As duas formas abaixo são o mesmo dado, e o YAML aceita as duas:

containers:
  - name: web

containers:
- name: web

Escolha a primeira e não misture. O kubectl devolve a primeira forma quando você pede -o yaml, e é a que a maioria dos exemplos usa. Misturar as duas no mesmo arquivo é fonte de erro de recuo que ninguém enxerga.

Um erro comum é esquecer o hífen — ou trocar o nome do campo por engano. Escrever container: no singular, com as chaves do container embaixo, faz o cluster procurar containers e não achar nada. O terminal responde assim (transcrição do painel, que reproduz a resposta do cluster):

$ kubectl apply -f cardapio.yaml
The Pod "cardapio" is invalid: spec.containers: Required value

“Required value” num campo que você jurou que escreveu é sempre sinal de que o campo com aquele nome não existe ali — pode ser o hífen que faltou, pode ser a letra trocada. E se a mensagem diz “must be a list”, o problema é parecido: o campo existe, mas não é uma lista. Nos dois casos, o erro está na forma, e a linha que o cluster cita é a chave pai, não a linha errada.

6. Indentação é estrutura

Chegamos ao erro número um. O recuo é o que define hierarquia, então cada nível precisa estar alinhado com precisão de coluna. Um espaço a mais e a chave muda de pai; um espaço a menos e a linha briga com a de cima. O YAML não conserta, não avisa com jeitinho: ele para de ler e devolve bad indentation of a sequence entry (“indentação ruim de um item de lista”) ou bad indentation of a mapping entry (“indentação ruim de um campo”).

Pior: a mensagem aponta um lugar que nem sempre é o lugar do erro. O YAML só percebe que algo está errado quando encontra uma linha que não encaixa no nível anterior. Na prática, olhe a linha citada e a de cima, e conte os espaços das duas.

A caixa abaixo tem o recuo torto de propósito: image está um espaço à esquerda de name. Rode, leia, e alinhe as duas chaves.

A chave image está desalinhada em relação a name. Corrija o recuo, rode de novo e veja o pod em Running no painel.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
     image: cardapio:1.0
error: error parsing cardapio.yaml: error converting YAML to JSON: yaml: line 1: bad indentation of a sequence entry

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0

A mensagem que aparece é error: error parsing cardapio.yaml: error converting YAML to JSON: yaml: line 1: bad indentation of a sequence entry. Três pedaços: error parsing diz que o problema é o arquivo; error converting YAML to JSON diz a etapa; e a parte depois de yaml: é a mensagem do tradutor. No cluster de verdade, esse número é a linha real; no painel deste guia ele vem fixo em line 1 — o que importa é o texto, e o texto diz “indentação de item de lista”, porque a linha anterior era um hífen.

Sobre o tab: nunca use a tecla Tab para indentar YAML. O padrão proíbe, e o terminal responde com uma frase que não deixa dúvida:

$ kubectl apply -f cardapio.yaml
error: error parsing cardapio.yaml: error converting YAML to JSON: yaml: line 1: tab characters must not be used in indentation

O motivo é histórico — tab não tem largura fixa, então dois editores mostrariam arquivos diferentes —, mas a regra é dura. Configure o editor para inserir dois espaços quando você aperta Tab, e o problema desaparece para sempre. Se você colar um trecho de um site e o erro falar de tab, é isso: selecione o bloco e converta.

7. Comentários, --- e vários objetos

Comentário começa com # e vale até o fim da linha. O kubectl descarta. Use para explicar decisões que o arquivo não conta sozinho: por que a memória é 256Mi, por que a imagem está presa naquele número, quem pediu aquele limite. Evite comentar o óbvio (# nome do pod em cima de name) — comentário que repete o código envelhece mal.

Um arquivo pode ter mais de um objeto, e o separador é uma linha com três hífens: ---. Cada documento é lido sozinho e aplicado na ordem. É assim que se guarda o site inteiro num arquivo só: o pod, o serviço, a configuração. O kubectl apply -f percorre os documentos e aplica um por um, mostrando uma linha de resposta para cada.

O erro clássico é esquecer o separador. Sem ---, o YAML vê o segundo apiVersion como se fosse uma segunda chave do primeiro documento, e responde duplicated mapping key (“chave repetida”). A caixa abaixo reproduz exatamente isso: dois objetos colados, sem separador.

O arquivo tem um pod e um ConfigMap, mas falta o separador de documentos. Acrescente a linha --- entre os dois e rode: o painel tem de criar os dois objetos.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio-config
data:
  preco: "3,50"
error: error parsing cardapio.yaml: error converting YAML to JSON: yaml: line 1: duplicated mapping key

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio-config
data:
  preco: "3,50"

Depois do conserto, o painel mostra pod/cardapio created e configmap/cardapio-config created, um para cada documento, na ordem do arquivo. Repare no "3,50" entre aspas: sem elas, o valor continuaria texto por causa da vírgula, mas com elas não há dúvida — e preço é texto, não número, porque tem vírgula e porque ninguém vai somar preço no cluster.

Existe ainda o bloco de texto, útil em ConfigMap que guarda arquivo de configuração. | preserva as quebras de linha; > junta tudo num parágrafo. Você vai ver os dois na aula de ConfigMap; por ora, saiba que existem e que a barra vertical é a que mantém o texto como você digitou.

E tem o fim de documento, ..., que quase ninguém usa. Se você encontrar num arquivo antigo, não é erro: é o marcador de que ali termina um documento. Ignore.

8. Erro de YAML ou erro do Kubernetes?

Vale treinar o reflexo mais útil desta aula: antes de investigar o cluster, descubra de quem é o erro. A mensagem conta. Se ela começa com error: error parsing, o arquivo nem foi lido — é YAML. Se vem The Pod "x" is invalid:, o arquivo foi lido e o conteúdo recusado — é validação do Kubernetes. Se é resource mapping not found, o YAML está bom e o apiVersion é que não combina com o kind. E se aparece Error from server (NotFound), o arquivo estava perfeito e o problema é o que existe (ou não) no cluster.

Há um detalhe que vale para todos: o YAML não tem como saber o que você quis dizer. Ele só sabe o que está escrito. Por isso containerPorts (plural) não gera erro de YAML — gera um campo desconhecido, que versões antigas ignoravam em silêncio e as novas, com validação estrita, acusam. Se um campo parece não ter efeito, confira a grafia antes de tudo: maiúscula no meio, plural a mais, hífen no lugar de nada.

Note a linha do 1.0: sem aspas, o YAML lê como número e o valor vira 1 quando alguém imprime. Por isso tag de imagem e versão de aplicação se escrevem como texto quando aparecem em campo de texto — e por isso image: cardapio:1.0 funciona: ali o valor inteiro é lido como texto, porque cardapio:1.0 não é um número.

9. Cenários do dia a dia

Cenário 1: o manifesto que só funciona na máquina dela

A Ana editou o cardapio.yaml no editor com tab configurado. Na máquina dela, o editor mostrava tudo alinhado e o arquivo aplicava. Ao mandar para o colega, o erro de tab apareceu. O conserto não foi no arquivo, foi no editor: ligar “insert spaces” e definir dois espaços por nível. Regra prática: se o arquivo passa na sua máquina e falha na do outro, o primeiro suspeito é espaço invisível.

Cenário 2: o pod que perdeu a etiqueta

Ela colou um bloco de labels de um exemplo e o recuo ficou um nível acima, então as etiquetas passaram a ser filhas de metadata.name em vez de metadata.labels. O YAML aceitou (é válido!), o pod subiu, e o Service não achava o pod. O erro não era de YAML: era de estrutura. O kubectl get pod -o yaml mostrou a bagunça na hora — e é por isso que vale sempre conferir o objeto que o cluster guardou, não só o arquivo que você enviou.

Cenário 3: um arquivo, o site inteiro

O time dela juntou pod, ConfigMap e Service num único site.yaml, separados por ---. O ganho é aplicar tudo com um comando e versionar junto. O custo é que um erro de indentação em qualquer documento derruba o arquivo inteiro: o kubectl lê todos antes de aplicar qualquer um. Quando um apply desse arquivo falha, divida em arquivos menores para achar o culpado — ou comente os documentos com # até o erro mudar de lugar.

11. Resumo

YAML é um formato de dados com três estruturas: o par chave: valor, o mapa (vários pares aninhados por recuo) e a lista (itens com hífen). O recuo é a estrutura: dois espaços por nível, nunca tab, e cada nível alinhado na coluna. O tipo do valor é adivinhado pelo formato — 8080 é número, "8080" é texto — e o Kubernetes valida isso com rigor.

Comentário começa com #; vários objetos no mesmo arquivo são separados por ---; o hífen marca item de lista, e esquecer o hífen transforma a lista em mapa. Erro de YAML vem com error parsing na frente e aparece antes de qualquer contato com o cluster; erro de validação vem com is invalid e traz o caminho do campo, com índices, para você achar a linha. Erro de versão vem com resource mapping not found.

Com isso, a Ana consegue ler o próprio arquivo. O passo seguinte é a pergunta que fica: o que exatamente o kubectl apply faz com esse arquivo — como ele decide criar, atualizar ou não mexer em nada, e como testar tudo isso sem tocar no cluster de verdade. É o assunto da próxima aula.

Para lembrar
  • chave: valor, com dois-pontos e um espaço. Sem o espaço, não é par.
  • Dois espaços por nível, sempre iguais. Tab é proibido.
  • Hífen marca item de lista; as chaves do item se alinham depois dele.
  • Sem aspas é número, booleano ou texto adivinhado; com aspas é texto.
  • # comenta a linha; --- separa documentos do mesmo arquivo.
  • error parsing é YAML; is invalid é validação; resource mapping not found é apiVersion.
