Cluster local completo

Até agora a Ana viu o cluster responder em caixas de aula. Chegou a hora de ter um de verdade: três nós, dentro da máquina dela, criados por um comando e apagados por outro. Nos próximos minutos você vai montar esse cluster, entender o que roda em cada nó, ver um DaemonSet ocupar os três — e derrubar tudo sem deixar container órfão, imagem gigante nem contexto perdido no kubeconfig.

Você vai aprender
  • O que é o kind e por que os nós dele são containers.
  • Como criar um cluster nomeado de três nós e conferir o contexto.
  • O que roda no control-plane e o que roda nos workers.
  • Por que um DaemonSet não entra no control-plane sem toleration.
  • Como apagar o cluster inteiro e o que sobra depois disso.
  • Onde o painel do guia para e o cluster da sua máquina começa.

1. O que você vai construir

No fim desta página a Ana tem um cluster chamado guia rodando na máquina dela, com um nó de controle e dois workers. Dentro dele, uma loja com três réplicas espalhadas e um agente que roda em todos os nós. E, no fim, o mesmo cluster apagado por um comando, com a máquina limpa.

A imagem mental é a de uma maquete de cidade montada na mesa da cozinha. Ela tem prefeitura (o control-plane), dois bairros (os workers) e ruas (a rede interna). Não é a cidade real, mas funciona igual o suficiente para testar o plano diretor: endereços, trânsito, distribuição de moradores. Quando você termina, desmonta a maquete inteira numa caixa — e a mesa volta a ficar livre.

O programa que monta essa maquete é o kind — o mesmo do primeiro cluster, agora com três nós: “Kubernetes in Docker”. Ele cria containers Docker e faz de cada um um nó do cluster. Um cluster de três nós custa três containers e alguma memória — bem menos do que três máquinas virtuais, e infinitamente menos do que três servidores alugados.

2. O cenário da padaria

A Ana quer testar três coisas antes de mexer no cluster da loja: um Deployment com três réplicas, um DaemonSet novo de coleta de logs e uma política de rede. No cluster da loja, cada teste é uma aposta: um DaemonSet mal configurado pode encher os nós de pods, e uma NetworkPolicy errada pode cortar o tráfego do site.

O cluster local resolve isso do jeito mais confortável possível: errar ali não custa nada. Se o DaemonSet ocupar todos os nós e travar a máquina, você apaga o cluster e cria outro em dois minutos. Se a política de rede cortar tudo, idem. Ninguém recebe alerta, nenhum cliente reclama, e o único limite é a memória do notebook.

Tem um preço, e é bom conhecê-lo desde já: o cluster local não tem a escala do cluster de produção. Ele tem três nós e vive de containers na mesma máquina — sem alta disponibilidade de verdade, sem o tráfego real, sem a conta do cloud. Serve para aprender e para testar manifesto; não serve para medir desempenho nem para hospedar o site.

3. Antes de começar

Três coisas precisam existir na máquina: o Docker (ou outro runtime de containers), o kubectl e o kind. O Docker é o pré-requisito que ninguém avisa — sem ele, o kind não tem onde criar os nós. O kubectl é o cliente que fala com o cluster. O kind é o programa que monta o cluster.

Existe uma alternativa ao kind que vale conhecer: o kwokctl, do projeto KWOK. Ele simula nós sem rodar container nenhum — cada “nó” é um objeto no etcd, e os pods aparecem como Running sem nenhum processo de verdade. Isso é ótimo para testar agendamento, taints, réplicas e DaemonSets com memória quase zero, e péssimo para testar imagem, volume ou log de aplicação, porque nada roda de fato. 4. Passo 1 — criar o cluster

Primeiro comando do projeto, e ele faz bastante coisa: baixa a imagem do nó, cria os containers, sobe o control-plane, instala a rede (CNI) e uma StorageClass padrão, e escreve o contexto no kubeconfig. O painel abaixo é um terminal: cada linha é um comando, e ele responde como responderia na máquina da Ana.

Troque a listagem pela criação: rode kind create cluster --name guia e depois kubectl config current-context. O painel tem de mostrar a criação e o contexto kind-guia.

kind get nodes
kubectl config current-context
ana@notebook:~$ kind get nodes
guia-control-plane
guia-worker
guia-worker2

ana@notebook:~$ kubectl config current-context
kind-guia

kind create cluster --name guia
kubectl config current-context

A saída da criação é uma sequência de etapas, cada uma com um emoji. Esta é a do motor, e é fiel ao que o kind imprime:

ana@notebook:~$ kind create cluster --name guia
Creating cluster "guia" ...
 • Ensuring node image (kindest/node:v1.37.3) 🐳
 • Preparing nodes 📦
 • Writing configuration 📜
 • Starting control-plane 👷
 • Installing CNI 💉
 • Installing StorageClass 📦
Set kubectl context to "kind-guia"
You can now use your cluster with:

kubectl cluster-info --context kind-guia

Duas etapas merecem atenção. Installing CNI é a rede entre pods: sem ela, os pods sobem mas não conversam entre si, e o cluster parece meio quebrado. Installing StorageClass é o provisionador local que faz PVCs funcionarem — é o mesmo tipo de objeto da aula de armazenamento, apontando para o disco do nó.

Se você rodar o comando de novo, com o mesmo nome, o kind reclama que o cluster já existe. Nomes são identidade: para ter dois clusters, use dois nomes (guia e teste), e o kubeconfig passa a ter dois contextos. É assim que se testa “o apply no cluster errado” sem apostar a loja.

5. Passo 2 — os três nós e o que roda em cada um

Cluster criado, hora de olhar para dentro. O comando kubectl get nodes mostra os três nós, com papel e versão. Um é control-plane (a prefeitura) e dois são workers (os bairros). Não existe “nó principal” além do control-plane: quem decide onde cada pod cai é o agendador.

A caixa abaixo tem a loja com três réplicas e um DaemonSet agente. Rode do jeito que está e conte os pods do agente: são dois, porque o control-plane tem uma taint que expulsa pods comuns. A missão é dar ao agente a toleration que o autoriza a entrar lá também.

Acrescente em spec.template.spec do DaemonSet uma toleration com key: node-role.kubernetes.io/control-plane, operator: Exists e effect: NoSchedule. Rode e confira os três pods do agente em nós diferentes.

Uma diferença entre o painel e o seu cluster que vale dizer: no painel, os três pods da loja são distribuídos entre os três nós. Num cluster kind de verdade, o control-plane tem a taint node-role.kubernetes.io/control-plane:NoSchedule, e pods comuns ficam nos workers — por isso o DaemonSet acima precisou de toleration. O painel simplifica o agendamento para você ver o espalhamento; a taint, ele mostra no manifesto e no efeito do DaemonSet.

6. Passo 3 — derrubar sem sujeira

Derrubar é mais importante do que parece. Um cluster kind esquecido consome memória, ocupa portas e guarda imagens que somam gigabytes. E o pior resíduo não é o disco: é o contexto no kubeconfig, que fica apontando para um cluster que não existe mais e faz todo kubectl falhar com erro de conexão recusada.

O comando certo apaga o cluster inteiro — containers, volumes, rede e a entrada no kubeconfig. A caixa parte de um cluster com a loja rodando; a missão é apagar o Deployment e o cluster, na ordem em que isso faz sentido.

Apague primeiro o Deployment cardapio e depois o cluster: kubectl delete deployment cardapio e kind delete cluster. Rode e confira as duas respostas.

kubectl get pods
kind get nodes
ana@notebook:~$ kubectl get pods

ana@notebook:~$ kind get nodes

A resposta do delete é curta e definitiva:

ana@notebook:~$ kind delete cluster
Deleting cluster "guia" ...
Deleted nodes: ["guia-control-plane" "guia-worker" "guia-worker2"]

Depois disso, kind get clusters responde com uma lista vazia, kubectl get nodes falha porque não há para onde conectar, e o contexto sai do kubeconfig. Se você criou dois clusters, apagar um não mexe no outro — o comando age sobre o nome que você passar.

7. Conferindo com o painel

Três comandos bastam para saber onde você está. kubectl config current-context diz qual cluster está no comando. kubectl cluster-info diz se ele responde. E kubectl get nodes diz quantos nós existem e se estão prontos.

Um quarto comando é útil justamente por falhar: kubectl top nodes pede métricas de CPU e memória ao servidor de métricas, que não vem instalado por padrão. No painel, a resposta é a do cluster sem metrics-server:

$ kubectl top nodes
error: Metrics API not available

Isso não é defeito do seu cluster local: é a configuração de fábrica. Para ter números, é preciso instalar o metrics-server — e, num kind, ele precisa de uma opção extra para confiar no certificado do kubelet. Enquanto isso, a leitura de consumo é por outro caminho: kubectl describe node mostra os pedidos e limites somados por nó, e é o que responde “cabe mais um pod aqui?”.

Com dois clusters criados, a conferência vira rotina de segurança: o comando kubectl config get-contexts lista todos, com um asterisco no atual. Antes de qualquer apply em ambiente que importa, olhe essa lista — é o mesmo hábito que salvou a Ana no projeto de multiambiente.

kubeconfig
Um arquivo só, em ~/.kube/config, com tudo o que o kubectl sabe sobre clusters, usuários e contextos. O kind escreve nele ao criar o cluster e apaga a entrada ao deletar.
clusters
Os endereços dos servidores de API e as autoridades certificadoras. Um por cluster, com nome próprio.
contexts
A ligação entre um cluster, um usuário e um namespace padrão. É o que aparece em get-contexts e o que o use-context troca.
current-context
O contexto em uso. Todo comando sem --context vai para ele — e é aqui que nascem os acidentes de aplicar no cluster errado.
--context nome
A flag que ignora o contexto atual e usa o que você mandar. Em produção, use sempre.

8. Quando não funciona

Cinco problemas cobrem quase toda primeira tentativa de cluster local. Nenhum é do Kubernetes; todos são de ambiente.

1. Docker parado. O kind responde que não conseguiu falar com o daemon. Conserto: abrir o Docker e esperar ele terminar de subir antes de rodar o comando de novo.

2. Cluster com o mesmo nome. O kind recusa a criação. Conserto: usar outro nome ou apagar o antigo com kind delete cluster --name guia.

3. Porta ocupada. Se você mapeia portas do cluster para a máquina (para abrir o site no navegador), duas tentativas na mesma porta brigam. Conserto: mapear outra porta, ou usar kubectl port-forward.

4. Contexto apontando para cluster morto. Todo comando falha com conexão recusada. Conserto: kubectl config get-contexts para ver, e kubectl config use-context para trocar.

5. Disco cheio de imagens. Cada cluster kind baixa a imagem de nó, e cada imagem de aplicação que você testa fica guardada. Conserto: docker system df para ver o tamanho e docker image prune para limpar o que não está em uso.

Cenário 1: o cluster que ficou ligado no fim de semana

A Ana criou o cluster na sexta para testar um DaemonSet e esqueceu. Na segunda, o notebook estava lento e o ventilador não parava. Eram três containers de nó e uma dúzia de pods consumindo memória havia dois dias. O conserto foi o hábito: kind delete cluster no fim de cada sessão, e kind get clusters para conferir se sobrou algum.

Cenário 2: o teste que não provava nada

O time montou um cluster com kwokctl para testar um Deployment com limites de memória. Os pods apareciam como Running, o HPA escalava, tudo verde. Ao levar para o kind, os pods morriam por falta de memória: com nós simulados, nenhum processo consome nada, então limite de memória não tem como ser testado. A lição: escolher a ferramenta pela pergunta — agendamento no kwok, execução no kind.

Cenário 3: o apply no cluster da loja

Com dois contextos no kubeconfig (o local e o da loja), o comando foi para o cluster errado: um kubectl delete namespace padaria digitado no terminal errado. O namespace era de teste, então o estrago foi pequeno. Desde então, todo comando em cluster de verdade leva --context explícito, e o prompt do terminal mostra o contexto atual.

9. O que ficou de aprendizado

Você tem um cluster de três nós na máquina, sabe o que roda em cada um e sabe derrubar tudo. O kind transforma containers em nós; o control-plane guarda o estado e decide, os workers executam. O DaemonSet é o objeto que traduz “em todos os nós” em pods — e o control-plane só entra na conta se você declarar a toleration.

A parte de limpeza não é detalhe: cluster esquecido consome memória, imagem esquecida consome disco, contexto esquecido quebra comando. Três comandos resolvem — kind get clusters, docker system df e kubectl config get-contexts — e valem a visita de vez em quando.

E a fronteira do painel, como sempre: ele entende kind e kubectl no terminal, prova nós, pods e distribuição, mas não baixa imagem, não roda container e não tem metrics-server. O que depende de processo de verdade — consumo, log de aplicação, falha de imagem — aparece aqui como transcrição, sempre identificada. O resto, você faz no cluster da sua máquina, com os mesmos comandos.

Para praticar sozinho

Crie um segundo cluster com kind create cluster --name teste, rode kubectl config get-contexts e alterne entre eles com use-context. Depois apague só o teste e confirme que o guia continua de pé. É o exercício mais próximo do dia a dia de quem opera dois ambientes com nomes parecidos.

Exercício: o nome do contexto

O cluster criado com kind create cluster --name guia ganha um contexto no kubeconfig. Complete o prefixo do nome dele, conforme o kind imprime na criação:

guia

Dica: é o mesmo prefixo que aparece em “Set kubectl context to …” na saída da criação — quatro letras e um hífen.

Resumo

Cluster local completo é o kind: containers viram nós, um comando cria, outro apaga. Um cluster de três nós tem um control-plane (apiserver, etcd, scheduler, controller-manager) e dois workers (kubelet, kube-proxy, CNI). O kubectl get nodes -o wide mostra nome, papel, IP e versão; o get pods -o wide mostra em qual nó cada pod caiu.

O DaemonSet é o objeto de “um por nó”, e o control-plane só participa se você declarar a toleration da taint node-role.kubernetes.io/control-plane. Já o kwokctl simula nós sem rodar nada: ótimo para agendamento, inútil para memória, imagem e log.

E a limpeza: kind delete cluster leva containers, volume, objetos e contexto. Sobram imagens no Docker, que se limpam com docker image prune. Com isso você fecha o ciclo — criar, testar, derrubar — sem deixar rastro e sem tocar em nada de ninguém. A partir daqui, o próximo passo é repetir o mesmo ciclo com as suas próprias aplicações: o cluster é seu.

Para lembrar
  • kind create cluster --name guia cria três nós e o contexto kind-guia.
  • Nó de kind é container; kwokctl simula nós sem processo nenhum.
  • Control-plane tem taint: DaemonSet só entra com tolerations.
  • kubectl top nodes falha sem metrics-server — isso é o padrão.
  • kind delete cluster apaga tudo do cluster, inclusive o contexto.
  • Imagens ficam no Docker: docker system df e image prune.
