GitOps: o Git como fonte da verdade

A Ana já entendeu o conceito de GitOps: o repositório manda e o cluster obedece. Entender não é o mesmo que ter. Neste projeto ela monta o fluxo inteiro da padaria — o chart e o values da loja versionados, a Application que amarra o repositório ao namespace, o primeiro sync — e depois faz o que separa GitOps de conversa: causa um drift de propósito, desfaz, e destrava um OutOfSync que não quer sair. No fim, o cluster vira descartável: se ele sumir hoje, o repositório reergue tudo amanhã.

Você vai aprender
  • Como separar o que é repositório do que é cluster, e por que isso muda a rotina do time.
  • A Application do Argo CD campo por campo: origem, destino e política.
  • O values.yaml como painel de botões do chart, e o manifesto como consequência dele.
  • O drift que um kubectl na mão provoca — e o tamanho do estrago.
  • O que o sync aplica, o que o prune apaga e o que o selfHeal devolve.
  • A rotina de conferência com argocd app get, diff e history.
  • Os cinco tropeços que mantêm um app em OutOfSync para sempre.

1. O que você vai construir

No fim deste projeto, a padaria tem três peças que conversam sozinhas. A primeira é o repositório git.loja.test/padaria/site.git, com o chart do Helm em chart/loja e os valores de produção em values-producao.yaml. A segunda é a Application loja, o objeto que diz ao Argo CD “olhe esta pasta deste repositório e deixe o namespace padaria igual a ela”. A terceira é o cluster, que passa a ser consequência das duas primeiras — e não mais o lugar onde alguém digita comandos.

Vale desenhar a imagem mental, porque ela resolve a maioria das dúvidas antes de aparecerem. Uma única seta: o commit entra no repositório, o Argo CD lê o repositório, o Argo CD escreve no cluster. A seta só aponta para um lado. Quando alguém muda o cluster na mão, o GitOps não importa a mudança para o repositório: ele apaga a mudança. Essa assimetria é o coração do assunto.

O teste de fogo é cruel de propósito: kind delete cluster, kind create cluster, instalar o Argo CD, aplicar a Application e esperar. Se a loja volta igual — mesma imagem, mesmas réplicas, mesmo Service —, o repositório é fonte da verdade. Se volta “quase”, o que faltou é exatamente o que falta versionar.

2. O cenário da padaria

Na sexta-feira o time da Ana publicou a versão 1.4.0 do cardápio. O commit entrou, a imagem foi construída, e alguém desligou o sync automático do Argo CD “só até o fim do mutirão”. O mutirão acabou, o sync ficou desligado, e ninguém lembrou. O repositório dizia cardapio:1.4.0 com três réplicas; o cluster continuou com cardapio:1.0.0 e duas.

No sábado, o filho da Ana quis testar a imagem nova e fez o que qualquer pessoa faria: kubectl set image com uma tag de teste e kubectl scale para cinco réplicas, para “ver se aguenta”. Funcionou. Ele foi almoçar. Na segunda-feira, a tela do Argo CD mostrava OutOfSync em vermelho, o cluster tinha cinco pods rodando uma imagem que não existe em lugar nenhum do repositório, e ninguém sabia dizer qual era a versão “oficial” do site.

O problema não foi o teste do sábado — testar é legítimo. O problema foi o teste não ter passado pelo repositório. Com GitOps, o cluster é considerado errado até prova em contrário, e a prova é o repositório.

3. Antes de começar

Você precisa de três coisas prontas: o cluster do curso respondendo, o kubectl configurado e o Argo CD instalado no namespace argocd — a aula de GitOps mostrou como; aqui a gente usa. O Helm entra só para renderizar o chart localmente e ver o que ele produz antes de publicar.

O contrato do projeto é uma única Application. Ela não guarda manifesto nenhum: guarda onde está o manifesto e para onde ele vai. O arquivo abaixo é o do projeto — repare que o time migrou a pasta de YAML solto para um chart, e a origem agora aponta para chart/loja:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: loja
  namespace: argocd
spec:
  project: padaria
  source:
    repoURL: https://git.loja.test/padaria/site.git
    targetRevision: main
    path: chart/loja
    helm:
      valueFiles:
        - values-producao.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: padaria
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
source
De onde vem o manifesto: o repositório, o ramo e a pasta. Sem isso o Argo não tem o que aplicar.
targetRevision
Qual ponto do repositório acompanhar: main, uma tag ou um commit. É o campo que congela a versão quando você quer estabilidade.
path
A pasta dentro do repositório. Aqui é o chart; o Argo renderiza o chart com os values antes de aplicar.
helm.valueFiles
Os arquivos de valores que o Argo passa ao chart. É o “botão de produção” do helm install, só que versionado.
destination
Onde aplicar: o cluster (kubernetes.default.svc é o próprio cluster) e o namespace de destino.
syncPolicy.automated
Como aplicar: prune apaga do cluster o que saiu do repositório e selfHeal desfaz mudança feita na mão.

Com a Application aplicada e o sync ligado, o argocd app get é a foto do contrato funcionando. Esta é a transcrição de um cluster de prova do guia — o painel das caixas não tem Argo CD instalado, então essa saída não vem dele:

Leia as três linhas do topo. Synced to main com o commit 9f3c1a2 entre parênteses é o Argo dizendo “o cluster está igual a este ponto do repositório”. Healthy é outra pergunta: as réplicas estão de pé e respondendo. As duas podem discordar — dá para estar Synced e Degraded ao mesmo tempo.

4. Passo 1 — o values no repositório

O chart é o molde; o values é o painel de botões. Tudo o que muda entre um release e outro está nos valores, e o manifesto no cluster é o resultado da conta. O arquivo abaixo é o values-producao.yaml do projeto: três réplicas e a tag 1.4.0.

replicaCount: 3

image:
  repository: cardapio
  tag: "1.4.0"

service:
  port: 80
  targetPort: 8080

ingress:
  host: loja.test
replicaCount
Quantas cópias do pod o Deployment deve ter. Vira o campo spec.replicas do manifesto renderizado.
image.repository
O nome da imagem, sem a tag: cardapio. O chart junta com o registro quando você usa um registro privado.
image.tag
A versão publicada. É o campo que mais muda e o que mais causa confusão: tag igual a latest esconde a versão em uso.
service.port
A porta que o Service expõe para os outros pods do cluster.
ingress.host
O endereço público do site. Fica no values porque muda entre produção e teste, e não no template.

O exercício do passo 1 é fazer a conta que o Argo faz: olhar o values e escrever o Deployment correspondente. A caixa começa com o manifesto do release anterior — a tag 1.0.0 e duas réplicas —, que é o que o chart gerou da última vez que o sync rodou. Os valores já mudaram no repositório; o manifesto ainda não.

O values-producao.yaml diz replicaCount: 3 e tag: "1.4.0". Ajuste o Deployment para ser o que o chart renderizaria agora: três réplicas, a imagem cardapio:1.4.0 e a label version em "1.4.0" nos dois lugares.

kind: Deployment

O painel mostra cardapio 3/3 e a linha deployment.apps/cardapio created. Você não “instalou” nada: descreveu o resultado e o cluster correu atrás. E a label version é o que responde, daqui a três semanas, qual versão está no ar sem abrir o repositório. Num chart de verdade ela se chama app.kubernetes.io/version; aqui está encurtada só para caber na meta do painel, que lê caminhos separados por ponto.

E vale dizer o que essa caixa não faz, porque o assunto depende disso: ela não renderiza Helm nem lê repositório. O manifesto que você editou é o que o chart produziria. Quem renderiza de verdade é o Argo CD, na hora do sync, com o helm template por baixo.

5. Passo 2 — o drift causado na mão

Agora a parte que dói. A caixa abaixo começa no cluster que o último sync deixou: 1.0.0 com duas réplicas. Os primeiros comandos são o que o filho da Ana fez no sábado — scale para cinco e set image para uma tag de teste. Rode assim e olhe o resultado: o cluster fica com cinco pods de uma imagem que não está em lugar nenhum do repositório. É o drift, e ele não avisa.

Os quatro primeiros comandos causam o drift: cinco réplicas e a imagem cardapio:9.9.9. Complete o roteiro com o que o Argo faria no próximo sync — voltar para 3 réplicas e cardapio:1.4.0, conferindo com rollout status — e rode.

O que aconteceu, em ordem. O get mostrou 2/2: o cluster estava como o repositório mandava, só desatualizado. O scale mudou o número no objeto vivo — não no repositório — e o set image fez o mesmo com a imagem. O get pods mostrou cinco pods em Running, todos sorrindo: nada no cluster acha que está errado. É por isso que drift é perigoso — ele não gera erro, gera um site que funciona com a versão errada.

Os quatro comandos do fim são o papel do Argo CD. scale de volta para três, set image de volta para 1.4.0 — e o rollout status respondendo successfully rolled out, que é o cluster confirmando que chegou onde devia. Num cluster com selfHeal: true você não digitaria nada disso: o controlador compararia o vivo com o repositório e desfaria o drift em poucos minutos.

A última linha da tabela justifica o projeto inteiro. Um cluster que pode ser apagado sem perda não é um risco: é um ativo descartável. Um cluster que guarda coisas que só existem nele é o contrário — cada dia mais difícil de reproduzir.

6. Passo 3 — o que o Argo sincroniza

O Deployment é só o primeiro objeto da pasta. Um app leva vários, e o sync aplica todos na mesma passada: Deployment, Service, ConfigMap, HPA, Ingress. Se um está no repositório e não no cluster, o Argo cria; se está nos dois e diferente, corrige; se está no cluster e não no repositório, o prune apaga. É esse terceiro caso que derruba gente.

A caixa abaixo conta a história ao contrário: um Service aplicado na mão, fora do repositório, com o seletor errado. Os pods estão etiquetados app: cardapio, mas o Service procura app: vitrine — ninguém atende ao chamado e o site fica sem tráfego, com todos os pods em Running. É o hotfix que alguém faz às três da manhã e esquece de commitar.

Este é o hotfix.yaml que nunca entrou no repositório. O Service aponta para app: vitrine e o painel mostra <none> em ENDPOINTS. Alinhe o seletor com a etiqueta dos pods do Deployment e rode: os IPs têm de aparecer com a porta 8080.

apiVersion: v1
kind: Service
metadata:
  name: cardapio
  labels:
    app: cardapio
spec:
  type: ClusterIP
  selector:
    app: vitrine
  ports:
    - port: 80
      targetPort: 8080
service/cardapio configured

NAME       ENDPOINTS   AGE
cardapio   <none>      2m

apiVersion: v1

metadata:

  labels:
    app: cardapio
spec:

Repare em dois detalhes do painel. Com o seletor errado, a primeira linha é service/cardapio configured — o cluster aceitou o manifesto e mudou o objeto, sem discutir. É o que o kubectl apply faz: aplica e cala. A tabela de endpoints mostra <none>, e é ali que o problema aparece, não no apply. Com o seletor certo, os IPs com :8080 aparecem.

O segundo detalhe é a palavra unchanged, que aparece em vez de configured quando o manifesto já é igual ao que existe. Na caixa, a solução mostra unchanged porque o painel recomeça do cluster de exemplo a cada Rodar e esse Service já estava certo; num cluster com o hotfix aplicado, você veria configured e os endpoints voltando.

ObjetoO que o sync garanteO que ele não faz
Deploymentréplicas, imagem e labels iguais ao repositórionão garante que a imagem existe no registro
Serviceportas e seletor iguais ao repositórionão garante que existe pod com a etiqueta
ConfigMapos dados estão no cluster, com o conteúdo do commitnão reinicia pod sozinho ao mudar
Ingresshost e rotas como estão no manifestonão garante DNS, certificado nem controlador
HPAmetas e limites como estão no manifestonão garante que o metrics-server exista

A coluna da direita separa “sincronizado” de “funcionando”. O Argo é ótimo em deixar o cluster igual ao repositório e péssimo em saber se o programa responde — para isso existem probes, endpoints e métricas. Site fora do ar com tudo Synced é problema de aplicação; com algo OutOfSync, é de sincronização.

7. Conferindo com o painel

A conferência tem quatro perguntas, da mais ampla para a mais estreita: o app está sincronizado? o que difere? o cluster tem os objetos e os IPs? o que mudou de um sync para o outro? As três primeiras saem do argocd e do kubectl; a última, do histórico.

A pergunta “o que difere?” é a mais útil e a menos usada. O argocd app diff mostra o vivo e o desejado lado a lado — e é isso que transforma “está vermelho” em “duas réplicas e uma tag”. Esta é a transcrição de um cluster de prova do guia:

ana@notebook:~$ argocd app diff loja
===== apps/Deployment padaria/cardapio ======
--- live
+++ target
 spec:
-  replicas: 2
+  replicas: 3
   template:
     spec:
       containers:
-        - image: cardapio:1.0.0
+        - image: cardapio:1.4.0

O sinal de menos é “está no cluster”; o de mais, “está no repositório”. Duas linhas de diferença, dois campos, um conserto: sincronizar. Se o diff mostrasse um Service inteiro ou um ConfigMap que ninguém escreveu, a pergunta mudaria de “sincronizar” para “quem criou isso e por quê”.

No painel das caixas, os comandos argocd não existem: não há Argo CD no simulador, e o objeto Application nem é um tipo conhecido lá. O painel mostra o resultado do sync no cluster — que é o que interessa. Por isso as caixas usam kubectl, e as saídas do argocd aparecem como transcrição, com o aviso em cima.

A rotina completa, para colar no mural:

argocd app get loja
argocd app diff loja
kubectl get deployment,pods -n padaria
kubectl get endpoints cardapio -n padaria

O primeiro diz o estado e o commit de origem; o segundo, o que difere; o terceiro, se os pods existem e quantos estão prontos; o quarto, se o Service entrega tráfego. Quando o primeiro diz Synced e o site não responde, o problema é da aplicação — vale voltar às aulas de readiness e de endpoints.

8. Quando não funciona

Quase todo OutOfSync que não sai cai em um dos casos abaixo. O primeiro é o targetRevision num ramo que não recebe mais commit: o Argo mostra Synced com um ponto antigo, e o cluster é que está velho. O segundo é o path errado — a pasta mudou de nome e o Argo responde app path does not exist. O terceiro é o namespace ausente com CreateNamespace=true de fora: namespaces "padaria" not found.

O quarto é o mais silencioso: selfHeal desligado — o drift dura para sempre e o Argo só avisa. O quinto assusta mais: prune ligado num app que aponta para uma pasta incompleta apaga do cluster o que não está no repositório sem perguntar, inclusive um Secret criado à mão. Antes de ligar prune, confira se tudo o que precisa existir está versionado.

ana@notebook:~$ argocd app history loja
ID  DATE                         REVISION
0   2026-11-20 09:12:44 +0000    main (1b2c3d4)
1   2026-11-24 18:40:02 +0000    main (8e7f6a5)
2   2026-11-27 07:05:11 +0000    main (9f3c1a2)

ana@notebook:~$ argocd app rollback loja 1
Name:               argocd/loja
Sync Status:        Synced to main (8e7f6a5)
Health Status:      Healthy

O history resolve a pergunta que mais trava um incidente: “o que estava no ar quando funcionava?”. O rollback volta o cluster a um desses pontos sem tocar no repositório — é remédio, não cura. Enquanto o commit problemático continuar no main, o próximo sync traz o problema de volta; a cura é o git revert.

Cenário 1: o hotfix que ninguém commitou

Às três da manhã o disco encheu e o time subiu o limite de memória na mão, direto no Deployment. O site voltou, todo mundo dormiu, e o commit nunca veio. Na semana seguinte o selfHeal devolveu o limite antigo e o disco encheu de novo — às três da manhã. A correção não é desligar o selfHeal: é fazer do hotfix um commit. Emergência sem commit é dívida com juros.

Cenário 2: o prune que apagou o Secret

O Secret da senha do banco foi criado à mão e nunca entrou no repositório. No dia em que o time ligou prune: true para limpar objetos órfãos, o Argo fez o que prometia: apagou tudo o que não estava no Git — Secret incluído. A lição: versionar o Secret (ainda que cifrado) ou marcá-lo com a anotação que pede ao Argo para ignorá-lo.

Cenário 3: o app que estava sincronizado com o ramo errado

A Application foi criada com targetRevision: develop e copiada para produção sem trocar o campo. Meses depois o argocd app get dizia Synced em verde e o site mostrava features que ninguém tinha aprovado. Nada estava quebrado — estava sincronizado com o lugar errado.

9. O que ficou de aprendizado

Você montou o laço inteiro: o chart e o values versionados, a Application amarrando repositório e namespace, o sync aplicando, o drift aparecendo e sendo desfeito. O que ficou não é a memória dos comandos — é a ordem de autoridade. O repositório decide; o cluster obedece; quem digita kubectl na mão está criando uma dívida que o próximo sync cobra. E o teste de fogo continua valendo: se o cluster sumir hoje, ele volta do Git?

Para continuar sozinho, três caminhos naturais. O primeiro é trocar o botão do sync por um pipeline que abre um pull request no values-producao.yaml quando sai imagem nova — é GitOps com revisão humana. O segundo é o Kustomize, quando o chart fica grande demais para poucos valores. O terceiro é o cofre externo, para o Secret nunca morar no repositório.

Exercício: o campo que devolve o estado

O time desligou o sync automático por um dia e, no dia seguinte, alguém escalou o Deployment na mão. Qual campo da Application faz o Argo desfazer essa mudança sozinho, sem esperar o próximo commit? Complete o manifesto:

syncPolicy: automated: prune: true : true

Dica: prune cuida do que saiu do repositório; o outro cuida do que mudou no cluster. É o campo que a seção 5 mostrou em ação, quando o painel voltou de cinco para três réplicas.

Resumo

GitOps é uma ordem de autoridade, não uma ferramenta: o repositório declara o estado desejado, um controlador compara com o estado atual e age. Na prática, três objetos contam a história — o values.yaml com os botões (réplicas, tag, portas), o chart que transforma valores em manifesto, e a Application que liga repositório, pasta e namespace com uma política de sync. O cluster inteiro é consequência dos três.

O drift é o que aparece quando alguém fura o fluxo: um scale na mão, um set image de teste, um hotfix de madrugada. Com selfHeal ele dura minutos; sem selfHeal, dura até alguém olhar. O prune é o irmão perigoso: apaga o que não está no repositório, então só ligue quando tudo o que precisa existir estiver versionado. E Synced não significa “funcionando” — significa “igual ao Git”; quem responde “está de pé?” são os pods, os endpoints e as probes.

As caixas deste projeto aplicam o manifesto que o controlador aplicaria, porque o painel não tem Argo CD. Num cluster de verdade o dia a dia é menor: commitar, abrir pull request, ler o argocd app get e o diff quando o vermelho aparece. O teste final é sempre o mesmo: apague o cluster e veja se o repositório o traz de volta.

Para lembrar
  • A Application amarra source (repo, ramo, pasta) a destination (cluster, namespace).
  • prune apaga o que saiu do Git; selfHeal desfaz o que mudou na mão.
  • O values é o painel de botões: replicaCount e image.tag viram manifesto no sync.
  • Cluster divergente não é cluster “meio certo”: é OutOfSync, e volta no próximo sync.
  • Synced + Healthy são duas perguntas diferentes; Synced não garante site no ar.
  • A rotina é argocd app get, argocd app diff, kubectl get pods e kubectl get endpoints.
  • OutOfSync eterno: ramo parado, pasta errada, namespace ausente ou selfHeal desligado.
  • rollback é remédio; a cura é git revert do commit.
