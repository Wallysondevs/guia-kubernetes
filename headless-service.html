Headless Service

Todos os Services que a Ana viu até aqui têm uma coisa em comum: um ClusterIP, um endereço virtual único que esconde os pods e divide o tráfego por baixo. Mas há um tipo de cliente que não quer isso. Um banco replicado, um cache distribuído, um sistema que precisa falar com cada réplica sabendo qual é qual — todos precisam da lista de pods, não de um endereço só. Para eles existe o headless Service: um Service sem ClusterIP, cujo nome DNS devolve os IPs dos pods.

Você vai aprender
  • O que muda quando um Service declara clusterIP: None.
  • O que o DNS responde num Service normal e o que responde num headless.
  • Como cada pod ganha um nome próprio, e o que o StatefulSet tem a ver com isso.
  • Por que o cliente passa a fazer o balanceamento (e quando isso é bom).
  • Quando usar headless e quando ele só cria problema.
  • Os tropeços: endpoints vazios, cache de DNS e aplicação que espera um IP só.

1. A cena: o cliente que precisa de todos

O cardápio da padaria cresceu e a Ana colocou um cache na frente do banco: três réplicas guardando os preços em memória. O site precisa consultar as três — não uma qualquer. Se cada consulta cair numa réplica diferente, metade das respostas vem de uma cópia desatualizada, e o preço muda conforme o cliente recarrega a página. O problema não é o Service: é que o Service foi feito para esconder os pods, e aqui a Ana precisa justamente do contrário.

Com um Service comum, o nome cache resolve para um ClusterIP, e o ClusterIP distribui as conexões entre as três réplicas. É ótimo para um site sem estado, que não se importa com qual réplica responde. É péssimo para um cliente que quer escolher: falar com a réplica 2 para escrever e com todas para ler, ou manter uma conexão fixa com cada uma delas.

O headless Service resolve exatamente isso: ele existe como Service — tem nome, seletor e portas, e o DNS do cluster responde por ele — mas não tem ClusterIP. Sem o endereço virtual, o nome resolve direto para os IPs dos pods. O cliente recebe a lista e decide o que fazer com ela, e o balanceamento passa a ser problema de quem chama.

2. O que é um headless Service

“Headless” quer dizer “sem cabeça” — sem o ClusterIP, que é a cabeça do Service tradicional. Não é um tipo novo no campo type; é o mesmo Service do tipo ClusterIP com um valor especial no campo clusterIP: a palavra None. A partir daí, o comportamento do DNS muda.

clusterIP: None
O que faz um Service ser headless. O cluster não cria endereço virtual para ele.
registros A
As respostas de DNS que apontam um nome para IPs. Num Service normal é um IP; num headless, um por pod.
nome por pod
Com StatefulSet, cada pod ganha pod-0.nome, pod-1.nome — endereços estáveis para réplicas que têm identidade.
serviceName
O campo do StatefulSet que liga os pods ao headless Service e habilita o nome por pod.
Endpoints
A lista de destinos, que existe igual nos dois casos — mas no headless é entregue ao cliente, e não escondida atrás de um IP.

Repare no que não muda: o seletor, as portas, o targetPort e os Endpoints são iguais. Se você trocar clusterIP: None por um Service normal, a lista de destinos continua a mesma — o que muda é quem a vê. No Service normal, o kube-proxy lê a lista e encaminha; no headless, o cliente lê a lista pelo DNS e conecta direto no pod.

Essa diferença tem uma consequência de rede importante: no headless, o cliente fala com o IP do pod, e não com um IP virtual. Se o pod morre, aquela conexão morre com ele — não há reencaminhamento mágico. É por isso que headless combina com clientes que sabem lidar com falha por conta própria, como drivers de banco e bibliotecas de cache distribuído.

3. O manifesto do headless

A mudança é de uma linha. A caixa abaixo tem o Service do cardápio do jeito tradicional e pede a transformação; repare que o resto do manifesto não muda nada.

O painel do código inicial mostra um ClusterIP normal, 10.96.147.79. Depois da missão, a coluna passa a mostrar None — e é a única diferença visível na tabela. O tipo continua ClusterIP, porque headless não é um tipo: é um ClusterIP sem endereço.

$ kubectl get services
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)   AGE
cardapio   ClusterIP   None         <none>        80/TCP    2m

A transcrição acima é a resposta do painel para o Service headless do cardápio. Comparada com a de um Service comum, a única diferença é a coluna do meio — e é justamente ela que muda o comportamento do DNS. Vale guardar essa imagem: o dia a dia é cheio de Services iguais, e o None é o sinal de que aquele nome devolve uma lista.

Repare que a coluna TYPE mentiria para quem só olha ela. Num inventário rápido, um Service headless parece um ClusterIP comum; o que o denuncia é a coluna CLUSTER-IP com None. Em time grande, vale uma etiqueta ou uma anotação para marcar os headless — quem procura “quem tem IP” não deveria precisar abrir objeto por objeto.

4. O que o DNS responde

Aqui está o coração da aula. Quando um cliente consulta o nome de um Service normal, o CoreDNS devolve um endereço: o ClusterIP. Quando consulta o nome de um headless, devolve todos os IPs dos pods prontos, um por registro. É a mesma consulta, com respostas de naturezas diferentes.

ConsultaService normalHeadless
o que o nome resolveum IP virtual (ClusterIP)um IP por pod pronto
quem balanceiao kube-proxy, por conexãoo cliente, com a lista que recebeu
nome por podnão existeexiste com StatefulSet

uso típicosite, API sem estadobanco, cache, filas com identidade

Essa resposta múltipla é o que permite ao cliente escolher. Uma biblioteca de cache lê a lista e mantém uma conexão com cada réplica; um driver de banco usa a lista para descobrir quem é o primário e quem são as réplicas; um serviço de fila conecta em todos para saber o estado do cluster. Em todos os casos, o DNS é só o catálogo de endereços — a inteligência está no cliente.

Um detalhe que costuma pegar: como a resposta é uma lista, o cliente escolhe um dos endereços quando faz a conexão, e costuma guardar essa escolha. Em linguagens cujo resolvedor tenta o primeiro IP e desiste se ele falhar, um pod fora do ar pode causar erro em parte das chamadas até o cache expirar. Bibliotecas boas tentam o próximo; bibliotecas simples, não. É um dos motivos pelos quais headless exige cliente adulto.

5. O headless também precisa de seletor

Sem ClusterIP, é tentador pensar que o Service “não faz nada”. Ele faz: continua sendo o seletor que gera a lista de endpoints e o nome que o DNS publica. Se o seletor não casa com nenhum pod, o nome existe e não resolve para lugar nenhum — e o cliente recebe erro de resolução, não erro de conexão.

O Service headless está sem selector e a lista de endpoints está vazia. Acrescente o seletor app: cardapio e rode: o IP do pod tem de aparecer.

É uma diferença de sintoma que ajuda no diagnóstico. Headless com endpoints vazios falha na resolução; headless com endpoints cheios e cliente que não conecta aponta para a porta ou para o próprio pod. Nos dois casos, o comando é o mesmo: kubectl get endpoints.

6. Um nome por pod

O headless tem um superpoder que só aparece na companhia de um StatefulSet: cada pod ganha um nome DNS próprio e estável, no formato pod.nome-do-service. O pod web-0 do StatefulSet web, ligado ao Service cardapio, responde em web-0.cardapio — e continua respondendo no mesmo nome mesmo depois de reiniciar e ganhar outro IP.

O StatefulSet está com uma réplica só. Suba para 2 réplicas e rode: o yaml dos endpoints tem de listar web-0 e web-1.

apiVersion: v1
kind: Service
metadata:
  name: cardapio
spec:
  clusterIP: None
  selector:
    app: cardapio
  ports:
    - port: 80
      targetPort: 8080
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: cardapio
  replicas: 1
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web

O yaml do código inicial mostra um endereço só, com targetRef: name: web-0. Depois da missão, dois endereços, web-0 e web-1, cada um com o seu IP e o seu nó. É a lista que o cliente de banco ou de cache precisa: identidade e endereço para cada réplica.

$ kubectl get pods -o wide
NAME    READY   STATUS    RESTARTS   AGE   IP               NODE
web-0   1/1     Running   0          9m    10.244.211.221   guia-control-plane
web-1   1/1     Running   0          3m    10.244.51.225    guia-worker

A transcrição acima é a resposta do painel para os pods do StatefulSet. Repare na diferença de nomes em relação a um Deployment: web-0 e web-1, previsíveis, em vez de web-6d8f89b786-88dn9. Essa previsibilidade é o que permite o nome DNS por pod existir — e é por isso que o serviceName no StatefulSet não é decoração: é ele que liga o pod ao Service headless.

Com o nome por pod, um cliente pode falar com uma réplica específica: web-0.cardapio sempre foi, é e será a primeira réplica, mesmo que o pod tenha sido recriado em outro nó. É a base de bancos de dados em Kubernetes: cada réplica precisa se reconhecer e ser reconhecida pelo cluster de dados.

7. Quando usar — e quando não

Use headless quando o cliente precisa da lista: banco de dados com réplica primária e secundárias, cache distribuído, sistemas de fila que descobrem membros, qualquer aplicação que implemente o próprio balanceamento. Use também quando você quer nomes por pod, o que praticamente implica StatefulSet.

Não use quando a aplicação espera um endereço único. Um site que faz fetch("http://api") e confia no balanceamento do cluster fica pior com headless: ele vai resolver um dos pods e ficar com ele, e algumas instâncias vão receber muito mais tráfego que outras. Nesse caso, o Service normal com ClusterIP faz o trabalho havia décadas.

Há um caso intermediário que confunde: o cliente que precisa de todos os endereços mas quer o balanceamento do cluster para as chamadas comuns. A solução usual é ter os dois — um Service normal para o tráfego de leitura e um headless para a descoberta de membros. São dois objetos com nomes diferentes, apontando para o mesmo conjunto de pods, e cada um serve ao seu propósito sem atrapalhar o outro.

Também não use como sinônimo de “Service mais avançado”. Headless não é um upgrade: é uma escolha de quem balanceia. Trocar um ClusterIP por headless num cliente que não sabe lidar com lista é uma forma silenciosa de quebrar disponibilidade — o cliente para de ter para onde cair quando um pod morre.

8. Os tropeços do headless

O primeiro é o cliente que espera um IP: bibliotecas antigas leem a primeira resposta do DNS e descartam o resto. O resultado é tráfego concentrado em um pod e erros quando ele morre. O segundo é o cache de DNS: respostas curtas são boas, mas um cliente que guarda a lista por dez minutos fica desatualizado depois de um rollout. O terceiro é tentar usar headless para fora do cluster: sem IP, não há como publicar.

9. Cenários do dia a dia

Cenário 1: o cache que lia sempre a mesma réplica

O time trocou o Service do cache por headless para “distribuir melhor” e o resultado foi o contrário: a biblioteca antiga pegava o primeiro IP da resposta e ficava com ele para sempre. Uma réplica recebia todo o tráfego e as outras ficavam ociosas. A correção foi voltar ao ClusterIP — o balanceamento por conexão, no kube-proxy, já era o que o cliente precisava.

Cenário 2: o banco que precisava de nomes

O banco da padaria cresceu para três instâncias: uma primária e duas secundárias. O driver precisa saber quem é quem, e para isso precisa de nomes estáveis por instância. Com StatefulSet e headless Service, as réplicas passaram a responder em banco-0, banco-1 e banco-2. Quando uma foi recriada em outro nó, o nome continuou o mesmo — o driver nem percebeu.

Cenário 3: o headless que ninguém precisava

Numa revisão de arquitetura, alguém propôs trocar todos os Services por headless “para eliminar o ClusterIP”. A aplicação era um site sem estado, com três réplicas idênticas, e passou a resolver um pod só por sessão. Bastou um pod cair para metade dos usuários ver erro. O ClusterIP não é legado: é a escolha certa para quem não quer escolher.

11. Resumo

Headless Service é um Service sem ClusterIP: clusterIP: None. Ele continua tendo nome, seletor, portas e endpoints — mas o DNS responde com os IPs dos pods em vez de um endereço virtual. O cliente recebe a lista e decide com quem falar, o que faz sentido para bancos replicados, caches distribuídos e qualquer sistema que implemente o próprio balanceamento.

Com StatefulSet, o headless ganha outra função: dar nome estável a cada pod, no formato pod.serviço. É o que permite a um banco saber quem é a réplica 0 e a 1, mesmo depois de recriadas em outros nós. O campo serviceName do StatefulSet é a ligação entre os dois.

Para o site comum, o ClusterIP continua sendo a escolha certa: endereço único, balanceamento automático e tolerância a pod que morre. Headless não é upgrade — é uma transferência de responsabilidade para o cliente. E, como todo Service, ele só funciona com endpoints: sem seletor, o nome não resolve para lugar nenhum.

Para lembrar
  • clusterIP: None é o que faz um Service ser headless.
  • O DNS devolve um IP por pod pronto, em vez de um endereço virtual.
  • Quem balanceia é o cliente — ele precisa saber lidar com lista e com pod que morre.
  • Com StatefulSet e serviceName, cada pod ganha pod-0.nome.
  • Seletor continua obrigatório para haver endpoints.
  • Headless não se publica para fora: não há IP para apontar.
