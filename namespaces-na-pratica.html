Namespaces na prática

A Ana já entendeu o conceito: namespace é a pasta lógica do cluster, e dois objetos com o mesmo nome convivem se estiverem em pastas diferentes. O que ela precisa agora é do dia a dia — criar a pasta antes de usar, não esquecer o -n na metade dos comandos, apagar sem levar o banco junto, e saber qual das três formas de escolher o namespace está valendo no comando que ela acabou de digitar. Nesta aula a padaria abre a filial, e o cluster responde a cada passo.

Você vai aprender
  • Criar o namespace antes do primeiro objeto — e o erro exato de quem esquece.
  • O -n em cada comando, e o que acontece quando ele falta.
  • Apagar namespace: o que leva junto e por que limpar antes é hábito.
  • O namespace escrito no manifesto e a diferença entre ele e a flag.
  • O nome completo de um Service visto de outro namespace.
  • O namespace corrente do contexto e o script que não depende dele.

1. A cena: a filial da padaria

O site da Ana cresceu. Além da loja do centro, ela abriu uma filial e quer testar mudanças de cardápio sem mexer no que os clientes veem. O plano é simples: o mesmo Deployment, a mesma imagem, o mesmo Service — um em producao, outro em teste. Duas cópias do mesmo manifesto, dois namespaces, zero chance de um experimento derrubar a loja.

No papel é fácil. Na prática, a Ana passou a tarde de ontem fazendo três coisas erradas em sequência: criou o objeto antes do namespace (e leu um erro que parecia do objeto), rodou kubectl get pods sem -n e concluiu que o pod tinha sumido, e apagou o namespace teste levando junto um banco de ensaio que ela nem lembrava que estava lá. Nenhuma das três coisas foi falta de conceito. Foram falhas de prática, e é isso que esta aula arruma.

Vale guardar a imagem certa: namespace não é uma partição nem uma máquina separada. Tudo continua no mesmo cluster, nos mesmos nós, na mesma rede. O namespace separa nomes, e é isso que permite o mesmo cardapio existir duas vezes. Quem separa rede é NetworkPolicy; quem separa recurso é cota; quem separa cluster é outro cluster. Namespace separa o espaço de nomes — e, por consequência, o lugar onde você procura as coisas.

2. As três formas de escolher o namespace

Antes dos comandos, é preciso saber quem manda. Um objeto pode receber namespace de três lugares, e quando dois deles discordam um vence. O vocabulário:

namespace
A divisão lógica onde o objeto mora. É um objeto do cluster como outro qualquer: tem nome e idade, e pode ser listado com kubectl get namespaces.
metadata.namespace
O campo do manifesto que diz onde o objeto deve nascer. Quando existe, é ele que vale — o -n vira só o padrão para quem não tem o campo.
-n / --namespace
A flag do comando. Escolhe em qual namespace o kubectl vai procurar ou criar. Sem ela, o kubectl usa o namespace corrente do contexto.
namespace corrente
O valor guardado no contexto do kubeconfig. É o que aparece quando você não escreve nem -n nem metadata.namespace. Nasce como default.
escopo
Se o tipo de objeto vive em namespace ou não. Pod, Deployment, Service e ConfigMap vivem; Node, Namespace e PersistentVolume não.

A regra prática que resolve 90% dos casos: no manifesto, escreva o namespace; no terminal, escreva o -n. O manifesto é o que fica guardado e viaja; o -n é o que você lê na tela e confere na hora. Quando os dois discordam, o manifesto ganha — e é por isso que um arquivo copiado de outro projeto pode criar o objeto “no lugar errado” mesmo com -n na linha de comando.

3. Criar antes de usar: o erro de ordem

O cluster não cria namespace por você. Se o comando aponta para uma pasta que não existe, ele recusa o objeto inteiro — e a mensagem fala do namespace, não do pod. A caixa abaixo começa exatamente assim.

O pod é criado no namespace padaria, que ainda não existe. Comece criando o namespace, repita o run e termine listando com -n padaria para ver o pod em Running.

kubectl run cardapio --image=cardapio:1.0 -n padaria
kubectl get pods -n padaria
ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0 -n padaria
Error from server (NotFound): error when creating "STDIN": namespaces "padaria" not found

ana@notebook:~$ kubectl get pods -n padaria
No resources found in padaria namespace.

kubectl create namespace padaria
kubectl run cardapio --image=cardapio:1.0 -n padaria
kubectl get pods -n padaria

O painel mostra a recusa: Error from server (NotFound): error when creating "STDIN": namespaces "padaria" not found. Três informações numa frase. O NotFound é o tipo do erro. O namespaces "padaria" not found é o que faltou. E o STDIN aparece porque o objeto veio de um comando, não de um arquivo — com apply -f, ali estaria o nome do seu YAML, o que ajuda a saber qual dos arquivos da pasta estava errado.

Depois do create, as duas linhas seguintes funcionam e o painel mostra o pod em Running. Repare que a listagem também leva -n padaria: sem ela, o comando olharia o default e responderia No resources found in default namespace. — verdade, mas não a verdade que a Ana queria ver.

4. O -n que falta não dá erro

Este é o engano mais caro do tema, porque não produz mensagem vermelha. Você cria num namespace, lista em outro, e recebe uma lista vazia — que o kubectl apresenta com a maior tranquilidade do mundo. Não é falha, é uma pergunta feita no lugar errado. A tabela abaixo é a cola que vale colar no monitor:

ComandoSem -n, olha…O que fazer
kubectl get podso namespace corrente (default)-n padaria para ver os da padaria; -n teste para os do teste
kubectl run, create, exposecria no namespace correntepasse -n em cada linha; conferir depois com get … -n
kubectl delete, logs, describeprocura só no namespace correnteo mesmo -n; objeto “inexistente” quase sempre está em outro lugar
kubectl get nodesnão aceita -n: nó não mora em namespacenada a fazer — o escopo é do tipo, não do comando
kubectl get nslista todos os namespacesé o primeiro comando quando aparece NotFound de namespace

A linha do nodes explica metade dos comandos que “não funcionam”: o -n só faz sentido para tipo que vive em namespace. E a do delete merece atenção redobrada, porque é a única que pode apagar a coisa errada — kubectl delete deployment cardapio sem -n apaga o do default, e a Ana já fez isso achando que estava limpando o teste.

Sobre listar tudo de uma vez: o kubectl de verdade aceita -A (ou --all-namespaces) e devolve uma coluna NAMESPACE na frente. No painel deste guia a listagem é sempre a do namespace corrente, então o caminho é conferir um por um com -n. É mais devagar e ensina melhor: quem lista por namespace vê o que está em cada um.

5. Apagar um namespace: o comando que leva tudo

Apagar namespace é o comando mais perigoso do Nível 1. Ele não pede confirmação, não lista o que vai levar, e responde com uma linha curta. Em cluster de verdade, tudo o que está dentro vai junto — pods, deployments, services, configmaps, secrets e os discos pedidos por PersistentVolumeClaim daquele namespace. A transcrição abaixo é de um cluster real:

ana@notebook:~$ kubectl delete namespace teste
namespace "teste" deleted

ana@notebook:~$ kubectl get pods -n teste
No resources found in teste namespace.

ana@notebook:~$ kubectl get namespaces
NAME          STATUS   AGE
default       Active   9d
kube-system   Active   9d
producao      Active   3d

O No resources found in teste namespace. depois do delete é a prova de que não sobrou nada: nem o namespace, nem os pods. Enquanto o cluster termina de apagar, o namespace aparece com STATUS igual a Terminating — pode levar minutos se houver volume preso. Nesse estado não dá para criar nada nele; a saída é esperar ou investigar o que está segurando.

O hábito que salva: limpar antes de apagar. Listar o que existe no namespace, tipo por tipo, e decidir conscientemente o que vai embora. A caixa abaixo treina exatamente isso — o pod sai primeiro, o namespace depois. Detalhe do painel: ele apaga o objeto Namespace mas não o conteúdo dele, então a meta só fecha quando o pod é apagado antes; é o mesmo procedimento que se recomenda num cluster de verdade, onde o delete do namespace levaria tudo de uma vez.

O namespace teste é descartável, mas ainda tem um pod dentro. Apague o pod e depois o namespace, e confirme no fim que a listagem está vazia.

kubectl create namespace teste
kubectl run cardapio --image=cardapio:1.0 -n teste
kubectl delete namespace teste
kubectl get pods -n teste
ana@notebook:~$ kubectl create namespace teste
namespace/teste created

ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0 -n teste
pod/cardapio created

ana@notebook:~$ kubectl delete namespace teste
namespace/teste deleted

ana@notebook:~$ kubectl get pods -n teste
NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          1m

kubectl create namespace teste
kubectl run cardapio --image=cardapio:1.0 -n teste
kubectl delete pod cardapio -n teste
kubectl delete namespace teste
kubectl get pods -n teste

Repare na diferença das respostas: pod/cardapio deleted e namespace/teste deleted. Mesmo formato, escopos diferentes. E repare no que a listagem final diz: No resources found in teste namespace. — a frase que, no começo da aula, era sinal de confusão, aqui é sinal de trabalho bem feito.

6. O namespace escrito no manifesto

Quando o time guarda tudo em arquivo, o namespace vira uma linha do YAML — e é comum precisar de dois objetos no mesmo arquivo: o namespace e o que vai dentro dele. Multi-documento resolve isso com --- entre os blocos, e a ordem importa: o namespace tem de vir primeiro, porque o apply aplica na ordem em que lê.

O Deployment aponta para o namespace padaria, que ainda não existe no arquivo. Acrescente o objeto Namespace no começo, separado por ---, e rode.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
  namespace: padaria
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080
Error from server (NotFound): error when creating "STDIN": namespaces "padaria" not found

apiVersion: v1
kind: Namespace
metadata:
  name: padaria
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
  namespace: padaria
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080

Sem o primeiro documento, o painel responde Error from server (NotFound): error when creating "STDIN": namespaces "padaria" not found — a mesma frase da seção 3, agora causada por um arquivo e não por um comando. Com ele, as duas linhas de criação aparecem e a listagem no fim mostra os dois pods em Running, direto no namespace padaria.

Aqui vale a comparação das três formas de escolher o namespace, porque cada uma tem um custo:

FormaOnde ficaQuando usarRisco
metadata.namespaceno manifesto, versionadoo que precisa cair sempre no mesmo lugarcopiar o arquivo para outro ambiente e esquecer de trocar
-n nomena linha do comandoexplorar, conferir, apagar um objeto específicoesquecer em uma linha e agir no namespace errado

A recomendação que fecha a seção: manifesto com namespace explícito, -n no terminal, e contexto no default. Assim o comando perigoso é sempre explícito, e o arquivo é sempre reproduzível.

7. O nome completo de um Service entre namespaces

Dentro do mesmo namespace, um pod chama o outro pelo nome curto do Service: http://cardapio. Fora dele, o nome curto não resolve — e o erro que aparece é de DNS, não de Service: “não achei esse nome”. O endereço completo tem três partes, e a ordem é do mais específico para o mais geral: cardapio.padaria.svc.cluster.local é “o Service cardapio, no namespace padaria, na zona svc, do cluster local”.

Duas abreviações funcionam: cardapio.padaria (o cluster completa o resto) e, de dentro do próprio namespace, só cardapio. O que não funciona é padaria/cardapio — não existe barra em nome de Service; a barra é do kubectl, não do DNS. Guarde também que o endereço aponta para o Service, nunca para o pod: o IP do pod muda a cada reinício, o nome do Service não.

É por isso que a arquitetura da Ana separa o que é “interno de um ambiente” do que é “compartilhado”. O banco de dados mora em producao e ninguém de teste chega nele por acidente: para chegar, alguém precisa escrever o nome completo, com namespace, de propósito. O nome comprido é uma cerca barata.

8. O namespace corrente do contexto

A terceira forma de escolher o namespace é a mais confortável e a mais traiçoeira: mudar o padrão do contexto. A partir daí, todo comando sem -n age naquele namespace, como se você tivesse digitado a flag em cada linha. A transcrição é de um cluster real:

ana@notebook:~$ kubectl config set-context --current --namespace=padaria
Context "kind-guia" modified.

ana@notebook:~$ kubectl get pods
NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          3m

ana@notebook:~$ kubectl config set-context --current --namespace=default
Context "kind-guia" modified.

Repare que não há confirmação nem aviso: o comando imprime Context "kind-guia" modified. e muda o padrão da sua sessão. Quem entra depois na mesma máquina herda o contexto e passa a ver o cluster pela lente de outro namespace. Se um dia kubectl get pods devolver algo inesperado, esse comando é o primeiro suspeito — e a cura é voltar para default explicitamente.

Em script, o padrão é não depender de contexto nenhum. Guarde o namespace numa variável e passe sempre ela: NS=padaria e depois kubectl get pods -n "$NS", kubectl logs cardapio -n "$NS", kubectl delete pod cardapio -n "$NS". Mudar de ambiente vira uma linha; e quem lê o script enxerga o alvo de cada comando sem precisar adivinhar o contexto de quem executou.

9. Cenários do dia a dia

Cenário 1: “o pod sumiu”

O pod estava lá, rodando há quarenta minutos. A Ana rodou kubectl get pods no default e viu a lista vazia. Antes de reiniciar qualquer coisa, o comando certo é kubectl get pods -n padaria — e, na dúvida, kubectl get ns para lembrar quais pastas existem. Lista vazia não é objeto inexistente; é busca no lugar errado.

Cenário 2: o apply que caiu no default

O manifesto não tinha namespace e o comando foi rodado sem -n. O Deployment nasceu no default, o Service que deveria apontar para ele não o encontrou (estava em padaria) e o site ficou fora do ar. O conserto: escrever metadata.namespace no arquivo, apagar o objeto criado no lugar errado e aplicar de novo. Manifesto sem namespace é uma bomba de tempo em cluster com mais de uma pasta.

Cenário 3: a limpeza que levou o banco de ensaio

Alguém apagou o namespace teste para “começar limpo”, e com ele foi o banco que o time usava para ensaiar migração. Não houve confirmação nem lista do que seria apagado. A regra que entrou no README: antes de apagar um namespace, listar o conteúdo por tipo — pods, deployments, services, configmaps, persistentvolumeclaims — e responder por escrito o que pode ir embora.

Exercício: o manifesto que não diz onde mora

Um Deployment precisa nascer sempre no namespace padaria, mesmo que quem aplique esteja com outro contexto. Complete o campo do manifesto que garante isso:

metadata: name: cardapio : padaria

Dica: a flag -n vale para um comando; o campo do manifesto vale para sempre. Quando os dois discordam, quem manda é o manifesto. O valor tem de ser minúsculo, com hífen se precisar, e o namespace precisa existir antes.

11. Resumo

Namespace é a pasta lógica do cluster, e o dia a dia é feito de três decisões: onde o objeto nasce (o campo metadata.namespace, que vence), onde o comando procura (a flag -n) e qual é o padrão da sessão (o namespace do contexto, que você quase nunca deve mudar). Criar o namespace vem antes de criar o objeto; sem ele, a resposta é Error from server (NotFound): namespaces "x" not found, e nada é criado pela metade.

Lista vazia não é erro: No resources found in default namespace. quer dizer que a busca foi feita ali. Confira com -n antes de concluir que o objeto sumiu. E lembre que nó, namespace e volume não moram em namespace — o -n nesses tipos não faz sentido.

Apagar namespace leva tudo o que está dentro, sem confirmação e sem lista: limpe antes, listando por tipo. Entre namespaces, o Service só responde pelo nome completo (cardapio.padaria.svc.cluster.local), e em script o certo é passar o namespace por variável, sem depender do contexto. Na próxima aula a Ana aprende a ler o que o kubectl devolve — tabela, YAML, JSON — e a escolher o formato certo para cada pergunta, na aula de saída do kubectl.

Para lembrar
  • kubectl create namespace padaria antes de qualquer objeto; sem isso, NotFound de namespace.
  • -n em todo comando; sem ele, o alvo é o namespace corrente, e a lista vazia engana.
  • metadata.namespace manda no manifesto; -n só preenche o que falta.
  • delete namespace leva o conteúdo inteiro: limpe antes, listando por tipo.
  • Nome completo entre namespaces: servico.namespace.svc.cluster.local.
  • Script com NS=padaria e -n "$NS" em todas as linhas: sem surpresa de contexto.
