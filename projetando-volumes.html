Volumes projetados

Todo kubectl describe pod já mostrou isso para a Ana e ela nunca entendeu: um volume chamado kube-api-access-xxxxx, do tipo Projected. Nesta aula ela descobre o que é um volume projetado — a possibilidade de juntar ConfigMap, Secret, dados do próprio pod e token de conta de serviço num diretório só —, aprende as quatro fontes, o que acontece quando duas delas escrevem o mesmo arquivo e por que isso resolve um problema que três volumes separados não resolvem.

Você vai aprender
  • O que é um volume projected e o que ele já faz em todo pod.
  • As quatro fontes: configMap, secret, downwardAPI e serviceAccountToken.
  • Como expor o nome, o namespace e as etiquetas do pod como arquivos.
  • Permissões, items e o que acontece quando duas fontes colidem.
  • Por que o token de ServiceAccount é projetado e não guardado num Secret.
  • Quando vale juntar tudo e quando três volumes separados são mais claros.

1. A cena: três volumes e uma pasta

O site da padaria precisava de três coisas ao subir: a tabela de preços (que vinha de um ConfigMap), a senha do banco (de um Secret) e o próprio nome do pod, para assinar as linhas de log e as métricas. A Ana resolveu do jeito óbvio: três volumes, três montagens, em três pastas diferentes — /config, /etc/padaria e /etc/podinfo.

Funcionou, e ficou feio. O programa passou a ter três caminhos para ler, o manifesto ficou com seis blocos repetidos e o time de plantão precisava lembrar de três pastas. Quando entrou mais um arquivo de configuração, virou quatro pastas. Foi aí que ela viu, no describe de um pod, um volume diferente de todos os que ela tinha escrito: Projected.

Aquele volume é do próprio Kubernetes. Todo pod ganha um, chamado kube-api-access-<código>, que junta num diretório só o token da conta de serviço, a cadeia de certificados do cluster e o namespace — tudo o que o programa precisa para falar com o servidor de API. É o mesmo recurso que a Ana precisava: várias fontes de dados, uma pasta, uma montagem.

O describe de qualquer pod mostra esse volume, e a leitura vale ouro para entender a mecânica:

ana@notebook:~$ kubectl describe pod web
Volumes:
  kube-api-access-t6csd:
    Type:                    Projected (a volume that contains injected data from multiple sources)
    TokenExpirationSeconds:  3607
    ConfigMapName:           kube-root-ca.crt
    Optional:                false
    DownwardAPI:             true

Leia as linhas de baixo: um único volume, três fontes. ConfigMapName é a cadeia de certificados do cluster, DownwardAPI diz que ele expõe o namespace do pod e TokenExpirationSeconds é o prazo do token. É o mesmo padrão de manifesto que você vai escrever nesta aula — só que escrito pelo próprio Kubernetes.

2. O que é um volume projetado

Um volume projected não guarda dados: ele projeta. Você declara uma lista de sources e o kubelet escreve o conteúdo de todas elas no mesmo diretório, como se fossem arquivos de uma pasta comum. Cada fonte continua sendo o que é — ConfigMap, Secret, informação do pod, token —, mas o container vê um diretório único.

A vantagem é dupla. Para o manifesto, é menos repetição: um volume, um volumeMount. Para o programa, é um caminho só: ele lê /etc/padaria/preco, /etc/padaria/senha e /etc/padaria/namespace sem saber de onde cada um veio. Aliás, é exatamente assim que as bibliotecas de cliente do Kubernetes encontram o token: elas procuram um caminho fixo e ele está lá porque o volume projetado padrão montou.

projected
O tipo de volume que junta várias fontes num diretório só.
sources
A lista obrigatória de fontes. Cada item é um configMap, secret, downwardAPI ou serviceAccountToken.
downwardAPI
A fonte que expõe informação do próprio pod: nome, namespace, etiquetas, limites de recurso.
fieldRef
O seletor de um campo do pod, como metadata.name ou metadata.namespace.
serviceAccountToken
A fonte que gera um token de conta de serviço com público e prazo definidos.
audience
Para quem o token vale. Um token com público próprio não serve para outro sistema.
defaultMode
Permissões dos arquivos do volume, em octal. Pode ser sobrescrito por fonte.

3. As quatro fontes

São quatro, e cada uma responde a uma pergunta diferente. A tabela abaixo é o mapa; o resto da aula percorre cada uma.

FonteO que trazExemplo de uso
configMapas chaves de um ConfigMap, um arquivo por chavetabela de preços, arquivo de configuração
secretas chaves de um Secret, decodificadassenha do banco, certificado
downwardAPIdados do próprio podnome do pod no log, namespace no relatório
serviceAccountTokentoken de conta de serviço com prazofalar com a API do cluster

Todas as fontes aceitam items, com key (para ConfigMap e Secret) e path (o nome do arquivo). No downwardAPI, o items é obrigatório: cada item diz qual fieldRef vai virar qual path. E todas podem receber um mode próprio, quando você quer permissões diferentes por arquivo.

4. Juntando ConfigMap e Secret

A caixa começa com o manifesto bagunçado da cena: dois volumes separados, duas pastas. A missão é juntar tudo num volume projetado, mantendo a leitura em /etc/padaria. O programa não muda uma linha — muda o manifesto.

Troque os dois volumes por um volume projected com as fontes configMap: cardapio e secret: banco, montado em /etc/padaria.

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio
data:
  preco: "4.50"
---
apiVersion: v1
kind: Secret
metadata:
  name: banco
data:
  senha: czNuaDQ=
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: cardapio:2.0
      volumeMounts:
        - name: config
          mountPath: /etc/padaria
        - name: segredos
          mountPath: /etc/padaria
  volumes:
    - name: config
      configMap:
        name: cardapio
    - name: segredos
      secret:
        secretName: banco

secret/banco created
pod/web created

              name: cardapio
          - secret:
              name: banco

O detalhe que faz a diferença está no que sai do manifesto: uma montagem só. No estado inicial, as duas montagens apontam para o mesmo mountPath, e o Kubernetes não junta o conteúdo de dois volumes no mesmo caminho — ele monta um e o outro fica inacessível (ou o pod nem sobe, dependendo da ordem). Não é um merge: é sobreposição, e sobreposição é sempre um erro.

Com projected, o merge é explícito e acontece dentro do volume. O diretório /etc/padaria passa a ter dois arquivos: preco, vindo do ConfigMap, e senha, vindo do Secret. Cada fonte mantém a regra de sempre: uma chave, um arquivo, nome da chave como nome do arquivo.

5. O downwardAPI: o pod falando de si

A terceira fonte é a mais subestimada. O downwardAPI expõe informação do próprio pod como arquivo: nome, namespace, etiquetas, anotações, limites de CPU e memória. É o que permite que a mesma imagem rode em dez ambientes diferentes e saiba onde está, sem variável injetada por fora.

Os campos mais usados em fieldRef.fieldPath são metadata.name, metadata.namespace, metadata.labels e metadata.annotations. Para recurso, existe o resourceFieldRef, que expõe limits.cpu e limits.memory — útil quando o programa quer dimensionar o próprio pool de conexões pelo limite que recebeu.

Acrescente ao volume projetado uma fonte downwardAPI que escreva o namespace no arquivo namespace e o nome do pod no arquivo pod. A pasta /etc/padaria já tem preço e senha.

              name: cardapio
          - secret:
              name: banco
          - downwardAPI:
              items:
                - path: namespace
                  fieldRef:
                    fieldPath: metadata.namespace
                - path: pod
                  fieldRef:
                    fieldPath: metadata.name

Repare na ordem dos campos do item: primeiro o path (o nome do arquivo dentro da pasta), depois o fieldRef com o fieldPath (o dado do pod). É o inverso do ConfigMap, onde key vem antes de path. Trocar isso é erro de validação — e, como o validador aponta o campo exato, sai do susto rápido.

Depois de aplicar, a pasta fica assim, com os dois arquivos novos ao lado dos que já existiam:

/ # ls /etc/padaria
namespace  pod  preco  senha

/ # cat /etc/padaria/namespace
default

Quatro arquivos, três fontes, um volume. E note que o cat do namespace devolve default — o mesmo valor que apareceria em metadata.namespace, sem ninguém precisar injetar variável nenhuma.

O uso clássico é o log. Um programa que escreve {"pod": "...", "ns": "..."} em cada linha permite que a busca no agregador de logs encontre tudo de um pod específico. Sem isso, você tem linhas soltas de três réplicas com a mesma aparência e nenhuma forma de separar. Com o arquivo ali, é uma leitura no start e o nome entra em todas as linhas.

6. O token projetado

A quarta fonte é a que explica o volume esquisito do describe. O serviceAccountToken gera um token novo para o pod, com dois parâmetros que importam: audience (para quem aquele token vale) e expirationSeconds (quanto tempo ele dura). O kubelet renova antes de vencer, e o arquivo no volume acompanha — como todo volume projetado.

O serviço vai chamar um sistema interno que exige um token próprio. Acrescente a fonte serviceAccountToken com audience: padaria, expirationSeconds: 3600 e path: token.

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio
data:
  preco: "4.50"
---
apiVersion: v1
kind: Pod

  name: web

  containers:
    - name: web
      image: cardapio:2.0
      volumeMounts:
        - name: tudo
          mountPath: /etc/padaria
  volumes:
    - name: tudo
      projected:
        sources:
          - configMap:
              name: cardapio

    - name: web
      image: cardapio:2.0
      volumeMounts:
        - name: tudo
          mountPath: /etc/padaria
  volumes:
    - name: tudo
      projected:
        sources:
          - configMap:
              name: cardapio
          - serviceAccountToken:
              audience: padaria
              expirationSeconds: 3600
              path: token

Aqui vale a honestidade sobre o painel: ele guarda o manifesto e mostra o pod em Running, mas não fabrica token nenhum — não há servidor de API emitindo credencial na simulação. Num cluster de verdade, o arquivo /etc/padaria/token existe com um JWT de verdade, válido por uma hora e renovado sozinho. O que você aprende aqui é a forma do manifesto e o motivo dela existir.

E o motivo é segurança. Antes, o token de uma conta de serviço era um Secret permanente, criado automaticamente, com prazo infinito e sem público definido: quem copiasse aquele objeto tinha acesso para sempre. O token projetado tem prazo, tem público e é rotacionado — três propriedades que um segredo estático nunca teve.

7. Permissões, colisões e o que mais dá errado

O defaultMode do volume projetado vale para todos os arquivos; cada fonte pode sobrescrever com o seu próprio defaultMode, e cada item pode ter o seu mode. Para segredo em pasta compartilhada, o ajuste comum é 0400 no Secret e 0444 no ConfigMap.

A colisão é o erro silencioso. Duas fontes escrevendo o mesmo path produzem um resultado indefinido na prática: uma sobrescreve a outra, e você descobre na madrugada. A regra é simples e vale como disciplina: cada fonte escreve em nomes diferentes. Se as chaves colidem, use items para renomear na hora de projetar — preco do ConfigMap pode virar preco.txt, e o preco do Secret continua sendo o dele.

SituaçãoO que aconteceO que fazer
duas fontes, mesmo pathuma sobrescreve a outrarenomear com items
fonte sem sourceserro de validação no applysources é obrigatório e não pode ser vazio
downwardAPI sem itemserro de validaçãocada campo precisa de path e fieldRef
ConfigMap ou Secret ausentepod parado antes de criar o containercriar a fonte antes, ou marcar como opcional
fonte opcional com optional: truea pasta monta sem aquela fonteusar quando o arquivo é enfeite

Uma palavra sobre o optional: true. Ele parece um detalhe de conveniência e é, na verdade, uma decisão sobre falhar cedo ou tarde: com a fonte opcional, a pasta monta sem o arquivo e o programa descobre na primeira leitura, com o erro que ele mesmo escreveu; sem ela, o pod nem sobe e o erro é do Kubernetes, na cara, antes de qualquer linha de código rodar. Para configuração obrigatória, prefira falhar antes — pod parado é mais fácil de diagnosticar que programa lendo arquivo vazio.

A penúltima linha é a que mais aparece em produção. O pod não falha: ele espera. Sem log, sem erro na aplicação, só um ContainerCreating que não anda. O motivo está no evento FailedMount do describe, e a causa costuma ser ordem: o manifesto aplicou o pod antes do ConfigMap.

Não existe resposta certa universal. Programa legado que exige cinco arquivos em /etc/app ganha muito com projetado. Configuração e credencial de assuntos diferentes, mantidas por times diferentes, ficam mais claras em volumes separados — quem mexe no ConfigMap não precisa abrir o manifesto do Secret.

8. Quando isso resolve um problema real

Três situações aparecem sempre. A primeira é o programa que só sabe ler de uma pasta: montar tudo em /etc/padaria evita gambiarra de caminho no código. A segunda é a identidade: o pod precisa saber o próprio nome e o namespace para log e métrica, e o downwardAPI entrega isso sem env e sem template. A terceira é o token com público próprio, para integrar com um sistema que recusa o token padrão do cluster.

Há ainda um quarto caso, mais sutil: reduzir a superfície. Um volume projetado monta exatamente os arquivos listados. Se o ConfigMap tem dez chaves e o programa só precisa de duas, o items de cada fonte corta o resto — e o container não vê o que não precisa ver. É o mesmo raciocínio de permissão mínima, aplicado a arquivos.

9. Cenários do dia a dia

Cenário 1: o nome do pod que ninguém sabia

Três réplicas escreviam log idêntico e o plantão não conseguia dizer qual delas estava lenta. A solução foi um downwardAPI projetando metadata.name em /etc/padaria/pod e o programa passando a incluir esse nome em cada linha. Nenhuma mudança de infraestrutura, nenhuma variável nova no Deployment: só o arquivo e a leitura dele.

Cenário 2: a colisão que ninguém viu

ConfigMap e Secret tinham a chave config, e as duas fontes foram projetadas na mesma pasta. O programa passou a ler o valor do Secret em vez do ConfigMap, e um preço virou senha no relatório. O conserto foi renomear com items — config virou config.json numa fonte e config.secret na outra. Desde então, o time projeta com nomes que dizem a origem.

Cenário 3: o token que durou para sempre

Um script antigo usava o token de um Secret permanente para chamar a API do cluster. Quando a política da empresa passou a exigir credencial de curta duração, o time trocou o Secret por serviceAccountToken com expirationSeconds: 3600 e público próprio. O script não mudou: ele já lia o token do arquivo. Mudou a fonte, e a credencial passou a expirar sozinha.

11. Resumo

Volume projetado é a resposta para “preciso de vários arquivos numa pasta só”. Você declara um volume projected com a lista de sources e uma única montagem; o kubelet escreve o conteúdo de todas as fontes no mesmo diretório. As quatro fontes são configMap, secret, downwardAPI e serviceAccountToken.

O downwardAPI expõe dados do pod (nome, namespace, etiquetas) como arquivos e é obrigatório com items. O token projetado tem público e prazo, é renovado sozinho e substituiu o Secret permanente de conta de serviço. Permissões vêm do defaultMode, ajustáveis por fonte e por item, e duas fontes com o mesmo caminho se sobrescrevem — renomeie com items.

A última aula deste bloco é a que organiza tudo o que veio antes: uma checklist de boas práticas de configuração — o que nunca pode entrar num ConfigMap, como nomear objetos, quando versionar e por que tornar imutável o que não muda.

Para lembrar
  • projected junta fontes; o sources é obrigatório.
  • Fontes: configMap, secret, downwardAPI, serviceAccountToken.
  • downwardAPI sempre com items (path + fieldRef).
  • Token projetado tem audience e expirationSeconds.
  • Mesmo path em duas fontes = colisão; renomeie.
  • Todo pod já tem um volume projetado: o kube-api-access-….
