kubectl delete

Sexta-feira a Ana fez testes no cluster: criou um pod para ver a imagem nova, outro para testar uma porta, um terceiro que ela nem lembra por quê. Domingo o nó ficou sem memória e um pod de verdade foi despejado. Os três de teste continuavam lá, esquecidos, ocupando espaço. Nesta aula ela aprende o kubectl delete — o único comando do trio que desfaz — e, mais importante, aprende a conferir antes de apagar, porque neste lugar não existe lixeira.

  • O roteiro de segurança: get antes, delete, get depois.

1. A cena: os pods esquecidos de sexta

O cluster da padaria roda num notebook com três nós pequenos. Cada pod que existe pede CPU e memória, mesmo quando não faz nada: o agendador reserva o pedido, e o nó fica sem espaço. Os três pods de teste da Ana não processavam requisição nenhuma, mas ocupavam a vaga — e foi por isso que o pod do cardápio foi despejado no domingo.

O kubectl delete é o comando que resolve isso: apaga o objeto do cluster. É o único dos comandos desta parte do guia que muda o mundo de forma destrutiva, e é o único que não tem “desfazer”. Não existe kubectl undo; o que existe é aplicar o manifesto de novo e esperar o cluster recriar. Para um pod de teste, isso é trivial. Para um Service que estava no ar, é um incidente.

A comparação com o sistema de arquivos continua valendo: se o get é o ls, o delete é o rm — e, como o rm, ele apaga o que você mandar apagar, sem perguntar “tem certeza?”. O cuidado tem de vir de você.

Há uma segunda razão para os pods esquecidos incomodarem: eles mentem na contagem. Quando a Ana olha get pods --show-labels e vê seis linhas, ela não sabe quais são de verdade e quais são restos de teste. Num incidente, essa dúvida custa minutos. Manter o cluster limpo é parte do trabalho, como manter a bancada da padaria sem sobra de farinha.

2. A forma do comando

O verbo é delete, o alvo é o tipo e o nome. Duas grafias funcionam e fazem a mesma coisa: kubectl delete pod cardapio e kubectl delete pod/cardapio. A segunda é a que o próprio kubectl usa nas mensagens, e é a forma que aparece no get pods -o name — copiar dali evita erro de digitação.

A resposta é curta, no mesmo estilo das outras: pod/cardapio deleted. Repare que ela confirma o pedido, não o resultado: o objeto foi marcado para remoção e, na prática, já saiu. Um get logo depois mostra a lista sem ele. E, se o nome não existir, a resposta é o NotFound que você já conhece:

ana@notebook:~$ kubectl delete pod brioche
Error from server (NotFound): pods "brioche" not found

Duas leituras dessa mensagem. A primeira: nada foi apagado, porque nada com esse nome existia — o comando é seguro nesse sentido, ele não apaga “parecido”. A segunda: o NotFound no delete quase sempre significa que o objeto já não estava lá (alguém apagou antes, o pod foi recriado com outro nome, ou você está olhando o namespace errado). Nenhum desses casos é desastre; é só um comando que não encontrou o alvo.

delete
Verbo do kubectl que remove um objeto do cluster. A resposta confirma o pedido, não o resultado.
NotFound
Erro do servidor quando o nome procurado não existe no namespace consultado. No delete, significa que nada foi apagado.
dono
O objeto que criou outro — Deployment cria ReplicaSet, que cria pod. Aparece no describe, em Controlled By.
cascata
A remoção dos filhos junto com o dono. Quem executa é o coletor de lixo do cluster.
estado desejado
O que o manifesto pede. Apagar à mão cria diferença que o controlador desfaz na próxima reconciliação.

3. Apagar e conferir

O roteiro que a Ana passou a seguir tem três passos: ver, apagar, ver de novo. A caixa começa no primeiro passo; falta apagar e conferir que a lista ficou vazia.

Crie o pod, apague-o com kubectl delete pod cardapio e liste de novo para confirmar que não sobrou nada. O painel tem de mostrar pod/cardapio deleted e No resources found.

kubectl run cardapio --image=cardapio:1.0
kubectl get pods
ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0
pod/cardapio created

ana@notebook:~$ kubectl get pods
NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          2m

kubectl run cardapio --image=cardapio:1.0
kubectl delete pod cardapio
kubectl get pods
ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0
pod/cardapio created
ana@notebook:~$ kubectl delete pod cardapio
pod/cardapio deleted
ana@notebook:~$ kubectl get pods
No resources found in default namespace.

O terceiro passo não é ritual: é ele que transforma “mandei apagar” em “está apagado”. Em cluster grande e movimentado, outra pessoa pode ter recriado o objeto no meio do caminho, ou o Deployment pode ter produzido um pod novo. A conferência responde a pergunta certa — o que existe agora? — em vez de confiar no que o comando disse.

Repare também que o delete aceita o mesmo --namespace do resto. Isso importa mais do que parece: apagar no namespace errado dá NotFound e você fica achando que o pod não existe, quando ele está lá, inteiro, do outro lado. É a seção seguinte.

4. O namespace certo

Como todo comando do kubectl, o delete olha o namespace default quando você não diz nada. Se o objeto estiver em outro, a resposta é NotFound — a mesma de um nome errado, o que atrapalha o diagnóstico. A caixa mostra o caso: o pod foi criado no namespace padaria.

O pod está no namespace padaria, e o delete procura no default. Acrescente -n padaria para conseguir apagar — o painel tem de mostrar pod/cardapio deleted.

kubectl create namespace padaria
kubectl run cardapio --image=cardapio:1.0 -n padaria
kubectl delete pod cardapio
ana@notebook:~$ kubectl create namespace padaria
namespace/padaria created

ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0 -n padaria
pod/cardapio created

ana@notebook:~$ kubectl delete pod cardapio
Error from server (NotFound): pods "cardapio" not found

kubectl create namespace padaria
kubectl run cardapio --image=cardapio:1.0 -n padaria
kubectl delete pod cardapio -n padaria

Um detalhe que parece detalhe e não é: quando você apaga com -n padaria, confira também com -n padaria. Um get pods sem flag mostra o default vazio, e a conclusão “apagou tudo” é falsa. O hábito de colar a mesma flag nos três comandos do roteiro evita esse tipo de conclusão errada.

Para quem apaga muito no mesmo namespace, existe um atalho que evita o erro: fixar a variável NS no terminal e usá-la em todos os comandos — kubectl delete pod cardapio -n $NS, kubectl get pods -n $NS. O erro de digitação passa a acontecer uma vez, na definição da variável, e não em cada comando. Em script, é a mesma ideia com uma constante no topo do arquivo. O que não vale é confiar na memória para lembrar em qual namespace você está.

5. O que vai junto

Apagar pod é simples. Apagar donos é onde as pessoas se machucam, porque cada tipo de objeto carrega filhos. A tabela é o mapa:

Você apagaO que costuma ir juntoO que fica
podnada — só eleo resto do cluster
deploymentos ReplicaSets e os pods deleo Service, que passa a não ter endpoints
serviceo ponto de acessoos pods, rodando e sem visita
namespacetodos os objetos daquele namespaceo que é do cluster: nós, namespaces, volumes persistentes
configmapnada imediatopods que já o montaram continuam com o conteúdo antigo até recriar

A primeira linha explica por que existe tanto pod órfão por aí: apagar um pod parece inofensivo e é. A segunda linha explica o susto: apagar o Deployment derruba o site inteiro, porque os pods que serviam o site eram dele. E a quarta explica o clássico “apaguei o namespace de teste e levei o banco junto”.

Há um caso intermediário que confunde: apagar um pod que faz parte de um Deployment com estratégia de rolling update. O Deployment não recria “o mesmo pod”; ele compara o número de réplicas e cria um novo, com nome novo, no nó que tiver espaço. Para quem está olhando a lista, parece que o pod voltou. Para quem está olhando o cluster, houve um pod a menos por alguns segundos — e, se aquele era o único, houve indisponibilidade por alguns segundos. É por isso que mexer em pods de um Deployment em produção é diferente de mexer em pod solto de teste.

Uma observação honesta sobre o painel desta página: ele remove exatamente o objeto que você nomeia e não simula a remoção em cascata. Se você apagar o Deployment na caixa, os pods podem continuar listados ali. No cluster de verdade, o coletor de lixo do Kubernetes apaga os filhos em seguida — é o controlador que “recolhe” o que ficou sem dono. A lição da tabela vale para os dois; só a demonstração visual é que fica incompleta no simulador.

6. As outras formas de apagar

Nomear um objeto é a forma segura. Existem outras, cada uma com um custo maior de risco. A tabela diz o que cada uma faz e o que o painel responde:

FormaO que fazNo painel
delete pod nomeapaga um objetofunciona
delete pod/nomeo mesmo, com a grafia das mensagensfunciona
delete -f arquivo.yamlapaga o que o arquivo descrevenão: o painel não carrega arquivo
delete pods --allapaga todos do tipo no namespacenão: use um por um aqui
delete pods -l app=cardapioapaga por etiquetanão: idem

O -f é a forma que combina com o resto do guia: você descreve o que quer no arquivo e o kubectl age sobre ele. É mais seguro do que digitar nome à mão, porque o arquivo está no repositório e passou por revisão. O --all e o -l são ferramentas de limpeza em massa — úteis num namespace de teste descartável, perigosas em qualquer lugar onde exista algo que você não escreveu. Antes de um --all, rode o mesmo filtro com get e leia a lista: se aparecer algo que você não esperava, não era para apagar.

Um recurso que não está no painel e vale conhecer: kubectl delete pod teste --dry-run=client -o yaml mostra o que seria apagado, sem apagar. É validação de intenção, do lado do cliente, e serve para conferir o alvo quando você montou o comando com um filtro complicado. O painel desta página não implementa --dry-run; no seu cluster, ele é o equivalente ao “olhar antes de puxar o gatilho” e custa uma linha.

7. Pensar antes: o delete não tem lixeira

Três perguntas antes de qualquer delete em ambiente que importa. A primeira: isso tem dono? Se tem, apagar agora não resolve — o dono recria. Um pod de Deployment apagado volta em segundos, com nome novo; se o objetivo é reduzir o número de pods, o caminho é mudar as réplicas no Deployment, não apagar pods. A segunda: alguém está usando? Um Service apontando para os pods apagados responde erro para todo mundo que estiver navegando, inclusive o cliente no balcão.

A terceira pergunta é a que separa quem tem experiência de quem está começando: qual é o estado desejado? O Kubernetes trabalha por diferença entre o que você descreve e o que existe. Se o objeto está ali, é porque algum manifesto ou algum comando o criou. Apagar à mão cria uma diferença que volta na próxima aplicação do manifesto — e aí você apaga de novo, e o ciclo continua. O conserto de verdade é tirar o objeto do manifesto, ou reduzir a réplica, ou corrigir o manifesto. O delete é para o que não é gerenciado por ninguém: o pod de teste, o serviço esquecido, o objeto criado à mão num momento de pressa.

Existe também o cuidado com o que não é recriado. Apagar um objeto criado à mão é irreversível se você não tem o manifesto anotado em algum lugar. Antes de apagar o que não está no repositório, o hábito é salvar a descrição: kubectl get pod teste -o yaml > teste.yaml — o arquivo fica com o objeto inteiro e serve para recriar depois. Custa um comando e salva uma tarde. E vale para Service, ConfigMap e qualquer coisa que ninguém lembrou de versionar.

8. Quem volta sozinho

Essa é a surpresa mais comum de quem começa. A Ana apagou um pod do cardápio e, dez segundos depois, lá estava ele de novo — com outro nome, do mesmo Deployment. Não é bug: é o controlador fazendo o trabalho dele. O Deployment guarda o número de réplicas desejado e compara com o que existe; faltando um, ele cria. Enquanto o Deployment existir, apagar pods é enxugar gelo.

Pod solto, criado com kubectl run, não tem dono e não volta. É por isso que a caixa da seção 3 usa um pod solto: ali o delete faz exatamente o que parece que faz. A distinção entre “tem dono” e “não tem dono” está no describe, na linha Controlled By — vale conferir antes de apagar, porque ela decide se você vai ver o objeto sumir ou renascer.

O cluster já tem o Deployment cardapio com duas réplicas. Apague o Deployment (não os pods) e liste de novo para confirmar: o painel tem de mostrar deployment.apps/cardapio deleted e No resources found.

kubectl get deployments
ana@notebook:~$ kubectl get deployments
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   2/2     2            2           2m

kubectl delete deployment cardapio
kubectl get deployments

Aqui a leitura é o que importa: o get deployments ficou vazio, e é isso que significa “o Deployment não existe mais”. Se você quisesse derrubar o site, este seria o comando. Se quisesse só reduzir, o caminho seria kubectl scale deployment cardapio --replicas=1, que muda o estado desejado em vez de brigar com ele.

9. Cenários do dia a dia

Cenário 1: a limpeza de segunda

Os três pods de teste da sexta continuavam no cluster no domingo. A Ana listou com get pods --show-labels, confirmou que eram os de teste (etiqueta run=teste), apagou um por um com delete pod e conferiu com get pods no fim. Levou dois minutos e devolveu memória ao nó — que é exatamente o tipo de tarefa em que o delete é a resposta certa.

Cenário 2: o pod que não ficava apagado

Ela apagou um pod do Deployment e ele voltou com outro nome. Apagou de novo, voltou de novo. O describe mostrou Controlled By: ReplicaSet/cardapio-7d9f8: havia um dono. A solução não era apagar mais rápido, e sim kubectl scale deployment cardapio --replicas=1 — mexer no pedido, não na consequência.

Cenário 3: o namespace que levou tudo

Num cluster de testes, alguém apagou o namespace homolog para “limpar”. Levou junto o banco de dados de homologação que o time usava para testar migração, e a recuperação levou um dia. A regra que ficou: namespace é a unidade mais perigosa do delete, porque ele não pede confirmação e não mostra o que vai junto. Antes de apagar um, listar o que existe dentro com get all equivalente, tipo por tipo.

11. Resumo

kubectl delete tipo nome apaga um objeto; a resposta é tipo/nome deleted. O roteiro seguro tem três passos — get antes, delete, get depois — e o mesmo -n nos três. NotFound significa que o objeto não está no namespace consultado, não que o comando falhou em apagar.

O que vai junto depende do que tem dono: apagar Deployment leva ReplicaSets e pods; apagar namespace leva tudo de dentro; apagar pod solto não leva nada. E o contrário também vale: objeto com dono volta sozinho, o que faz de delete a ferramenta errada para reduzir réplicas — para isso existe scale. Na próxima aula a Ana conhece as pastas do cluster, os namespaces, que ela já usou sem cerimônia várias vezes.

Para lembrar
  • kubectl delete pod cardapio responde pod/cardapio deleted.
  • Confirme com get antes e depois; use o mesmo -n nos dois.
  • NotFound = nome errado, namespace errado ou já não existia.
  • Deployment leva os pods dele; namespace leva todos os objetos de dentro.
  • Pod com dono volta com nome novo: para reduzir, use scale.
  • Não existe desfazer: o conserto é aplicar o manifesto de novo.
