O GitOps

O site da padaria da Ana já não é aplicado à mão: os manifestos moram num repositório Git, e uma ferramenta chamada Argo CD lê esse repositório e mantém o cluster igualzinho a ele. Parece só uma formalidade — até a madrugada em que alguém conserta um problema com kubectl set image e esquece de desfazer. Nesta aula a Ana entende o que é GitOps de verdade, o que é drift, como o Argo CD decide que o cluster está fora de sincronia e por que o botão de prune é o mais perigoso da tela.

Você vai aprender
  • O que significa dizer que o Git é a fonte da verdade — e o que isso muda no dia a dia.
  • O que o Argo CD faz: comparar, sincronizar e corrigir, num laço que não para.
  • O que é drift e por que ele aparece mesmo em time organizado.
  • O que selfHeal e prune fazem, e quando eles assustam.
  • Por que o hotfix feito com kubectl às duas da manhã sempre volta como dívida.
  • O que não deve ir para o Git: segredo, dado e o que não é manifesto.

1. A cena: o cluster que não bate com o repositório

Sexta passada a Ana fez o deploy do cardápio novo. O repositório dizia cardapio:2.1.0, o pipeline rodou, o Argo CD mostrou “Synced” em verde e ela foi dormir. Na segunda-feira, o site ainda mostrava o preço antigo. Ela abriu o repositório: a imagem lá era 2.1.0. Abriu o cluster: cardapio:2.0.0. As duas coisas estavam “certas” e não batiam. Levou uma hora para descobrir o motivo: no sábado, de madrugada, alguém tinha feito um teste com kubectl set image e esquecido de voltar.

Esse desencontro tem nome: drift, ou desvio. É a diferença entre o que você quis que existisse e o que existe de fato no cluster. Em um cluster administrado por comandos soltos, o drift é o estado normal — cada pessoa que digitou kubectl deixou uma marca que ninguém viu. Em um cluster com GitOps, o drift é uma condição temporária: alguém compara os dois lados o tempo todo e corrige a diferença.

A pergunta que resume a diferença é simples: se este cluster sumisse agora, você conseguiria recriá-lo exatamente igual só com o que está no repositório? Se a resposta é “quase”, você tem drift. Se é “de jeito nenhum, metade foi feita na mão”, você tem um cluster que ninguém sabe reproduzir — e o dia em que ele cair vai ser longo.

2. Git como fonte da verdade

Pense no caderno de receitas da padaria. Durante anos, cada padeiro anotou a sua versão do pão de queijo num papel diferente, e a receita “oficial” era a que estava na cabeça da Ana. Um dia ela juntou tudo num caderno único, numerado, com data e assinatura em cada mudança. A partir daí, a receita é o caderno. Se o pão sair diferente, o problema é de quem não seguiu o caderno — não existe “a receita do Zé”.

GitOps é isso aplicado ao cluster. O repositório Git guarda os manifestos — os arquivos YAML que descrevem Deployments, Services, ConfigMaps. Uma ferramenta dentro do cluster lê esses arquivos e faz o cluster ficar igual a eles, continuamente. Não é uma pessoa aplicando; é um controlador, do mesmo jeito que o controlador do Deployment cria pods para chegar ao número de réplicas pedido.

Quatro propriedades fazem a diferença na prática. Primeiro, o manifesto é declarativo: você descreve o resultado, não os comandos. Segundo, tudo é versionado: cada mudança tem autor, data e diff, e voltar atrás é um git revert. Terceiro, o estado é reconciliado: alguém compara o desejado com o atual sem parar. Quarto, é auditável: a pergunta “quem mudou as réplicas para cinco?” tem resposta no histórico, e não num log de auditoria do cluster que ninguém ligou.

estado desejado
O que está escrito no repositório: os manifestos, com imagens, réplicas e configuração. É a intenção.
estado atual
O que existe no cluster naquele instante: objetos criados, imagens em execução, réplicas prontas.
drift
A diferença entre os dois. Pode nascer de um kubectl manual, de um objeto criado por outra ferramenta ou de um manifesto que não foi aplicado.
reconciliação
O laço que compara desejado e atual e age para fechar a diferença. É o coração do GitOps e o mesmo padrão que o Kubernetes usa desde sempre.
sync
O ato de aplicar o que está no Git no cluster. Pode ser manual (um botão, um comando) ou automático.
Application
O objeto do Argo CD que amarra um repositório, uma pasta e um namespace de destino. É o “contrato” de sincronização.

Repare no que muda de lugar. Sem GitOps, o cluster é o bem mais valioso e o repositório é documentação. Com GitOps, o repositório é o bem mais valioso e o cluster é descartável: se ele morrer, você aplica o repositório em outro e a padaria volta. Isso só é verdade se tudo estiver no repositório — e é aí que a maioria dos times descobre que metade do cluster foi feita na mão.

3. O Argo CD, em uma frase

O Argo CD é um controlador que roda dentro do cluster e faz uma coisa só: manter o cluster igual ao repositório. Ele baixa os manifestos, renderiza (Helm, Kustomize ou YAML puro), compara com o que está vivo e aplica a diferença. A configuração dele é um objeto chamado Application, que diz onde está o quê e para onde vai:

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cardapio
  namespace: argocd
spec:
  project: padaria
  source:
    repoURL: https://git.loja.test/padaria/site.git
    targetRevision: main
    path: deploy/padaria
  destination:
    server: https://kubernetes.default.svc
    namespace: padaria
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

Leia de baixo para cima, como quem lê uma receita. destination diz onde aplicar: o próprio cluster onde o Argo roda (kubernetes.default.svc é o endereço interno do API server) e o namespace padaria. source diz de onde vem: o repositório, o ramo main e a pasta deploy/padaria. syncPolicy diz como: automático, apagando o que saiu do Git (prune) e corrigindo à força o que alguém mudar na mão (selfHeal).

O Argo CD não é o único. O Flux faz o mesmo trabalho com outra filosofia: é um conjunto de controladores menores, sem interface gráfica própria, operado por linha de comando e pelos próprios objetos do Kubernetes. A escolha entre os dois é menos importante do que o hábito que ambos exigem: parar de aplicar na mão. Uma ferramenta de GitOps num time que continua usando kubectl apply é só mais um componente para dar problema.

4. Sync, drift e o laço que não para

O Argo CD compara três coisas, não duas: o que está no Git, o que está vivo no cluster e o que ele mesmo aplicou na última sincronização. Essa terceira parte é o que permite a ele distinguir “alguém mudou o cluster” de “o Git mudou”. O resultado da comparação vira um estado, e é esse estado que você vê na tela ou no kubectl get applications:

EstadoO que significaO que fazer
Syncedo cluster bate com o Gitnada; é o estado saudável
OutOfSyncexiste diferença entre Git e clusterolhar o diff: quem mudou foi o Git (falta sincronizar) ou o cluster (alguém mexeu)?
Progressinga sincronização está em andamentoesperar; se demorar, kubectl get pods no namespace de destino
Degradedaplicou, mas a aplicação não ficou saudávelé problema de pod, não de Git: logs e describe
Missingo objeto está no Git e não existe no clustersincronizar; se voltar sozinho, algo está apagando
Unknowno Argo não conseguiu compararcredencial do repositório, rede ou permissão do namespace

Duas confusões custam tempo. A primeira é achar que OutOfSync é sinônimo de erro: não é. Significa apenas que os dois lados divergem — e às vezes o lado certo é o cluster, quando alguém corrigiu uma emergência e ainda não commitou. A segunda é achar que sincronizar é aplicar por cima: o Argo calcula a diferença e mexe só no que precisa, o que é bem diferente de reaplicar o arquivo inteiro.

Com automated ligado, o laço roda a cada poucos minutos e também quando o repositório muda. Com selfHeal: true, qualquer alteração manual no cluster é revertida — inclusive a sua, inclusive durante um incidente. É esse detalhe que separa GitOps de “aplicar automaticamente”: no primeiro, o cluster defende o estado do Git.

5. A caixa: devolver o cluster ao que o Git diz

Compare com o seu arquivo: o cluster tem muito mais campos. Todos os que você não escreveu (progressDeadlineSeconds, strategy, revisionHistoryLimit, dnsPolicy...) foram preenchidos pelo API server com os padrões, e o status no fim é o que o controlador calculou. É por isso que “o cluster é igual ao Git” nunca quer dizer byte a byte: quer dizer que os campos que o Git gerencia estão iguais. Todo o resto é conversa entre o cluster e ele mesmo — e é também por isso que o GitOps precisa saber quais campos ele é dono, senão briga com o cluster para sempre.

6. O que muda na cabeça de quem aplicava na mão

A mudança técnica é pequena: em vez de kubectl apply -f, você faz git push. A mudança de cabeça é grande, porque inverte quem tem pressa. Antes, o caminho mais rápido era o terminal: descobriu o problema, colou um kubectl set image, resolveu. Agora o caminho mais rápido é commit, revisão e sincronização — e o terminal passou a ser o caminho que cria drift.

PerguntaCluster aplicado na mãoCluster com GitOps
quem aplica?cada pessoa com acesso, no seu terminalum controlador, sempre do mesmo jeito
como sei o que mudou?pelo histórico do seu shell, se você lembrarpelo git log e pelo diff da Application
como volto atrás?kubectl rollout undo, se o objeto tiver históricogit revert e sincronizar
quem precisa de credencial?todo mundo que aplicasó o Argo CD; o time não precisa de acesso de escrita
revisão antes de aplicarnão existeé o pull request
cluster de teste igual ao de produçãoquase nuncamesma pasta, valores diferentes

O item da credencial é o mais subestimado. Num time que aplica na mão, todo mundo tem cluster-admin — porque é mais fácil dar tudo do que pensar em permissão. Com GitOps, o cluster aceita mudanças vindas de um único lugar, e as pessoas passam a precisar só de leitura. Isso reduz o estrago possível de um erro humano: ninguém apaga um namespace por engano às onze da noite.

E tem o efeito colateral bom: o git blame responde “quem mudou e por quê”. O commit traz a mensagem, o pull request traz a discussão, o diff traz a linha. Nada disso existe num cluster onde a única pista é um evento com created by ana — que é o que o painel deste guia mostra quando você aplica um manifesto.

7. Prune: o que está no Git é o que existe

Existe uma diferença sutil entre “aplicar o que está no Git” e “o cluster ser o que está no Git”. A primeira parte cria e atualiza; ela nunca apaga. A segunda exige prune: apagar o que foi criado por aquela aplicação e não está mais no repositório. Sem prune, o cluster acumula objetos órfãos — o ConfigMap de um teste de março, o Service de uma versão que ninguém usa — e o drift cresce pelo lado do que sobra.

A caixa abaixo mostra a versão sem prune e a versão com prune, de forma condensada: o repositório tem um ConfigMap, o cardapio. Aplique só o que o Git manda.

O repositório define apenas o ConfigMap cardapio, com modo: producao. Apague do arquivo o que não deveria existir e rode: o painel tem de mostrar um único ConfigMap.

O painel mostra dois ConfigMaps na primeira tentativa e um só na segunda. No Argo CD, esse “apagar o que sobra” é o prune: true — e ele é o botão que exige respeito. Com prune ligado, um manifesto que renderiza vazio (um helm template que falhou, uma pasta errada no path, um overlay sem recursos) pode apagar tudo o que aquela Application gerencia. Já viram isso acontecer com namespace inteiro.

Duas proteções ajudam. A primeira é olhar o diff antes de sincronizar quando o prune está ligado: a tela do Argo mostra exatamente o que será apagado. A segunda é separar aplicações por dono — uma Application para o site, outra para o banco, outra para o ingress — para que um erro de render em uma não leve junto o que não é dela. E, claro, o que nunca entra no Git: segredos. Um Secret commitado é um segredo vazado para sempre, porque o histórico do Git não esquece. As soluções para isso (Sealed Secrets, External Secrets, Vault) estão na aula de segredos externos.

8. O hotfix de madrugada e o preço do desvio

Voltemos ao sábado. O site estava fora do ar, a Ana não ia abrir pull request às duas da manhã, e ela fez o que qualquer pessoa faria: apontou o Deployment para a imagem anterior com kubectl set image. Em trinta segundos o site voltou. O problema não foi o comando — foi o que aconteceu depois: nada. A caixa abaixo reproduz a sequência inteira, inclusive o arrependimento.

A primeira linha já está escrita: ela aponta o Deployment para uma imagem de teste e espera o rollout. Depois desfaça a mudança e mostre o histórico de revisões — o painel tem de trazer as três respostas: imagem atualizada, rollout concluído e mudança desfeita.

kubectl set image deployment/cardapio web=cardapio:9.9.9
kubectl rollout status deployment/cardapio
ana@notebook:~$ kubectl set image deployment/cardapio web=cardapio:9.9.9
deployment.apps/cardapio image updated

ana@notebook:~$ kubectl rollout status deployment/cardapio
deployment "cardapio" successfully rolled out

kubectl set image deployment/cardapio web=cardapio:9.9.9
kubectl rollout status deployment/cardapio
kubectl rollout undo deployment/cardapio
kubectl rollout history deployment/cardapio

O rollout undo volta para a revisão anterior — e é a rede de segurança que existe mesmo em cluster com GitOps, para o caso de o Git estar errado. O que ele não faz é avisar o repositório: o Git continua dizendo 2.1.0, o cluster agora diz 1.0, e a diferença vai aparecer como OutOfSync. Se o selfHeal estiver ligado, o Argo desfaz o seu undo em minutos — e isso é o sistema funcionando, não uma falha.

O histórico que o comando imprime é a história do cluster, não a do Git:

REVISION   CHANGE-CAUSE
1          <none>
3          <none>

Repare no CHANGE-CAUSE vazio. Revisão 1 foi a criação, revisão 3 foi o undo (a 2 foi a imagem de teste, que saiu do histórico ao ser desfeita). Nada ali diz “corrigido por causa do incidente de sábado”. Num cluster real, a boa prática é anotar a causa no manifesto — e é justamente o que um pipeline com GitOps faz de graça, porque a mensagem do commit vira o registro da mudança.

A regra que a Ana adotou depois disso: hotfix no cluster é dívida com prazo de duas horas. Se em duas horas o mesmo ajuste não estiver commitado (ou o problema não tiver sido resolvido de outra forma), o próximo deploy vai brigar com ele. Com selfHeal ligado, nem é preciso esperar: o cluster volta sozinho ao que o Git diz, e o incidente continua aberto — o que é honesto, porque o problema nunca foi resolvido de verdade, só escondido.

9. Cenários do dia a dia

Cenário 1: o selfHeal desfez o conserto

A Ana aplicou um hotfix no cluster e, cinco minutos depois, o Argo o desfez. O site voltou a cair e ela achou que a ferramenta estava quebrada. Não estava: selfHeal faz exatamente isso. O caminho correto é commitar o ajuste (mesmo que simples, mesmo que provisório) e deixar o Argo aplicar — ou desligar o selfHeal daquela Application durante a janela de incidente, com data para religar.

Cenário 2: o Pull Request que já está no ar

Num time, a Application aponta para o ramo main e sincroniza sozinha: o merge é o deploy. Em outro, aponta para um ramo de produção que só recebe merge depois do aval — e o deploy é um segundo merge. As duas formas são GitOps; a diferença é quantas pessoas precisam concordar entre o commit e o cluster. O que não funciona é apontar para o ramo de desenvolvimento e fingir que existe revisão.

Cenário 3: o cluster de teste que ninguém olha

A Ana tem duas Applications, uma para padaria e outra para padaria-teste, apontando para a mesma pasta do repositório com valores diferentes (o Kustomize resolve isso com overlays). O risco aparece quando os valores de teste ficam meses sem ser usados: no dia em que ela precisa testar um upgrade, o cluster de teste está três versões atrás e não prova nada. Cluster de teste que não é aplicado pelo mesmo repositório vira museu.

11. Resumo

GitOps é a disciplina de tratar o repositório como fonte da verdade do cluster: o que está lá é o que deve existir, e um controlador — o Argo CD, o Flux — compara os dois lados sem parar e corrige a diferença. O objeto que amarra tudo é a Application: repositório, ramo, pasta, destino e política de sincronização.

O problema que ele resolve tem nome: drift. Um kubectl set image de madrugada, um scale esquecido, um objeto criado por outra ferramenta — tudo isso afasta o cluster do Git. Sincronizar fecha a diferença; selfHeal impede que ela volte; prune apaga o que sobrou, e é onde mora o perigo, porque um manifesto que renderiza vazio pode levar embora o que não devia.

O que muda de verdade é a ordem das coisas: commit, revisão, sincronização — e o terminal deixa de ser o caminho da pressa. O cluster fica descartável, o repositório vira o bem precioso, e a pergunta “quem mudou isso?” passa a ter uma resposta. O segredo continua fora do Git, e a aula de segredos externos mostra como.

Para lembrar
  • Git é a fonte da verdade; o cluster é consequência.
  • OutOfSync não é erro: é diferença. Olhe o diff antes de sincronizar.
  • selfHeal desfaz o seu kubectl; se precisar de hotfix, commite.
  • prune apaga — e um manifesto vazio com prune ligado apaga tudo.
  • Segredo não vai para o Git; o histórico não esquece.
