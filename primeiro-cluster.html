O primeiro cluster

Com o kubectl e o kind instalados, chegou a hora que a Ana estava esperando: ver um cluster nascer. Ela vai rodar um comando, acompanhar as seis etapas da criação, entender o que cada emoji daquela saída significa, olhar os nós que apareceram, descobrir o que já vem instalado dentro do cluster e apagar tudo no fim — sem dó e sem medo. No painel, ela faz o mesmo, com as respostas reais que o cluster dá.

Você vai aprender
  • O que o kind create cluster faz, etapa por etapa.
  • Por que os nós de um cluster kind são containers.
  • Como conferir que o cluster está no ar com cluster-info.
  • Os namespaces que já existem antes de você criar qualquer coisa.
  • Quanta memória e CPU o cluster consome.
  • Apagar e recriar do zero — e por que isso é uma vantagem.

1. A cena: cinco minutos e um cluster

“Um cluster inteiro em cinco minutos?” A Ana não acreditou. Ela já tinha visto instalação de banco de dados levar uma tarde, com senha, porta, serviço e arquivo de configuração. Mas o kind existe exatamente para isso: ele baixa uma imagem de nó pronta, sobe containers que se comportam como máquinas e, dentro deles, inicia o Kubernetes completo — servidor de API, banco de dados do cluster, escalonador, controladores.

O comando é um só. A saída tem seis linhas de etapas e três de instruções. E, no fim, existe um cluster de verdade respondendo a comandos — com a diferença de que ele mora dentro do seu computador, ocupa alguns gigabytes de disco e pode ser apagado com outro comando. Nada de cartão de crédito, nada de nuvem.

Antes de rodar, o cuidado de sempre: o Docker precisa estar no ar. Se o motor estiver parado, a criação falha na primeira etapa com uma mensagem sobre o daemon. É o mesmo pré-requisito da aula anterior, e vale repetir porque é o tropeço número um de quem chega aqui.

2. O comando que cria o cluster

O kind trabalha com clusters com nome. Se você não passar nome nenhum, ele usa o padrão kind. Passar um nome explícito é boa prática: você pode ter mais de um cluster local ao mesmo tempo, e cada um vira um contexto separado no kubeconfig. Vamos usar guia, o mesmo nome do cluster que o painel já tem.

A primeira linha cria o cluster; a segunda tenta buscar um nó chamado só guia, que não existe. Troque a segunda por kubectl get nodes e veja os três nós com o prefixo do cluster no nome.

kind create cluster --name guia
kubectl get node guia
ana@notebook:~$ kind create cluster --name guia
Creating cluster "guia" ...
 • Ensuring node image (kindest/node:v1.37.3) 🐳
 • Preparing nodes 📦
 • Writing configuration 📜
 • Starting control-plane 👷
 • Installing CNI 💉
 • Installing StorageClass 📦
Set kubectl context to "kind-guia"
You can now use your cluster with:

kubectl cluster-info --context kind-guia

ana@notebook:~$ kubectl get node guia
Error from server (NotFound): nodes "guia" not found

kind create cluster --name guia
kubectl get nodes

A mensagem Error from server (NotFound): nodes "guia" not found é didática: o nó não se chama guia, e sim guia-control-plane, guia-worker e guia-worker2. O kind prefixa o nome de cada nó com o nome do cluster — é assim que ele sabe quais containers pertencem a qual cluster na hora de apagar. Se você criar um cluster chamado padaria, os nós serão padaria-control-plane e assim por diante.

Quando você roda kubectl get nodes, a resposta tem três linhas com STATUS Ready. “Ready” é o estado que importa: significa que o nó está registrado no cluster, com o kubelet conversando com o servidor de API e com a rede do cluster pronta. Um nó NotReady aparece quando o kubelet cai, quando a rede do cluster falha ou quando o container que faz o papel de nó está sem memória.

3. Lendo a saída da criação

Vale ler o que o kind imprime, porque cada linha corresponde a uma peça real que está sendo montada. A saída é sempre parecida com esta:

ana@notebook:~$ kind create cluster --name guia
Creating cluster "guia" ...
 • Ensuring node image (kindest/node:v1.37.3) 🐳
 • Preparing nodes 📦
 • Writing configuration 📜
 • Starting control-plane 👷
 • Installing CNI 💉
 • Installing StorageClass 📦
Set kubectl context to "kind-guia"
You can now use your cluster with:

kubectl cluster-info --context kind-guia

Ensuring node image é o download (ou reaproveitamento do cache) da imagem kindest/node, que nada mais é do que um sistema Debian com containerd e os binários do Kubernetes dentro. Na primeira vez são alguns minutos e centenas de megabytes; nas seguintes, segundos.

Preparing nodes cria os containers que farão o papel de máquinas e injeta a configuração de cada um. Writing configuration gera o arquivo do kubeconfig e o endereço da API. Starting control-plane sobe os componentes de controle dentro do primeiro nó. Installing CNI instala a rede de pods (no kind, o kindnet) — sem ela, pod não consegue falar com pod. E Installing StorageClass instala o provisionador de disco local, que permite usar volume persistente sem nuvem.

No fim, Set kubectl context to "kind-guia": o kubectl já sai sabendo com quem falar. Repare no prefixo kind- — o contexto tem nome diferente do cluster para não colidir com clusters de outros provedores que você venha a configurar na mesma máquina. E o kind ainda imprime o comando com --context kind-guia, que é útil quando você tem vários clusters e não quer depender do contexto atual.

Seis etapas, seis conceitos. Vale guardar o vocabulário, porque ele volta em toda mensagem de erro que você vai encontrar pela frente — inclusive nas aulas de diagnóstico, no Nível 3:

plano de controle
O conjunto de componentes que decide e guarda o estado: API, etcd, escalonador, controladores.
nó
A máquina que roda os pods. No kind, um container; na nuvem, uma instância.
kubelet
O agente que roda em cada nó e conversa com a API para manter os pods vivos.
CNI
O padrão de rede de pods. Sem ele instalado, pod não recebe IP e não conversa com ninguém.
etcd
O banco de dados do cluster: guarda tudo o que existe nele. Perder o etcd é perder o cluster.
StorageClass
O modelo de disco que o cluster oferece quando um pod pede volume persistente.

4. O cluster está no ar?

Criar não é garantia de que está tudo certo. A pergunta seguinte é sempre a mesma: o cluster responde? O comando kubectl cluster-info faz uma chamada simples à API e imprime o endereço do plano de controle e dos serviços internos que estão de pé. É o equivalente a discar para o número e ouvir o “alô”.

A primeira linha está com um espaço onde deveria ter hífen, e o kubectl trata cluster como se fosse um verbo. Corrija para kubectl cluster-info e acrescente kubectl get namespaces — que é o mesmo que get ns.

kubectl cluster info
kubectl get ns
ana@notebook:~$ kubectl cluster info
error: unknown command "cluster" for "kubectl"

ana@notebook:~$ kubectl get ns
NAME          AGE
default       8m
kube-system   9m

kubectl cluster-info
kubectl get namespaces

A resposta Kubernetes control plane is running at https://127.0.0.1:6443 confirma três coisas de uma vez: o cluster existe, a API responde e ela está na porta 6443 da sua própria máquina. Em cluster de nuvem, esse endereço seria um nome público. Depois vem a linha do CoreDNS, o serviço que resolve nome de serviço dentro do cluster — se ele está de pé, descoberta de serviço funciona.

O --context kind-guia que o kind sugeriu também aparece aqui em forma de dica: se você tiver dois clusters e o contexto atual for o outro, o comando fala com o cluster errado e você perde tempo depurando um problema que não existe. Quando estiver em dúvida, olhe o contexto antes de qualquer coisa.

5. O que já vem dentro

Ao criar o cluster, você não recebe uma tela em branco: recebe uma casa mobiliada. Existem namespaces — divisórias lógicas que separam grupos de objetos — já criados, e dentro deles rodam os componentes do próprio Kubernetes. O único que você vai usar no dia a dia é o default, onde seus pods nascem quando você não especifica nada.

O outro é o kube-system, onde moram as peças do sistema: servidor de API, banco de dados do cluster, escalonador, controladores, DNS, proxy de rede. Você não cria nada ali; você olha quando precisa investigar por que um pod não sobe. Uma transcrição de cluster real mostra a casa mobiliada de verdade:

ana@notebook:~$ kubectl get ns
NAME                 STATUS   AGE
default              Active   8m
kube-node-lease      Active   8m
kube-public          Active   8m
kube-system          Active   8m
local-path-storage   Active   8m

ana@notebook:~$ kubectl get pods -n kube-system
NAME                                          READY   STATUS    RESTARTS   AGE
coredns-6f9b8c7d4b-2xj9k                      1/1     Running   0          7m
etcd-guia-control-plane                       1/1     Running   0          7m
kindnet-4mzqp                                 1/1     Running   0          7m
kube-apiserver-guia-control-plane             1/1     Running   0          7m
kube-controller-manager-guia-control-plane    1/1     Running   0          7m
kube-proxy-t8w6r                              1/1     Running   0          7m
kube-scheduler-guia-control-plane             1/1     Running   0          7m
local-path-provisioner-7b8f5d9c4d-hq2vn       1/1     Running   0          7m

Esses nomes valem ouro na hora do problema. O etcd guarda o estado do cluster: se ele cai, o cluster inteiro fica sem memória do que existe. O kube-apiserver é a porta de entrada — todo comando do kubectl bate nele. O kube-controller-manager é quem roda os controladores que comparam desejado com real. O kube-scheduler decide em qual nó cada pod vai. O coredns resolve nomes. O kube-proxy cuida das regras de rede de cada nó.

Uma nota honesta sobre o painel: ele simplifica e mostra apenas default e kube-system, e não modela os pods do sistema. Então kubectl get pods -n kube-system no painel responde “nenhum recurso encontrado”, enquanto no cluster real você vê a lista acima. É uma limitação da simulação, não do Kubernetes — e é por isso que a transcrição está aqui, identificada como transcrição.

6. Os nós são containers

Essa é a ideia que faz o kind funcionar, e entender isso resolve metade das dúvidas sobre “meu cluster sumiu”. Cada nó é um container Docker rodando a imagem kindest/node. Se você pedir ao Docker a lista de containers, vê os nós como se fossem aplicações quaisquer:

ana@notebook:~$ docker ps --format "{{.Names}}\t{{.Image}}\t{{.Status}}"
guia-worker2        kindest/node:v1.37.3   Up 8 minutes
guia-worker         kindest/node:v1.37.3   Up 8 minutes
guia-control-plane  kindest/node:v1.37.3   Up 9 minutes

O primeiro da lista terminou de subir depois dos outros — daí o minuto de diferença. O control-plane é o cérebro; os worker são os músculos. Num cluster kind padrão, esse arranjo com um plano de controle e dois workers já vem montado, e é o suficiente para quase tudo o que você vai estudar neste guia.

Consequência prática: quando o Docker para — você fechou o Docker Desktop, reiniciou a máquina, mandou o sistema suspender —, os containers param junto. O cluster não é um serviço do sistema operacional; ele é um conjunto de containers. Ao voltar, basta subir o Docker e, se preciso, recriar o cluster. Como tudo o que importa está em manifestos, recriar não é perda: é rotina.

7. Apagar sem medo

Cluster kind é descartável, e é assim que ele deve ser tratado. O comando de remoção apaga os containers dos nós, as redes e os volumes associados, e tira o contexto do kubeconfig. Um comando, alguns segundos, e a máquina volta a ter o espaço que tinha antes.

A primeira linha usa o plural clusters e o kind só entende o singular. Rode para ver a mensagem e depois corrija para kind delete cluster --name guia.

kind delete clusters --name guia
kind get clusters
ana@notebook:~$ kind delete clusters --name guia
kind: use get clusters, create cluster ou delete cluster

ana@notebook:~$ kind get clusters
guia

kind delete cluster --name guia
kind get clusters

As duas linhas da resposta contam a história: Deleting cluster "guia"... avisa que começou, e Deleted nodes: ["guia-control-plane" "guia-worker" "guia-worker2"] lista exatamente o que foi embora. Nada de “talvez”: o kind sabe quais containers são dele e apaga todos.

No painel, a lista de kind get clusters continua mostrando guia depois da remoção, porque a simulação usa uma lista fixa de clusters. Na sua máquina, o nome sai da lista e o comando responde No kind clusters found quando não sobrar nenhum. Diferença de simulação, mais uma vez — o comportamento real é o da sua máquina.

Recriar é o mesmo comando de antes. E aqui está a parte boa de ter tudo em manifesto: apagar e recriar se torna uma forma legítima de “limpar a bagunça”. Errou a configuração do cluster? Apaga, cria de novo, aplica os arquivos. É mais rápido e mais seguro do que tentar consertar peça por peça.

8. Quanto isso custa em memória

Cluster local não é de graça: cada nó é um container rodando um sistema inteiro. Um cluster kind de três nós fica confortável com 8 GB de RAM na máquina e sofre com 4 GB. O disco também sente: a imagem de nó ocupa algumas centenas de megabytes, e cada cluster usa espaço próprio para o estado do etcd e para volumes.

Comando do kindO que fazO que muda na máquina
kind create cluster --name guiacria o cluster com seus nóscontainers novos, contexto novo no kubeconfig
kind get clusterslista os clusters locaisnada: só leitura
kind delete cluster --name guiaapaga o cluster inteirocontainers, redes e volumes removidos; contexto sai do kubeconfig
kubectl cluster-infopergunta se a API respondenada
kubectl get nodeslista os nós do cluster atualnada

Se a máquina estiver apertada, existe a saída de criar cluster com um nó só: kind create cluster --name guia --config apontando para um arquivo que declara um único nó. Menos nós significa menos memória e menos isolamento — para estudo de pod e Deployment, um nó basta. Para estudar como o escalonador distribui pods entre máquinas, você vai querer os três.

Vale medir antes de reclamar. O comando docker stats mostra, em tempo real, quanta memória cada container está usando — e os três nós do kind aparecem lá com nome e sobrenome. Num cluster ocioso, o consumo fica na casa de algumas centenas de megabytes por nó; quando você começa a criar pods, sobe. Se a máquina começar a trocar memória para o disco, tudo fica lento de um jeito que parece bug do Kubernetes e não é: é falta de RAM. Nesse caso, apague o cluster que não está usando antes de abrir outro.

9. Cenários do dia a dia

Cenário 1: o cluster que “sumiu” depois do almoço

A Ana fechou o notebook para almoçar, voltou, e kubectl get nodes respondeu que não conseguiu conectar. Ela não perdeu nada: o Docker Desktop havia parado junto com a tampa fechada, e os containers estavam parados. Reabriu o Docker, esperou o ícone estabilizar e os nós voltaram. Se não voltassem, seria recriar o cluster e reaplicar os manifestos — dois minutos, porque tudo estava escrito.

Cenário 2: dois clusters, um contexto

Ela criou um cluster chamado teste para arriscar um manifesto e esqueceu que o contexto tinha mudado. Rodou kubectl delete deployment cardapio achando que estava no cluster de estudo e apagou o site do cluster principal. Sorte que era local. A lição: confira o contexto antes de comando destrutivo, e prefira --context explícito quando houver mais de um cluster.

Cenário 3: o nó que ficou NotReady

Num dia de muitas aulas, dois clusters ao mesmo tempo, a máquina ficou sem memória e o nó guia-worker2 passou a NotReady. Os pods dele foram marcados como perdidos e recomeçaram em outro nó. Foi o primeiro contato dela com a cura automática de verdade — e o primeiro sinal de que 8 GB é o mínimo confortável para estudar com dois clusters.

11. Resumo

Criar um cluster local é um comando: kind create cluster --name guia. A saída mostra seis etapas reais — imagem do nó, preparação, configuração, plano de controle, rede e storage — e termina apontando o contexto kind-guia para o cluster novo. Conferir é igualmente curto: kubectl cluster-info prova que a API responde e kubectl get nodes mostra os nós com Ready.

Dentro do cluster você não encontra vazio: existem namespaces prontos, e no kube-system rodam as peças do próprio Kubernetes. Seus objetos ficam no default até você aprender a criar outros. E os nós não são máquinas de verdade: são containers kindest/node — o que explica por que o cluster para quando o Docker para, e por que recriar é tão barato.

Apagar é kind delete cluster --name guia, sem cerimônia. Com o cluster no ar e a máquina entendida, falta o assunto que muda tudo no dia a dia: os comandos do kubectl — ver, descrever, aplicar e apagar. É a próxima aula.

Para lembrar
  • kind create cluster --name guia cria; kind delete cluster apaga.
  • Nós se chamam guia-control-plane, guia-worker, guia-worker2.
  • O contexto ganha prefixo: kind-guia.
  • kubectl cluster-info é o teste “está no ar?”.
  • default é o seu espaço; kube-system é do sistema.
  • Nós são containers: Docker parado, cluster parado.
  • Recriar cluster é rotina quando tudo está em manifesto.
