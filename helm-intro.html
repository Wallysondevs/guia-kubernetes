Helm

O site da Ana tem sete manifestos: Deployment, Service, ConfigMap, Secret, Ingress, HPA e um Job de migração. Funciona no ambiente de teste. Para produção, três linhas mudam — a imagem, o número de réplicas e o endereço do banco — e a Ana copia a pasta inteira, edita as três linhas à mão e reza para não ter esquecido nenhuma. Na terceira cópia, o Service de produção apontava para o ConfigMap de teste. O Helm existe para acabar com essa cópia: um pacote só, com os valores de cada ambiente separados do resto.

Você vai aprender
  • O problema concreto que o Helm resolve — e o que ele não resolve.
  • O que é um chart, uma release e um values.
  • O primeiro helm install, e por que o nome da release importa.
  • Revisões: upgrade, histórico e rollback.
  • O que o chart instala de verdade: os manifestos renderizados.
  • Onde o Helm guarda o estado e quando vale usar kubectl apply no lugar dele.

1. A cena: o mesmo site em três ambientes

Teste, homologação e produção rodam o mesmo site. As diferenças são pequenas e previsíveis: em teste uma réplica e a imagem cardapio:1.0; em homologação duas réplicas e a mesma imagem; em produção quatro réplicas, a imagem promovida, mais memória e um banco diferente. Sete manifestos por ambiente, vinte e um arquivos, todos parecidos.

Copiar e editar funciona até o dia em que não funciona. Ninguém revisa vinte e um arquivos com atenção; a diferença de um espaço em branco não aparece no diff; e quando o time corrige um bug no Deployment de teste, a correção não chega nos outros dois. O sintoma clássico é o “funciona em homologação” seguido de um erro de digitação em produção.

A ideia do Helm é separar duas coisas que a cópia mistura: a receita (quais objetos existem, com que estrutura) e os ingredientes de cada ambiente (imagem, réplicas, endereços). A receita é escrita uma vez; cada ambiente informa só os seus valores. E, de brinde, o Helm guarda o histórico do que foi instalado — o que permite voltar atrás com um comando.

2. O que é o Helm

O Helm se apresenta como “o gerenciador de pacotes do Kubernetes”, e a comparação com um gerenciador de pacotes de sistema ajuda: ele instala um conjunto de arquivos com nome, versão e dependências, e mantém registro do que instalou. A diferença é que o pacote aqui são manifestos e o “instalado” são objetos no cluster.

Três palavras aparecem em toda conversa e vale fixar antes de qualquer comando. O chart é a receita: uma pasta com Chart.yaml, values.yaml e templates/. A release é a instalação de um chart no cluster, com nome próprio — o mesmo chart pode virar três releases, uma por ambiente. E values são os valores que entram na receita, mudando o resultado sem mudar o texto dos templates.

chart
O pacote: pasta com metadados, valores padrão e templates. Tem nome e versão próprios.
release
Uma instalação nomeada de um chart, num namespace. É a release que tem histórico de revisões.
revision
O número da versão da release. Instalar é a revisão 1; cada upgrade soma uma.
values
Os valores que preenchem os templates. Vêm em cascata: padrão do chart, arquivos e --set.
repository
Um endereço onde charts publicados ficam guardados, como uma prateleira de pacotes.
template
Um arquivo de manifesto com buracos (marcados com {{ }}) que o Helm preenche com values.

Se você já viu Helm 2 em algum lugar, uma diferença importa: não existe mais o Tiller, o programa que rodava no cluster com poder quase total. No Helm 3, o cliente fala direto com o API server com as suas permissões, e o estado das releases fica em Secrets no namespace. Isso tirou do Helm o papel de “componente privilegiado do cluster”, o que é uma boa notícia para quem cuida de segurança.

3. O problema que o Helm resolve

Vale ser concreto, porque “gerenciador de pacotes” é uma frase que não diz muito a quem nunca usou um. A tabela compara a vida sem e com o Helm no caso da padaria.

SituaçãoSem HelmCom Helm
mesmo site em três ambientestrês pastas de manifestos copiadosum chart, três arquivos de valores
mudar a imagem em produçãoeditar o YAML no lugar certo e rezarmudar uma linha nos values e upgrade
saber o que está instaladoprocurar objetos por etiquetahelm list e helm history
voltar atráseditar tudo de volta à mãohelm rollback
corrigir um bug em todoscorrigir em três pastascorrigir no chart e subir a versão
reaproveitar algo prontocopiar YAML de um bloghelm install de um chart do repositório

O que o Helm não resolve: ele não valida se o seu manifesto faz sentido, não cuida da saúde dos pods e não substitui o kubectl. Se o chart tiver um Deployment com seletor errado, o Helm vai entregar o Deployment errado ao cluster — o erro é o mesmo, só muda quem apertou o botão.

E ele não é a única resposta: existe o Kustomize, que faz sobreposição de YAML puro sem template. A diferença de filosofia é real, e a aula de Kustomize volta a ela. Por ora, guarde: Helm brilha quando você distribui algo que outras pessoas vão instalar com valores diferentes; Kustomize brilha quando o seu time mantém os próprios manifestos.

4. O primeiro helm install

A forma do comando é helm install NOME DO-CHART. O primeiro argumento é o nome da release — e essa é a decisão que mais confunde quem começa, porque é um nome que você inventa, não o nome do chart. Na padaria, o chart se chama cardapio e a release de produção também: os objetos criados ganham nomes derivados da release.

Falta o nome da release. Instale o chart ./cardapio com o nome cardapio e confira o bloco de resposta.

helm install ./cardapio
helm list
ana@notebook:~$ helm install ./cardapio
NAME: ./cardapio
LAST DEPLOYED: Fri Nov 27 15:50:21 2026
NAMESPACE: default
STATUS: deployed
REVISION: 1
NOTES:
O cardápio está no ar em http://./cardapio.loja.test

ana@notebook:~$ helm list
NAME         NAMESPACE   REVISION   UPDATED               STATUS     CHART    APP VERSION
./cardapio   default     1          2026-11-27 15:50:21   deployed   -0.1.0   1.0.0

helm install cardapio ./cardapio
helm list

A resposta traz o nome, a data, o namespace, o status e a revisão. STATUS: deployed quer dizer que o Helm entregou tudo ao cluster e considerou a release instalada; REVISION: 1 é a primeira versão dessa release. As notas (NOTES) vêm de um arquivo do chart e costumam trazer o endereço do serviço recém-instalado.

Se você rodar sem nome, o Helm usa o primeiro argumento como nome — e a release fica com um nome esquisito, derivado do caminho do chart. Ela funciona, mas aparece na listagem como ./cardapio e ninguém sabe o que é. Escolher um nome curto e estável, igual ao do serviço, é o padrão que evita dor de cabeça.

5. A release: revisão, histórico e rollback

Instalar é o começo. Toda mudança depois disso é helm upgrade, e cada uma soma uma revisão. É esse histórico que dá ao Helm um superpoder que o kubectl apply não tem: voltar para uma revisão anterior sabendo exatamente o que estava lá.

A caixa abaixo tem só um install. Troque por um upgrade e veja a revisão subir para 2.

A release já está instalada. Suba uma nova versão com helm upgrade e repare no número da revisão.

helm install cardapio ./cardapio
helm list
ana@notebook:~$ helm install cardapio ./cardapio
NAME: cardapio
LAST DEPLOYED: Fri Nov 27 15:50:21 2026
NAMESPACE: default
STATUS: deployed
REVISION: 1
NOTES:
O cardápio está no ar em http://cardapio.loja.test

ana@notebook:~$ helm list
NAME       NAMESPACE   REVISION   UPDATED               STATUS     CHART              APP VERSION
cardapio   default     1          2026-11-27 15:50:21   deployed   ./cardapio-0.1.0   1.0.0

helm upgrade cardapio ./cardapio
helm list

O histórico completo, num cluster de verdade, é uma tabela como esta (transcrição):

$ helm history cardapio
REVISION  UPDATED                  STATUS      CHART           APP VERSION  DESCRIPTION
1         2026-11-20 09:12:44 UTC  superseded  cardapio-0.3.0  1.3.0        Install complete
2         2026-11-24 18:03:10 UTC  superseded  cardapio-0.3.1  1.4.0        Upgrade complete
3         2026-11-27 15:50:21 UTC  deployed    cardapio-0.3.1  1.4.0        Upgrade complete

Leia as colunas: cada revisão guarda o chart usado, a versão da aplicação e uma descrição. As antigas ficam superseded (substituídas) e a atual deployed. Com isso, helm rollback cardapio 1 volta o cluster ao estado da primeira revisão e cria a revisão 4 com o conteúdo da 1 — o histórico nunca reescreve o passado, o que é ótimo para auditoria.

O helm list também mostra o essencial de cada release instalada. Esta é a saída de um cluster com três ambientes (transcrição):

$ helm list -A
NAME        NAMESPACE     REVISION  UPDATED                  STATUS    CHART           APP VERSION
cardapio    padaria-prod  3         2026-11-27 15:50:21 UTC  deployed  cardapio-0.3.1  1.4.0
cardapio    padaria-teste 1         2026-11-26 11:02:37 UTC  deployed  cardapio-0.3.0  1.3.0
relatorio   padaria-prod  2         2026-11-27 08:15:02 UTC  deployed  relatorio-0.1.2 0.9.1

Repare que existem duas releases chamadas cardapio, em namespaces diferentes. Isso é normal e é assim que o Helm separa ambientes: o nome da release é único dentro do namespace. Como os objetos também vivem no namespace, não há conflito de nomes entre teste e produção.

6. O que o chart instala de verdade

Aqui está o ponto que separa quem entendeu de quem só decorou comandos: o Helm não tem nada de mágico. Ele lê os templates, preenche os buracos com os values e entrega ao cluster manifestos YAML comuns — os mesmos que você escreveria à mão. Se o chart tem um Deployment e um Service, o resultado são um Deployment e um Service.

Por isso é possível (e recomendado) pedir ao Helm que mostre o resultado antes de aplicar: helm template imprime os manifestos renderizados, e helm install --dry-run faz o mesmo com o contexto da release. É a maneira mais barata de descobrir que o seu template gerou replicas: 0 em produção.

O painel do guia aplica os dois documentos e mostra os pods; a verificação confere as réplicas prontas e a porta do Service. Vale dizer o que ele não faz: ele não executa o Helm nem renderiza templates — os comandos helm têm resposta simulada, e o que você vê aqui é o manifesto final, aplicado como qualquer outro. É a parte que importa para entender o que um chart entrega.

7. Onde o estado mora

Se não existe mais Tiller, onde fica o registro das releases? Em Secrets no namespace da release, com nomes que começam por sh.helm.release.v1.. Cada revisão vira um Secret separado, contendo o chart e os values usados. Isso explica três comportamentos que surpreendem:

O primeiro: quem tem permissão de ler Secrets no namespace consegue ver os values da release — inclusive os que você passou por --set com senha. Values não é lugar de segredo; para isso existem os objetos de Secret e os cofres externos.

O segundo: apagar o namespace apaga as releases junto, porque o registro mora ali. E o terceiro: migrar uma release de namespace não é um comando, é um procedimento — o histórico está preso ao namespace antigo.

Do lado das permissões, o Helm usa a sua credencial do kubeconfig. Se você pode criar Deployments, pode instalar charts que criam Deployments. Isso significa que instalar um chart de terceiro é dar a ele as suas permissões: vale ler os templates antes, com helm template, como você leria qualquer manifesto que cai de paraquedas no cluster.

8. Helm ou kubectl apply?

Os dois convivem, e saber qual usar em cada momento evita discussão de time. A regra prática é sobre quem consome aquele conjunto de manifestos.

SituaçãoFerramentaPor quê
um manifesto que você edita e aplicakubectl applysimples, direto, sem intermediário
algo que outras pessoas vão instalar com valores própriosHelmo chart é o contrato; os values são a entrada
software de terceiro (banco, proxy, monitoramento)Helmalguém já empacotou e mantém as atualizações
três ambientes com poucas diferençasHelm ou Kustomizedepende se você quer template ou sobreposição
experimento de cinco minutoskubectlcriar chart para testar é desperdício

Uma armadilha comum é misturar os dois no mesmo objeto: instalar a release com Helm e depois editar o Deployment com kubectl edit. O Helm não sabe da edição, o próximo upgrade desfaz a sua mudança sem avisar, e alguém passa a tarde tentando entender por que o ajuste “não pega”. Se a release é do Helm, mude pelos values e dê upgrade.

9. Instalando um chart de terceiro

Até aqui a Ana instalou o próprio chart, numa pasta local. Metade do uso real do Helm é o contrário: pegar algo que outra pessoa empacotou. O caminho tem três passos e nenhum mistério.

Primeiro, adicionar o repositório — a prateleira de onde os charts vêm: helm repo add bitnami https://charts.bitnami.com/bitnami. Segundo, atualizar o índice local com helm repo update, que baixa a lista de charts e versões disponíveis. Terceiro, procurar e instalar: helm search repo lista o que existe, e helm install meu-banco bitnami/postgresql --version 16.4.1 --namespace padaria --create-namespace instala a versão escolhida num namespace próprio.

Antes de instalar, dois comandos economizam arrependimento: helm show values bitnami/postgresql imprime todos os valores que aquele chart aceita (é a documentação real dele) e helm template meu-banco bitnami/postgresql mostra os manifestos que seriam criados. Num chart grande, a lista de values tem centenas de linhas — e é normal: você sobrescreve cinco e deixa o resto no padrão de quem escreveu.

Fixar a versão com --version não é preciosismo. Sem ela, o Helm usa a última disponível, e um upgrade feito meses depois pode pular três versões de uma vez. Em produção, a versão do chart é tão parte da receita quanto a versão da imagem.

10. Cenários do dia a dia

Cenário 1: a release que ninguém sabia que existia

Um serviço antigo tinha sido instalado com Helm por alguém que saiu do time. Quando o novo Deployment foi aplicado com kubectl apply, os dois brigaram pelo mesmo nome de objeto e o resultado foi um rollout eterno. O desempate veio de helm list -A: quem instala com Helm registra a release, e isso é a documentação mínima de que aquilo existe.

Cenário 2: o rollback que salvou a madrugada

Um upgrade mudou a imagem para uma versão com um bug que só aparecia com carga. Em vez de caçar o manifesto anterior, a Ana rodou helm rollback cardapio, sem número, que volta para a última revisão que funcionou. O cluster voltou em menos de um minuto, e a investigação ficou para o dia seguinte.

Cenário 3: a senha no --set

Alguém instalou um chart passando a senha do banco com --set senha=.... Funcionou — e a senha ficou gravada em claro no Secret de histórico da release, visível para qualquer um com permissão de leitura no namespace. A correção foi mover a senha para um Secret criado à parte e referenciado pelo chart.

12. Resumo

Helm é o gerenciador de pacotes do Kubernetes. O chart é a receita (metadados, values padrão e templates), a release é a instalação nomeada num namespace e a revisão é o número que sobe a cada mudança. Instalar é helm install NOME ./chart; mudar é helm upgrade; voltar é helm rollback.

O que o Helm entrega ao cluster são manifestos comuns, gerados pelos templates com os values. Por isso helm template e --dry-run existem: ver antes de aplicar. O estado das releases mora em Secrets no namespace — motivo pelo qual values não é lugar de segredo e por que apagar o namespace apaga o histórico.

Use Helm quando distribui algo que outras pessoas instalam com valores próprios; use kubectl apply para o manifesto solto do dia a dia. E não misture os dois no mesmo objeto: se a release é do Helm, a mudança passa pelos values. Na aula seguinte a Ana abre o chart por dentro: o que é Chart.yaml, como o template vira manifesto e por que a renderização às vezes quebra.

Para lembrar
  • chart = receita; release = instalação nomeada; revision = versão da release.
  • helm install NOME ./chart: o primeiro argumento é o nome que você inventa.
  • helm list -A mostra as releases; helm history, as revisões.
  • helm template mostra o manifesto renderizado antes de aplicar.
  • Sem Tiller: o estado fica em Secrets sh.helm.release.v1.* no namespace.
  • Não edite com kubectl o que o Helm instalou: o próximo upgrade desfaz.
