Ingress

O site da padaria cresceu: cardápio, painel de pedidos e uma API de preços, cada um com o seu Service. Para o cliente, isso virou um endereço esquisito com porta de cinco dígitos por aplicação. A Ana queria o contrário — um endereço só, padaria.test, com cada caminho levando para o serviço certo. É exatamente o que um Ingress faz: uma regra de roteamento HTTP escrita em YAML e entregue ao cluster. Nesta aula você monta a primeira regra, entende o que ela precisa para funcionar e aprende a achar o erro quando o caminho não chega.

Você vai aprender
  • O que é um Ingress e por que ele não substitui o Service.
  • O papel do controller de Ingress e o que acontece sem ele.
  • Como ler uma regra: host, path, pathType e backend.
  • O que cada pathType faz na prática.
  • Como apontar um caminho para um Service e o que acontece quando o nome erra.
  • Como descobrir por que um Ingress não roteia, olhando os três elos da corrente.

1. A cena: um endereço por aplicação

Até ontem, cada parte do site tinha o seu Service do tipo NodePort. O cardápio respondia em uma porta alta, o painel em outra, a API de preços em uma terceira. A Ana anotou as três num papel colado no balcão e mandou o link para os clientes. Funcionava — do jeito que funciona uma casa com três campainhas na porta.

O problema aparece quando o número de aplicações cresce. Cada porta nova é uma linha a mais no papel, um link a mais para explicar e uma chance a mais de o cliente digitar errado. Pior: o certificado HTTPS vale para um domínio, não para uma porta. Se o site quer ser padaria.test — e a Ana quer — alguém precisa receber o tráfego na porta 80 ou 443 e decidir para onde mandar cada caminho.

Esse “alguém” é o Ingress. Ele é a recepção do prédio: um único endereço na rua, e uma lista na portaria dizendo que o 3º andar é o cardápio, o 5º é o painel e o subsolo é a API. O cliente continua vendo um endereço só; quem separa é a regra.

2. O Ingress não substitui o Service

A confusão mais comum é achar que o Ingress “é o Service novo”. Não é. O Service responde a uma pergunta de rede interna: “quais pods atendem esta etiqueta, e em que porta?”. O Ingress responde a uma pergunta de HTTP: “para qual Service vai uma requisição com este host e este caminho?”. Um aponta para o outro: o Ingress tem um backend, e o backend é um Service.

Ingress
Objeto que descreve roteamento HTTP: host, caminho e o Service de destino. Não abre porta sozinho; quem escuta é o controller.
controller de Ingress
O programa que lê os objetos Ingress e configura o proxy de verdade (nginx, Traefik, HAProxy). Sem ele, o Ingress é só um registro no banco do cluster.
ingressClassName
Qual controller deve atender este Ingress. Num cluster com mais de um controller, é o que evita que a regra caia no lugar errado.
host
O nome de domínio da regra: padaria.test. Requisição com outro host não entra nessa regra.
path e pathType
O caminho (/, /api) e como compará-lo: Prefix, Exact ou ImplementationSpecific.
backend
O Service de destino e a porta dele (number ou name). É para cá que o tráfego do caminho vai.
defaultBackend
O destino de tudo o que não casou com nenhuma regra. Sem ele, o que não casa recebe 404 do controller.

Guarde essa hierarquia, porque é ela que organiza o diagnóstico: cliente → controller → Ingress → Service → pods. Se o site não abre, o erro está em um desses cinco elos, e cada um tem um sintoma diferente. O Ingress é só o terceiro.

Para fixar a diferença, vale ver os três objetos lado a lado, cada um com a pergunta que responde. É essa separação que permite diagnosticar por camada, sem misturar as causas.

ObjetoPergunta que respondeO que ele não faz
Servicequais pods atendem esta etiqueta, em que porta?não entende HTTP, host nem caminho
Ingresspara qual Service vai este host e este caminho?não abre porta nem fala com pods
controllerquem escuta na borda e aplica as regras?não cria pods nem altera o Service

Repare na terceira linha: o controller é software, não um objeto do Kubernetes. Ele roda como um Deployment qualquer, com Service e tudo. Isso significa que ele também pode estar fora do ar, sem réplicas prontas ou com a versão errada — e nesse caso todos os Ingress do cluster param juntos.

3. O controller: quem realmente escuta

Um manifesto de Ingress não abre porta nenhuma. Ele é uma intenção guardada na API. Quem lê essa intenção e escreve a configuração do proxy é o controller — no caso mais comum, o ingress-nginx, que roda como um Deployment dentro do próprio cluster e fica exposto por um Service do tipo LoadBalancer ou NodePort.

Isso explica dois sintomas que assustam. O primeiro: você aplica o Ingress, o kubectl get ingress mostra ADDRESS vazio (ou pendente) e nada funciona. O objeto existe; o controller é que não está lá para preencher. O segundo: o Ingress aparece com endereço, mas o domínio não resolve — porque o DNS do mundo real precisa apontar para esse endereço, e isso é configuração de registro, não de Kubernetes.

Neste guia o painel não simula tráfego: ele mostra o que o Kubernetes guardaria e o que o kubectl get responderia. O roteamento em si — o proxy recebendo a requisição e escolhendo o pod — aparece nas transcrições, sempre identificadas como tal. É a mesma honestidade das aulas de pod: o que é cálculo o motor faz; o que depende de rede real vem de fora.

Um jeito rápido de confirmar que o controller está no caminho é olhar o log de acesso dele. Esta é uma transcrição de um cluster real, com o ingress-nginx recebendo três requisições:

192.0.2.54 - - [27/Nov/2026:09:14:02 +0000] "GET / HTTP/1.1" 200 615 "-" "curl/8.5.0"
192.0.2.54 - - [27/Nov/2026:09:14:07 +0000] "GET /api/precos HTTP/1.1" 200 132 "-" "curl/8.5.0"
192.0.2.54 - - [27/Nov/2026:09:14:12 +0000] "GET /cardapio HTTP/1.1" 503 190 "-" "curl/8.5.0"

Três linhas, três histórias. As duas primeiras são 200: o controller achou a regra e o Service respondeu. A terceira é 503: a regra existe, mas o backend não tem para onde mandar — Service inexistente ou sem pods prontos. Um 404 no fim da linha contaria outra história: nenhuma regra casou com aquele caminho.

4. A caixa: a regra sem pathType

O primeiro erro de todo mundo ao escrever um Ingress é esquecer o pathType. Ele não é opcional: a API recusa o objeto e diz qual caminho está sem ele. A caixa tem um Ingress apontando para o Service cardapio, com o caminho / e sem o tipo.

Falta o pathType do caminho /. Rode e leia o erro; depois acrescente pathType: Prefix embaixo de path e rode de novo.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cardapio
spec:
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            backend:
              service:
                name: cardapio
                port:
                  number: 80
The Ingress "cardapio" is invalid: spec.rules[0].http.paths[0].pathType: Required value

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cardapio
spec:
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapio
                port:
                  number: 80

A resposta é spec.rules[0].http.paths[0].pathType: Required value. O caminho do erro é literalmente o endereço do campo dentro do manifesto: regra 0, caminho 0. Com o tipo preenchido, o painel mostra ingress.networking.k8s.io/cardapio created e a tabela do get ingress com HOSTS padaria.test e ADDRESS 192.0.2.10.

Repare na coluna PORTS: ela mostra 80, 443 mesmo que o backend seja a porta 80 de um Service. Não é engano: o Ingress descreve o que o controller deve escutar na borda — HTTP e HTTPS — e o número do backend é outra coisa, resolvida depois, no salto para o Service.

5. Lendo a regra em voz alta

Um Ingress se lê como uma frase: “quando o pedido vier para este host, com este caminho, mande para este Service nesta porta”. Cada pedaço dessa frase é um campo, e o YAML tem exatamente a mesma ordem. Vale treinar a leitura com o manifesto da caixa anterior:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cardapio
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapio
                port:
                  number: 80

O apiVersion é networking.k8s.io/v1, e não v1: Ingress mora no grupo de rede. Trocar para v1 dá aquele erro de “no matches for kind” que você já viu no Deployment. O metadata.name é o nome do Ingress; o spec tem as regras.

Dentro de rules há uma lista, e cada item é um host. Um Ingress pode ter vários hosts no mesmo objeto: a padaria usa padaria.test para o site e admin.padaria.test para o painel. Dentro de cada host, http.paths é outra lista: os caminhos. E cada caminho tem backend, que é sempre um Service — nunca um pod direto. Essa é a regra que mais gente esquece: Ingress não fala com pod; fala com Service.

6. A caixa: o backend com nome errado

O erro seguinte não é de validação: o manifesto é aceito, o Ingress é criado e o cliente recebe um 503 do controller. O motivo é que o Service apontado no backend não existe. A caixa tem o nome com uma letra a mais.

O backend aponta para o Service cardapioo, que não existe. Corrija o nome para cardapio e rode.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cardapio
spec:
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapioo
                port:
                  number: 80
ingress.networking.k8s.io/cardapio created

Repare no contraste com a caixa anterior: aqui o apply passa sem reclamar. O Kubernetes não verifica se o Service do backend existe — ele guarda a intenção e deixa o controller descobrir na hora de configurar. Essa diferença é a razão de o diagnóstico de Ingress ter duas etapas: primeiro “o objeto está certo?”, depois “o que ele aponta existe?”.

Nesta transcrição de um cluster real, o controller responde exatamente isso quando o backend não existe:

A tabela Rules é o coração do describe de um Ingress: cada linha mostra host, caminho e o backend com o endereço para onde ele resolve. Se o endereço aparece entre parênteses, o controller achou o Service; se o backend aparece com o nome errado e sem endereço, é ali que está o problema.

7. Prefix, Exact e o caminho que pega tudo

O pathType decide como o controller compara o caminho da requisição com o caminho da regra. São três valores, e a diferença entre eles explica a maioria dos “rotas erradas” que aparecem em produção.

pathTypeComo comparaQuando usar
Prefixcasa com o caminho e com tudo abaixo dele, por segmentos: /api casa com /api e /api/precoso caso normal de uma aplicação com subrotas
Exactcasa só com o caminho escrito, sem nada depoisrotas pontuais, como /saude ou um /login
ImplementationSpecificdeixa a comparação para o controllerquando você usa o modo nativo do nginx ou de outro proxy

Prefix compara por segmentos, não por letras. Isso importa: /api casa com /api/precos, mas não casa com /apice — o segmento seguinte precisa começar depois de uma barra. Já Exact com / casa apenas a raiz do site: quem pedir /cardapio recebe 404. É um erro clássico de quem quer “a home” e acaba derrubando o site inteiro.

Quando duas regras casam, o controller usa a mais específica: o caminho mais longo vence. É assim que a Ana pode ter /api para a API de preços e / para o site no mesmo host, sem conflito. A ordem em que as regras aparecem no YAML não decide nada — o que decide é o tamanho do caminho.

8. A caixa: dizendo qual controller deve atender

Num cluster com mais de um controller — o nginx da padaria e o do provedor de nuvem, por exemplo — um Ingress sem ingressClassName fica órfão: cada controller pode ignorá-lo, e o objeto aparece criado, com endereço vazio. A caixa tem esse caso.

Acrescente ingressClassName: nginx ao spec e rode. A coluna CLASS da tabela tem de mostrar nginx.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cardapio
spec:
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapio
                port:
                  number: 80
ingress.networking.k8s.io/cardapio created

NAME       CLASS    HOSTS          ADDRESS      PORTS     AGE
cardapio   <none>   padaria.test   192.0.2.10   80, 443   2m

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cardapio
spec:
  ingressClassName: nginx
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapio
                port:
                  number: 80

Com a classe preenchida, a tabela mostra CLASS nginx. Em cluster de um controller só, isso costuma ser opcional — o controller assume tudo o que não tem classe. Em cluster compartilhado, é a diferença entre a regra funcionar e a regra existir sem efeito, e o sintoma é sempre o mesmo: ADDRESS vazio e o cliente recebendo erro de conexão.

Uma nota sobre a versão antiga: você vai encontrar manifestos com kubernetes.io/ingress.class nas anotações. Era o jeito antigo de dizer a mesma coisa, e ainda funciona em muitos controllers, mas o campo ingressClassName é o moderno e o que a documentação recomenda. Se os dois aparecerem e discordarem, o comportamento depende do controller — melhor não misturar.

9. Cenários do dia a dia

Cenário 1: o Ingress criado e o site sem resposta

A Ana aplicou o Ingress, viu created, abriu o navegador e nada. O get ingress mostrava ADDRESS vazio: o controller não estava instalado no cluster. Instalar o ingress-nginx resolveu na hora — e o objeto nem precisou ser reaplicado. O Ingress era uma intenção esperando quem a executasse.

Cenário 2: o 404 que vinha do pathType

O painel do balcão ficava em /admin e o Ingress tinha pathType: Exact. A tela inicial abria, mas qualquer link interno dava 404, porque /admin/pedidos não casa com Exact /admin. A troca para Prefix resolveu — e a lição foi entender que o caminho de uma aplicação quase nunca é um endereço só.

Cenário 3: o domínio certo apontando para o lugar errado

Depois de tudo funcionando, a Ana comprou o domínio e apontou o DNS para o IP do cluster. O site abria o cardápio em /, mas a API respondia 404: o Ingress da API tinha host api.padaria.test e o cliente chamava padaria.test/api. A regra estava certa; o pedido chegava com outro host. Um segundo caminho no mesmo Ingress resolveu sem tocar no DNS.

11. Resumo

Ingress é a camada HTTP do cluster: um endereço só, com regras que distribuem host e caminho entre Services. Ele não abre porta nem fala com pods — quem escuta é o controller, e o destino é sempre um Service. Sem controller, o objeto existe e não faz nada; é a primeira coisa a conferir quando o ADDRESS está vazio.

A regra se lê como uma frase: host, caminho, tipo de comparação e backend. pathType é obrigatório, Prefix é o caso normal, Exact serve para rotas pontuais e o caminho mais específico vence quando dois casam. O nome do Service no backend não é validado no apply — ele é descoberto na hora de configurar, e é aí que aparece o 503.

Na próxima aula o mesmo Ingress ganha HTTPS: um certificado guardado num Secret, o bloco tls apontando para ele e o redirecionamento de HTTP para HTTPS. É o passo que transforma um site de teste num site que o cliente pode usar sem aviso do navegador.

Para lembrar
  • Ingress roteia HTTP por host e caminho; o destino é sempre um Service.
  • Sem controller (e sem ingressClassName correto), o Ingress não tem efeito.
  • pathType é obrigatório: Prefix, Exact ou ImplementationSpecific.
  • O caminho mais específico vence; a ordem no YAML não importa.
  • ADDRESS vazio = controller ausente ou DNS ainda não apontado.
  • Backend errado não dá erro no apply: aparece como 503 ou no describe.
