Mensagens de erro

São três da manhã, o site da padaria está fora do ar e a Ana tem uma tela com uma palavra em inglês. Esta página é o catálogo que ela abre nessa hora: o estado que aparece no get, a mensagem que aparece no describe, a causa em uma linha e o que fazer. Está tudo em tabela, na ordem em que os problemas costumam aparecer.

1. Para que serve esta página (e o que ela não cobre)

Mensagem de erro no Kubernetes tem três origens diferentes, e confundi-las é o que faz a madrugada durar mais: o API server recusa o manifesto, o agendador não encontra lugar, e o kubelet não consegue rodar o container. Cada uma deixa a mensagem num lugar diferente.

Esta página é a consulta por sintoma: você sabe o que está vendo e quer a causa provável. Ela não ensina a depurar do zero — o roteiro completo está na aula de checklist — e não entra em problema de rede entre pods, que tem página própria.

O que fica de fora: CrashLoopBackOff com causa de aplicação (vai para a aula de crashloop), ImagePullBackOff com registro privado (vai para a aula de imagem) e erro de Service sem endpoint. No fim há o link de cada uma.

Para usar a página com pressa, procure pelo texto exato que está na tela: Pending, 137, Forbidden, not found. O navegador acha em um segundo, e a linha da tabela já traz a causa e o próximo passo. Se a mensagem não estiver aqui, o caminho é o describe — ele quase sempre tem uma frase mais específica do que a do get.

Um aviso honesto sobre este guia: o painel não executa container. Ele calcula agendamento, validação e contagem de pods, mas CrashLoopBackOff, ImagePullBackOff e OOMKilled não acontecem ali — aparecem nesta página como transcrição de cluster real, sempre identificada. O que o painel mostra de verdade são os erros de apply e o Pending por falta de lugar.

2. O essencial em 10 linhas

  1. Comece pelo kubectl get pods: a coluna STATUS diz qual dos três mundos é o problema.
  2. Pending é o agendador: nenhum nó coube, ou falta um PVC.
  3. ContainerCreating é o kubelet: imagem baixando ou volume montando.
  4. ImagePullBackOff é imagem: nome, tag ou credencial de registro.
  5. CreateContainerConfigError é referência: ConfigMap ou Secret que não existe.
  6. CrashLoopBackOff é o programa: ele sobe e morre, e o intervalo entre tentativas cresce.
  7. OOMKilled com código 137 é memória: o limite era menor do que o consumo.
  8. Forbidden é RBAC: verbo, recurso, grupo e namespace na própria mensagem.
  9. Invalid é validação: o campo errado vem antes dos dois-pontos.
  10. O describe guarda os eventos; o logs guarda a saída do programa. Um não substitui o outro.

Há um hábito que economiza mais tempo do que qualquer comando: antes de olhar o cluster, responda duas perguntas. O que mudou nas últimas horas — imagem, manifesto, configuração, nó? E o problema é de um pod só ou de todos? Um pod só aponta para manifesto; todos apontam para nó, cota, imagem ou configuração compartilhada. Sem essas duas respostas, o plantão vira tentativa e erro, e cada tentativa apaga um pouco da evidência.

O roteiro de trinta segundos, na ordem: get pods, describe pod, ler os eventos, logs, e só então mexer em alguma coisa. Pular direto para “vou reiniciar” costuma apagar a única evidência que existia.

3. Anatomia: onde cada erro aparece

Toda mensagem do Kubernetes tem um formato parecido, e reconhecer as partes acelera a leitura. A anatomia abaixo é a dos campos que você vai encontrar no get, no describe e na resposta do apply.

STATUS
a coluna do get pods: Pending, ContainerCreating, Running, CrashLoopBackOff, Completed, Error, Terminating. É o primeiro indício, não o diagnóstico.
READY
containers prontos sobre o total. 1/1 com Running é saudável; 0/1 com Running é sonda de prontidão falhando.
Events
o bloco no fim do describe, com Type, Reason, Message e contagem. É onde o kubelet e o agendador escrevem o motivo real.
Reason
o motivo em uma palavra: FailedScheduling, FailedMount, FailedPull, BackOff, OOMKilled, Evicted.
Last State / Exit Code
no describe, o estado anterior do container e o código com que ele saiu. 137 é memória; 143 é encerramento educado; 1 é erro do programa.
Error from server (…)
o prefixo das respostas do API server, com o motivo entre parênteses: Forbidden, NotFound, Invalid, AlreadyExists, Conflict.

Há ainda uma quarta origem, que não é erro de pod: o controlador. Quando um Deployment não cria pods, o problema pode estar no ReplicaSet; quando um Job não termina, o motivo pode estar no backoffLimit. Nesses casos o get pods não mostra nada de errado, porque o pod nem existe — e o describe do objeto pai é que conta a história, no mesmo bloco de eventos.

A leitura útil é sempre de fora para dentro: status → evento → estado do container → saída do programa. Cada camada responde uma pergunta e elimina metade das hipóteses. Quem começa pela última camada — abrindo o código da aplicação — costuma investigar o problema errado.

5. Os campos que mais confundem

A confusão mais comum é entre o que o describe mostra e o que o logs mostra. O primeiro conta o que o cluster fez com o pod; o segundo conta o que o programa disse. Quando o container nunca chegou a rodar, não existe log — e a ausência de log é uma informação, não um beco sem saída.

A linha do log vazio explica metade dos plantões: se o container não iniciou, o kubectl logs responde Error from server (BadRequest): container "web" in pod "cardapio" is waiting to start: CreateContainerConfigError. A mensagem está dizendo que não há log para mostrar e, de brinde, qual é o estado. O caminho é o evento, não o log.

Vale distinguir as duas recusas que mais se confundem na leitura rápida. NotFound é o cluster dizendo “não existe objeto com esse nome e esse tipo aqui” — quase sempre namespace errado ou nome digitado errado. Forbidden é o cluster dizendo “existe, mas você não pode ver” — e, por segurança, ele não confirma se o objeto existe. Quem trata as duas como iguais perde tempo conferindo o nome de um pod que está lá, no namespace ao lado.

A outra metade é o logs --previous. Quando o pod está em CrashLoopBackOff, o container atual pode estar dormindo entre tentativas; o --previous mostra a saída da última tentativa que morreu, que é onde está o erro de verdade.

A primeira transcrição é de um pod que não agenda por falta de memória. Repare que o evento diz quantos nós foram considerados e por quê — a informação está toda ali:

$ kubectl describe pod forno
...
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  18s   default-scheduler  0/3 nodes are available: 3 Insufficient memory. preemption: 0/3 nodes are available: 3 No preemption victims found for incoming pod.

A segunda é o caso clássico de memória: o container morreu, o kubelet reiniciou, e o estado anterior ficou registrado. O 137 com OOMKilled é a assinatura:

$ kubectl describe pod relatorio
...
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
    Ready:          False
    Restart Count:  6

A mensagem de cota é a que mais confunde porque o pod nem aparece no get pods: a recusa acontece na criação, e o texto vem com quatro números — o que foi pedido, o que já está em uso, o limite e o nome da cota. exceeded quota: padaria-quota, requested: pods=1, used: pods=10, limited: pods=10 quer dizer que o namespace já tem dez pods e a cota permite dez. O conserto é apagar o que não usa ou pedir aumento; mudar o manifesto não resolve, porque a regra está no namespace, não no pod.

Traduzindo o conjunto: o container foi morto pelo kernel por passar do limite de memória (OOMKilled), saiu com 137, e o kubelet está esperando antes de tentar de novo (CrashLoopBackOff). O conserto é no limits.memory ou no consumo do programa — não é reiniciar o pod, que já reiniciou seis vezes.

7. Duas coisas para praticar agora

As duas caixas são erros que o painel reproduz de verdade: validação do API server. A primeira é o seletor que não casa com as labels; a segunda é o apiVersion do grupo errado — dois campeões de frequência.

O apply recusa o Deployment porque o seletor não casa com as labels do template. Corrija as labels para app: cardapio e rode de novo.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: cardapio:1.0

A mensagem é literal, e sempre aponta o bloco das labels do template: spec.template.metadata.labels: Invalid value: {"app":"web"}: `selector` does not match template `labels`. O conserto é igualar os dois blocos — nunca “forçar” o apply.

8. Para ir além

As aulas abaixo pegam um erro cada e contam a história completa: o que a Ana viu, o que ela testou e o que resolveu. A ordem é a de leitura.

  • Pod em Pending — o agendador, a reserva e os taints.
  • ImagePullBackOff — nome, tag, registro privado e segredo de pull.
  • CrashLoopBackOff — o laço de reinício e o que o log conta.
  • Logs e eventos — as duas fontes, lado a lado.
  • Diagnóstico com describe — como ler o bloco de eventos.
  • Checklist de depuração — o roteiro completo, em ordem.
  • Eviction e OOMKilled — as duas mortes, por dentro.
  • RBAC — o Forbidden e os verbos que faltam.
  • Probes e recursos — a sonda que reinicia e o limite que mata.

Um detalhe de tempo que engana: os eventos do cluster são apagados sozinhos depois de cerca de uma hora. Se o pod está reiniciando desde a madrugada, o evento original já não existe — o que sobra é a contagem (x14 over 2h), que ainda diz muito, e o Last State do describe. Em cluster de produção, quem guarda histórico é o agregador de logs, não o Kubernetes.

Para conferir a mensagem antes de sair procurando, dois comandos ajudam: kubectl get events --sort-by=.lastTimestamp mostra a linha do tempo do namespace, e kubectl describe no objeto certo — pod, pvc, deployment — mostra o bloco de eventos daquele objeto. A mensagem é quase sempre literal: se diz not found, é nome ou namespace; se diz Insufficient, é reserva.

Resumo

Erro no Kubernetes vem de três lugares: API server (validação e permissão), agendador (Pending e FailedScheduling) e kubelet (ImagePullBackOff, CreateContainerConfigError, CrashLoopBackOff). O get dá o status, o describe dá o evento, o logs dá a voz do programa — e o --previous dá a voz da tentativa que morreu.

OOMKilled com 137 é memória; 143 é encerramento pedido; 1 é erro do programa; 127 é comando inexistente. Forbidden é RBAC e traz verbo, recurso, grupo e namespace na mensagem; no matches for kind é apiVersion do grupo errado; does not match template labels é seletor diferente das labels.

No painel deste guia, os erros de validação e o Pending por falta de lugar acontecem de verdade; os de runtime são transcrição. Saber qual é qual evita procurar no lugar errado — e, às três da manhã, isso é metade do conserto.

Para lembrar
  • get → describe → eventos → logs: nesta ordem, sempre.
  • Pending é lugar; ContainerCreating é imagem ou volume; BackOff é o programa.
  • Sem log não é beco: o container não iniciou, e o evento diz por quê.
  • 137 = memória; 143 = encerramento pedido; 127 = comando não encontrado.
  • Forbidden = RBAC; NotFound = nome ou namespace.
  • apiVersion errado é recusa na hora, com o grupo certo na mensagem.
