edit e patch

A Ana já sabe aplicar um manifesto inteiro. O problema é quando só uma coisinha precisa mudar: uma réplica a mais, uma imagem nova, uma etiqueta que faltou. Reescrever o arquivo inteiro parece exagero, e é aí que aparecem os dois comandos que mudam um objeto sem reaplicá-lo — kubectl edit, que abre o YAML no seu editor, e kubectl patch, que manda só o pedaço que muda. Nesta aula a Ana usa os dois, vê onde eles mordem e aprende quando o caminho chato é o certo.

Você vai aprender
  • O que o kubectl edit faz por baixo: buscar, abrir, salvar e mandar a diferença.
  • Como é a sessão do editor e o que acontece quando você sai sem mudar nada.
  • kubectl patch e os três tipos de patch: strategic, merge e json.
  • Os riscos: conflito de edição, apply que desfaz, campo digitado errado.
  • As ferramentas cirúrgicas do dia a dia: set image e scale.
  • Por que o manifesto completo continua sendo o caminho que não tem surpresa.

1. A cena: onze da noite e uma etiqueta faltando

O monitoramento da padaria não enxergava mais o cardápio. O pod estava de pé, o Service respondia, mas o painel filtrava por app=cardapio e o Deployment estava sem a etiqueta. Consertar exigia mudar um objeto que já existia — e havia quatro caminhos, todos válidos, todos com um custo diferente.

O primeiro é abrir o objeto no editor: kubectl edit deployment cardapio baixa o YAML, abre no vi, e quando você salva ele manda a diferença de volta ao cluster. O segundo é mandar só a mudança, sem abrir nada: kubectl patch. O terceiro é a ferramenta que já sabe o formato daquela mudança — kubectl label para etiqueta, kubectl set image para imagem, kubectl scale para réplicas. E o quarto é o velho apply com o manifesto inteiro corrigido.

A analogia que ajuda: o objeto no cluster é a receita escrita no caderno da cozinha. O edit é abrir o caderno, riscar e escrever por cima; o patch é mandar um bilhete dizendo “troque o açúcar por mel”; o set image é trocar o rótulo de um pote específico; e o apply é reescrever a página inteira e colar por cima da antiga. Os quatro mudam a receita. Só o último deixa uma página nova, datada e guardada no repositório.

2. O que está por baixo dos dois comandos

Nenhum dos dois é mágica: os dois terminam no mesmo lugar, um PATCH enviado à API. A diferença está em como a diferença é calculada e em quem a escreve. O vocabulário:

edit
Abre o objeto inteiro no editor de texto do seu terminal, espera você salvar e envia como patch o que mudou. Se você sair sem salvar, nada acontece.
patch
Recebe um documento pequeno com só o pedaço que muda e o tipo de mesclagem. Não abre editor e não depende de você.
editor
O programa que o edit chama: o $EDITOR da sua sessão, normalmente vi. Sem editor, o comando não abre.
strategic merge
O tipo de patch padrão do kubectl: mescla mapas e, em listas com chave (como containers), casa pelo name em vez de substituir a lista inteira.
last-applied
A annotation em que o apply guarda o último manifesto aplicado. É ela que permite ao apply saber o que você tirou do arquivo — e é ela que faz o edit ser desfeito.

Repare no ponto que decide tudo: o cluster não guarda história. Ele guarda o estado atual do objeto. Quem tem história é o seu repositório. Por isso uma mudança feita com edit ou patch existe no cluster e não existe em lugar nenhum que possa ser revisado, comparado ou revertido com um clique. Não é proibido — é uma dívida, e ela vence no próximo apply.

3. O ciclo do edit, na prática

O comando é curto e a sessão é longa: o vi abre com o objeto inteiro, precedido por um bloco de comentários que o kubectl ignora. A transcrição abaixo é de um cluster real, com o Deployment do cardápio:

ana@notebook:~$ kubectl edit deployment cardapio
# Please edit the object below. Lines beginning with a '#' will be ignored,
# and an empty file will abort the edit. If an error occurs while saving this file will be
# reopened with the relevant failures.
#
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
  namespace: padaria
spec:
  replicas: 2
  ...
deployment.apps/cardapio edited

Três coisas acontecem nessa tela. Primeiro, o kubectl faz um GET do objeto e escreve o YAML num arquivo temporário. Segundo, abre esse arquivo no seu editor. Terceiro, quando você salva e sai, ele compara o arquivo novo com o antigo, monta o patch e envia. Se você não mudou nada, a resposta é Edit cancelled, no changes made. — o comando é educado, mas não é idempotente na sua cabeça: sair sem salvar é o único caso em que nada acontece.

O que o editor não faz por você: validar a intenção. Ele valida o formato — se você quebrar a indentação, o kubectl reabre o arquivo com o erro e você conserta ali mesmo. Mas se você digitar replicas: 20 querendo 2, o cluster aceita vinte réplicas com a maior tranquilidade e o seu nome fica no evento. Campo válido com valor errado passa por qualquer validação.

4. Os riscos do editor

O primeiro risco é o conflito. O edit manda a diferença calculada sobre a versão que ele leu. Se alguém — ou o próprio controlador — mudou o objeto nesse meio-tempo, o cluster recusa. A mensagem é esta, e ela aparece mais do que se imagina em cluster com time grande:

ana@notebook:~$ kubectl edit deployment cardapio
error: the object has been modified; please apply your changes to the latest version and try again

A leitura é direta: alguém mexeu entre a sua leitura e a sua escrita, o cluster recusou a sobrescrita e nada foi salvo — repare que não há linha edited no fim. A cura é repetir o comando e refazer a mudança; chato, mas seguro. O segundo risco é mais silencioso: o apply seguinte desfaz o que o edit fez, se a mudança não estiver no arquivo. Não é vingança do kubectl; é o modelo declarativo funcionando. O apply compara o arquivo com o último aplicado e força o objeto a ficar igual ao arquivo.

O terceiro risco é o hábito. Quem se acostuma a resolver tudo no edit passa a ter um cluster que ninguém consegue reproduzir: some o objeto e não há arquivo para recriá-lo igual. Em time pequeno isso dura meses; no dia em que alguém precisa recriar o ambiente, ninguém sabe quais foram as edições feitas “na mão”. A regra que a Ana adotou depois do susto: edit para olhar e para emergência, arquivo para tudo o que precisa durar.

5. patch: mandar só o pedaço que muda

O patch recebe um documento pequeno, em JSON, e o tipo de mesclagem. O padrão do kubectl é o strategic merge, que mescla mapas e casa itens de lista pelo nome. Na prática, você escreve só o caminho que muda:

ana@notebook:~$ kubectl patch deployment cardapio --type=strategic -p '{"spec":{"replicas":3}}'
deployment.apps/cardapio patched

ana@notebook:~$ kubectl patch deployment cardapio --type=json -p '[{"op":"replace","path":"/spec/replicas","value":2}]'
deployment.apps/cardapio patched

A resposta é sempre patched, mesmo quando o valor já era aquele — o comando não é um “verificador”, é um pedido de mudança. O patch não cria objeto: se o nome não existir, a resposta é Error from server (NotFound), igual a qualquer outro comando que fala de um objeto específico. E, ao contrário do edit, ele não abre nada: roda em script, em pipeline, em kubectl patch dentro de um job de deploy.

Os três tipos não são sinônimos. O strategic é o mais amigável e o único que entende a semântica do Kubernetes (listas com chave, como containers e portas). O merge é o JSON Merge Patch puro: substitui o que você mandar, sem conhecer a estrutura. O json é o JSON Patch: uma lista de operações com op, path e value, capaz de remover um item de lista por índice.

--typeComo pensaServe quandoCuidado
strategic (padrão)mescla por chave; lista com name casa pelo nomemudar um campo de Deployment, Service, Podnão existe para todo tipo de objeto
mergesubstitui o que veio, sem conhecer estruturaobjeto simples, campo de textolista inteira é trocada, não mesclada
jsonlista de operações add, remove, replaceremover item de lista, mudar por índiceerrou o índice, mudou o item errado

6. O patch no painel deste guia

O motor que roda as caixas aplica manifestos e executa comandos, mas não aplica patch: ele responde com uma frase explicando isso, e é importante que você veja a frase em vez de um resultado inventado. O painel é um simulador de respostas, não um cluster com API de escrita completa.

Rode o patch e leia a resposta do painel. Depois faça a mesma mudança com a ferramenta cirúrgica que muda imagem de container: kubectl set image deployment/cardapio cardapio=cardapio:1.1.

kubectl create deployment cardapio --image=cardapio:1.0
kubectl patch deployment cardapio --type=strategic -p '{"spec":{"replicas":3}}'
ana@notebook:~$ kubectl create deployment cardapio --image=cardapio:1.0
deployment.apps/cardapio created

ana@notebook:~$ kubectl patch deployment cardapio --type=strategic -p '{"spec":{"replicas":3}}'
error: neste painel, patch não é aplicado — use kubectl apply -f com o manifesto completo (a aula de patch mostra a saída real).

kubectl create deployment cardapio --image=cardapio:1.0
kubectl set image deployment/cardapio cardapio=cardapio:1.1

O que a caixa ensina, além do comando: existe uma família de comandos que já conhece o formato da mudança e evita você escrever JSON na mão. Para imagem, set image; para réplica, scale; para etiqueta, label; para annotation, annotate. Todos respondem com uma frase curta e todos são, por baixo, um patch — a diferença é que o kubectl monta a estrutura por você.

7. A ferramenta certa para cada pedaço

No Deployment que já está no ar, o container tem nome próprio — e é por ele que o set image acha quem trocar. Errar esse nome produz um dos erros mais comuns de quem começou ontem, e o painel devolve exatamente a mensagem de um cluster real:

O container do Deployment se chama web, não cardapio. Rode o comando como está, leia o erro e troque a imagem usando o nome certo do container.

kubectl set image deployment/cardapio cardapio=cardapio:1.1
ana@notebook:~$ kubectl set image deployment/cardapio cardapio=cardapio:1.1
error: unable to find container named "cardapio"

kubectl set image deployment/cardapio web=cardapio:1.1

A frase error: unable to find container named "cardapio" não diz que a imagem não existe nem que o Deployment sumiu. Diz que, dentro do molde do pod, não há container com aquele nome. O formato do comando é tipo/nome container=imagem, e os dois nomes são diferentes de propósito: o Deployment é o pacote; o container é o programa dentro dele. Nome de container, aliás, tem regra de formato igual à de nome de objeto: minúsculas, números e hífen.

8. O caminho sem surpresa: o manifesto completo

O apply não é o mais rápido, mas é o único que deixa o cluster igual ao arquivo. Se a mudança importa, ela vai para o YAML, o YAML vai para o repositório, e o apply faz o resto. A caixa abaixo aplica o manifesto completo num Deployment que já existe: repare que a resposta é configured, e não created.

O Deployment do cardápio está no ar com duas réplicas e a imagem 1.0. Mude o manifesto para três réplicas e a imagem 1.1 e aplique — o painel tem de mostrar três pods prontos.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
deployment.apps/cardapio configured

NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   2/2     2            2           2m

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 3
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.1

O configured é a palavra que conta a história: o objeto já existia, e o cluster ajustou o que estava diferente. O created aparece só na primeira vez. É por isso que o mesmo apply pode rodar mil vezes sem medo: aplicar o mesmo arquivo de novo responde unchanged.

Agora a comparação que fecha o assunto, com o custo de cada caminho:

CaminhoO que mudaFica registrado?Quando usar
kubectl edito objeto inteiro, à mãonão: só no histórico do shellolhar o objeto, emergência de madrugada
kubectl patchsó o campo do documentosó se o patch estiver num arquivo do repositórioautomação e correção pontual
set image, scale, labelum campo conhecidosó se virar script versionadomudança rápida e previsível
kubectl apply -fo que o arquivo pede, inclusive remoçõessim: o arquivo é a fonte da verdadetudo o que precisa durar e ser reproduzido

E o efeito colateral que mais aparece: você faz um edit, o time roda o apply do pipeline meia hora depois, e a sua mudança some. Não houve erro em lugar nenhum — o arquivo mandou, e o cluster obedeceu. Se a mudança é boa, ela pertence ao arquivo.

9. Cenários do dia a dia

Cenário 1: o patch que ninguém achou depois

Alguém subiu as réplicas de 2 para 5 com kubectl scale durante um pico. No dia seguinte o pipeline reaplicou o manifesto com replicas: 2 e o cluster voltou para dois pods — no meio do horário de maior movimento. A correção não foi desfazer o scale: foi mudar o número no arquivo.

Cenário 2: o edit que abriu o caderno errado

Com dois terminais abertos, a Ana editou o Deployment de teste achando que estava em producao. O edit obedece ao namespace corrente sem avisar. Desde então ela digita -n producao em todo edit, mesmo quando o contexto já está no namespace certo: uma flag explícita custa quatro teclas e evita meia hora de confusão.

Cenário 3: o erro de digitação que passou

Num patch de emergência, replicas virou repicas. A API recusou com unknown field e nada mudou — sorte. No edit, o mesmo typo teria sido recusado também, mas um valor válido e errado (três em vez de dois) passaria sem reclamação. Validação de formato não é validação de intenção.

11. Resumo

edit e patch mudam um objeto que já existe, e os dois terminam no mesmo lugar: um PATCH na API. O edit abre o YAML no seu editor e manda a diferença quando você salva; sair sem salvar responde Edit cancelled, no changes made.. O patch recebe só o pedaço que muda, em strategic merge, merge ou JSON Patch, e roda sem ninguém olhando.

Os riscos são de natureza diferente. O edit pode conflitar com uma mudança concorrente (the object has been modified), depende do seu editor e não deixa rastro. O patch é ótimo em automação e péssimo para quem tenta ler depois o que aconteceu. E os dois são desfeitos pelo próximo apply do arquivo — porque o arquivo é a fonte da verdade.

Para o dia a dia, prefira as ferramentas que já sabem o formato: set image, scale, label, annotate. Para o que precisa durar, o manifesto. E guarde o edit para olhar e para a emergência em que não há arquivo à mão — sabendo que, na manhã seguinte, a mudança precisa virar commit. Na próxima aula a Ana dá um passo acima do arquivo único e conhece o Kustomize, que monta o manifesto de cada ambiente a partir de uma base comum.

Para lembrar
  • kubectl edit tipo/nome: abre no $EDITOR, salva como patch, Edit cancelled, no changes made. se você sair sem mudar.
  • kubectl patch tipo/nome --type=strategic|merge|json -p '…': só o campo, sem editor.
  • Conflito de edição: the object has been modified; please apply your changes to the latest version.
  • set image deployment/x container=imagem: o nome é o do container, não o do Deployment.
  • O apply seguinte desfaz o que não estiver no arquivo. Mudança boa vira commit.
  • No painel, patch responde com uma explicação; use set image, scale ou apply.
