O que é Kubernetes

A Ana tem um site de padaria que roda num programa só, aberto no terminal do notebook dela. Já aconteceu de o notebook reiniciar de madrugada e o site ficar fora do ar até as sete da manhã, quando ela abriu a janela de novo. Kubernetes existe para resolver exatamente esse tipo de problema — mas antes de decorar comandos, vale entender que problema é esse. Nesta primeira aula a Ana vê a ideia central (descrever o que quer, em vez de mandar o que fazer), conhece as peças de um cluster e aplica o primeiro manifesto no painel do guia.

Você vai aprender
  • Que problema o Kubernetes resolve — e qual ele não resolve.
  • A diferença entre mandar comandos e descrever o estado desejado.
  • O que é um cluster, um nó, um pod e um manifesto.
  • O papel do control plane e do kubelet, sem decoreba.
  • Como aplicar um manifesto no painel deste guia e ler a resposta.
  • Por que quase tudo em Kubernetes é um arquivo de texto.

1. A cena: o site que cai de madrugada

O site da padaria é um programa pequeno: quando alguém abre o endereço, ele responde com o cardápio, os preços e o horário. A Ana sobe esse programa à mão, com node servidor.js, e deixa a janela do terminal aberta. Enquanto a janela estiver ali, funciona. Se o notebook reiniciar, se o terminal fechar, se o programa travar às três da manhã, o site sai do ar e ninguém fica sabendo até o primeiro cliente reclamar.

Ela já tentou resolver com boa vontade: uma anotação colada no monitor dizendo “abrir o terminal e rodar o comando”. Funciona quando ela está acordada. O problema não é o comando estar difícil — é que a responsabilidade de ficar de olho está na cabeça de uma pessoa. E pessoa dorme.

Kubernetes é um programa que assume esse papel de vigia. Você instala num computador (ou num conjunto de computadores) e passa a entregar pedidos para ele: “quero este programa rodando, nesta imagem, nesta quantidade”. De tempos em tempos, ele compara o que você pediu com o que está de fato acontecendo e corrige a diferença: liga o que faltou, recoloca no ar o que caiu, tira o que sobrou. Isso tem um nome — reconciliação — e é a alma do negócio.

2. A ideia central: descrever, em vez de mandar

Existem dois jeitos de pedir uma pizza. O primeiro é ligar e ditar cada passo: “corta a cebola agora, põe no forno, tira em quinze minutos”. O segundo é dizer “quero uma pizza de muçarela” e deixar a cozinha se virar. O primeiro é imperativo, o segundo é declarativo. A maior parte dos comandos que você conhece é imperativa; Kubernetes trabalha declarativamente.

Você não manda o Kubernetes “subir um container”. Você descreve o estado final: “quero um pod com a imagem cardapio:1.0”. É essa descrição que fica guardada. O cluster compara continuamente o que está escrito com o que está rodando e age para que os dois coincidam. Se o programa morre, a descrição continua lá, então o cluster liga de novo. Se alguém apaga o pod por engano, a descrição continua lá, e o cluster cria outro.

A consequência prática é grande: você guarda as descrições num arquivo de texto, coloca no repositório do projeto e pode recriar o site inteiro em qualquer lugar, do mesmo jeito, quantas vezes quiser. É a diferença entre “está rodando porque eu digitei um comando” e “está rodando porque este arquivo diz que deve estar”.

estado desejado
O que você pediu que existisse. Fica guardado no cluster, mesmo que o programa esteja fora do ar naquele instante.
estado atual
O que está de fato rodando: quantos pods existem, onde estão, prontos ou não.
reconciliação
O laço que compara os dois estados e age para fechar a diferença. Roda para sempre, em silêncio.
manifesto
O arquivo de texto que descreve um ou mais objetos. É o que você entrega ao cluster.
objeto
Uma coisa guardada no cluster: um pod, um service, um deployment. Tem nome, tipo e campos.
cluster
O conjunto de máquinas que roda tudo isso: o cérebro (control plane) e os nós de trabalho.

3. O que Kubernetes é — e o que ele não é

Kubernetes é open source, feito pelo Google e mantido por uma comunidade enorme, hoje sob o guarda-chuva da CNCF. A versão que este guia usa é a 1.37. O nome tem origem grega, quer dizer timoneiro, e o apelido dele é k8s — o 8 está no lugar das oito letras entre o k e o s. Você vai ver as duas formas por aí; são a mesma coisa.

Ele também não é um programa que você abre numa janela. Kubernetes vem em pedaços: um conjunto de programas que rodam em servidores e conversam entre si por rede. Quem fala com tudo isso é um cliente de linha de comando, o kubectl — o “cubo-controle”. Você digita kubectl no terminal, ele manda um pedido por HTTP para o cluster e mostra a resposta.

Agora a parte importante do “não é”. Kubernetes não compila o seu site, não cuida do banco de dados por você, não substitui o Docker (ele usa containers, que é outra tecnologia) e não adivinha o que o seu programa precisa. Ele é um gerente de infraestrutura: recebe descrições, arranja lugar para elas e mantém de pé. Programe, teste e empacote o site continua sendo trabalho seu.

4. As partes de um cluster

Um cluster tem, por baixo, máquinas — físicas ou virtuais. Cada máquina que participa do cluster é um nó (node). Num nó comum roda o seu site; no nó especial que comanda o resto roda o control plane, o cérebro. Num cluster de estudo, é comum o mesmo computador fazer os dois papéis: você tem um “nó de controle” e um ou dois “nós de trabalho”, todos desenhados por software na sua máquina.

O cérebro tem quatro peças que você vai ouvir por nome cedo ou tarde. O API server é a porta de entrada: tudo passa por ele, inclusive o seu kubectl. O etcd é o caderno onde o estado desejado fica anotado. O scheduler decide em qual nó cada pod vai cair. E o controller manager fica comparando o que está escrito com o que existe, ligando os controladores que corrigem a diferença.

Do outro lado, em cada nó de trabalho, roda o kubelet: um agente que conversa com o cérebro e cuida dos containers daquela máquina, usando um runtime de containers (o mais comum é o containerd). Se o kubelet percebe que um container do seu pod parou, ele reinicia. Se o nó inteiro cai, o cérebro percebe que os pods de lá sumiram e cria substitutos em outro lugar.

5. O vocabulário mínimo

Cinco palavras aparecem em toda aula daqui para a frente, e vale fixar cada uma com uma imagem mental. Elas não são sinônimos: cada uma responde uma pergunta diferente.

PalavraO que éPergunta que responde
clustero conjunto todo: cérebro mais nósonde as coisas rodam?
nó (node)uma máquina do clusterem qual computador?
poda menor unidade que o cluster agenda: um ou mais containers juntos, com o mesmo endereço de redeo que está rodando?
objetoum registro no cluster: pod, service, deployment, configmap o que eu pedi?
manifestoo arquivo YAML que descreve objetoscomo eu peço?

O pod merece um parágrafo à parte, porque é a peça que confunde. Ele não é o seu programa e não é o container: é o pacote que o cluster liga. Dentro dele pode haver um container (o caso comum) ou vários, que compartilham rede e ciclo de vida — se um cai, o pacote inteiro é considerado problemático. O cluster não agenda “containers”; ele agenda pods.

Além dos nós, o cluster guarda namespaces: gavetas onde os objetos moram. Todo cluster nasce com duas, e ver isso é um bom primeiro sinal de vida. A transcrição abaixo é de um cluster local recém criado:

ana@notebook:~$ kubectl get ns
NAME          AGE
default       8m
kube-system   9m

default é onde o seu pedido cai quando você não escolhe outro lugar. kube-system é onde moram os programas do próprio Kubernetes — o DNS do cluster, o controlador de rede e por aí. Você não vai mexer nessa gaveta no começo, e é bom que ela exista: é o que faz o cluster funcionar antes de você pedir qualquer coisa.

6. Vendo o cluster responder

Chega de teoria por um minuto. A caixa abaixo é um terminal: cada linha é um comando que a Ana digitaria, e o painel mostra a resposta do cluster. O primeiro comando pergunta a versão do kubectl instalado no notebook. O segundo lista os nós — as máquinas que formam o cluster.

Só falta ver as máquinas. Acrescente a linha kubectl get nodes embaixo do primeiro comando e rode.

kubectl version --client
ana@notebook:~$ kubectl version --client
Client Version: v1.37.3
Kustomize Version: v5.8.1

kubectl version --client
kubectl get nodes

A primeira resposta tem duas linhas: Client Version: v1.37.3 e a versão do kustomize que vem embutida. A segunda é uma tabela com três nós: guia-control-plane (o cérebro), guia-worker e guia-worker2 (os trabalhadores). A coluna STATUS em Ready quer dizer que o cérebro consegue falar com o nó e considera que ele está saudável. Nó NotReady é nó com problema — e, quando isso acontece, os pods dele são recriados em outro lugar.

Repare no nome: guia é o nome do cluster de estudo, e o kind (a ferramenta que cria clusters de teste, que você instala na aula 4) batiza os nós com esse prefixo. Num cluster de nuvem, os nomes são compridos e feios, tipo ip-10-0-1-23; a lógica é a mesma.

7. O pedido escrito em YAML

Ver o cluster responder é bom; pedir alguma coisa é melhor. Todo pedido em Kubernetes tem a mesma estrutura de três andares: apiVersion (a versão da API que você está usando), kind (o tipo do objeto) e metadata (a identidade: nome, etiquetas). Depois vem spec, que é o conteúdo do pedido. A caixa abaixo tem um manifesto de pod faltando um desses andares. Rode e leia o erro antes de consertar.

Falta dizer que tipo de objeto é. Acrescente a linha kind: Pod embaixo do apiVersion e rode de novo.

apiVersion: v1
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
error: unable to decode "STDIN": Object 'Kind' is missing

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0

A mensagem do erro é curta e direta: error: unable to decode "STDIN": Object 'Kind' is missing. Traduzindo: “não consegui ler, o objeto não tem kind”. O kubectl leu o texto, tentou descobrir de que tipo era e não achou; sem tipo, ele não sabe nem qual validação aplicar. Com a linha kind: Pod, o pod é criado e aparece Running.

O spec desse manifesto tem uma lista de containers, com nome e imagem. Note que o nome aparece duas vezes: metadata.name é o nome do pod (cardapio), e o name dentro de containers é o nome do container (web). São coisas diferentes: um pod pode ter vários containers, cada um com seu nome.

CampoObrigatório?O que vai ali
apiVersionsima versão da API: v1 para Pod, apps/v1 para Deployment
kindsimo tipo do objeto: Pod, Service, Deployment
metadata.namesimo nome, em minúsculas e com hífen
metadata.labelsnãoetiquetas para agrupar e filtrar
specsimo conteúdo do pedido, diferente para cada tipo
statusnãopreenchido pelo cluster; você não escreve

8. Um pedido, dois pods

O pod é a unidade, mas pedir um pod sozinho é frágil: se ele morrer, ninguém recria. Por isso o jeito normal de pedir é um Deployment, que diz “quero esta imagem, com esta quantidade de cópias”. O Deployment é um controlador: ele cria os pods, vigia cada um e repõe o que faltar. A caixa abaixo pede uma cópia; a missão é pedir duas, sem criar o segundo pod na mão.

Troque replicas: 1 por replicas: 2 e rode. O cluster tem de criar o segundo pod sozinho.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080
deployment.apps/cardapio created

NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   1/1     1            1           2m

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080

A tabela do Deployment mostra READY 2/2: duas cópias prontas de duas pedidas. Se você rodasse kubectl get pods na sequência (o comando da aula de kubectl), veria dois pods de nome comprido, do tipo cardapio-xxxxx-yyyyy. Esses nomes são inventados pelo controlador, e é por isso que eles têm essa cara: cada pod é descartável, o nome dele não importa. O que importa é o Deployment cardapio, esse sim com nome fixo.

Para ver os pods por trás do Deployment, o comando é kubectl get pods. A transcrição abaixo é do mesmo cluster local, com o Deployment pedindo duas cópias:

ana@notebook:~$ kubectl get pods
NAME                        READY   STATUS    RESTARTS   AGE
cardapio-pvx6crj8rr-64bgk   1/1     Running   0          3m
cardapio-pvx6crj8rr-w5m2v   1/1     Running   0          1m

Repare que os dois nomes começam igual — cardapio-pvx6crj8rr — e terminam com um sufixo aleatório. A parte do meio é o ReplicaSet, o objeto que o Deployment criou para cuidar das cópias; o sufixo é o nome único de cada pod. É por isso que você nunca escreve o nome de um pod num script: ele muda a cada recriação.

O bloco template é o molde do pod: tudo o que está ali dentro vira cada uma das cópias. E o selector é como o Deployment reconhece os pods que são dele — ele procura pods com a etiqueta app: cardapio, a mesma que o molde coloca. Se as duas não casarem, o controlador cria pods e não os enxerga como seus, num vaivém infinito. É um erro clássico, e a aula de labels e selectors volta nele.

9. Cenários do dia a dia

Cenário 1: “mas eu já tinha subido o site”

A Ana achou que o cluster estava “rodando o site” do mesmo jeito que o terminal rodava. Não é: o cluster roda o que está descrito. Quando ela apagou o arquivo do projeto e pensou que o site continuaria, descobriu que o manifesto, não o programa, é a fonte da verdade. Quem descreve, manda; o que roda é consequência.

Cenário 2: o cluster não é um servidor mágico

Ela tentou “subir” uma pasta do notebook com o site e o comando não fez sentido nenhum: Kubernetes não copia código para dentro do cluster. O que viaja é a imagem — o pacote do programa, construído antes, num registro. Todo o resto é descrição. Se a imagem não existe no registro, o pod não sobe, e o motivo aparece no describe.

Cenário 3: o manifesto que ninguém sabe ler

Ela copiou um YAML de um blog e o cluster recusou com uma mensagem sobre apiVersion. O arquivo era de uma versão antiga de outro tipo de objeto. Manifesto não é texto sagrado: é um pedido com três andares (versão, tipo, identidade) e um conteúdo. Quando algo falha, o primeiro passo é olhar esses andares antes de qualquer outra coisa.

11. Resumo

Kubernetes é um gerente de infraestrutura declarativo: você descreve o estado desejado num manifesto, o cluster guarda essa descrição e reconcilia — liga o que falta, repõe o que caiu, tira o que sobra. Não é linguagem, não é nuvem, não constrói imagem: ele usa containers e cuida de mantê-los vivos no lugar certo.

As peças têm nomes: cluster é o conjunto, nó é a máquina, control plane é o cérebro (API server, etcd, scheduler, controller manager) e kubelet é o agente que trabalha em cada nó. A unidade que o cluster agenda é o pod, e o Deployment é quem pede pods em quantidade e os vigia.

Todo manifesto tem os mesmos andares: apiVersion, kind, metadata e spec — e é o kind que falta que produz o erro mais comum de quem está começando. Na próxima aula a Ana olha para dentro dessa hierarquia: o que é um cluster, o que é um nó e o que é um pod, com os comandos que mostram cada um.

Para lembrar
  • Kubernetes guarda o estado desejado e reconcilia com o real, sem parar.
  • Cluster = cérebro (control plane) + nós de trabalho.
  • Pod é a unidade que o cluster agenda; container é o que está dentro.
  • Manifesto tem apiVersion, kind, metadata e spec.
  • kubectl é o cliente que fala com o cluster.
  • Deployment pede cópias e repõe as que caem; pod solto não volta.
