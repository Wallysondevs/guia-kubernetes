Backup

Um colega da Ana digitou kubectl delete namespace padaria para limpar um teste e acertou o namespace de produção. Levou quatro segundos. O site, os ConfigMaps, os Secrets e o volume com as fotos dos produtos sumiram junto — porque, no Kubernetes, apagar um namespace apaga tudo o que mora dentro dele. Nesta aula a Ana descobre o que é (e o que não é) backup de cluster, por que o repositório Git cobre só uma parte, como o Velero entra na história e por que um backup que nunca foi restaurado é apenas uma esperança bem armazenada.

Você vai aprender
  • As três camadas de backup: estado do cluster, objetos e dados.
  • O que o Git já resolve e o que ele nunca vai resolver.
  • Como o Velero funciona: os objetos Backup, Schedule e Restore.
  • Snapshot de volume (CSI) versus backup de arquivos (Kopia/Restic).
  • Como fazer um teste de restauração de verdade, sem tocar em produção.
  • Frequência, retenção e o que fica de fora de qualquer backup de cluster.

1. A cena: quatro segundos e um namespace a menos

O comando era para o namespace teste. O dedo escorregou e o Tab completou padaria. O kubectl perguntou “tem certeza?” e alguém respondeu que sim. Quatro segundos depois, o cluster estava sem o site: Deployment, Service, ConfigMap, Secret e o volume com as fotos do cardápio foram embora na mesma operação, porque o namespace é o pacote e o pacote inteiro foi descartado.

A primeira pergunta da Ana foi “o Git tem tudo, né?”. Tinha o Deployment, o Service e o ConfigMap. Não tinha o Secret (que é gerado por outra ferramenta), não tinha o conteúdo do volume e não tinha o histórico de revisões. Reaplicar o repositório traria o site de volta, vazio — como uma loja com as prateleiras montadas e nenhum produto.

Backup de cluster é a resposta para essa pergunta, mas ele não é uma coisa só. É um conjunto de cópias com propósitos diferentes, e quem trata os três como um só descobre na hora do aperto que metade faltava. Vamos separar as camadas.

2. As três camadas de backup

Pense numa padaria. Existe o prédio (a estrutura, que pode ser reconstruída a partir de uma planta), existe o mobiliário e a configuração (onde fica cada balcão, qual a receita de cada pão) e existem os produtos (a farinha no estoque, os pães prontos). Perder o prédio é diferente de perder a receita, que é diferente de perder o estoque. Cada um tem a sua cópia e o seu tempo de recuperação.

No Kubernetes, o prédio é o estado do cluster: tudo o que o API server guarda, que vive no etcd. A cópia dessa camada é o snapshot do etcd, e ela é tudo ou nada — restaura o cluster inteiro como estava naquele instante, incluindo o que você não queria. É a camada do “perdi o plano de controle”.

A configuração é o conjunto de objetos: Deployments, Services, ConfigMaps, Secrets, PVCs, Roles. A cópia natural dessa camada é o próprio YAML — no Git, quando é declarativo; exportado do cluster, quando não é. É a camada do “alguém apagou o namespace”. E os produtos são os dados: o conteúdo dos volumes persistentes e o banco de dados. Nenhum YAML traz isso de volta; só uma cópia do conteúdo, feita por snapshot de volume ou por dump da aplicação.

Repare que as três camadas têm donos diferentes na maioria das empresas: o time de plataforma cuida do etcd, o time de aplicação cuida do Git e do banco, e o time de armazenamento cuida dos snapshots. O desastre acontece justamente na fronteira — quando cada um acha que o outro tinha a cópia.

3. O Git é meio backup (e é bom saber qual metade)

Com GitOps, a camada de objetos está resolvida para tudo o que é declarativo: se o namespace sumir, você recria o namespace, aponta a Application e o Argo CD reaplica o que está no repositório. Em minutos o site está de pé de novo. Isso é backup? É — de configuração. E é um backup melhor que o tradicional, porque é versionado e revisado.

Só que o Git tem três buracos conhecidos. O primeiro são os objetos que nascem no cluster e não no repositório: o Secret criado por um operador, o PVC que o StatefulSet gerou, o token que alguém criou com kubectl create secret. O segundo são os dados: o Git guarda o caminho do volume, não o conteúdo dele. O terceiro é o histórico de execução: réplicas escaladas no meio de um pico, revisões de rollout, eventos — nada disso está no repositório.

Por isso a pergunta certa não é “tenho backup?”, e sim “para cada camada, qual é a minha cópia e quando foi a última vez que eu a usei?”. Se a resposta da camada de objetos é “o Git”, ótimo. Se é “o Git” para os dados também, há um buraco — e é o buraco que dói mais, porque dado perdido não se recria com apply.

Vale um exercício de humildade: apague um namespace de teste e tente reconstruí-lo só com o repositório, cronometrando. Você vai descobrir em quinze minutos o que o plano de recuperação levaria um ano para revelar — inclusive os objetos que faltam no Git e ninguém percebeu.

4. O Velero: o que ele faz

O Velero é a ferramenta mais usada para backup de objetos no Kubernetes, e a ideia é simples: ele é um controlador que mora no cluster, com uma CLI do lado de fora, e que copia objetos para um armazenamento externo. Não copia para dentro do cluster, e isso é essencial: backup guardado no mesmo lugar que o original não é backup.

Ele funciona com três objetos principais. Backup é uma execução: o que copiar, com quais filtros, e onde guardar. Schedule é a repetição: o mesmo backup, num horário, com prazo de validade. Restore é a volta: o que restaurar, para quais namespaces, com quais ajustes. Existem ainda BackupStorageLocation (onde os arquivos ficam) e VolumeSnapshotLocation (onde os snapshots de volume ficam).

apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: padaria-diario
  namespace: velero
spec:
  schedule: "0 3 * * *"
  template:
    includedNamespaces:
      - padaria
    includedResources:
      - deployments
      - services
      - configmaps
      - secrets
      - persistentvolumeclaims
    storageLocation: padaria-backup
    volumeSnapshotLocations:
      - padaria-snapshots
    ttl: 720h
  useOwnerReferencesInBackup: false

O campo ttl: 720h é a retenção: trinta dias, e o Velero apaga o backup sozinho depois disso. includedNamespaces limita o escopo — um backup de tudo, incluindo kube-system, é grande, lento e quase nunca restaurável de forma limpa. E o horário segue a mesma sintaxe de cron do CronJob do Kubernetes: cinco campos, minuto, hora, dia do mês, mês e dia da semana.

Por trás, o Velero precisa de um provedor de armazenamento: um plugin que fala com o seu armazenamento de objetos (S3, MinIO, Azure Blob, GCS, o que você tiver). Sem esse plugin configurado, o backup fica em PartiallyFailed ou nem começa — e é a causa mais comum de “o Velero está instalado mas nunca funcionou”.

5. Snapshots de volume: dois jeitos de copiar dado

Objeto é fácil: é YAML. Dado é difícil, porque o volume pode estar em uso enquanto é copiado. Existem duas abordagens, e elas não são equivalentes.

A primeira é o snapshot de volume, feito pela camada de armazenamento via CSI. É rápido e consistente: o provedor tira uma foto do disco naquele instante, sem passar pelo sistema de arquivos. Em compensação, só existe se o seu storage suportar, e o snapshot costuma ficar preso ao provedor — restaurar em outro cluster com outro storage pode não funcionar.

A segunda é o backup de arquivos: um agente no nó (o node-agent do Velero, com Kopia ou Restic) lê os arquivos do volume e os envia para o armazenamento de objetos. É mais lento, mas independente do provedor e funciona em qualquer lugar, inclusive em cluster local. O preço é CPU e tempo de cópia — um volume de cem gigabytes não é copiado em segundos.

Nas duas abordagens existe o mesmo problema de consistência: copiar um banco de dados em uso, arquivo por arquivo, pode produzir uma cópia que “abre” mas está corrompida. É por isso que banco de dados quase sempre tem o seu próprio mecanismo — dump lógico, backup contínuo, replica. O backup do Kubernetes não substitui o backup do banco, e o contrário também não vale.

6. A caixa: exportar o manifesto antes de mexer

Antes de falar de ferramenta, o gesto mais barato de todos: exportar o que existe antes de mexer. Um YAML salvo no seu computador já resolve o “apaguei sem querer” mais comum. A caixa abaixo começa com o comando que mostra a tabela; troque pelo comando que devolve o objeto inteiro em YAML.

Use -o yaml para exportar o Deployment cardapio inteiro e depois liste os pods. O painel tem de mostrar o kind: Deployment, a imagem e as réplicas dentro do YAML.

kubectl get deployment cardapio
kubectl get pods
ana@notebook:~$ kubectl get deployment cardapio

cardapio   2/2     2            2           2m

ana@notebook:~$ kubectl get pods

cardapio-wj4jsx2tcw-q65ng   1/1     Running   0          1m
cardapio-wj4jsx2tcw-t4jwn   1/1     Running   0          10m

kubectl get deployment cardapio -o yaml
kubectl get pods

O painel mostra o objeto completo, com kind: Deployment, replicas: 2, image: cardapio:1.0 e o status no fim. Salve isso num arquivo (kubectl get deployment cardapio -o yaml > cardapio.yaml) e você tem uma cópia datada do objeto. Repita para cada tipo que importa — Deployment, Service, ConfigMap, Secret, PVC — e pronto: a camada de objetos está coberta para aquele namespace.

Um aviso importante sobre o que sai nesse YAML. O status vem junto, e reaplicar um objeto com status é pelo menos estranho; o ideal é limpar essa parte. O Service traz o clusterIP fixo, que não serve em outro cluster. Veja o Service do cardápio exportado pelo painel:

apiVersion: v1
kind: Service
metadata:
  name: cardapio
  namespace: default
spec:
  clusterIP: 10.96.147.79
  clusterIPs:
    - 10.96.147.79
  ipFamilies:
    - IPv4
  ipFamilyPolicy: SingleStack
  ports:
    - port: 80
      protocol: TCP
      targetPort: 8080
  selector:
    app: cardapio
  sessionAffinity: None
  type: ClusterIP

Se você aplicar esse arquivo em outro cluster, o clusterIP pode conflitar com um IP já usado e a criação falha. É por isso que ferramentas de backup de verdade limpam campos gerenciados pelo cluster na hora de restaurar. À mão, a receita é remover clusterIP, clusterIPs, ipFamilies, ipFamilyPolicy e todo o status.

7. O teste de restauração que ninguém faz

Todo mundo tem backup. Quase ninguém tem restauração. A diferença aparece no dia do incidente, quando se descobre que o backup estava sendo feito num bucket que foi apagado junto, ou que o arquivo tem um formato que a versão nova não lê, ou que o tempo de volta é de seis horas e não de trinta minutos.

O ensaio é sempre o mesmo: restaurar em um lugar separado, conferir que o serviço funciona e medir o tempo. Nunca restaurar em cima do que está no ar para “testar” — o teste perfeito para derrubar produção é restaurar no namespace de produção. A caixa abaixo simula o ensaio no painel: o Deployment original se chama cardapio; o restaurado tem de se chamar cardapio-restaurado, com as duas réplicas e a imagem do backup.

Ajuste o manifesto restaurado: duas réplicas e a imagem cardapio:1.0, como no backup. O painel tem de mostrar o Deployment restaurado com 2/2.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio-restaurado
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cardapio-restaurado
  template:
    metadata:
      labels:
        app: cardapio-restaurado
    spec:
      containers:
        - name: web
          image: cardapio:latest
          ports:
            - containerPort: 8080
deployment.apps/cardapio-restaurado created

NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
cardapio-restaurado   1/1     1            1           28s

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio-restaurado
spec:
  replicas: 2
  selector:
    matchLabels:
      app: cardapio-restaurado
  template:
    metadata:
      labels:
        app: cardapio-restaurado
    spec:
      containers:
        - name: web
          image: cardapio:1.0
          ports:
            - containerPort: 8080

Restaurar com outro nome é o truque que torna o ensaio seguro: nada do que está no ar é tocado, e você pode comparar os dois lado a lado. No Velero, o equivalente é restaurar em outro namespace, com --namespace-mappings padaria:padaria-teste, e só depois de conferir apontar o tráfego para lá.

E tem o caso chato: restaurar em um cluster onde o objeto ainda existe. O Velero marca o restore como PartiallyFailed e lista os conflitos; o kubectl, no comando equivalente, responde assim:

Error from server (AlreadyExists): deployments.apps "cardapio" already exists

Traduzindo: o objeto já está lá, e criar de novo não é possível. As saídas são três — restaurar em outro namespace (o ensaio), apagar o objeto antes de restaurar (janela de manutenção) ou pedir ao Velero para sobrescrever (existingResourcePolicy: update). As três têm consequência; escolher no meio do incidente é pior do que escolher no ensaio.

8. Frequência, retenção e onde guardar

Backup tem duas perguntas de negócio e uma de engenharia. Quanto dado você aceita perder (RPO)? Quanto tempo você aceita ficar fora (RTO)? E onde a cópia fica guardada? As duas primeiras definem a frequência; a terceira define se o backup sobrevive ao desastre.

Se perder uma hora de pedidos é aceitável, um backup por hora resolve — mas o dado do banco talvez precise de replicação contínua, porque uma hora de pedidos é dinheiro. Se o RTO é de trinta minutos, o ensaio tem de mostrar trinta minutos, não seis horas: restaurar um volume de duzentos gigabytes pelo node-agent não é rápido.

A regra do armazenamento é curta e absoluta: fora do cluster e fora da conta. Backup no mesmo provedor, na mesma conta e na mesma região é o primeiro item que some num incidente de conta comprometida. Guardar com versionamento e trava de objeto (immutable bucket) protege contra o pior cenário: alguém com credencial válida apagando os backups.

A caixa abaixo é um CronJob — o mesmo relógio que um Schedule do Velero usa. Ele está suspenso e rodando de cinco em cinco minutos; ajuste para a rotina da padaria, todo dia às três da manhã, ativo.

Mude o horário para 0 3 * * * (todo dia às 3h) e tire o suspend: true — ou troque por false. O painel tem de mostrar o CronJob com o horário novo.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-cardapio
spec:
  schedule: "*/5 * * * *"
  suspend: true
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: velero/velero:v1.16.1
cronjob.batch/backup-cardapio created

kind: CronJob
metadata:
  name: backup-cardapio
  namespace: default
spec:
  concurrencyPolicy: Allow
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 6
      template:
        spec:
          containers:
            - image: velero/velero:v1.16.1
              imagePullPolicy: IfNotPresent
              name: backup
              resources:
                limits: {}
                requests: {}
              terminationMessagePath: /dev/termination-log
              terminationMessagePolicy: File
          dnsPolicy: ClusterFirst
          restartPolicy: OnFailure
          schedulerName: default-scheduler
          securityContext: {}
          terminationGracePeriodSeconds: 30
  schedule: "*/5 * * * *"
  successfulJobsHistoryLimit: 3
  suspend: true

apiVersion: batch/v1

  schedule: "0 3 * * *"
  suspend: false

O painel mostra o CronJob com schedule: 0 3 * * * e suspend: false, mais os padrões que o API server preenche (successfulJobsHistoryLimit: 3, failedJobsHistoryLimit: 1). Aviso honesto: o painel não dispara CronJob — ele mostra o objeto, não a execução. A rotina de backup de verdade é observada pela ferramenta: no Velero, o Schedule cria Backups, e cada um tem status próprio.

9. Cenários do dia a dia

Cenário 1: o backup que estava dentro do cluster

A equipe instalou o Velero e apontou o armazenamento para um PVC do mesmo cluster. Funcionou por seis meses, com relatórios verdes. No dia em que o cluster foi recriado, o PVC foi junto — e os backups também. Backup precisa sobreviver ao que ele protege: armazenamento de objetos externo, outra conta, outra credencial.

Cenário 2: o restore que faltou um pedaço

O restore do namespace terminou com sucesso, mas o site subiu sem as fotos dos produtos: o PVC voltou vazio, porque o backup tinha sido feito sem snapshot de volume (ou com o volumeSnapshotLocations apontando para um storage que não existia mais). Objeto e dado são camadas diferentes — conferir as duas no ensaio é o que revela esse tipo de buraco antes do incidente.

Cenário 3: o ensaio que durou seis horas

O backup estava perfeito; a restauração, não. O banco tinha 400 GB e o restore pelo node-agent levou seis horas — muito acima do RTO combinado. A descoberta só apareceu no ensaio, o que é ótimo: o time trocou a estratégia para snapshot de volume mais replica de leitura, e o RTO caiu para quarenta minutos. Ensaio não é burocracia; é onde o plano é corrigido.

Exercício: o backup da vitrine

Você vai criar um Schedule do Velero para o namespace padaria, todo dia às 3h, com retenção de 30 dias, guardando em padaria-backup. Depois responda: qual campo do spec guarda o horário?

spec:: "0 3 * * *"

Dica: schedule usa a mesma sintaxe de cron do CronJob: minuto, hora, dia do mês, mês e dia da semana.

11. Resumo

Backup de cluster tem três camadas e elas não se substituem: o estado do cluster (snapshot do etcd, tudo-ou-nada), os objetos (Git quando declarativo, Velero quando precisa ser seletivo) e os dados (snapshot de volume, node-agent ou backup do próprio banco). O Git cobre bem a segunda camada e nunca cobre a terceira.

O Velero organiza a cópia de objetos em Backup, Schedule e Restore, guardando fora do cluster num armazenamento de objetos configurado por plugin. Para dados, escolhe-se entre snapshot CSI (rápido, preso ao provedor) e backup de arquivos (portátil, lento). Em qualquer caso, o que decide o desenho são o RPO e o RTO combinados — e o RTO só se conhece ensaiando.

O ensaio de restauração é a parte que separa plano de esperança: restaurar em outro namespace, conferir objetos e dados, medir o tempo, corrigir o plano. E lembrar do que fica de fora: imagem, banco externo, dados dentro do volume, segredo de cofre externo. Cada um desses tem um dono — e o backup só funciona quando o dono sabe que é dele.

Para lembrar
  • Backup é por camada: etcd, objetos, dados.
  • Git é backup de configuração, não de dado.
  • Velero: Schedule agenda, Backup executa, Restore volta.
  • Ensaie a restauração em outro namespace e cronometre.
  • Guarde fora do cluster, fora da conta, com trava contra exclusão.
