CrashLoopBackOff

O pod do relatório da madrugada apareceu em Running, a Ana comemorou, e dois minutos depois ele estava de novo em CrashLoopBackOff, com RESTARTS em 7. Dessa vez o problema não é o cluster: é o programa. Ele sobe, faz alguma coisa, morre, e o kubelet o reinicia com uma espera cada vez maior. Nesta aula você aprende a ler essa dança — o número de reinícios, o código de saída, o estado anterior — e a descobrir o motivo antes de mexer em qualquer coisa.

Você vai aprender
  • O que CrashLoopBackOff quer dizer, e por que o RESTARTS é a pista principal.
  • Quem reinicia o container e qual é o papel do restartPolicy.
  • Como ler Last State, Exit Code e Reason no describe.
  • Como usar kubectl logs e kubectl logs --previous para ver a mensagem do programa.
  • As cinco causas que respondem por quase todo CrashLoopBackOff.
  • Por que um pod que termina com Succeeded não é um pod que falhou.

1. A cena: sobe, morre, sobe de novo

O relatório é um programa de linha de comando: ele acorda de madrugada, lê as encomendas, monta um resumo em texto e termina. A Ana o colocou num pod, aplicou o manifesto e viu o status mudar em segundos: ContainerCreating, Running, Error, CrashLoopBackOff. O RESTARTS foi de 0 para 1, 2, 4, 7. Nenhuma mensagem no terminal, nenhum aviso além do nome comprido.

A leitura errada é “o Kubernetes está reiniciando meu pod sem motivo”. A leitura certa é “o meu container está terminando, e o Kubernetes está fazendo o que você mandou: reiniciar”. O status tem duas partes de novo. Crash é a queda do container: o processo saiu, por erro ou porque terminou mesmo. LoopBackOff é a política de espera entre tentativas: dez segundos, vinte, quarenta, até cinco minutos. O cluster não está nervoso; ele está esperando o intervalo que ele mesmo calcula.

Há uma diferença sutil, e é ela que confunde: o STATUS do pod pode voltar para Running entre uma tentativa e outra. Você olha a tela, vê verde, respira — e trinta segundos depois está vermelho de novo. O que não engana é a coluna RESTARTS: se ela sobe enquanto você olha, o container está morrendo em série. Pod que reinicia de propósito não existe; pod que reinicia sem parar é o que esta aula investiga.

2. Quem reinicia, e por quê

Três conceitos explicam o comportamento: o processo sai com um código, o kubelet lê esse código, e o restartPolicy diz o que fazer. Se o processo sai com zero, foi sucesso. Se sai com qualquer outro número, foi erro — e aí entra a política: Always reinicia em qualquer saída; OnFailure reinicia só quando o código é diferente de zero; Never não reinicia nunca.

CrashLoopBackOff
O container sobe, termina e é reiniciado em ciclo, com espera crescente entre tentativas.
exit code
O número que o processo devolve ao sair. Zero é sucesso; 1 é erro genérico; 137 costuma ser morte por memória (128 + 9).
restartPolicy
A regra de reinício do pod: Always (padrão), OnFailure ou Never.
backoff
A espera crescente entre tentativas. Começa em segundos e chega a minutos; reinicia a contagem se o container ficar de pé por tempo suficiente.
Last State
No describe, o estado da execução anterior do container — onde aparecem o motivo e o código de saída.
logs --previous
Mostra a saída do container anterior, quando o atual ainda não produziu nada. É o comando que salva no meio do loop.
livenessProbe
A verificação de vida. Se falhar vezes seguidas, o kubelet mata o container e o reinicia — o que também aparece como reinício.

Guarde a consequência prática: reiniciar é comportamento normal, não punição. Um servidor web com Always que morre por falta de memória vai morrer de novo em loop, para sempre. O trabalho do diagnóstico não é parar o loop — é descobrir por que o processo sai antes de completar o trabalho.

A escolha entre os três valores muda o comportamento de um jeito bem concreto. Vale comparar antes de escolher, porque é a decisão que transforma um pod que terminou num pod que reinicia para sempre.

ValorO que fazQuando usar
Alwaysreinicia o container sempre que ele sai, com zero ou com erro servidor que deve ficar no ar; é o padrão dos pods
OnFailurereinicia só quando o código de saída é diferente de zero trabalho que pode ser repetido: relatórios, importações
Nevernunca reinicia; o pod fica Succeeded ou Failedtarefa única em que repetir atrapalha

Repare no caso do servidor: se o processo cai por erro de configuração, Always o reinicia para sempre — e é exatamente isso que produz o CrashLoopBackOff. O loop não é um defeito da política; é o sintoma de que o programa não consegue ficar de pé. Já no trabalho em lote, a política certa evita o loop: um relatório que terminou com zero não precisa rodar de novo.

3. A caixa: a política escrita em português

Antes de investigar o programa, vale conferir a regra que manda reiniciar. O campo restartPolicy aceita exatamente três valores em inglês, e escrever sempre não é “quase certo”: a API recusa o objeto inteiro. A caixa tem esse erro de propósito.

O manifesto escreveu sempre. Rode, leia a lista de valores aceitos e troque por OnFailure — o certo para um relatório que termina sozinho.

apiVersion: v1
kind: Pod
metadata:
  name: relatorio
spec:
  restartPolicy: sempre
  containers:
    - name: relatorio
      image: busybox:1.36
The Pod "relatorio" is invalid: spec.restartPolicy: Unsupported value: "sempre": supported values: "Always", "Never", "OnFailure"

apiVersion: v1
kind: Pod
metadata:
  name: relatorio
spec:
  restartPolicy: OnFailure
  containers:
    - name: relatorio
      image: busybox:1.36

A resposta é spec.restartPolicy: Unsupported value: "sempre": supported values: "Always", "Never", "OnFailure". A mensagem lista os três valores aceitos, na ordem em que o Kubernetes os conhece. É o tipo de erro bom: diz o que está errado e o que deveria estar lá.

Com OnFailure, o pod sobe e o container termina. Se terminasse com zero, o pod ficaria Succeeded — e a política não o reiniciaria. Se terminasse com erro, ele seria reiniciado, e é nesse caso que você veria o CrashLoopBackOff. A escolha da política não conserta um programa quebrado; ela decide o que o cluster faz com o programa que já está quebrado.

Repare que restartPolicy é campo do pod, não do container. Todos os containers de um pod obedecem à mesma regra. E ele é imutável depois que o pod nasceu: para trocar, apaga-se o pod e cria-se outro (num Deployment, isso é um novo rollout).

4. O describe de um container que morre

Agora o caso real: o container sobe e cai. O lugar onde isso fica registrado é o describe, na seção de containers. Esta é uma transcrição de cluster real, de um pod que já tinha reiniciado sete vezes:

Containers:
  relatorio:
    Image:          cardapio:1.1
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
      Started:      Fri, 27 Nov 2026 06:12:04 +0000
      Finished:     Fri, 27 Nov 2026 06:12:05 +0000
    Ready:          False
    Restart Count:  7

Leia em três camadas. State: Waiting com Reason: CrashLoopBackOff é o agora: o container não está rodando, está esperando a próxima tentativa. Last State: Terminated é o anterior: ele rodou e saiu. Exit Code: 1 é a resposta do programa ao sair — 1 é erro genérico. E Restart Count: 7 é o placar.

O tempo conta uma história também: começou às 06:12:04 e terminou às 06:12:05. Um segundo de vida. Container que morre em um segundo não é “servidor que caiu depois de um tempo”: é programa que não chega a iniciar — falta configuração, falta arquivo, comando errado. Se o intervalo fosse de trinta minutos, a suspeita mudaria para vazamento de memória ou dependência que cai depois.

Alguns códigos aparecem tanto que vale decorar. 0 é sucesso (e, com OnFailure, não reinicia). 1 é erro de aplicação. 2 costuma ser uso errado de comando. 137 é o famoso OOMKilled: o kernel matou o processo porque passou do limite de memória — nesse caso o Reason aparece como OOMKilled e o conserto é resources.limits.memory. 143 é SIGTERM: alguém pediu para o processo parar, o que é normal em desligamento.

5. A caixa: terminar não é falhar

Antes de ver por que o relatório morre, vale entender o que é não morrer. Um Job é um pod que roda até terminar, e o certo para ele é sair com zero — o status fica Succeeded, e o READY fica em 0/1, porque não há nada pronto para receber tráfego. É um pod “morto de propósito”, e isso não é erro nenhum.

A caixa começa só olhando os pods, e não há nenhum. Crie o Job com kubectl create job relatorio --image=busybox:1.36 e rode: o pod do Job aparece em Succeeded.

kubectl get pods
ana@notebook:~$ kubectl get pods
No resources found in default namespace.

kubectl create job relatorio --image=busybox:1.36
kubectl get pods

O painel mostra relatorio-bzfhv 0/1 Succeeded. O nome comprido vem do Job, que cria o pod com um sufixo próprio — a mesma ideia dos pods de Deployment. E o 0/1 aqui não é problema: um Job concluído não tem container rodando para ficar pronto.

Essa distinção resolve metade das dúvidas de quem está começando: Succeeded com RESTARTS zero é sucesso; CrashLoopBackOff com RESTARTS subindo é falha; Running com RESTARTS subindo é falha intermitente, o caso mais chato de todos. E existe o caso do Job que falha: ele fica Error e o controlador tenta de novo até um limite — o backoffLimit, que por padrão é 6.

6. A caixa: o Job tem regra própria

Como o Job existe para terminar, ele não aceita a política Always. É uma regra do próprio tipo de recurso, e a mensagem do Kubernetes é bem direta. A caixa tem um Job com Always no template, do jeito que muita gente copia de um manifesto de Deployment.

O Job não aceita restartPolicy: Always. Troque por OnFailure e rode: o Job é criado e o pod dele termina em Succeeded.

apiVersion: batch/v1
kind: Job
metadata:
  name: relatorio
spec:
  template:
    spec:
      restartPolicy: Always
      containers:
        - name: relatorio
          image: busybox:1.36
The Job "relatorio" is invalid: spec.template.spec.restartPolicy: Unsupported value: "Always": supported values: "OnFailure", "Never"

apiVersion: batch/v1
kind: Job
metadata:
  name: relatorio
spec:
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: relatorio
          image: busybox:1.36

A mensagem é spec.template.spec.restartPolicy: Unsupported value: "Always": supported values: "OnFailure", "Never" — dois valores, não três. Note também o caminho: dentro de um Job, o pod mora em spec.template.spec, porque o Job usa um modelo para criar pods, como o Deployment. Errar o caminho é o segundo erro mais comum: colocar restartPolicy em spec e não em spec.template.spec não dá erro, mas também não vale nada.

Com OnFailure, o pod do Job nasce, o container roda e sai com zero, e o Job fica completo. A tabela do get pods mostra Succeeded, e a meta da caixa confere as duas coisas: que o objeto Job/relatorio existe e que o painel mostra o resultado. É a diferença entre “o cluster aceitou meu pedido” e “o trabalho terminou”.

7. As cinco causas de um CrashLoop

Depois de algumas horas de plantão, o padrão aparece. Quase todo CrashLoopBackOff cai em uma destas cinco famílias, e cada uma deixa uma marca diferente no describe ou no log.

CausaComo apareceConserto
comando erradoexit 127, log com “not found”corrigir command e args
configuração faltandoexit 1, log reclamando de variável ou arquivocriar env, ConfigMap ou Secret que o programa lê
arquivo não montadoexit 1, log com “no such file”conferir volumeMounts e o caminho
verificação de vida falhandoRESTARTS sobe sem log de erroajustar livenessProbe (caminho, porta, tempo)
memória estouradaReason: OOMKilled, exit 137subir resources.limits.memory ou corrigir vazamento

As três primeiras são as que você vai encontrar nesta semana, e todas se resolvem lendo o log. A quarta é traiçoeira porque o log pode estar limpo: o container funciona, mas a verificação de vida bate na porta errada e o kubelet mata o processo por desconfiança. A quinta aparece com o Reason certo no describe e é a única em que o conserto costuma ser no manifesto, não no código.

Uma sexta causa merece parágrafo: o programa que espera um serviço que ainda não existe. O banco sobe depois, o DNS interno demora, e o relatório tenta conectar nos primeiros segundos e desiste. Nesse caso o ciclo se resolve sozinho quando a dependência fica de pé — e o backoff é justamente o que dá tempo para isso. Se não resolver, o caminho é initContainer ou uma nova tentativa dentro do próprio programa.

8. Logs: a mensagem que o cluster não dá

O describe diz o que aconteceu; o log diz o que o programa achou disso. São duas fontes diferentes e você precisa das duas. O comando é kubectl logs, e ele tem uma variação que salva a vida no meio do loop: --previous, que mostra a saída do container anterior, já que o atual pode estar em espera e não ter produzido nada.

ana@notebook:~$ kubectl logs relatorio
ana@notebook:~$ kubectl logs relatorio --previous
Iniciando o relatorio da madrugada
Lendo /config/cardapio.json
Erro: arquivo /config/cardapio.json nao encontrado
ana@notebook:~$

Esse é o caso clássico: o log atual vem vazio, o anterior conta tudo. A mensagem “arquivo não encontrado” aponta direto para o volumeMounts — provavelmente o ConfigMap não foi criado, ou o caminho montado é outro. Sem o --previous, a Ana teria concluído que o programa “não loga nada”, e perdido mais uma hora.

Duas limitações do log valem saber. A primeira: log é do container, não do pod. Num pod com vários containers, use -c nome para escolher. A segunda: o log guarda só as últimas linhas (o kubelet rotaciona), então um container que reiniciou cinquenta vezes pode ter perdido a primeira mensagem — nesse caso, o --previous te dá a última execução, não a primeira.

Dois complementos úteis do comando: --tail=50 mostra só as últimas cinquenta linhas, e -f acompanha o log ao vivo, como um tail -f. Acompanhar ao vivo é ótimo para ver o programa subindo e cair na sua frente — a última linha antes do silêncio costuma ser a culpada. Em pod com mais de um container, -c nome escolhe qual log ler; sem ele, o kubectl pega o primeiro.

E existe o log que não é do seu programa: mensagens do próprio runtime do container, quando a imagem falha ao iniciar por falta de permissão de arquivo ou comando inexistente. Elas também aparecem no kubectl logs, com o prefixo do runtime. Se a mensagem não parece ter sido escrita pelo seu código, provavelmente é disso que se trata — e o conserto volta a ser no manifesto, não no programa.

9. Cenários do dia a dia

Cenário 1: o “funciona no meu terminal”

A Ana rodou a imagem no notebook, com as variáveis de ambiente exportadas na sessão, e funcionou. No cluster, o pod caiu com exit 1 e o log dizia que faltava DATABASE_URL. O container não herda o ambiente do seu terminal: o que existe é o que está no manifesto, em env ou envFrom. O conserto foi declarar a variável no YAML.

Cenário 2: o relatório que reiniciava de minuto em minuto

O relatório rodava em 40 segundos, terminava com zero e o pod voltava. O restartPolicy era Always — herdado de um manifesto copiado. Com OnFailure, o pod terminou uma vez e ficou em Succeeded. O programa nunca teve problema; a política é que mandava reiniciar um trabalho já concluído.

Cenário 3: o log limpo e o reinício sem explicação

Um pod reiniciava a cada dois minutos com log vazio e exit 137. O describe mostrou Reason: OOMKilled: o limite era limits.memory: 128Mi e o programa usava 200 MB. Não havia bug — havia limite baixo. A Ana subiu para 512Mi e o ciclo parou. Foi o caso em que o conserto coube numa linha de YAML.

11. Resumo

CrashLoopBackOff é o container que sobe, sai e é reiniciado em ciclo, com espera crescente. O sintoma que não engana é o RESTARTS subindo; o status pode até voltar a Running entre tentativas. Quem decide reiniciar é o restartPolicy: Always, OnFailure ou Never, e um Job só aceita os dois últimos.

A investigação tem duas fontes. O describe mostra Last State, Reason e Exit Code — 1 para erro de aplicação, 137 para memória estourada, e OOMKilled escrito por extenso. O logs, com --previous quando o atual está vazio, mostra a mensagem do programa: variável faltando, arquivo não encontrado, comando inexistente. Cinco causas cobrem quase tudo, e quatro delas se resolvem no manifesto.

Na próxima aula o olho vai para as duas fontes com calma: o que exatamente o kubectl logs mostra, o que a seção de eventos do describe conta, e como usar uma para confirmar a outra. É a aula de logs e eventos.

Para lembrar
  • RESTARTS subindo = container morrendo em série; o status pode oscilar.
  • restartPolicy aceita Always, OnFailure e Never; Job só aceita os dois últimos.
  • describe → Last State, Exit Code, Reason.
  • Exit 1 = erro do programa; 137 / OOMKilled = memória.
  • kubectl logs --previous mostra a execução anterior quando a atual está em espera.
  • Succeeded com RESTARTS 0 é sucesso, não falha.
