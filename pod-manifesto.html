O manifesto do Pod

A Ana já aplicou um pod, já viu o created e já sabe ler o YAML. Agora ela quer entender o arquivo inteiro: o que é obrigatório, o que é opcional, o que o servidor acrescenta sozinho e o que ela nunca deve escrever. Nesta aula cada bloco do manifesto do pod é aberto com calma — apiVersion, kind, metadata, spec e o status que só o cluster preenche —, com os erros de validação mais comuns aparecendo na caixa de verdade. No fim, ela vai olhar um manifesto de trinta linhas e saber quais linhas pode tirar.

Você vai aprender
  • Os quatro blocos que você escreve e o quinto, que é resposta do cluster.
  • O que vai em metadata: nome, namespace, etiquetas e anotações.
  • O que vai em spec: a lista de containers e as decisões do pod.
  • Os padrões que o servidor preenche sozinho e que não aparecem no seu arquivo.
  • Por que status, uid e resourceVersion não se escrevem.
  • O que significa cada tipo de erro de validação e onde olhar.
  • Como usar kubectl explain para descobrir um campo sem abrir a internet.

1. A cena: o manifesto de trinta linhas

O cardapio.yaml da Ana cresceu. Começou com sete linhas, hoje tem trinta: etiquetas, anotações, política de reinício, limite de memória e um bloco de portas. Funciona — ela aplicou e o pod subiu. Mas ela não sabe dizer o que cada linha faz, e isso incomoda: se alguém perguntar “por que essa linha está aqui?”, a resposta honesta é “veio do exemplo”.

O pior é o medo de mexer. Toda vez que ela apaga uma linha, o pod “não sobe” ou sobe diferente, e ela devolve a linha. O arquivo vira uma relíquia que ninguém entende e todos copiam. É o começo do fim de um manifesto: quando ninguém sabe o que é obrigatório, tudo vira obrigatório.

Este é o problema que a aula resolve. Um pod não tem cem campos possíveis na prática: tem quatro blocos, e dentro deles pouca coisa realmente obrigatória — metadata.name e spec.containers[].name e image. Todo o resto é opcional, tem padrão, ou é resposta do cluster. Quando você sabe quais são os três, o arquivo encolhe e o medo vai embora.

2. Os quatro blocos, e o quinto que é resposta

Todo manifesto do Kubernetes, de pod a Ingress, tem a mesma moldura. apiVersion diz qual versão da API conhece aquele tipo. kind diz o tipo. metadata guarda a identidade. spec guarda o que você quer. E o status guarda o que o cluster conta de volta — esse você não escreve nunca.

BlocoObrigatório?O que temQuem escreve
apiVersionsima versão da API: v1 para Podvocê
kindsimo tipo do objeto: Podvocê
metadatasim, pelo menos o nomenome, namespace, etiquetas, anotaçõesvocê
specsimcontainers, portas, política de reinício, volumesvocê
statusnãofase, IP, nó, condições, reinícioso cluster

O apiVersion é o campo que mais confunde quem copia manifesto. Ele não é “a versão do Kubernetes” nem “a versão da sua aplicação”: é o endereço da API que define aquele tipo. Pod mora no grupo antigo, sem nome, e por isso é só v1. Deployment mora em apps/v1. Job, em batch/v1. Se você trocar o apiVersion do pod para apps/v1, o cluster não tenta adivinhar: responde que não conhece aquele tipo naquela versão. A caixa abaixo tem esse erro.

O pod está declarado em apps/v1, que é o grupo dos workloads, não do pod. Troque para a versão certa (v1) e rode.

apiVersion: apps/v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
error: resource mapping not found for name: "cardapio" namespace: "" from "STDIN": no matches for kind "Pod" in version "apps/v1"
ensure CRDs are installed first

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0

A resposta é error: resource mapping not found for name: "cardapio" namespace: "" from "STDIN": no matches for kind "Pod" in version "apps/v1", seguida de ensure CRDs are installed first. Traduzindo: “não achei o mapeamento desse recurso; nenhum tipo Pod combina com a versão apps/v1”. O “namespace vazio” é porque o manifesto também não disse o namespace. E a linha sobre CRDs é um conselho genérico do kubectl: ele sugere que talvez você esteja usando um tipo instalado por um operador — não é o caso, é só a versão errada.

Existe um jeito de não errar mais nisso: kubectl api-resources lista todos os tipos que o cluster conhece, com a versão e o escopo de cada um. Quando bater dúvida sobre apiVersion, é ali que se confere — não no blog de 2019.

3. metadata: a identidade do pod

metadata responde “quem é este objeto”. Quatro campos importam no começo. name é o nome, obrigatório, em minúsculas com hífen. namespace é a divisão lógica onde ele mora; se você não disser nada, vai para default. labels são etiquetas usadas por seletores — o assunto da próxima aula. annotations são anotações livres, para ferramentas e para gente, que nenhum seletor usa.

Etiqueta e anotação parecem a mesma coisa e não são. A etiqueta é indexada: o cluster consegue filtrar por ela, e é assim que um Service encontra os pods (kubectl get pods -l app=cardapio). A anotação é depósito: o controlador de Ingress guarda ali a configuração, o time guarda o link do chamado, o Versionamento guarda o commit. Nenhuma das duas muda o comportamento do pod sozinha — quem muda é quem as lê.

O detalhe que pega iniciante: etiqueta é sempre texto. O YAML adivinha tipos, e versao: 2 vira número. O cluster recusa com metadata.labels: Invalid value: "2": must be a string. Escreva versao: "2" — entre aspas — e passa. O mesmo vale para versao: true, que viraria booleano. A caixa abaixo tem o caso.

A etiqueta versao está como número. Ponha o valor entre aspas para ele virar texto e rode de novo.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
  labels:
    app: cardapio
    versao: 2
spec:
  containers:
    - name: web
      image: cardapio:1.0
The Pod "cardapio" is invalid: metadata.labels: Invalid value: "2": must be a string

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
  labels:
    app: cardapio
    versao: "2"
spec:
  containers:
    - name: web
      image: cardapio:1.0

Repare que a mensagem não fala de aspas nem de YAML: ela diz “must be a string”, “precisa ser texto”. A tradução para a vida real é sempre a mesma — o valor chegou como número, e o campo só aceita texto. Números com aspas, booleanos com aspas, e o problema desaparece. Quando o valor é uma versão como 1.0, aspas são obrigatórias de qualquer jeito: sem elas, o YAML lê como número e imprime 1.

Sobre name: o nome é a identidade e não muda. Não existe “renomear pod”: o que existe é criar outro e apagar o antigo. É por isso que o nome do pod importa menos do que parece — em produção quem cria pods é o Deployment, com nomes gerados. Mas enquanto você aprende, com pod solto, o nome é o endereço do objeto em todo comando: kubectl describe pod cardapio, kubectl logs cardapio, kubectl delete pod cardapio.

4. spec: o que você quer que exista

spec é o coração do manifesto: a descrição do pod. Dentro dele há duas categorias. A primeira é o que o pod tem — a lista containers, os volumes, as variáveis. A segunda é como o pod se comporta — a política de reinício, o nó preferido, a conta de serviço, o tempo de tolerância para encerrar.

A lista de containers é obrigatória e não pode ser vazia. Um pod sem container é recusado com spec.containers: Required value. Cada item tem três campos essenciais: name (o nome do container dentro do pod, obrigatório e único), image (de qual imagem ele nasce, obrigatório) e ports (a lista de portas que ele expõe, opcional). Portas, aqui, são documentação: o cluster não abre nem fecha nada por causa delas. Elas servem para o Service encontrar o alvo e para o leitor do manifesto saber onde a aplicação escuta.

O nome do container não é o nome do pod. Um pod chamado cardapio pode ter um container chamado web. Isso importa em dois momentos: quando você pede log de um container específico (kubectl logs cardapio -c web) e quando há mais de um container no pod. Os dois nomes seguem a mesma regra de formato — minúsculas, hífen no meio — mas são independentes.

As decisões de pod mais usadas são poucas. restartPolicy diz o que fazer quando o container morre: Always (o padrão), OnFailure ou Never. nodeSelector prende o pod a nós com certas etiquetas. serviceAccountName escolhe a identidade que a aplicação usa para falar com a API. terminationGracePeriodSeconds é quanto tempo o cluster espera antes de matar o processo à força — 30 segundos por padrão.

5. A lista de containers, campo por campo

Vale abrir um container inteiro, porque é onde 90% dos manifestos passam o tempo:

spec:
  containers:
    - name: web
      image: cardapio:1.0
      ports:
        - containerPort: 8080
      env:
        - name: MODO
          value: producao

Leia de fora para dentro. containers é uma lista (hífen). Cada item é um mapa com name, image, ports e env. ports também é uma lista, e o item dela é um mapa com containerPort. env é lista de mapas com name e value. Lista dentro de mapa dentro de lista — e é sempre o recuo que diz onde você está.

Os nomes dos campos são exatos, e o YAML não perdoa erro de digitação. containers no plural, containerPort com P maiúsculo no meio, image sem “n”. Escrever container: no singular não gera “campo desconhecido” — gera spec.containers: Required value, porque o cluster procurou a lista obrigatória e não achou. É a mensagem mais enganosa do começo, e a caixa abaixo mostra ela acontecendo.

name
O nome do container dentro do pod, obrigatório e único no pod. É ele que você cita em kubectl logs cardapio -c web. Não confunda com o nome do pod.
image
De onde o container nasce: cardapio:1.0. Obrigatório. Sem tag, latest é assumido — e o cluster passa a tentar baixar a imagem sempre.
ports
Lista de portas que a aplicação escuta, com containerPort obrigatório. É documentação e contrato: o cluster não abre nada por causa dela.
env
Lista de variáveis de ambiente, cada uma com name e value. Texto sempre, mesmo quando o valor parece número.
resources
O que o container pede e o que ele pode consumir, em requests e limits. Sem isso, o pod é BestEffort e recebe o que sobrar.

O campo está escrito container, no singular, e por isso o cluster não vê a lista obrigatória. Corrija o nome para containers e rode.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  container:
    - name: web
      image: cardapio:1.0
The Pod "cardapio" is invalid: spec.containers: Required value

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0

The Pod "cardapio" is invalid: spec.containers: Required value. “Required value” quer dizer “campo obrigatório sem valor”. Você olha o arquivo, vê que o bloco está lá e não entende. A explicação é que o campo container não existe: o cluster ignorou o que ele não conhece e reclamou do que faltou. A regra prática é boa: quando a mensagem diz “Required value” num campo que você jurou ter escrito, procure letra trocada ou plural faltando nesse campo.

Para conferir o nome exato sem sair do terminal existe kubectl explain. Ele mostra a documentação do campo, tirada do próprio cluster: kubectl explain pod traz a descrição do tipo, kubectl explain pod.spec desce um nível, e assim por diante. A saída é em inglês e um pouco seca, mas é a fonte mais confiável que existe — é a versão do cluster que você está usando, não a de um site qualquer.

6. O que o servidor acrescenta

O seu arquivo é menor do que o objeto que o cluster guarda. O servidor preenche os campos que você omitiu com valores padrão, e é por isso que o pod funciona mesmo com um manifesto de sete linhas. Conhecer os padrões evita duas coisas: repetir no arquivo o que já é padrão, e ser surpreendido por um comportamento que você não pediu.

CampoPadrãoO que muda quando você define
restartPolicyAlwaysNever deixa o container morrer sem reiniciar; OnFailure só reinicia com erro
dnsPolicyClusterFirstusa o DNS do cluster para achar serviços por nome
serviceAccountNamedefaultmuda a identidade que a aplicação usa para falar com a API
terminationGracePeriodSeconds30quanto tempo o processo tem para terminar antes do SIGKILL
imagePullPolicyIfNotPresent (com tag fixa)com :latest vira Always: o cluster sempre tenta baixar

Além dos padrões, o cluster preenche tudo o que só ele sabe: o IP do pod, o nó onde ele caiu, o horário de início, as condições (PodScheduled, Initialized, Ready) e o status de cada container. É isso que aparece quando você descreve o pod:

$ kubectl describe pod cardapio
Name:            cardapio
Namespace:       default
Priority:        0
Service Account: default
Node:            guia-control-plane/192.0.2.28
Start Time:      Fri, 27 Nov 2026 15:50:25 +0000
Labels:          run=cardapio
Annotations:     <none>
Status:          Running
IP:              10.244.3.71
IPs:             IP:  10.244.3.71
Controlled By:   <none>

Containers:
  cardapio:
    Image:          cardapio:1.0
    Port:           80/TCP
    State:          Running
    Ready:          True
    Restart Count:  0
    Environment:    <none>

Traduzindo o que veio de onde: Name e Namespace você escreveu; Service Account: default o servidor preencheu; Node, Start Time, Status e IP o agendador e o cluster informaram; Labels: run=cardapio foi o kubectl run que colocou (um manifesto com labels mostraria as suas); Ready e Restart Count são o estado do container. Nada disso estava no arquivo.

A mesma informação em forma de tabela, com -o wide, mostra o que o agendador decidiu:

$ kubectl get pods -o wide
NAME       READY   STATUS    RESTARTS   AGE   IP            NODE                 NOMINATED NODE   READINESS GATES
cardapio   1/1     Running   0          2m    10.244.3.71   guia-control-plane   <none>           <none>

Duas colunas que não existem no seu manifesto: IP, que o cluster atribuiu, e NODE, que o agendador escolheu. O pod não pediu nó nenhum — foi o agendador que olhou a capacidade dos três e escolheu um. Se amanhã você prender o pod a um nó com nodeSelector, essa coluna passa a ser sua decisão, não do acaso.

7. O que não se escreve no manifesto

Existe um erro de iniciante que merece seção própria: pegar o resultado de kubectl get pod cardapio -o yaml, colar num arquivo e tentar aplicar. O resultado tem campos que o servidor recusa, porque são dele. Os principais:

status inteiro — fase, IP, condições, estado dos containers. Você não descreve o status; você descreve o que quer e o cluster conta se conseguiu. Tentar escrever status é o equivalente a preencher o campo “resultado” antes da prova.

metadata.uid e metadata.resourceVersion — identificadores internos. O uid é único para sempre; o resourceVersion muda a cada alteração e é como o cluster controla concorrência. Mandar um resourceVersion antigo num apply com controle de versão faz o cluster recusar com the object has been modified — é o mecanismo funcionando, não um defeito.

metadata.creationTimestamp e metadata.generation — carimbo de tempo e contador de mudanças, também do servidor. E metadata.ownerReferences, que diz quem é o dono do pod: quando é o Deployment, é ele que apaga o pod ao reduzir réplicas. Escrever isso à mão é assumir um vínculo que você não controla.

A regra é simples e vale para todo tipo de objeto: no manifesto vão apiVersion, kind, metadata (sem os campos do servidor) e spec. O resto é resposta. Se um dia precisar copiar o objeto do cluster para um arquivo, apague o status, o uid, o resourceVersion e o creationTimestamp antes.

8. Quando o manifesto é recusado

Toda recusa de conteúdo segue o mesmo formato: The Kind "nome" is invalid: seguido do caminho do campo e do motivo. O caminho é a parte útil — ele desce por spec, containers, índice da lista e campo, tudo com ponto e colchete. Aprender a lê-lo é o que separa “deu erro” de “deu erro no containerPort do primeiro container”.

MensagemTraduçãoConserto
metadata.name: Required valuefalta o nomeacrescente name em metadata
metadata.name: Invalid value: "Cardapio"nome com maiúsculaminúsculas, hífen no meio
spec.containers: Required valuea lista não existe (ou o nome do campo está errado)confira containers, no plural
spec.containers[0].image: Required valueo container não tem imagemtodo container precisa de image
metadata.labels: Invalid value: "2": must be a stringetiqueta numéricaponha o valor entre aspas
no matches for kind "Pod" in version "apps/v1"apiVersion não combina com o kindPod é v1

Duas notas sobre o que a mensagem não diz. A primeira: ela mostra um erro por vez, e o primeiro pode esconder o segundo. Conserte, rode de novo, veja o próximo — é um processo, não um veredito. A segunda: o caminho usa índices a partir de zero, então [0] é o primeiro item da lista. Se você tem três containers e o erro fala de containers[1], é o segundo.

E existe o erro que não é erro de validação: o campo que o cluster aceita e ignora. Versões recentes do kubectl validam contra o esquema do tipo e reclamam de campo desconhecido, mas nem toda instalação está configurada assim. Se um campo parece não fazer efeito, confira a grafia em kubectl explain antes de suspeitar do cluster.

9. Cenários do dia a dia

Cenário 1: o manifesto que veio do -o yaml

A Ana copiou o objeto do cluster para um arquivo e tentou aplicar em outro ambiente. O cluster recusou por causa do resourceVersion e do status. O conserto foi apagar os campos do servidor e ficar só com apiVersion, kind, metadata e spec. Regra prática: -o yaml serve para ler, não para virar manifesto sem limpeza.

Cenário 2: o pod que subia sem a porta

Ela tirou o bloco ports para “enxugar” o manifesto e o pod continuou subindo — então concluiu que portas não servem para nada. Semanas depois, o Service não achava o alvo, porque o targetPort apontava para uma porta que o manifesto não declarava. Porta de container não abre nada, mas é contrato: ela documenta onde a aplicação escuta e é o que o Service usa para casar.

Cenário 3: dois times, o mesmo nome de campo

O colega dela usou containerPorts e o manifesto passou, sem efeito nenhum. A versão do kubectl dele não estava em modo estrito e o campo desconhecido foi descartado em silêncio. Descobriram porque o describe mostrava Port: <none>. O hábito que ficou: depois de aplicar, descrever o objeto e conferir se os campos que importam apareceram.

Exercício: o padrão que reinicia sempre

Você quer um pod que não reinicie quando o programa terminar. Complete o valor da política de reinício:

spec: restartPolicy:

Dica: são três políticas — Always (o padrão), OnFailure e a que nunca reinicia. Maiúscula na primeira letra, exatamente como o cluster escreve.

11. Resumo

O manifesto do pod tem quatro blocos que você escreve e um que o cluster devolve. apiVersion e kind dizem o que o objeto é (Pod é v1); metadata guarda identidade — nome obrigatório, namespace opcional, etiquetas e anotações; spec guarda o que você quer, com a lista containers obrigatória e, em cada item, name e image. O status é resposta e não entra no arquivo.

O servidor preenche padrões que você nem escreveu: restartPolicy: Always, dnsPolicy: ClusterFirst, conta de serviço default, 30 segundos de tolerância e a política de pull que depende da tag. Ele também preenche o que só ele sabe — IP, nó, condições e horário —, e é isso que aparece no describe e no -o wide. Copiar o objeto do cluster e reaplicar sem limpar é pedir recusa: uid, resourceVersion, creationTimestamp e status são do servidor.

Erro de validação sempre vem no formato The Pod "nome" is invalid: caminho: motivo, e o caminho é o mapa. “Required value” num campo que você jurou ter escrito significa nome errado ou plural faltando. Com o manifesto entendido, a próxima pergunta é como o cluster encontra um pod no meio de tantos — e a resposta está em três palavras do metadata: etiqueta, seletor e o casamento entre as duas.

Para lembrar
  • Pod é apiVersion: v1; Deployment é apps/v1; Job é batch/v1.
  • Obrigatórios: metadata.name e spec.containers[].name e image.
  • Etiquetas e anotações são texto; número vira erro must be a string.
  • O servidor preenche restartPolicy, dnsPolicy, conta de serviço e tolerância.
  • status, uid, resourceVersion e creationTimestamp não se escrevem.
  • kubectl explain pod.spec mostra o campo certo sem sair do terminal.
