command e args

A imagem cardapio:1.0 da Ana já sabe como começar: quando o pod sobe, o programa abre o servidor na porta 8080 e fica esperando pedidos. Isso funciona até o dia em que ela precisa do mesmo programa em outro modo — um que só mostra a versão, outro que roda a migração do banco e termina. O lugar onde se troca isso é o manifesto, nos campos command e args. Nesta aula a Ana descobre por que esses dois campos confundem tanto, aprende a regra que resolve 90% dos casos e vê o que acontece quando eles são trocados: o pod sobe, morre e reinicia em loop.

Você vai aprender
  • O que a imagem já traz pronto (o ENTRYPOINT e o CMD do Dockerfile).
  • Como command e args substituem esses dois pedaços.
  • A tabela oficial: o que roda em cada combinação dos dois campos.
  • Por que a ordem de um sh -c importa e como o erro aparece no cluster.
  • O que fazer quando o container termina: exit code, Completed e CrashLoopBackOff.
  • Onde ver o comando que está de fato rodando, no describe e no -o yaml.

1. A cena: o mesmo programa, outro modo

O site da padaria é um programa Node pequeno. A imagem cardapio:1.0 foi construída com uma instrução no fim do Dockerfile parecida com esta: CMD ["node", "servidor.js"]. É por isso que a Ana nunca precisou dizer como rodar o programa: ela manda a imagem, e a imagem já sabe o que fazer.

Só que o mesmo código tem outros modos. Existe um arquivo versao.js que imprime a versão e sai. Existe um migrar.js que arruma as tabelas do banco e sai. Nenhum dos dois abre servidor na porta 8080 — os dois fazem uma coisa e terminam. Se a Ana criar um pod com a imagem do jeito que está, ele vai abrir o servidor e ficar lá para sempre; ela precisa de um pod que rode outro comando.

É exatamente para isso que existem command e args. Eles não mudam a imagem: mudam o que o cluster executa naquele pod, naquela execução. A mesma imagem pode abrir o servidor num pod e rodar a migração em outro, sem rebuild, sem tag nova, sem imagem duplicada.

2. A receita que já vem dentro da imagem

Antes de mexer, vale entender o que a imagem entrega. Todo Dockerfile termina com duas instruções opcionais que formam, juntas, o comando de partida. O ENTRYPOINT é o executável — o que é chamado primeiro. O CMD, quando vem depois do entrypoint, é a lista de parâmetros padrão. Pense num bolo de padaria: a imagem é a receita impressa, com o nome do bolo e o recheio já sugerido.

O Kubernetes pega esses dois pedaços e batiza de outro jeito, o que é metade da confusão: o command do manifesto fala com o ENTRYPOINT da imagem, e o args do manifesto fala com o CMD. Os nomes não combinam, e é por isso que tanta gente troca os dois na primeira vez.

ENTRYPOINT (imagem)
O executável de partida, definido no Dockerfile. É quem o command do manifesto substitui.
CMD (imagem)
Os parâmetros padrão, também do Dockerfile. É o que o args do manifesto substitui.
command
Campo do manifesto, uma lista de strings: o executável e, se você quiser, os primeiros argumentos. Sobrescreve o ENTRYPOINT.
args
Campo do manifesto, também uma lista: só os argumentos. Sobrescreve o CMD.
exit code
O número que o processo devolve ao terminar. 0 é sucesso; qualquer outro é falha, e cada número tem um significado.

Quando a Ana não escreve nenhum dos dois no manifesto, o cluster usa os dois da imagem. É o caso de todos os pods que ela criou até agora na aula do primeiro pod — eles funcionaram justamente porque a imagem tinha um padrão bom.

3. command: você assume o volante

O command é uma lista, e cada item é uma palavra do comando. Para rodar o script de versão, a Ana escreve assim:

spec:
  containers:
    - name: versao
      image: cardapio:1.0
      command: ["node", "versao.js"]

Repare que é uma lista com dois itens, não uma frase. Se você escrever a lista numa linha só, com colchetes, o YAML entende. Se preferir o formato de baixo, com hífen em cada item, também vale — é o mesmo conteúdo:

spec:
  containers:
    - name: versao
      image: cardapio:1.0
      command:
        - node
        - versao.js

Ao definir command, o ENTRYPOINT da imagem é ignorado por inteiro. Isso tem uma consequência que pega muita gente: se a imagem não tem um shell — as imagens "distroless" e algumas mínimas não têm —, você não pode escrever ["sh", "-c", "..."], porque o sh não existe lá dentro. O comando falha antes de rodar qualquer coisa, com exec: "sh": executable file not found in $PATH. O erro não é seu YAML; é a imagem que não tem esse programa.

E o args, nesse caso? Se você define command e não define args, os parâmetros padrão da imagem são descartados. O cluster roda exatamente o que está na sua lista, nada mais. É por isso que command: ["node", "versao.js"] funciona: você escreveu o programa e o argumento no mesmo lugar.

4. args: só os parâmetros, o programa fica

O args é o irmão educado: ele troca só os parâmetros e deixa o executável da imagem no lugar. Serve quando o que muda é o modo, não o programa. A imagem nginx, por exemplo, tem ENTRYPOINT ["/docker-entrypoint.sh"] e um CMD que roda o nginx em primeiro plano. Para mudar o comportamento sem perder o entrypoint, a Ana escreve só os argumentos.

spec:
  containers:
    - name: estatico
      image: nginx:1.29
      args: ["-c", "/etc/nginx/nginx.conf"]

Aqui a regra é a inversa: como você não escreveu command, o ENTRYPOINT da imagem continua valendo, e os seus args entram no lugar do CMD. O nginx recebe -g "daemon off;" e fica em primeiro plano — que é o que o Kubernetes quer, porque container que termina é container que o cluster tenta reiniciar.

Juntando as duas ideias, existe uma tabela oficial, do próprio manual do Kubernetes, que mostra as quatro combinações. Vale decorar pela lógica: o que você escreve vence.

commandargsO que o container executa
nãonãoENTRYPOINT + CMD da imagem
simnãosó o seu command — o CMD da imagem é ignorado
nãosimENTRYPOINT da imagem + os seus args
simsimo seu command + os seus args

Leia a segunda linha com atenção, porque ela é a que surpreende: definir command sozinho joga fora os argumentos da imagem. Se o entrypoint original era ["node", "servidor.js", "--porta"] e o CMD era ["8080"], escrever command: ["node"] não te dá "node com o resto"; te dá só node, esperando entrada pelo teclado que nunca vem.

5. Os dois juntos: o caso de quem quer controle total

Quando command e args aparecem juntos, você controla tudo — e é aí que a maioria dos manifestos reais vive. É o caso de rodar um shell com um script embutido, muito comum para tarefas de manutenção:

spec:
  containers:
    - name: forno
      image: cardapio:1.0
      command: ["/bin/sh"]
      args: ["-c", "echo assando; sleep 30"]

O comando executado é a concatenação: /bin/sh seguido de -c, echo assando; sleep 30. O -c diz ao shell "o próximo item é o script". Sem ele, o shell tentaria abrir um arquivo chamado echo e reclamaria. Com ele, o texto vira um programa de verdade, com ponto e vírgula, redirecionamento e tudo o mais.

Duas observações práticas. A primeira: o shell no command e o -c no args — sempre nessa ordem, porque /bin/sh é o executável. A segunda: nesse formato, o processo principal do container é o sh, e não o seu programa. Se o programa morrer, o shell devolve o código e o container termina. Faz diferença quando a aula de probes chegar; por ora, guarde que o primeiro item da lista é quem manda.

6. O tropeço número um: command e args invertidos

Como os nomes não combinam com o Dockerfile e os dois são listas de strings, o erro é quase inevitável: colocar as flags no command e o executável no args. O YAML não reclama — é tudo texto. O cluster aceita. O pod é criado. E o container tenta executar um programa chamado -c, que não existe.

A caixa abaixo tem esse manifesto, de propósito. Rode, leia a resposta do cluster e depois conserte: /bin/sh é o command; -c e o script são args.

Conserte a ordem: o executável vai em command e as flags em args. Depois rode e confira no objeto, no painel, onde cada coisa caiu.

spec:

    - name: forno
      image: cardapio:1.0
      command: ["-c", "echo assando"]
      args: ["/bin/sh"]

O painel mostra o objeto inteiro depois do apply, no formato do kubectl get pod forno -o yaml. Procure o bloco do container: command: com /bin/sh e args: com os dois itens. Se você rodar sem consertar, o mesmo bloco mostra o inverso — e é essa inversão que produz o CrashLoopBackOff da seção 8.

Vale um aviso honesto sobre o painel: ele mostra alguns campos internos da simulação (iniciadoEm, no, ready) e não é uma cópia caractere por caractere do que um cluster real imprime. O que importa aqui é a estrutura: spec.containers é uma lista, cada container tem name, image, command e args, e o status conta o que o cluster fez.

7. O tropeço número dois: as flags no lugar do programa

O segundo erro clássico é o inverso do primeiro, e acontece com imagens que já têm um entrypoint esperto, como o nginx. A pessoa quer apontar o nginx para outro arquivo de configuração, vê o campo command no manifesto e escreve a flag ali. O resultado: o entrypoint do nginx é descartado, e o container tenta executar um programa chamado -c, que não existe.

A caixa abaixo está assim. Conserte movendo as flags para args e deixando o command fora — quem escolhe o programa é a imagem.

Tire o command e ponha os dois itens em args: a flag -c e o caminho do arquivo de configuração. O ENTRYPOINT da imagem volta a valer e o pod fica Running.

apiVersion: v1
kind: Pod
metadata:
  name: estatico
spec:
  containers:
    - name: estatico
      image: nginx:1.29
      command: ["-c", "/etc/nginx/nginx.conf"]
pod/estatico created

NAME       READY   STATUS    RESTARTS   AGE
estatico   1/1     Running   0          24s

apiVersion: v1
kind: Pod
metadata:
  name: estatico
spec:
  containers:
    - name: estatico
      image: nginx:1.29
      args: ["-c", "/etc/nginx/nginx.conf"]

A diferença entre as duas caixas é a lição inteira desta aula. Na primeira, o programa é seu e você escreve os dois campos. Na segunda, o programa é da imagem e você escreve só o args. O manifesto não tem como adivinhar sua intenção: se você preenche command, você está dizendo "esqueça o entrypoint, o programa sou eu".

8. Quando o comando termina: exit code, Completed e CrashLoop

Comando que termina não é erro por si só. versao.js imprime e sai com código 0; o container fica com o estado Terminated e o motivo Completed. O pod, com a política padrão Always, reinicia o container — e você vê o RESTARTS subindo, sem que nada esteja quebrado. Isso é o assunto da aula de restartPolicy, e é a razão de tarefas que terminam usarem Job em vez de pod solto.

Quando o programa falha, o número do exit code diz muita coisa. Ele é a única informação que o cluster tem do seu processo — o container não tem canal para explicar o que deu errado.

Exit codeSignificaOnde olhar
0terminou bemCompleted no describe
1erro do próprio programakubectl logs, a mensagem de erro aparece ali
126achou o arquivo, mas não pôde executarpermissão do binário na imagem
127comando não encontradonome errado no command, ou imagem sem aquele binário
137morto por SIGKILL, quase sempre memóriao evento OOMKilled no describe

O caso da troca de command com args não chega a rodar o programa: o runtime tenta executar -c e não encontra. O cluster marca a falha de start e reinicia. Esta é a transcrição de um cluster local com esse manifesto, para você ver o formato — o painel do guia não simula container rodando, então aqui a saída vem de fora:

$ kubectl get pods
NAME    READY   STATUS             RESTARTS      AGE
forno   0/1     CrashLoopBackOff   4 (28s ago)   2m11s

$ kubectl describe pod forno | tail -n 8
Events:
  Type     Reason     Age                    From               Message
  ----     ------     ----                   ----               -------
  Normal   Pulled     2m11s                  kubelet            Successfully pulled image "cardapio:1.0"
  Warning  Failed     2m11s (x3 over 2m11s)   kubelet            Error: failed to start container "forno": exec: "-c": executable file not found in $PATH
  Normal   Pulled     2m10s                  kubelet            Successfully pulled image "cardapio:1.0"
  Warning  BackOff    28s (x5 over 2m9s)     kubelet            Back-off restarting failed container forno in pod forno_default

Leia a mensagem com calma: exec: "-c": executable file not found in $PATH. O cluster tentou executar um programa chamado -c. Nenhum log de aplicação vai aparecer, porque a aplicação nunca começou — e é por isso que kubectl logs vem vazio nesse caso, enquanto o describe explica tudo nos eventos. Regra prática: logs é o que o programa disse; describe é o que o cluster tentou fazer.

9. Ver o comando que está rodando

Rampa de leitura, na ordem em que eu faria: kubectl get pods para ver o estado, kubectl describe pod para ver o comando, os args e o último estado, e kubectl get pod -o yaml para ver exatamente o que você entregou. O describe de um pod que rodou um comando curto fica assim (transcrição):

Containers:
  versao:
    Image:          cardapio:1.0
    Command:
      node
    Args:
      versao.js
    State:          Terminated
      Reason:       Completed
      Exit Code:    0
      Started:      Fri, 27 Nov 2026 15:50:25 +0000
      Finished:     Fri, 27 Nov 2026 15:50:26 +0000
    Ready:          False
    Restart Count:  0

Esses dois campos — Command e Args — são a prova do que você escreveu. Se o describe mostra Command: -c, o manifesto está invertido; se mostra o comando certo e o pod ainda assim reinicia, o problema é dentro do programa, e aí é logs. Quando Command não aparece, é porque você não definiu command: quem manda é a imagem.

A caixa abaixo é um terminal, como nos primeiros passos do guia: cada linha é um comando. Ela cria um pod sem command e sem args e pede o objeto inteiro. O objetivo é você ver que os dois campos simplesmente não estão lá — e que, mesmo assim, o pod está Running.

Crie o pod e troque o get pods pela leitura do objeto inteiro (-o yaml). Procure command e args: não existem.

kubectl run forno --image=cardapio:1.0
kubectl get pods
ana@notebook:~$ kubectl run forno --image=cardapio:1.0
pod/forno created

ana@notebook:~$ kubectl get pods
NAME    READY   STATUS    RESTARTS   AGE
forno   1/1     Running   0          5m

kubectl run forno --image=cardapio:1.0
kubectl get pod forno -o yaml

O que o painel mostra é o pod inteiro, com os campos que o cluster preencheu sozinho: restartPolicy: Always, dnsPolicy: ClusterFirst, terminationGracePeriodSeconds: 30, imagePullPolicy. Esses valores não estavam no seu comando e mesmo assim existem — são os padrões do Kubernetes, e conhecê-los evita susto quando você compara o que escreveu com o que aparece na tela.

Sobre o kubectl run: ele aceita argumentos depois de --, e esses argumentos viram args no pod. Funciona no cluster de verdade, mas o painel do guia não simula essa parte — aqui, comando e argumentos entram pelo manifesto, que é onde você vai conviver com eles no dia a dia.

10. Cenários do dia a dia

Cenário 1: a migração do banco que rodava de novo toda hora

A Ana criou um pod com command: ["node", "migrar.js"] para arrumar o banco. O script rodou, saiu com 0, e o pod reiniciou — porque restartPolicy padrão é Always. A migração rodou de novo. E de novo. O conserto não é no command: é trocar o tipo de objeto por um Job, que sabe que tarefa que termina é tarefa cumprida.

Cenário 2: o "sh: not found" da imagem mínima

O time dela trocou a imagem base por uma distroless, menor e mais segura, e os manifests que usavam command: ["sh", "-c", "..."] pararam de subir, com exit code 127 e a mensagem exec: "sh": executable file not found in $PATH. Não era YAML errado: a imagem não tem shell. A saída é chamar o binário direto (["node", "script.js"]) ou voltar para uma base com shell.

Cenário 3: o comando certo, o pod errado

Um pod de teste com args apontando para um arquivo de configuração em /config subiu, mas saiu com código 1 e a mensagem "ENOENT: no such file or directory". O comando estava certo; o arquivo é que não existia dentro do container. É a diferença entre como rodar (command e args) e com o que rodar (ConfigMap, volume, variável de ambiente) — assuntos das próximas aulas.

Exercício: o pod que só imprime a versão

Escreva no papel o manifesto de um pod chamado versao, com a imagem cardapio:1.0, que rode node versao.js e termine. Onde vai cada pedaço?

spec: containers: - name: versao image: cardapio:1.0 : ["node", "versao.js"]

Dica: o programa e o argumento caminham juntos quando o programa é escolhido por você. Se o executável viesse da imagem, você escreveria só os parâmetros em args.

12. Resumo

A imagem carrega um comando de partida, feito de duas peças: o ENTRYPOINT (o executável) e o CMD (os parâmetros padrão). No manifesto do pod, command substitui o ENTRYPOINT e args substitui o CMD. Os dois são listas de strings, e a regra é simples: o que você escreve vence, e o que você deixa de fora mantém o padrão da imagem — com a exceção importante de que definir command sozinho descarta os argumentos da imagem.

O tropeço comum é inverter os dois, e o sintoma é peculiar: o pod é criado, entra em CrashLoopBackOff, kubectl logs não mostra nada e o describe traz exec: "-c": executable file not found in $PATH. Comando que termina bem fica Completed com exit code 0; comando que termina mal deixa o código (1, 126, 127, 137) no describe, e é por ali que se começa o diagnóstico.

Para ver o que está de fato rodando, kubectl describe pod mostra Command e Args, e -o yaml mostra o que você entregou. Na próxima aula a Ana olha para o outro lado da conta: quanto de CPU e de memória o pod pede e quanto ele pode consumir — os campos que decidem se o pod cabe num nó.

Para lembrar
  • command substitui o ENTRYPOINT; args substitui o CMD.
  • Os dois são listas: ["/bin/sh", "-c"], não uma frase entre aspas.
  • Só args: o programa continua sendo o da imagem. Só command: os args da imagem somem.
  • Exit code 127 é comando não encontrado; 137 é quase sempre memória; 0 é sucesso.
  • describe mostra o que o cluster tentou; logs mostra o que o programa disse.
