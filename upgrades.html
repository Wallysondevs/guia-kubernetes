Upgrades

O cluster da padaria roda Kubernetes 1.36 e a Ana recebeu o aviso: aquela versão sai de suporte em três meses. Ela já sabe que atualizar um Deployment é rotina. Atualizar o cluster é outra coisa: mexe no que todos os objetos usam, e o que estava funcionando pode parar de existir — não porque alguém errou, mas porque a API que o seu manifesto usava foi removida. Nesta aula você vê o que quebra, por que o kubectl desalinhado dá mensagens esquisitas e qual é a ordem segura de subir uma versão sem derrubar o site.

Você vai aprender
  • O que existe dentro de “uma versão do Kubernetes” (não é uma peça só).
  • A regra de desalinhamento: quanto cada componente pode ficar atrás.
  • Como descobrir uma API removida antes de ela quebrar o seu manifesto.
  • A ordem segura: control plane, nós, complementos, kubectl.
  • O que cordon, drain e uncordon fazem num upgrade de nó.
  • Por que voltar atrás é quase impossível — e o que fazer no lugar.

1. A cena: o aviso de fim de suporte

O cluster de produção da Ana roda 1.36 desde março. Funciona. Ninguém reclama. E é justamente por isso que o aviso é fácil de ignorar: uma versão do Kubernetes sai de suporte mais ou menos catorze meses depois de lançada, o que dá tempo de sobra — até o dia em que dá.
Quando isso acontece, você para de receber correção de segurança, o time de suporte não atende mais chamado daquela versão e, o pior, o salto fica grande: sair de 1.33 para 1.37 de uma vez não é permitido, porque o Kubernetes só aceita subir uma versão menor por vez.

“Ah, então eu atualizo em um sábado à noite.” É o que todo mundo pensa antes do primeiro upgrade. O problema não é o comando — é que a atualização do cluster mexe no contrato da API. Um Deployment escrito com extensions/v1beta1 funcionava em 2018; em 1.16 esse grupo de API saiu, e o mesmo arquivo passou a ser recusado com “no matches for kind”. O manifesto não mudou: o mundo mudou embaixo dele.

Upgrade de cluster é, na prática, um projeto pequeno: inventário do que está instalado, leitura das notas de versão, troca de manifestos com API velha, teste em cluster de ensaio, atualização em janela combinada e um plano B se der errado. Esta aula é esse projeto, em ordem.

2. O que existe dentro de “uma versão”

Quando você diz “meu cluster é 1.37”, está resumindo um conjunto de programas que podem estar em versões diferentes. No plano de controle: o kube-apiserver (recebe os pedidos), o etcd (guarda o estado), o kube-scheduler e o kube-controller-manager. Em cada nó: o kubelet (cuida dos pods), o kube-proxy (cuida da rede dos Services) e o runtime de containers. Na sua mesa: o kubectl. E ainda os complementos, que quase ninguém lembra: CoreDNS, o plugin de rede (CNI), o controlador de Ingress, o metrics-server, os operadores que instalaram CRDs.

Cada um desses pedaços tem o seu próprio relógio de atualização. O plano de controle você atualiza junto (é um pacote só, na maioria das distribuições). Os nós, um por vez. Os complementos, conforme o projeto de cada um. O kubectl, quando você quiser — desde que respeite a regra da próxima seção.

versão menor (minor)
O número do meio: 1.37.1. É o que muda em um upgrade de cluster. Só se sobe uma por vez.
versão de correção (patch)
O último número: 1.37.3. Correções de bug e segurança; atualizar dentro da mesma menor é rotina e não muda API.
desalinhamento (skew)
A diferença de versão menor entre dois componentes. O Kubernetes define quanto é permitido.
depreciação
O aviso de que uma API ou campo vai sair. Durante a depreciação, ela ainda funciona.
remoção
O dia em que a API deixa de existir. Manifesto com ela é recusado na hora do apply.
drain
Esvaziar um nó: os pods são convidados a sair para outros nós, e o nó fica marcado para não receber novos.

3. A regra do ±1: quem pode ficar atrás de quem

A pergunta que mais aparece é “posso atualizar o kubectl depois?”. Pode — dentro de um limite. O kubectl é compatível com o API server uma versão menor para trás e uma para frente. Mais que isso, ele começa a mandar pedidos em formatos que o servidor não entende, e você vê erros que parecem bugs do cluster mas são do cliente.

O kubelet tem mais folga: pode ficar até três versões menores atrás do API server. É o que permite atualizar o plano de controle primeiro e os nós depois, com calma. O contrário não vale: um nó com kubelet mais novo que o API server não é suportado. Os complementos seguem o ritmo do projeto deles — CoreDNS e CNI costumam ter matriz de compatibilidade própria, e vale conferir antes.

Num cluster recém-criado, todos os nós mostram a mesma versão. É esta a imagem que você quer ver no começo e no fim de um upgrade:

$ kubectl get nodes
NAME                 STATUS   ROLES           AGE   VERSION
guia-control-plane   Ready    control-plane   8m    v1.37.3
guia-worker          Ready              4m    v1.37.3
guia-worker2         Ready              4m    v1.37.3

A coluna VERSION é a versão do kubelet daquele nó. Durante o upgrade, é normal ver duas versões diferentes por algumas horas — o primeiro nó atualizado e o segundo ainda no antigo. O que não é normal é a diferença persistir por dias: significa que alguém esqueceu um nó no meio do caminho, e o próximo upgrade vai acumular duas versões de distância.

Detalhe que confunde: o kubectl da sua máquina não aparece no get nodes. Ele é um binário local, e a versão dele você vê com kubectl version --client. Se o time tem gente com kubectl de duas versões atrás, é aí que nascem os “aqui não dá esse erro”.

4. API deprecada: como descobrir antes que quebre

Toda API do Kubernetes segue um caminho: alfa (pode sumir sem aviso), beta (existe, mas pode mudar), estável (é o que você usa). Depois de estável, uma API pode ser deprecada — continua funcionando, com aviso — e só então removida. Entre uma coisa e outra costumam passar várias versões menores, e o aviso vem nos release notes. O trabalho do upgrade é achar, no seu inventário, o que usa algo que vai sair.

O primeiro comando é o inventário do que o cluster conhece. Ele mostra, para cada tipo de objeto, a versão da API que o servidor aceita hoje:

Guarde a coluna APIVERSION: é ela que o seu manifesto tem de usar. Se o seu arquivo diz apps/v1beta1 e a tabela diz apps/v1, você está usando uma versão antiga que o servidor ainda aceita por compatibilidade — até o dia em que não aceita mais. O mesmo vale para networking.k8s.io/v1beta1 de Ingress, autoscaling/v2beta2 de HPA e policy/v1beta1 de PodDisruptionBudget.

A caixa abaixo tem o erro clássico, com a mensagem real do API server. O Deployment está declarado com um grupo de API que não existe mais: extensions/v1beta1, o endereço dos Deployments até a versão 1.16. Ajuste e rode.

Troque o apiVersion pelo grupo que o cluster aceita hoje (apps/v1) e rode. O painel tem de criar o Deployment com 2/2 prontos.

kind: Deployment

Rodando a caixa como está, o painel devolve o mesmo erro — e é bom ler a mensagem inteira, porque ela nomeia o tipo e a versão. Antes de aplicar em produção, três hábitos resolvem quase tudo. Primeiro, procure no repositório as strings das APIs que vão sair (grep -r v1beta1) — inclusive nos charts de Helm e nos overlays do Kustomize, que às vezes guardam o apiVersion antigo escondido. Segundo, use uma ferramenta de varredura (kubent e pluto são as mais conhecidas) contra o cluster: ela lista objetos vivos que usam API deprecada, o que pega o que não está no repositório. Terceiro, escute os avisos: o kubectl moderno imprime uma linha de warning quando você aplica algo com API deprecada, e essa linha é o seu prazo.

A mensagem que você vê no painel é esta (e é a mesma do cluster de verdade): no matches for kind "Deployment" in version "extensions/v1beta1", seguida de ensure CRDs are installed first.

Traduzindo: “não achei o tipo Deployment nessa versão de API”. A segunda linha é uma sugestão genérica do kubectl — ela fala de CRDs porque esse é o motivo comum do erro em outros casos. No seu, o motivo é o grupo de API que saiu. Conserte trocando o apiVersion; se o objeto também mudou de forma (foi o caso do Ingress na 1.22), conserte os campos junto.

5. A ordem segura de atualizar

A ordem não é capricho: cada etapa depende da anterior. Primeiro o plano de controle, porque é ele que fala a API nova e os nós antigos continuam compatíveis por três versões. Depois os nós, um por vez, porque o kubelet novo precisa de um API server que entenda os campos que ele manda. Depois os complementos, que costumam acompanhar a versão do cluster. Por último o kubectl, quando todo mundo já está na versão nova.

ComponenteQuanto pode ficar atrásPor quê
API server / plano de controlenada: é o primeiro a subirdefine a API que todos os outros usam
kubelet dos nósaté 3 versões menorespermite atualizar nós aos poucos, sem parada
kubectl1 para trás ou 1 para frentefora disso, manda pedidos em formato que o servidor não entende
CoreDNS, CNI, Ingresssegue a matriz do projetocada um tem a sua compatibilidade declarada
CRDs e operadoresdepende do operadoro CRD pode ter versão de API removida junto com o cluster

Antes de tocar em qualquer coisa, duas providências. A primeira é ler as notas de versão da versão de destino e da intermediária (se você vai pular, leia todas as notas do caminho). A segunda é ter um backup do etcd — o banco do cluster — feito naquele dia. Sem backup, “voltar atrás” é uma frase sem plano; com backup, é um procedimento. A aula de backup fala disso em detalhe.

Um upgrade de 1.36 para 1.37 num cluster de três nós é, em resumo: atualizar o plano de controle, atualizar cada kubelet com drain e uncordon, atualizar complementos, conferir tudo com get nodes e get pods -A, e só então atualizar o kubectl do time. Nada disso é feito “de uma vez” em produção.

6. Um nó por vez: cordon, drain e uncordon

Para atualizar o kubelet de um nó, o nó precisa estar vazio. O caminho é sempre o mesmo: cordon marca o nó como “não receba pods novos”, drain tira os que estão lá, você atualiza o software, uncordon devolve o nó ao serviço. Enquanto um nó está fora, os outros seguram a carga — e é por isso que se faz um por vez.

Coloque o nó guia-worker em manutenção, esvazie-o e confira a lista de nós no fim. O painel tem de mostrar o nó marcado, o esvaziamento e a tabela com Ready.

kubectl get nodes
kubectl cordon guia-worker
ana@notebook:~$ kubectl get nodes
NAME                 STATUS   ROLES           AGE   VERSION
guia-control-plane   Ready    control-plane   8m    v1.37.3
guia-worker          Ready    <none>          4m    v1.37.3
guia-worker2         Ready    <none>          4m    v1.37.3

ana@notebook:~$ kubectl cordon guia-worker
node/guia-worker cordoned

kubectl get nodes
kubectl cordon guia-worker
kubectl drain guia-worker --ignore-daemonsets
kubectl get nodes

O drain imprime o nó marcado e depois evicting pod... e node/guia-worker drained. O --ignore-daemonsets é obrigatório quando há DaemonSets no nó: esses pods não podem ser movidos para outro nó (cada nó tem o seu), então o drain se recusa a continuar sem essa bandeira. O mesmo vale para pods sem controlador: o drain para e avisa, porque apagar um pod solto é perder o pod.

Nada disso é instantâneo. Cada pod recebe um pedido de saída e tem um tempo (terminationGracePeriodSeconds, padrão 30 segundos) para fechar as conexões abertas. Um pod de banco de dados pode precisar de mais. E se o pod não sai, o drain espera — ou desiste, se o tempo estourar. Por isso a janela de manutenção existe: esvaziar nó com tráfego é diferente de esvaziar nó vazio.

Tem um detalhe de segurança que muita gente descobre tarde: o drain respeita o PodDisruptionBudget. Se o PDB do site diz “pelo menos duas réplicas sempre no ar” e só existem duas, o drain fica esperando até que uma terceira apareça — e é assim que deve ser. O orçamento de interrupção é justamente o contrato que impede a manutenção de derrubar o serviço.

7. O que mais quebra: além da API

API removida é o campeão, mas não é o único. Quando o kubelet sobe para a versão nova e o API server ainda está na antiga, você vê erro de conexão nos logs do nó, e os pods podem ficar Pending sem motivo aparente. Quando o complemento de rede não é atualizado, os pods sobem mas não conversam entre si: o sintoma é timeout entre serviços, não erro no get pods — o que manda você procurar no lugar errado.

O Ingress é o exemplo mais conhecido dessa mudança de forma. Na versão antiga, o destino era escrito com serviceName e servicePort; na versão atual, é um objeto service com name e port.number, e o caminho passou a exigir pathType. A caixa abaixo tem o manifesto no formato velho. Converta para o formato que o cluster aceita hoje e rode.

Troque o apiVersion para networking.k8s.io/v1 e reescreva o backend no formato novo, com pathType: Prefix. O painel tem de criar o Ingress e mostrar a tabela.

apiVersion: networking.k8s.io/v1beta1
kind: Ingress
metadata:
  name: cardapio
spec:
  rules:
    - host: loja.test
      http:
        paths:
          - path: /
            backend:
              serviceName: cardapio
              servicePort: 80
error: resource mapping not found for name: "cardapio" namespace: "" from "STDIN": no matches for kind "Ingress" in version "networking.k8s.io/v1beta1"
ensure CRDs are installed first

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cardapio
spec:
  rules:
    - host: loja.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapio
                port:
                  number: 80

A resposta é ingress.networking.k8s.io/cardapio created e a tabela mostra o host loja.test. Repare que o pathType não é enfeite: ele diz se o caminho é prefixo ou correspondência exata, e sem ele o objeto é recusado. Quando a API muda de grupo, quase sempre muda de forma também — não é só trocar uma linha do topo do arquivo.

Os CRDs merecem um parágrafo. Quando um operador instala um tipo novo (um Certificate, um Backup, um Application), ele registra uma versão de API. Se essa versão saiu do cluster, a mensagem é a mesma do “no matches for kind”, mas a correção não é sua: é atualizar o operador, ou o CRD, na ordem que o projeto dele manda. Vale sempre conferir os operadores no inventário antes de subir a versão do Kubernetes.

O segundo erro clássico no dia do upgrade é o kubectl desalinhado. Imagine o cluster em 1.37 e a sua máquina com kubectl 1.33. Comandos simples funcionam; os que dependem de campos novos falham com mensagens de validação que não têm nada a ver com o seu manifesto. O time perde uma tarde achando que o objeto está errado, quando o problema é o binário. A conferência é de dez segundos: kubectl version --client contra a versão que o get nodes mostra.

8. Voltar atrás: o plano B que quase não existe

Downgrade de versão menor não é suportado. O cluster pode até subir, mas o etcd foi gravado em um formato que a versão antiga não lê — e o “voltar” deixa de ser um comando para ser uma restauração. Na prática, o plano B de um upgrade é: restaurar o snapshot do etcd feito antes de começar, ou recriar o cluster na versão antiga e reaplicar os manifestos. Os dois caminhos são demorados, e é por isso que o backup é pré-requisito, não recomendação.

Dentro da mesma versão menor, a vida é mais fácil: um patch pode ser revertido com o mesmo procedimento de instalação do pacote, e o formato de dados é o mesmo. Atualizar de 1.37.1 para 1.37.3 é manutenção de rotina; de 1.36 para 1.37 é projeto. Trate os dois de forma diferente — inclusive na conversa com o time.

E vale dizer o óbvio: atualizar cedo é mais barato que atualizar tarde. Um cluster sempre uma versão atrás do lançamento atual tem um caminho curto e conhecido; um cluster três versões atrás tem que fazer três upgrades em sequência, cada um com a sua janela, e não pode pular nenhum. A dívida técnica do Kubernetes tem prazo de validade impresso na nota de lançamento.

Cenário 1: o manifesto que funcionava ontem

A Ana atualizou o cluster de 1.36 para 1.37 e, na segunda, o pipeline falhou aplicando o Ingress. O arquivo estava igual havia dois anos. O que mudou foi o grupo de API (networking.k8s.io/v1beta1 saiu) e a forma do backend: agora é service.name e service.port.number, não serviceName e servicePort. Corrigir o manifesto é rápido; descobrir por que o erro aparece só agora é o que custa tempo.

Cenário 2: o nó que ficou atrás

O upgrade terminou e o get nodes mostra dois nós em 1.37 e um em 1.36. Ninguém percebe, porque tudo funciona. Três meses depois, começa o próximo upgrade: o nó atrasado precisa de duas atualizações, e o kubelet dele já está no limite de desalinhamento. A conferência de versão no fim do upgrade não é formalidade — é o que evita o problema composto.

Cenário 3: o complemento esquecido

Plano de controle e nós atualizados, tudo verde, e os serviços começam a falhar com timeout. O controlador de Ingress ainda é a versão antiga, incompatível com a API nova do cluster. Complemento não aparece no get nodes e não aparece no get pods -A se estiver em outro namespace — é o tipo de coisa que só entra no inventário se alguém lembrar de listar. Anote os complementos junto com a versão de cada um.

11. Resumo

“Versão do cluster” é um conjunto de programas com relógios diferentes: plano de controle, kubelet de cada nó, complementos e o seu kubectl. A regra de desalinhamento permite kubelet até três versões atrás e kubectl uma para cada lado — mais que isso, os erros que aparecem não têm nada a ver com o problema real.

O que quebra num upgrade quase sempre é uma API que saiu. Descubra antes com kubectl api-resources, com uma varredura do repositório e com as notas de versão; o erro “no matches for kind … in version …” é a versão tardia dessa descoberta. A ordem segura é plano de controle, nós um por vez (com cordon, drain e uncordon), complementos, e o kubectl no fim.

Voltar atrás não é um comando: é restaurar um backup do etcd ou recriar o cluster. Por isso o backup do dia é pré-requisito, e por isso atualizar cedo — uma versão por vez, com janela e plano B — sai muito mais barato do que deixar três versões acumularem.

Para lembrar
  • Uma versão menor por vez; patch dentro da mesma versão é rotina.
  • kubectl ±1, kubelet até 3 atrás, API server primeiro.
  • kubectl api-resources é o inventário das APIs vivas.
  • cordon marca, drain esvazia, uncordon devolve.
  • Sem backup do etcd, não existe plano B.
