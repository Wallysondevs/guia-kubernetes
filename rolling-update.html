Rolling update

A versão 2.0 do site da Ana está pronta: cardápio novo, carrinho mais rápido, um desconto de domingo. Falta o passo que assusta — colocar no ar. No ano passado ela apagou o pod antigo e subiu o novo; durante quatro minutos o site respondeu erro, e quatro minutos de domingo são muitas vendas perdidas. Nesta aula ela aprende o jeito do Kubernetes: trocar as cópias uma de cada vez, sem fechar a padaria. O nome disso é rolling update.

Você vai aprender
  • O que é um rollout e por que ele é diferente de apagar e recriar.
  • Publicar uma imagem nova com kubectl set image, sem editar arquivo.
  • Descobrir o que dispara um rollout — e o que não dispara.
  • Acompanhar com kubectl rollout status até a última réplica.
  • Ler os sinais de um rollout em andamento no get e no describe.
  • Reconhecer um rollout travado: pods novos que nunca ficam prontos.

1. A cena: publicar sem fechar a padaria

Existem dois jeitos de trocar a vitrine de uma loja aberta. O primeiro é fechar as portas, arrancar a vitrine velha, montar a nova e abrir de novo — simples, rápido e catastrófico num domingo. O segundo é trocar uma peça por vez, de madrugada, com a loja funcionando: enquanto uma parte está sendo montada, a outra continua atendendo. O Kubernetes faz o segundo, e chama isso de atualização gradual.

A ideia por trás é simples: as réplicas são substituíveis, então não é preciso derrubar todas. O controlador cria pods com o modelo novo, espera que fiquem prontos, e só então apaga os antigos. Se os novos não ficarem prontos, ele para no meio do caminho e mantém os antigos no ar. O site nunca fica sem nenhuma cópia — e é essa garantia que a Ana quer comprar.

O preço é que a atualização deixa de ser instantânea. Ela leva o tempo de subir pods, e durante esse tempo convivem duas versões. Isso tem consequência de projeto: o banco de dados precisa aceitar as duas, as duas precisam responder o mesmo formato de API, e uma compra começada na versão velha tem de terminar na nova. Quem ignora isso descobre o problema no pior momento — no meio do deploy.

2. O vocabulário do rollout

Três palavras aparecem em toda conversa sobre publicação e é bom separá-las agora. O rollout é o processo de levar o Deployment de um modelo para outro. A revisão é o número que o Deployment guarda de cada modelo já aplicado. E o ReplicaSet antigo é o que fica para trás, com zero réplicas, guardado para um rollback rápido.

rollout
A troca gradual dos pods de um modelo antigo pelos de um modelo novo, feita pelo controlador do Deployment.
revisão
Um número inteiro que sobe a cada mudança no modelo de pod. Aparece em deployment.kubernetes.io/revision e no rollout history.
maxSurge
Quantos pods a mais que o desejado podem existir durante a troca. 25% com duas réplicas permite um pod extra.
maxUnavailable
Quantos pods podem faltar durante a troca. 0 significa “nunca menos que o desejado”, o que exige um pod extra antes de apagar o antigo.
rollout status
O comando que acompanha o rollout até o fim, imprimindo o progresso ou a mensagem de sucesso.

Os dois últimos termos vivem em spec.strategy.rollingUpdate e têm uma aula própria, logo depois desta. Por enquanto, guarde a intuição: eles são os dois botões que dizem quão rápido a troca acontece e quanta falta o serviço pode sentir no meio. Sem eles, o padrão do Kubernetes é 25% para cima e 25% para baixo.

3. kubectl set image: publicar sem editar o arquivo

O caminho mais direto para publicar uma imagem nova é o kubectl set image. Ele recebe o Deployment, o nome do container e a imagem nova, no formato container=imagem. Não é declarativo como o apply: é uma alteração pontual, ótima para um hotfix e péssima como registro do que está no ar. A caixa abaixo publica a 2.0 no cluster da padaria.

Publique a imagem cardapio:2.0 no container web, acompanhe o rollout e confira a imagem no describe.

kubectl get deployments
kubectl get pods
ana@notebook:~$ kubectl get deployments
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   2/2     2            2           2m

ana@notebook:~$ kubectl get pods
NAME                        READY   STATUS    RESTARTS   AGE
cardapio-wj4jsx2tcw-q65ng   1/1     Running   0          1m
cardapio-wj4jsx2tcw-t4jwn   1/1     Running   0          10m

kubectl set image deployment/cardapio web=cardapio:2.0
kubectl rollout status deployment/cardapio
kubectl describe deployment cardapio

A resposta tem três atos. Primeiro deployment.apps/cardapio image updated: o Deployment aceitou o modelo novo. Depois deployment "cardapio" successfully rolled out: o controlador chegou ao fim. No describe, a linha Image: mostra cardapio:2.0 e a anotação de revisão subiu para "2" — a prova de que o Kubernetes registrou a mudança como uma geração nova, não como um ajuste qualquer.

O detalhe do formato web=cardapio:2.0 pega muita gente. O lado esquerdo é o nome do container dentro do pod, não o nome do Deployment. Se você errar, a resposta é error: unable to find container named "site". Em pods com um container só, o nome costuma ser web ou o nome do serviço; confira no describe, na seção Containers.

4. O que dispara um rollout (e o que não dispara)

Nem toda mudança no Deployment vira uma geração nova. O critério é o template: se a mudança está dentro do modelo de pod, o Kubernetes precisa substituir os pods e cria uma revisão. Se está fora — o número de réplicas, as etiquetas do próprio Deployment, uma anotação —, ele ajusta o objeto e nada é recriado. A caixa abaixo compara os dois casos no mesmo cluster.

Escale para três réplicas, olhe o histórico (continua uma revisão) e depois publique a cardapio:2.0: o histórico passa a ter duas.

kubectl scale deployment/cardapio --replicas=3
kubectl rollout history deployment/cardapio
kubectl get pods
ana@notebook:~$ kubectl scale deployment/cardapio --replicas=3
deployment.apps/cardapio scaled

ana@notebook:~$ kubectl rollout history deployment/cardapio
deployment.apps/cardapio
REVISION   CHANGE-CAUSE
1          <none>

ana@notebook:~$ kubectl get pods
NAME                        READY   STATUS    RESTARTS   AGE
cardapio-wj4jsx2tcw-2h4sk   1/1     Running   0          3m
cardapio-wj4jsx2tcw-q65ng   1/1     Running   0          1m
cardapio-wj4jsx2tcw-t4jwn   1/1     Running   0          10m

kubectl scale deployment/cardapio --replicas=3
kubectl rollout history deployment/cardapio
kubectl set image deployment/cardapio web=cardapio:2.0
kubectl rollout history deployment/cardapio

Depois do scale, o histórico continua mostrando uma linha: escalar não muda o modelo, só a conta. Depois do set image, aparece a segunda. É uma distinção que economiza sustos — quem vê a revisão subir sem ter mudado a imagem deve procurar o que mudou no template: uma variável de ambiente, um limite de memória, a porta do container.

MudançaEstá no template?Dispara rollout?
imagem do containersimsim: revisão nova e pods substituídos

porta, limites e pedidos de recursosimsim
spec.replicasnãonão: só a contagem de pods muda

Existe uma armadilha no fim dessa tabela. As etiquetas do pod ficam em spec.template.metadata.labels, e essas disparam rollout — mas mudá-las quebra o selector se você não mudar os dois lados. Já as etiquetas em metadata.labels, no topo do arquivo, são do Deployment e não têm efeito nenhum sobre os pods. Duas linhas parecidas, dois comportamentos opostos.

5. rollout status: esperar até o fim

Publicar é fácil; saber se terminou é o que separa um deploy tranquilo de uma noite em claro. O kubectl rollout status fica acompanhando até o último pod novo ficar pronto e então imprime uma linha de sucesso. Se o rollout travar, ele continua imprimindo o progresso e o comando não volta — o que, num terminal de verdade, é um aviso: algo não está subindo.

$ kubectl set image deployment/cardapio web=cardapio:2.0
deployment.apps/cardapio image updated

$ kubectl rollout status deployment/cardapio
deployment "cardapio" successfully rolled out

$ kubectl get deployments
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   2/2     2            2           2m

Essa é a saída que a caixa devolve, copiada do painel. Em produção, o mesmo comando pode demorar minutos e imprimir linhas de progresso antes da última — algo como “Waiting for deployment … rollout to finish” com a contagem de réplicas atualizadas. A frase de sucesso só aparece quando todas as réplicas novas estão prontas. Por isso ele é o comando certo para o fim de um pipeline: se o deploy travar, o comando não termina, e o pipeline falha em vez de fingir que deu certo.

Uma ressalva prática: o rollout status tem um tempo limite padrão e desiste depois de um tempo sem progresso. Quando ele desiste, não significa que o rollout foi cancelado — significa que o kubectl parou de esperar. O Deployment continua tentando, e a investigação começa no get pods.

6. O que o painel faz (e o que ele não faz)

Vale ser explícito, porque esta é a aula em que a diferença mais aparece. O painel roda o controlador: ele atualiza o Deployment, calcula a revisão nova, responde o rollout status e mostra o histórico. O que ele não roda é o kubelet, o pedaço que cria e destrói containers. Por isso os pods que ele lista depois de um set image continuam sendo os do ReplicaSet que já existia.

Num cluster de verdade, mudar o template cria um ReplicaSet novo — nome diferente, mesmo sufixo de antes mais um resumo do modelo novo. Os pods antigos vão saindo um a um e os novos entrando, e durante alguns segundos o get pods mostra sufixos das duas gerações convivendo. O describe então lista o antigo em OldReplicaSets e o atual em NewReplicaSet. É esse teatro que os dois botões de estratégia comandam.

O que você pode aprender aqui é a metade do controlador: o objeto que muda, a revisão que sobe, o comando que espera, a mensagem de sucesso. É a metade que resolve 90% dos problemas de deploy, porque é ela que diz se terminou. A outra metade se aprende olhando um cluster de verdade — e o guia mostra essas passagens como transcrição, sempre identificadas.

7. O rollout que trava

Um rollout trava quando os pods novos não ficam prontos. O motivo mais comum é falta de recurso: o modelo novo pede mais memória ou mais CPU do que o cluster tem livre, e os pods ficam em Pending. O controlador não apaga os antigos, porque isso deixaria o serviço sem cópias — ele simplesmente espera, e o Deployment fica no meio do caminho. A caixa abaixo reproduz o caso.

Rode e veja os três pods sem lugar. Depois baixe a memória pedida para 1Gi e rode de novo: o rollout termina.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cardapio
spec:
  replicas: 3
  selector:
    matchLabels:
      app: cardapio
  template:
    metadata:
      labels:
        app: cardapio
    spec:
      containers:
        - name: web
          image: cardapio:2.0
          resources:
            requests:
              memory: "5Gi"
deployment.apps/cardapio created

cardapio-52qpnw7szc-vcfxb   0/1     Pending   0          6m

O painel devolve a lista de pods com os três em Pending e READY 0/1. O get deployments mostraria 0/3, e o rollout status nunca chegaria ao fim. É o retrato de um deploy parado no meio — e a diferença entre “parado” e “quebrado” é justamente que os pods antigos continuariam atendendo, se este fosse um cluster de verdade.

NAME                        READY   STATUS    RESTARTS   AGE
cardapio-52qpnw7szc-ml2v4   0/1     Pending   0          10m
cardapio-52qpnw7szc-vcfxb   0/1     Pending   0          6m
cardapio-52qpnw7szc-vlhhg   0/1     Pending   0          8m

Essa lista é a que a caixa devolve para o caso acima, copiada do painel. O sufixo igual nas três linhas confirma que são do mesmo modelo novo; o que falta não é imagem, é lugar. Num cluster real, o describe do pod traria o evento FailedScheduling com o motivo — memória insuficiente, no caso. Baixar o pedido para 1Gi libera o agendamento e o rollout termina.

8. Publicar pelo manifesto, como o time faz

O set image é ótimo para um teste, mas o jeito que sobrevive ao tempo é editar o arquivo e aplicar. O apply compara o que você mandou com o que existe e responde configured quando o objeto já existia. A diferença de comportamento em relação ao set image é pequena — os dois mudam o template e disparam uma geração nova —, mas a diferença de processo é enorme: o arquivo fica no repositório, passa por revisão e conta a história do que está no ar.

Há um cuidado que só aparece quando o time cresce: se você usar set image num cluster e o manifesto continuar dizendo a versão antiga, o próximo apply desfaz o hotfix sem avisar. Não é vingança do Kubernetes; é o arquivo mandando, como deve ser. A regra prática é escolher um dos dois caminhos e ser consistente — e, se o hotfix foi feito na mão, atualizar o arquivo logo depois.

Independente do caminho, o fim é o mesmo: kubectl rollout status até a linha de sucesso, kubectl get deployments para conferir os números e kubectl get pods para ver a idade das réplicas. Se algo soar estranho, kubectl rollout history mostra quantas gerações existem, e o describe conta qual ReplicaSet está no comando. Três comandos, um minuto de leitura, e você sabe exatamente o que está no ar.

9. Cenários do dia a dia da padaria

Cenário 1: o deploy que ninguém viu acontecer

A Ana publicou a 2.0 às 6h, com o site recebendo pedido de café da manhã. Nenhum cliente percebeu: as duas réplicas foram trocadas uma de cada vez, e sempre havia uma respondendo. O preço apareceu no servidor de banco: durante três minutos, as duas versões gravaram pedidos, e o relatório do dia somou tudo em dobro. Atualização gradual não elimina o trabalho de pensar na compatibilidade dos dados.

Cenário 2: a imagem errada publicada às pressas

Um set image com a tag cardapio:2.O (letra O no lugar do zero) fez o rollout travar: os pods novos não baixam a imagem e ficam em ErrImagePull. O Deployment continua com as réplicas antigas no ar, o site não cai, e o rollout status nunca termina. É o tipo de erro que o painel não calcula — ele não roda container —, mas que num cluster real aparece no describe pod em segundos.

Cenário 3: a versão nova que consome o dobro

A 2.0 do site passou a usar cache em memória e cada pod foi de 200Mi para 900Mi. O rolling update funcionou; o problema veio depois, quando os nós começaram a ficar sem memória e a despejar pods. Rollout saudável não quer dizer versão saudável: os números de recurso precisam ser revistos junto com o código, e é o que a Ana aprendeu na semana seguinte.

11. Resumo

Rolling update é a troca gradual: pods novos entram, ficam prontos, e só então os antigos saem. Quem comanda é o controlador do Deployment, e os dois botões que regulam o ritmo são maxSurge e maxUnavailable. Publicar pode ser um comando (kubectl set image deployment/cardapio web=cardapio:2.0) ou um arquivo aplicado com apply.

Só o que está dentro do template dispara uma geração nova. Escalar, mudar etiquetas do Deployment ou anotar o objeto não cria revisão. Para saber se terminou, kubectl rollout status; para saber o que existe, get deployments e get pods; para saber a história, rollout history.

E quando trava? Quase sempre é o pod novo que não fica pronto: falta de recurso, imagem errada, uma restrição de nó. O describe diz o motivo em uma linha. Na próxima aula a Ana aprende o caminho de volta — o rollback —, que é o que transforma um deploy travado em um susto de cinco minutos.

Para lembrar
  • kubectl set image deployment/nome container=imagem publica uma imagem nova.
  • Rollout é do template: réplicas e etiquetas do Deployment não criam revisão.
  • kubectl rollout status deployment/nome espera o fim e falha se travar.
  • Rollout travado = pods novos sem ficar prontos; leia o evento antes de mexer em qualquer coisa.
