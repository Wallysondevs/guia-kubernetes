O Primeiro Pod

A Ana já sabe que o Kubernetes existe, já instalou o kubectl e já viu o cluster responder “olá”. Agora ela quer ver a coisa: um pedaço de software rodando dentro do cluster. É o pod — a menor unidade que o Kubernetes liga e mantém de pé. Nesta aula a Ana cria o primeiro pod de duas maneiras (um comando e um arquivo YAML), aprende a ler a resposta do kubectl e vê, com os próprios olhos, o que acontece quando o nome está errado, quando a imagem não existe e quando o pod não cabe em lugar nenhum.

Você vai aprender
  • O que é um pod, na prática, e por que ele é a unidade do cluster.
  • Criar um pod com kubectl run e com um manifesto YAML.
  • Ler a tabela do kubectl get pods: READY, STATUS, RESTARTS e AGE.
  • Usar kubectl describe para ver nó, IP, imagem e eventos.
  • Reconhecer os três primeiros erros de todo mundo: nome inválido, imagem que não existe e pod que não agenda.
  • Entender o que a caixa faz: aplica o seu manifesto num cluster simulado que responde como o kubectl de verdade.

1. A cena: o site rodando na mão

O site da padaria da Ana é um programa pequeno: um servidor que responde na porta 8080 com o cardápio, os preços e o horário. Até ontem ele rodava “na mão” — a Ana abria o terminal, digitava node servidor.js e deixava a janela aberta. Se o computador reiniciasse, o site saía do ar e ela precisava lembrar de abrir de novo. Se ela fechasse o terminal sem querer, idem. E se o programa travasse às três da manhã, ninguém ficava sabendo até o primeiro cliente reclamar.

O Kubernetes resolve esse tipo de problema com uma ideia simples: em vez de você mandar comandos para ligar o programa, você descreve o que quer e entrega a descrição para o cluster. “Quero uma cópia desse programa rodando, com essa imagem, nessa porta.” O cluster então liga, monitora e recoloca no ar sozinho quando algo cai. A unidade que ele liga tem nome: pod.

Pod é uma palavra esquisita para quem vem de fora — parece coisa de ficção científica. Pense num pod como uma caixinha de entrega com um ou mais programas dentro, rodando juntos no mesmo endereço de rede. O cluster não liga “um container”; ele liga um pod. O container é o que está dentro; o pod é o pacote que o cluster agenda, move e reinicia.

2. O que é um pod, na prática

Todo pod tem três partes, e você vai ver essas três palavras em todo manifesto deste guia. O metadata é a identidade: nome, namespace e etiquetas. O spec é o que você quer que exista: os containers, as imagens, as portas, os limites. E o status é o que o cluster conta de volta: em que nó o pod caiu, qual IP ele ganhou, se está pronto. Você escreve metadata e spec; o status é resposta.

pod
A menor unidade que o Kubernetes agenda: um ou mais containers que compartilham rede e ciclo de vida. Tem nome, namespace e um IP próprio.
container
O programa empacotado com as suas dependências (a imagem cardapio:1.0, por exemplo). Um pod pode ter vários containers.
node
A máquina (física ou virtual) que roda pods. O cluster escolhe em qual nó cada pod cabe.
namespace
Uma divisão lógica dentro do cluster. Sem escolher, tudo vai para o namespace default.
manifesto
O arquivo YAML que descreve o que você quer. kubectl apply -f arquivo.yaml entrega esse arquivo ao cluster.

Uma coisa importante, que confunde no começo: você quase nunca cria pods soltos em produção. O normal é descrever um Deployment, que cria e cuida dos pods por você (o assunto do Nível 2). Mas o pod é a peça embaixo de tudo, e é por ele que se aprende: quando você entende um pod, entende o que qualquer Deployment está produzindo.

3. O primeiro pod, em um comando

A forma mais rápida de criar um pod é o kubectl run. Ele recebe um nome, uma imagem e pouco mais. É o comando que a Ana usa para testar se o cluster está de pé, antes de escrever qualquer arquivo. A caixa abaixo é um terminal: cada linha é um comando, e o painel mostra o que o kubectl responderia.

Troque a imagem do pod para cardapio:1.0 (a imagem do site da padaria) e rode. O painel tem de mostrar o pod cardapio em Running.

kubectl run cardapio --image=nginx:1.29
kubectl get pods
ana@notebook:~$ kubectl run cardapio --image=nginx:1.29
pod/cardapio created

ana@notebook:~$ kubectl get pods
NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          2m

kubectl run cardapio --image=cardapio:1.0
kubectl get pods

Duas linhas, duas respostas. A primeira é pod/cardapio created — o cluster aceitou o pedido e criou o objeto. A segunda é a tabela do get pods, e ela é o retrato do cluster naquele instante. Repare que o READY já está em 1/1 e o STATUS em Running: entre o “created” e a tabela, o cluster agendou o pod num nó, baixou a imagem e subiu o container. Isso costuma levar de segundos a um minuto na vida real.

O nome do pod é o que você pediu. Isso é diferente do que acontece com um Deployment, que inventa nomes compridos (cardapio-6d8f89b786-88dn9) porque ele cria e recria pods o tempo todo. Pod solto tem nome fixo porque ninguém vai recriá-lo por você: se ele morrer, morreu.

4. O mesmo pod, agora em YAML

O kubectl run é ótimo para um teste rápido, mas não serve para guardar a receita. O jeito de verdade é escrever o manifesto — um arquivo de texto que descreve o pod inteiro — e entregá-lo com kubectl apply -f. A caixa abaixo tem o manifesto completo de um pod. Rode e veja o que o cluster responde.

Mude a imagem para cardapio:1.0 e acrescente a etiqueta tier: web embaixo de labels. Depois rode.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
  labels:
    app: cardapio
spec:
  containers:
    - name: web
      image: nginx:1.29
      ports:
        - containerPort: 8080
pod/cardapio created

NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          2m

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
  labels:
    app: cardapio
    tier: web
spec:
  containers:
    - name: web
      image: cardapio:1.0
      ports:
        - containerPort: 8080

O painel mostra duas coisas: a linha do apply (pod/cardapio created) e a tabela do get pods com o pod já em Running. As quatro primeiras linhas do manifesto são a identidade — apiVersion, kind, metadata.name e as etiquetas. O resto é o spec, e dentro dele o spec.containers, que é uma lista (por isso o hífen antes de name: web). Cada item da lista é um container com nome, imagem e portas.

Repare no apiVersion: v1. Cada tipo de recurso pertence a um grupo da API, e o grupo faz parte do endereço. Pod é v1 (o grupo antigo, sem nome). Deployment é apps/v1. Job é batch/v1. Se você trocar o apiVersion de um Deployment para v1, o kubectl nem tenta validar: ele responde que não conhece aquele tipo naquela versão. É um dos erros mais comuns de copiar e colar manifesto pela internet.

5. Lendo a tabela do get pods

A tabela parece simples, mas cada coluna conta uma história diferente. NAME é o nome do pod. READY diz quantos containers estão prontos sobre o total — 1/1 é “um de um”, 0/1 é “o container existe mas não está pronto”. STATUS é a fase: Pending (aceito, ainda não rodando), Running, Succeeded (terminou bem), Failed ou Unknown. RESTARTS conta quantas vezes o container já reiniciou, e AGE é o tempo desde a criação.

ColunaO que significaQuando assusta
READYcontainers prontos / total0/1 com Running: o container subiu mas não passa na verificação de prontidão
STATUSfase do podPending por muito tempo: ninguém agendou o pod
RESTARTSquantas vezes o container reiniciounúmero subindo de 5 em 5 minutos: o programa está morrendo e o cluster tentando de novo
AGEtempo de vidapod com AGE de 3 segundos toda vez que você olha: algo está recriando o pod

Uma segunda leitura, com -o wide, mostra IP e nó. Vale comparar com o que a Ana vê no terminal dela, num cluster de verdade (a transcrição é de um cluster local de três nós):

$ kubectl get pods -o wide
NAME                        READY   STATUS    RESTARTS   AGE    IP         NODE          NOMINATED NODE   READINESS GATES
cardapio-5cbfb4c44d-4jjxx   1/1     Running   0          3m2s   10.244.1.5   guia-worker   <none>           <none>
cardapio-5cbfb4c44d-nxfdg   1/1     Running   0          3m2s   10.244.2.4   guia-worker2  <none>           <none>

O IP do pod é interno ao cluster: ninguém na internet chega nele. Quem quiser acessar o site de fora precisa de um Service (Nível 2) — o pod sozinho é uma caixa fechada. E o NODE mostra onde ele caiu: dois pods do mesmo Deployment em nós diferentes é o normal, e é o que dá sobrevivência quando um nó cai.

A saída começa com o cabeçalho Name, Namespace, Priority, Service Account, Node, Start Time, Labels, Status e IP. Depois vem Containers, com a imagem, a porta, o estado (Running, Waiting, Terminated) e o número de reinícios. No fim, Conditions, Volumes, QoS Class e Events.

Sempre que um pod estiver esquisito, leia os events primeiro. Eles dizem o que o cluster tentou fazer e por que desistiu. Este é um evento real de um pod que não coube em nó nenhum, copiado de um cluster de prova:

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  11s   default-scheduler  0/3 nodes are available: 3 Insufficient cpu.
  preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

Traduzindo: três nós foram avaliados, nenhum tinha CPU sobrando para o pedido do pod, e o cluster não achou nada que pudesse ser despejado para abrir espaço. A frase é feia, mas é específica — e é ela que diz se o problema é CPU, memória, etiqueta de nó ou alguma restrição que você mesmo colocou. Sem o describe, você ficaria olhando um Pending sem saber por quê.

7. Quando dá errado: os três primeiros tropeços

Nenhum desses erros é raro; todos acontecem na primeira semana. O primeiro é o nome. O Kubernetes exige nomes em minúsculas, com letras, números e hífen, começando e terminando por letra ou número. Cardapio com C maiúsculo não é “um nome feio”: é inválido, e o cluster recusa o objeto inteiro. A caixa abaixo tem esse erro de propósito — rode e leia a resposta.

Rode do jeito que está e leia o erro. Depois troque o nome para cardapio, rode de novo e veja o pod nascer.

apiVersion: v1
kind: Pod
metadata:
  name: Cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
The Pod "Cardapio" is invalid: metadata.name: Invalid value: "Cardapio": a lowercase RFC 1123 subdomain must consist of lower case alphanumeric characters, '-' or '.', and must start and end with an alphanumeric character (e.g. 'example.com', regex used for validation is '[a-z0-9]([-a-z0-9]*[a-z0-9])?(\.[a-z0-9]([-a-z0-9]*[a-z0-9])?)*')

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0

A mensagem é longa porque o Kubernetes repete a regra inteira: “a lowercase RFC 1123 subdomain must consist of lower case alphanumeric characters, '-' or '.', and must start and end with an alphanumeric character”. Guarde só o começo: nome em minúsculas, hífen no meio, começa e termina com letra ou número. O resto é a regex que o cluster usa, e ela é a mesma para pods, services, configmaps e quase tudo.

O segundo tropeço é a imagem. Se você digitar cardapio:1.0 quando a imagem se chama cardapio:1.0.0, o pod é criado (o objeto existe) mas o container não sobe: o cluster tenta baixar a imagem, falha, e o status fica ErrImagePull e depois ImagePullBackOff — “vou tentar de novo, com espera crescente”. O describe mostra o motivo exato, e é sempre uma destas três coisas: o nome está errado, a imagem é privada e falta credencial, ou o registro está fora do ar.

O terceiro é o pod que não agenda. Acontece quando o pod pede mais recurso do que qualquer nó tem, ou quando você prende o pod a uma etiqueta de nó que não existe, ou quando o nó tem uma restrição (taint) que o pod não aceita. O sintoma é sempre o mesmo: STATUS em Pending, READY em 0/1, e um evento FailedScheduling explicando o motivo. A caixa abaixo reproduz o caso do recurso grande demais — repare que o pod existe, mas nunca sai do lugar.

Rode. Depois reduza o pedido de CPU para 500m e rode de novo: o pod passa a Running.

apiVersion: v1
kind: Pod
metadata:
  name: forno
spec:
  containers:
    - name: forno
      image: cardapio:1.0
      resources:
        requests:
          cpu: "64"
pod/forno created

NAME    READY   STATUS    RESTARTS   AGE
forno   0/1     Pending   0          5m

apiVersion: v1
kind: Pod
metadata:
  name: forno
spec:
  containers:
    - name: forno
      image: cardapio:1.0
      resources:
        requests:
          cpu: "500m"

O painel mostra Pending e o cluster explica o motivo no evento. 64 em CPU quer dizer 64 núcleos — muito mais do que qualquer nó de teste tem. 500m é meio núcleo (m = milésimo). Esse é o tipo de número que parece detalhe e decide se o pod sobe.

8. O que a caixa faz (e o que ela não faz)

Vale ser honesto sobre o painel, porque o resto do guia depende dele. O manifesto que você escreve é lido pelo mesmo interpretador de YAML do ecossistema Node, validado com as mensagens do API server de verdade (as frases foram conferidas contra um cluster real, uma a uma) e aplicado num cluster simulado: nós com capacidade, agendador, controladores que criam e vigiam pods, serviços que descobrem endpoints. A resposta que aparece é a que o kubectl daria naquele cluster — mesmo formato de tabela, mesmo texto de erro, mesmos campos no -o yaml.

O que não existe ali é o kubelet, o pedaço que roda o container de fato. Por isso o painel não simula “imagem não encontrada” nem “programa que morre no boot”: esses estados aparecem nas aulas como transcrições de um cluster real, e o texto diz quando é transcrição. A regra é simples: o que é cálculo (validar, agendar, criar pods, casar etiquetas, calcular endpoints) o motor faz; o que depende de rodar o container vem de fora, identificado.

9. Cenários do dia a dia

Cenário 1: o pod nasce, morre e nasce de novo com outro nome

A Ana criou um pod solto, e alguém apagou o container por dentro (um processo que saiu). O restartPolicy padrão é Always, então o kubelet reinicia o container dentro do mesmo pod — o nome não muda, o RESTARTS sobe. Já se ela apagar o pod inteiro, ninguém recria: pod solto não tem dono. Quem recria é o Deployment, e por isso o nome dele é comprido e o do pod solto é curto.

Cenário 2: dois containers no mesmo pod

O time dela pôs um segundo container no pod para exportar métricas. Os dois compartilham o mesmo IP, e conversam por localhost. Isso funciona e é comum (o padrão “sidecar”), mas tem consequência: se um dos containers falhar, o pod inteiro é considerado não pronto, e o Service para de mandar tráfego para ele. Container no mesmo pod é casamento, não coleguismo.

Cenário 3: o pod que reinicia sozinho toda hora

O RESTARTS subindo e o STATUS em CrashLoopBackOff querem dizer que o programa está morrendo no boot e o cluster tentando de novo com espera crescente. O caminho é kubectl logs (mensagem do programa) e depois kubectl describe (o evento com o código de saída). Nove entre dez vezes é configuração faltando — uma variável de ambiente, um arquivo que não foi montado, uma porta ocupada.

11. Resumo

Pod é a unidade do cluster: um ou mais containers que compartilham rede e ciclo de vida. Você cria com kubectl run (rápido, descartável) ou com um manifesto YAML entregue por kubectl apply -f (o jeito que se guarda). O manifesto tem apiVersion, kind, metadata e spec; o status é a resposta do cluster.

A tabela do get pods é o resumo — READY, STATUS, RESTARTS e AGE — e o describe é o raio-x, com os eventos no fim. Pod em Pending é falta de lugar; 0/1 em Running é falta de prontidão; RESTARTS subindo é programa morrendo. Nome inválido o cluster recusa na hora, com a regra inteira na mensagem.

Duas coisas para levar: pod solto não é recriado por ninguém, e é por isso que o dia a dia usa Deployment; e o pod, sozinho, não é alcançável de fora — quem faz essa ponte é o Service. Na próxima aula a Ana aprende a olhar o cluster inteiro com kubectl get em todos os recursos, e a partir daí entra no YAML com calma.

Para lembrar
  • kubectl run nome --image=imagem cria um pod; kubectl apply -f aplica um manifesto.
  • Nome em minúsculas, com hífen no meio: cardapio sim, Cardapio não.
  • Pending = não achou lugar; Running com 0/1 = não está pronto; RESTARTS subindo = o programa está morrendo.
  • kubectl describe pod nome e leia os events antes de mexer em qualquer coisa.
