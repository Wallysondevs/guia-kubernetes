Secret na prática

O site da padaria não precisa de uma senha: precisa de três credenciais, com formatos diferentes e destinos diferentes. A senha do banco, que o driver só aceita se estiver num arquivo; o token do gateway de pagamento, que é uma variável de ambiente; e a chave do serviço de e-mail, que é uma linha de texto. Nesta aula a Ana monta o mapa de credenciais de um sistema de verdade — um objeto por dono, o formato certo para cada uso, e um punhado de hábitos para o segredo não vazar no caminho.

Você vai aprender
  • Decidir, para cada credencial, se ela vira arquivo ou variável de ambiente.
  • Montar um Secret como arquivo, com items e readOnly, expondo só o necessário.
  • Misturar ConfigMap e Secret no mesmo container — endereço de um, credencial de outro.
  • Usar dois envFrom no mesmo pod e entender a precedência.
  • Gerar e conferir os valores sem deixá-los no histórico nem no repositório.
  • O que fazer quando a credencial muda: a rotação passo a passo.

1. A cena: três credenciais, três formatos

O sistema da padaria tem três dependências externas, e cada uma pede a credencial de um jeito. O banco de dados usa um driver que lê um arquivo de credencial — a senha precisa existir como arquivo no disco, com permissão restrita. O gateway de pagamento recebe o token numa variável de ambiente, no formato GATEWAY_TOKEN. E o serviço de e-mail usa uma chave de API de uma linha, que o programa lê do ambiente também.

Na primeira versão, a Ana resolveu tudo do jeito fácil: senha e token escritos no manifesto do pod, e o arquivo de credencial do banco embutido na imagem. Três problemas apareceram em uma semana. O primeiro: o manifesto estava no repositório, com a senha. O segundo: a imagem era a mesma em teste e produção, então o arquivo de credencial era o de teste — e o site de produção tentava autenticar no banco errado. O terceiro: quando o token do gateway venceu, ela não sabia em quantos lugares ele estava.

A arrumação é o que esta aula faz. Três credenciais, três destinos, cada uma no objeto certo: a senha do banco num Secret montado como arquivo, o token e a chave como variáveis vindas de Secrets, e todos os parâmetros não sensíveis (endereço do banco, porta, nome da fila) num ConfigMap. O pod recebe tudo, e o manifesto não tem nenhum valor secreto.

2. O mapa de credenciais de um sistema

Antes de escrever YAML, vale montar a tabela mental — o mesmo raciocínio da aula de Secret. Para cada credencial, três perguntas: quem é o dono (a qual serviço ela pertence), como o programa a lê (arquivo ou variável) e com que frequência ela muda. As respostas decidem o nome do objeto, a forma de entrega e o processo de rotação.

credencial
O par de identificação e prova: usuário e senha, conta e token, certificado e chave. Cada credencial pertence a um serviço.
dono
O serviço a que a credencial dá acesso. É o que define o nome do Secret: banco, gateway, email.
secretKeyRef
A referência a uma chave de Secret, usada no env quando o programa lê uma variável.
secret (volume)
A montagem de um Secret como arquivos. Usa secretName no volume e items para escolher as chaves.
defaultMode
A permissão dos arquivos montados, em octal. O padrão é 0644; para credencial, algo como 0400 é mais adequado.

A regra de bolso que a Ana adotou: se o programa abre um arquivo, monte como arquivo; se ele lê uma variável, entregue como variável. Parece óbvio e quase sempre é ignorado — gente que monta arquivo para programa que só lê variável acaba com um arquivo inútil; gente que transforma arquivo em variável acaba com uma linha de duzentos caracteres, do mesmo jeito que o JSON do cardápio.

E o dono importa mais do que parece. Um Secret por serviço (banco, gateway, email) permite dar a cada um a sua rotação, a sua permissão e o seu histórico. Um Secret gigante chamado credenciais obriga a trocar tudo junto e a dar acesso a tudo junto — o oposto de segurança.

3. A senha do banco como arquivo

O driver do banco quer o arquivo. A caixa começa com o Secret inteiro montado em /etc/credenciais: o container vê usuario e senha, quando precisaria ver só a senha — e com permissão restrita, porque um arquivo de credencial legível por todo mundo dentro do container é uma porta aberta a mais.

Monte apenas a chave senha, no arquivo senha, e marque a montagem como somente leitura. A pasta /etc/credenciais continua a mesma.

apiVersion: v1
kind: Secret
metadata:
  name: banco
type: Opaque
data:
  usuario: YW5h
  senha: czNuaDQ=
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: cardapio:1.0
      volumeMounts:
        - name: credenciais
          mountPath: /etc/credenciais
  volumes:
    - name: credenciais
      secret:
        secretName: banco
secret/banco created
pod/web created

        items:

O painel mostra os dois objetos criados e o pod em Running. O que a meta confere é a ligação: o volume aponta para o Secret certo, o items escolhe a chave senha e a montagem é somente leitura. O efeito dentro do container é o mesmo do ConfigMap como volume — a chave vira o arquivo /etc/credenciais/senha —, com uma diferença de conteúdo: o valor é decodificado. O arquivo tem s3nh4, não czNuaDQ=.

Esse é o ponto que mais confunde: o base64 existe no objeto guardado, não no arquivo entregue. O kubelet decodifica na hora de montar, e o programa vê o texto. O mesmo vale para a variável de ambiente: o processo recebe o valor decodificado. Base64 é formato de armazenamento, não camada de uso.

Sobre a permissão: readOnly: true impede escrever no arquivo, e defaultMode cuida do modo. Para credencial, 0400 é o valor comum — só o dono lê. Vale lembrar que isso protege contra acidente dentro do container, não contra quem tem acesso ao cluster: quem pode ler o Secret lê o valor de qualquer jeito.

4. Endereço no ConfigMap, senha no Secret

A segunda credencial vive ao lado de parâmetros que não são segredo, e essa mistura é o teste de maturidade de quem está montando a configuração. O banco precisa de quatro valores: DB_HOST, DB_PORTA, DB_USUARIO e DB_SENHA. Os dois primeiros são públicos; os dois últimos, não. Misturar tudo num Secret é a preguiça que depois cobra caro: mudar o endereço passa a exigir mexer num objeto sensível.

O pod pega o host do lugar errado e a senha de um ConfigMap. Faça o DB_HOST vir do ConfigMap banco-config (chave host) e o DB_SENHA vir do Secret banco (chave senha).

apiVersion: v1
kind: ConfigMap
metadata:
  name: banco-config
data:
  host: db.loja.test
  porta: "5432"
---
apiVersion: v1
kind: Secret
metadata:
  name: banco
type: Opaque
data:
  usuario: YW5h
  senha: czNuaDQ=
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: cardapio:1.0
      env:
        - name: DB_HOST
          value: db.loja.test
        - name: DB_SENHA
          valueFrom:
            configMapKeyRef:
              name: banco
              key: senha

O painel mostra os três objetos criados e o pod em Running. O manifesto ficou maior e mais chato — e é exatamente o que se quer: qualquer pessoa que abrir o arquivo entende de onde vem cada valor sem ver nenhum segredo. O DB_SENHA aponta para o Secret; o DB_HOST, para o ConfigMap. Trocar o endereço do banco é editar um ConfigMap com dois campos públicos; trocar a senha é outra operação, com outro dono.

Um detalhe de ordem: no env, a lista é avaliada na ordem em que aparece. Se você usar uma variável para montar outra — DB_URL com $(DB_HOST) dentro —, a variável referenciada precisa vir antes. O Kubernetes expande as referências $(NOME) na ordem da lista, e uma referência a variável que ainda não foi definida fica literal no valor. É um detalhe pequeno que aparece nos diagnósticos mais confusos.

5. Dois envFrom no mesmo pod

Quando o pod precisa de muitos valores dos dois tipos, listar um por um vira uma lista enorme. A saída é combinar dois envFrom: um do Secret, com as credenciais, e um do ConfigMap, com o resto. O resultado é o pod recebendo duas famílias de variáveis, cada uma da fonte certa.

O pod só recebe as credenciais. Acrescente o envFrom do ConfigMap cardapio, mantendo o do Secret banco na primeira posição.

apiVersion: v1
kind: ConfigMap
metadata:
  name: cardapio
data:
  moeda: BRL
  horario: 6h as 19h
---
apiVersion: v1
kind: Secret
metadata:
  name: banco
type: Opaque
data:
  usuario: YW5h
  senha: czNuaDQ=
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: cardapio:1.0
      envFrom:
        - secretRef:
            name: banco

O painel mostra os três objetos e o pod em Running. Agora o container recebe usuario e senha (do Secret) e moeda e horario (do ConfigMap), todas com o nome da chave. Repare no problema que isso cria: usuario e senha em minúsculas são nomes ruins para variável de ambiente — a convenção é maiúscula, e muitos programas são rígidos.

É por isso que, em sistema de verdade, envFrom com Secret costuma vir acompanhado de prefix, ou é substituído por env explícito com secretKeyRef. O prefix resolve o caso em que os nomes podem ser prefixados: prefix: BANCO_ gera BANCO_usuario e BANCO_senha. Continua feio por causa da caixa, e continua entregando todas as chaves ao processo — inclusive as que ele não usa.

ana@notebook:~$ kubectl create secret generic banco --from-literal=usuario=ana --from-literal=senha=s3nh4
secret/banco created
ana@notebook:~$ kubectl create secret generic gateway --from-literal=token=tok_live_9f2
secret/gateway created
ana@notebook:~$ kubectl get secrets
NAME      DATA   AGE
banco     2      5m
gateway   1      4m

A transcrição acima é a resposta do painel para a criação das duas credenciais da padaria: a do banco, com usuário e senha, e a do gateway, com o token. Repare que uma delas pede duas chaves e a outra pede uma — e que cada uma tem o seu nome, o seu dono e o seu ciclo de vida. É esse desenho que faz a rotação do token não mexer na senha do banco.

6. Gerando e conferindo os valores

O trabalho de criar Secret é, na maior parte, trabalho de gerar base64 e não errar na cópia. Três hábitos economizam horas. O primeiro: gere o valor com o comando, nunca à mão — printf sem quebra de linha, base64 e pronto. O segundo: confira o resultado com a volta — base64 -d — antes de aplicar. O terceiro: use --dry-run=client -o yaml para ver o manifesto que o kubectl create produziria e colar dali, em vez de digitar.

ana@notebook:~$ printf 'tok_live_9f2' | base64
dG9rX2xpdmVfOWYy
ana@notebook:~$ printf 's3nh4' | base64
czNuaDQ=
ana@notebook:~$ printf 'czNuaDQ=' | base64 -d
s3nh4

Repare na diferença entre criar pelo terminal e criar por manifesto. O kubectl create secret generic recebe o valor em texto e converte; o manifesto exige o base64 já pronto. Para produção, o caminho mais comum é gerar o manifesto em um lugar seguro (a máquina de quem tem a credencial) e aplicar de lá, sem que o arquivo passe pelo repositório. Para o dia a dia de teste, o comando direto resolve.

Existe também o --from-file, que lê o valor de um arquivo — útil quando a credencial já está num arquivo (uma chave privada, um certificado). O nome da chave vira o nome do arquivo, e o conteúdo vira o valor. É o caminho natural para o caso do driver do banco desta aula: a Ana gera o arquivo local, cria o Secret a partir dele e apaga o arquivo do notebook depois.

Para conferir o que ficou guardado, use kubectl describe secret banco: ele mostra as chaves e o tamanho de cada valor, sem o conteúdo. Se precisar mesmo ver o valor (e isso deve ser raro), o comando é kubectl get secret banco -o yaml, que devolve o base64 — e, portanto, deve ser evitado em terminal compartilhado, em gravação de sessão e em qualquer lugar onde o histórico fique.

7. Onde cada credencial deve morar

A pergunta “onde eu guardo isso” tem uma resposta por tipo de valor. A tabela abaixo é a que a Ana colou no runbook da padaria, e vale para quase todo sistema.

ValorOnde moraComo chega ao pod
endereço, porta, nome da filaConfigMapenvFrom ou configMapKeyRef
senha, token, chave de APISecret (um por serviço)secretKeyRef ou envFrom
arquivo de credencial, certificado, chave privadaSecretvolume com secretName e items
dezenas de valores de configuraçãoConfigMap com um arquivo e volumevolume em /config

E os lugares onde nada disso deve aparecer: o repositório (nem em branch, nem em commit apagado depois), o manifesto do pod, o log da aplicação, o histórico do shell sem cuidado, e o print de tela no chat do time. Nenhum desses é teoria: os vazamentos reais quase sempre vêm de um desses cinco, e quase sempre por alguém com pressa numa sexta-feira.

Uma nota sobre o cluster: o conteúdo dos Secrets fica no banco de dados do cluster (o etcd). Em cluster de produção, esse banco deve ter criptografia em repouso ligada — é uma configuração do próprio cluster, feita uma vez, e não muda nada no seu manifesto. Sem ela, quem tem acesso ao arquivo do etcd lê todos os segredos, com ou sem RBAC.

8. Rotação: o dia em que a credencial muda

Credencial muda. Token vence, senha é trocada depois de um desligamento, certificado expira. O processo é sempre o mesmo, e vale escrevê-lo antes de precisar dele: gerar o valor novo, atualizar o Secret (ou criar um novo e apontar para ele), reiniciar quem usa, conferir que subiu com o valor novo, e apagar o valor antigo no serviço de origem.

O passo que as pessoas esquecem é o terceiro. O valor é lido no start do container: atualizar o Secret não atualiza o processo que já está rodando. Um Deployment precisa de um kubectl rollout restart para nascer com o valor novo — e é por isso que rotacionar credencial e reiniciar o serviço são a mesma tarefa, na prática. A última aula deste grupo trata exatamente desse momento.

9. Cenários do dia a dia

Cenário 1: o arquivo de credencial que veio da imagem

O driver do banco procurava ~/.pgpass, e a imagem trazia um arquivo de exemplo no lugar. Em teste funcionava; em produção, o programa autenticava com a credencial errada e o log dizia “permissão negada”, que parece problema de rede. A correção foi montar o Secret em /etc/credenciais, apontar o driver para lá por variável e remover o arquivo da imagem. Configuração não volta para a imagem.

Cenário 2: dois times, um Secret

O time do site e o do aplicativo de entregas usavam o mesmo Secret credenciais, com a senha do banco e o token do gateway. Quando o gateway trocou o token, os dois times precisaram coordenar a atualização — e um deles esqueceu. Separar em banco e gateway, cada um com o seu dono, fez o próximo vencimento passar sem reunião.

Cenário 3: a senha no log de boot

O programa imprimia a configuração inteira no boot “para facilitar o diagnóstico” — incluindo a senha, que chegava por variável de ambiente. O log ia para o agregador e ficava retido por trinta dias, legível por qualquer pessoa do time. A correção foi mascarar os campos sensíveis na hora de imprimir. Vale a regra: o log é o lugar mais fácil de vazar um segredo sem perceber.

Exercício: a montagem só da senha

Complete o volume para montar apenas a chave senha do Secret banco:

volumes: - name: credenciais secret: : banco items: - key: senha path: senha

Dica: no volume de Secret, o campo do nome é secretName (com “Name” no meio); no env, a referência é secretKeyRef.

11. Resumo

Um sistema de verdade tem várias credenciais, e cada uma merece o seu objeto: um Secret por serviço, com nome que diga a que ele dá acesso. O formato de entrega segue o que o programa faz — arquivo para quem abre arquivo, variável para quem lê variável —, e o que não é segredo fica no ConfigMap, mesmo que apareça na mesma linha do código.

Montar um Secret como arquivo é igual a montar um ConfigMap: volume com secretName, volumeMounts com mountPath, e items para expor só o necessário. O valor chega decodificado ao container; o base64 é só o formato de armazenamento. readOnly e defaultMode restringem o arquivo, e dois envFrom no mesmo pod combinam as duas famílias de variáveis.

E a rotina: gerar com printf | base64, conferir com base64 -d, criar pelo terminal quando o valor não deve passar por arquivo, conferir com describe, e — quando a credencial muda — lembrar que o processo que já está rodando continua com a antiga até reiniciar. É esse último passo que a próxima aula junta com o ConfigMap, num só roteiro.

Para lembrar
  • Um Secret por serviço: banco, gateway, email.
  • Arquivo para quem lê arquivo; variável para quem lê variável.
  • O container recebe o valor decodificado; base64 é o formato guardado.
  • items + readOnly expõem só o necessário.
  • Dois envFrom no mesmo pod funcionam; evite a mesma chave nas duas fontes.
  • Atualizou a credencial? Reinicie quem usa, senão o processo fica com a antiga.
