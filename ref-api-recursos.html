Recursos da API

A Ana já reparou que o apiVersion do Pod é v1 e o do Deployment é apps/v1, mas nunca entendeu por quê. A resposta é simples: o Kubernetes não é uma API só, são vários grupos de recursos publicados no mesmo endereço. Esta página é o mapa desses grupos — o que é apps, o que é batch, o que é networking.k8s.io —, com o jeito de descobrir tudo isso no seu próprio cluster em vez de decorar.

Como usar esta página
  • A tabela 1 é por grupo; a tabela 2 é por tipo. Use a que estiver mais perto da sua dúvida.
  • A seção 6 é a que resolve na prática: dois comandos que respondem “qual é a versão?” e “qual é o campo?”.
  • O que é “namespaced” muda o comando que você digita — a seção 5 explica com exemplos.

1. Para que serve esta página (e o que ela não cobre)

Esta é a folha de consulta da superfície da API: os grupos, as versões, os escopos e os apelidos. Ela responde a três perguntas que aparecem em quase todo manifesto que não sobe: qual é o apiVersion deste tipo, este tipo vive em namespace ou no cluster inteiro, e como eu descubro isso no meu próprio cluster quando esqueço.

Ela não ensina o que cada campo de cada recurso faz — para isso existem as páginas Pods, Deployments e Services e Ingress. Também não é uma lista completa: o Kubernetes tem mais de cinquenta tipos, e o seu cluster provavelmente tem outros que alguém instalou. Por isso o fim desta página insiste em dois comandos: kubectl api-resources e kubectl explain.

Por que a API é dividida assim? Porque cada grupo evolui no seu ritmo. O núcleo (v1) está congelado há anos: mudar o formato de um Pod quebraria todos os manifestos do mundo. Já os grupos com domínio no nome podem nascer, amadurecer e ganhar versões novas sem tocar no núcleo — o apps/v1 substituiu extensions/v1beta1, e o autoscaling/v2 convive com o v1 até hoje. Essa separação é o que permite ao Kubernetes mudar sem parar o mundo.

Uma ideia que ajuda a entender o resto: pensa no Kubernetes como uma biblioteca com várias prateleiras. Cada prateleira é um grupo (apps, batch, networking.k8s.io), cada grupo tem uma ou mais versões (v1, v2) e cada versão publica tipos (Deployment, Job, Ingress). O endereço completo de um tipo é a combinação grupo/versão/tipo — e é isso que o apiVersion mais o kind escrevem no manifesto.

2. O essencial em 10 linhas

  • O núcleo da API usa apiVersion: v1 e não tem grupo no nome.
  • Todo o resto tem grupo: apps/v1, batch/v1, networking.k8s.io/v1.
  • apiVersion aceita v1 ou grupo/versão; nunca grupo sozinho.
  • kind é o tipo, com maiúscula; o plural em minúsculas é o que você digita no get.
  • Quase tudo vive num namespace; alguns tipos vivem no cluster inteiro.
  • Namespaced: Pod, Deployment, Service, ConfigMap, Secret, Job, PVC, Ingress, HPA.
  • Cluster: Namespace, Node, PersistentVolume, StorageClass, ClusterRole, CRD.
  • kubectl api-resources lista nome, apelido, versão e escopo de tudo.
  • kubectl explain TIPO mostra a versão e os campos daquele tipo.
  • Recurso customizado (CRD) também aparece nos dois comandos — a API é extensível.

Sobre a palavra beta: uma versão v1beta1 é uma promessa mais fraca. Ela funciona, é usada em produção por muita gente, mas pode mudar de forma ou ser removida numa versão futura do Kubernetes — e quando é removida, os manifestos que a usavam param de aplicar com no matches for kind. Uma versão v1 não muda assim. Se você está começando um projeto hoje, prefira sempre a versão estável que o api-resources mostra.

Duas consequências práticas dessas dez linhas. A primeira: quando o manifesto é recusado com no matches for kind, o problema está na combinação grupo/versão/tipo — e o api-resources dá a resposta em uma tela. A segunda: quando você cria um objeto cluster-scoped, o -n não faz diferença nenhuma; quando cria um namespaced sem -n, ele vai para default.

Uma distinção de vocabulário que o guia usa o tempo todo: recurso é o tipo publicado pela API (deployments), objeto é uma instância daquele tipo (o Deployment cardapio). O api-resources lista recursos; o get lista objetos. Quando alguém diz “o recurso não existe”, quase sempre quer dizer que o tipo não está registrado no cluster — e não que o objeto sumiu.

E uma armadilha de leitura: o kind do manifesto é singular e maiúsculo (Deployment), mas o comando aceita singular, plural e apelido (deployment, deployments, deploy). São três grafias para a mesma coisa, e nenhuma delas funciona no lugar da outra: no kind, só a primeira.

3. Anatomia de um nome de API

grupo
A prateleira: apps, batch, networking.k8s.io, rbac.authorization.k8s.io. O núcleo não tem grupo e é chamado de core.
versão
A edição daquela prateleira: v1, v2, v1beta1. Versões beta podem mudar ou desaparecer; v1 é estável.
apiVersion
O que você escreve no manifesto: v1 para o núcleo e grupo/versão para o resto. É a junção dos dois campos acima.
kind
O tipo, em CamelCase: Deployment, ConfigMap, Job. É o que decide qual spec é válido.
plural e apelido
Como o kubectl chama o tipo no comando: deployments e deploy, services e svc. É o que o api-resources mostra nas duas primeiras colunas.
escopo
Namespaced (vive dentro de um namespace) ou cluster-scoped (existe no cluster inteiro). Muda o -n e muda quem pode criar.

Juntando as peças: apiVersion: apps/v1 + kind: Deployment quer dizer “prateleira apps, versão v1, tipo Deployment”. No endereço HTTP da API isso vira /apis/apps/v1/deployments; no núcleo, sem grupo, vira /api/v1/pods — a diferença do /apis com “s” é um detalhe do desenho da API, que você vê quando usa kubectl get --raw.

Uma curiosidade que explica os nomes: só os grupos do núcleo e os primeiros grupos ganharam nome curto (apps, batch). Os grupos criados depois usaram o domínio do projeto (networking.k8s.io, rbac.authorization.k8s.io) para não colidir com nada. É por isso que a coluna APIVERSION tem linhas de dois formatos, e é por isso que apiVersion: networking/v1 não existe: o nome do grupo é o domínio inteiro, não a primeira palavra.

Repare que nem todo tipo tem apelido. jobs não tem, e isso não é esquecimento: apelido é uma conveniência, e só existe quando alguém pediu. Se você digitar kubectl get job, o kubectl aceita o singular; se digitar kubectl get j, ele responde que não conhece o tipo — o que ensina a diferença entre “nome do recurso” e “apelido do recurso”.

5. Namespaced e cluster-scoped

Essa distinção parece burocracia e é o motivo de metade dos comandos que “não acham nada”. Um objeto namespaced existe dentro de um namespace, como um caderno dentro de uma gaveta: o mesmo nome pode existir em duas gavetas, e o -n escolhe a gaveta. Um objeto cluster-scoped existe no cluster inteiro, como a porta da frente: só existe uma, e o -n não muda nada.

RecursoEscopoPor quê
Pod, Deployment, Service, ConfigMap, Secretnamespacedé a carga da padaria, e cada time tem a sua
Job, CronJob, PVC, Ingress, HPAnamespacedpertencem a uma aplicação, num ambiente
Role, RoleBindingnamespacedpermissão válida dentro de um namespace
Namespaceclusteré a própria gaveta; não cabe dentro de outra
Nodeclustera máquina não pertence a um time
PersistentVolume, StorageClassclustero disco é do cluster; o PVC é que é do namespace
ClusterRole, ClusterRoleBindingclusterpermissão válida em todos os namespaces
CustomResourceDefinitionclustero tipo novo vale para o cluster inteiro

Uma pista para não decorar: se o tipo representa “o que roda” ou “o que configura uma aplicação”, ele é namespaced; se representa “o que sustenta o cluster” ou “o que vale para todos”, é cluster-scoped. A regra tem exceção (o PersistentVolume é o caso clássico), mas acerta na maioria das dúvidas.

Na prática, o escopo decide três coisas. Primeiro, o comando: kubectl get pods -n padaria faz sentido; kubectl get nodes -n padaria aceita a flag e a ignora. Segundo, o nome: você pode ter um Service cardapio em default e outro em padaria, mas não pode ter dois Nodes com o mesmo nome. Terceiro, a permissão: um Role só vale dentro do namespace onde foi criado; para valer em todos, é ClusterRole.

Um exemplo do dia a dia fecha a ideia. A Ana tem o namespace default (onde ela testa) e o padaria (onde o site roda). O Service cardapio existe nos dois, com o mesmo nome e configurações diferentes: um aponta para a versão de teste, o outro para a de produção. Já o Node guia-worker existe uma vez só — não faz sentido ter “o mesmo nó” em dois namespaces, porque o nó é a máquina, e a máquina é do cluster.

Há um caso que confunde de propósito: o PersistentVolume é cluster-scoped e o PersistentVolumeClaim é namespaced. O PV é o disco em si (do cluster); o PVC é o pedido de um time por um disco (do namespace). Quando um PVC encontra um PV, os dois se ligam por um vínculo que atravessa o escopo — e é por isso que apagar o namespace não apaga o PV automaticamente em todas as configurações.

Vale aprender a ler as colunas do api-resources em ordem, porque cada uma responde uma pergunta. NAME é o plural que você digita no comando; SHORTNAMES traz os apelidos separados por vírgula (vazio quando não há); APIVERSION é o valor que vai no manifesto; NAMESPACED é true ou false; e KIND é o tipo com maiúscula, exatamente como você escreve no kind.

Uma última utilidade do explain: ele aceita o caminho inteiro com índices de lista, como deployment.spec.template.spec.containers, e costuma funcionar mesmo quando o campo é novo e não está em tutorial nenhum. É a documentação que viaja com o cluster.

Duas leituras rápidas dessas saídas. No api-resources, a coluna APIVERSION é exatamente o que vai no manifesto — copie daí e não erre. No explain, o campo aparece com o tipo entre sinais de menor e maior: <string> é texto, <[]IngressRule> é lista de objetos (o [] é o sinal da lista), e <int32> é número inteiro.

7. Duas coisas para praticar agora

A primeira caixa é a sessão de descoberta: listar os recursos e abrir um tipo. A segunda é o conserto mais comum de apiVersion quando o assunto é rede — o Ingress copiado de um tutorial antigo, com uma versão que o cluster não publica mais.

Rode a sessão de descoberta: liste os recursos da API e abra o tipo Deployment. O painel tem de mostrar a versão apps/v1 e a coluna NAMESPACED.

kubectl get pods

No painel, a segunda caixa mostra a tabela do get ingress depois do conserto: nome, classe, host, endereço, portas e idade. A coluna CLASS vem <none> porque o manifesto não declara ingressClassName, e a coluna HOSTS traz loja.test, o host que você escreveu na regra. Num cluster de verdade, sem um controller de Ingress instalado, a coluna ADDRESS ficaria vazia — o endereço é do controller, não do objeto.

Sobre o painel: api-resources funciona inteiro e é a melhor forma de conferir as tabelas desta página. O explain responde para pod, deployment e deployment.spec.strategy; nos outros campos, ele devolve o aviso de que o campo não existe no motor — é quando a transcrição acima vira a sua referência. Nada disso muda a lição: quem manda é o cluster, e os dois comandos são a consulta oficial.

Duas coisas para observar. No erro da segunda caixa aparece a frase ensure CRDs are installed first: ela é a dica padrão do kubectl quando não acha o tipo, e no nosso caso não há CRD nenhuma faltando — só a versão trocada. E, mesmo com o Ingress criado, não há tráfego de verdade no painel: a rede é modelo (quem descreve o roteamento é o manifesto, não o tráfego). O mesmo vale para o ADDRESS que aparece na tabela: é o endereço de documentação 192.0.2.10.

Resumo

A API do Kubernetes é organizada em grupos: o núcleo (v1, sem grupo no nome) e os grupos com domínio (apps/v1, batch/v1, networking.k8s.io/v1, rbac.authorization.k8s.io/v1, autoscaling/v2, storage.k8s.io/v1). O apiVersion do manifesto é a junção grupo + versão, e o kind é o tipo publicado ali.

Quase tudo vive dentro de um namespace (Pod, Deployment, Service, ConfigMap, Secret, Job, PVC, Ingress, HPA); alguns tipos vivem no cluster inteiro (Namespace, Node, PV, StorageClass, ClusterRole, CRD). O escopo muda o efeito do -n, a unicidade do nome e o alcance da permissão. Para descobrir tudo isso no seu próprio cluster: kubectl api-resources lista nome, apelido, versão e escopo, e kubectl explain TIPO abre os campos do tipo — os dois respondem offline e valem mais do que qualquer tabela fixa.
