CI/CD

A Ana mudou uma linha do cardápio às nove da manhã e, às nove e nove, o site novo estava no ar — sem ela abrir um terminal. No meio do caminho, uma máquina baixou o código, rodou os testes, construiu uma imagem, empurrou para o registro e avisou o cluster. Nesta aula você acompanha esse caminho estação por estação, entende por que latest é uma armadilha, vê onde o kubectl deve (e não deve) aparecer e descobre o que um Job de migração tem a ver com tudo isso.

Você vai aprender
  • O que é CI e o que é CD, sem sopa de letrinhas.
  • As cinco estações do caminho: commit, build, teste, imagem e deploy.
  • Por que tag imutável importa e por que latest engana o rollout.
  • Como o pipeline publica a imagem e como o cluster baixa dela (pull secret).
  • Onde o kubectl entra — e por que muitos times o tiram do pipeline.
  • Como rodar uma migração antes do deploy, com Job e backoffLimit.

1. A cena: o commit que virou site no ar

Antes, cada deploy da padaria era um ritual. A Ana abria o terminal, rodava docker build, esperava, fazia docker push, editava o YAML na mão, aplicava, lembrava de conferir os pods, e torcia. Levava quarenta minutos e, metade das vezes, ela descobria no meio que tinha esquecido de mudar a tag da imagem no manifesto.

Agora o ritual virou um pipeline: uma receita que roda sozinha sempre que alguém faz commit. A receita tem estações, e cada estação só começa se a anterior deu certo. Se o teste falha, nada é construído. Se o build falha, nada é publicado. Se a publicação falha, o cluster nem fica sabendo. É essa ordem — e essa teimosia — que transforma “deploy” em algo que não depende de memória humana.

As siglas: CI, integração contínua, é a parte que pega o código e prova que ele funciona (build + testes + imagem). CD é a parte que leva o resultado até o cluster — entrega contínua, quando o último passo espera um clique, ou implantação contínua, quando vai direto. O que separa as duas é só quanta gente precisa concordar no fim.

2. O caminho em cinco estações

Pense numa linha de produção de pão: a massa entra crua numa ponta e sai embalada na outra, e cada estação faz uma coisa só. Se a massa não cresceu, ninguém embala — a esteira para. O pipeline é isso, com uma vantagem: cada estação deixa um registro do que fez, e a caixa que sai no fim tem um número que diz exatamente de qual fornada ela veio.

Na prática, as cinco estações são estas. Commit: alguém faz push num ramo e o servidor de CI acorda. Build: baixa o código, instala dependências e compila (ou, em linguagem interpretada, só valida que empacota). Teste: roda os testes automatizados. Imagem: constrói a imagem do container e a publica num registro, com uma tag que identifica aquela fornada. Deploy: atualiza o manifesto no repositório de configuração (ou aplica direto) e o cluster passa a rodar a imagem nova.

pipeline
A receita executada pelo servidor de CI: uma sequência de passos, em ordem, que para no primeiro erro.
build
Transformar código-fonte no que vai rodar. No caso do Kubernetes, o resultado final é uma imagem.
imagem
O pacote com o programa e suas dependências. Tem nome e tag: registry.loja.test/padaria/cardapio:2.4.0.
registro
O armário de imagens (Docker Hub, GHCR, Harbor...). O cluster baixa daqui, não do seu computador.
tag imutável
Uma tag que aponta para uma imagem só, para sempre — normalmente o número da versão ou o hash do commit.
artefato
O que uma estação produz e a seguinte consome: o binário, o relatório de testes, a imagem.

Repare que o Kubernetes entra só no fim. Ele não constrói, não testa e não publica: ele baixa uma imagem que já existe e a mantém rodando. Todo o trabalho de CI acontece fora do cluster — e é bom que seja assim, porque um build dentro do cluster de produção disputa CPU com o site da padaria.

3. Tag imutável: por que latest sabota o rollout

A tag é o sobrenome da imagem. cardapio:2.4.0 é uma fornada específica; cardapio:latest é “a fornada mais recente”, o que parece prático e é uma armadilha. O problema: quando você publica uma imagem nova com a mesma tag, o manifesto continua igual. O kubectl apply responde unchanged, o Deployment não vê mudança nenhuma, nenhum pod é recriado, e o cluster continua rodando a imagem antiga que já estava no nó.

Pior: dois nós podem ter imagens diferentes com a mesma tag. Um baixou ontem, outro baixou hoje. Você tem duas versões do site rodando ao mesmo tempo, com o mesmo nome, e o balanceamento manda metade dos clientes para cada uma. Quando o bug aparece, ninguém consegue reproduzir.

A saída é usar tag que nunca se repete: número de versão (2.4.0), data e hora (2026-11-27-1) ou, melhor ainda, o hash do commit (a3f91c2). Com tag imutável, mudar a versão muda o manifesto, o Deployment percebe, o rollout acontece — e o kubectl rollout undo volta para uma imagem que existe de verdade, com o mesmo conteúdo de antes. Se você quiser ser rigoroso ao extremo, pode fixar o digest (cardapio@sha256:...), que é o hash do conteúdo da imagem: aí nem a tag pode mentir.

Um detalhe prático que economiza muita dor: o imagePullPolicy. Com tag fixa, o padrão IfNotPresent aproveita a imagem que já está no nó. Com latest, o Kubernetes assume Always e baixa de novo a cada start — o que só disfarça o problema, porque o manifesto continua sem mudar e o rollout continua não acontecendo.

4. Do build ao registro: credenciais e o pull secret

Publicar imagem exige login no registro. O pipeline recebe uma credencial (um token, guardado no cofre do servidor de CI, nunca no repositório) e faz docker push — ou usa uma ferramenta que constrói sem daemon, como o Kaniko, que roda dentro de um container e é a escolha comum quando o CI também roda em Kubernetes.

Baixar imagem privada também exige credencial, mas do outro lado: quem baixa é o kubelet, no nó, e ele não conhece o cofre do CI. A ponte é um Secret do tipo kubernetes.io/dockerconfigjson, referenciado no pod por imagePullSecrets. Sem ele, o pod fica em ImagePullBackOff com a mensagem unauthorized — o erro clássico de quem publicou a imagem no registro privado e esqueceu de avisar o cluster.

Duas boas práticas que evitam confusão. A primeira: um Secret por registro, com nome claro (registry), criado no namespace do time e não no default. A segunda: quando possível, amarrar o Secret à ServiceAccount do pod (imagePullSecrets na própria conta), para que cada Deployment não precise repetir a referência. As duas funcionam; a segunda é menos repetitiva e por isso menos esquecida.

5. A caixa: o manifesto que o pipeline aplica

A caixa abaixo é o manifesto que o último passo do pipeline entrega ao cluster. Ele tem dois problemas de júnior: a imagem é cardapio:latest, tirada de um registro sem credencial, e o pod não sabe como baixar de um registro privado. Corrija os dois e rode.

As duas linhas de resposta são secret/registry created e deployment.apps/cardapio created, e a tabela mostra 2/2. Note que o painel não tenta baixar a imagem: ele agenda o pod e o considera pronto. Quem baixaria de verdade é o kubelet, no nó — e é por isso que ImagePullBackOff só aparece nas aulas como transcrição, nunca como resultado de uma caixa.

O e30= no Secret é o conteúdo {} codificado em base64: um arquivo de credencial vazio, só para o exemplo ficar válido. Num cluster de verdade, esse campo é o .dockerconfigjson gerado por kubectl create secret docker-registry, com usuário, senha e servidor. Nunca escreva a credencial no YAML que vai para o Git — o assunto está na aula de segredos externos.

6. Onde entra o kubectl (e onde não entra)

Existem dois desenhos de pipeline, e a diferença é quem tem a credencial do cluster. No primeiro, o servidor de CI guarda um kubeconfig com permissão de escrita e roda kubectl apply no fim. No segundo, o CI só publica a imagem e atualiza o manifesto; quem aplica é um controlador dentro do cluster (o Argo CD da aula passada), que lê o repositório.

O primeiro é mais fácil de montar e mais perigoso de manter: a credencial do cluster vive num servidor que qualquer pessoa com acesso ao CI pode usar, e o histórico do que foi aplicado fica espalhado em logs de build. O segundo tira a credencial do CI e deixa um único ponto de aplicação. Em troca, exige o controlador, o repositório de configuração e mais um conceito para o time aprender.

ItemPipeline com kubectlPipeline que só publica

Um meio-termo comum e honesto: o CI aplica em desenvolvimento e só publica a imagem para produção, onde o Argo CD sincroniza. O importante é saber qual dos dois mundos você está vivendo — pipeline que aplica é GitOps pela metade, e a metade que falta é justamente a que impede o drift da aula anterior.

7. A caixa: o passo de deploy, com as respostas certas

Quando o pipeline aplica, ele faz três coisas e confere uma. A caixa abaixo é o fim de um job de deploy num cluster que já tem o site rodando (o cenário da padaria). Complete a sequência: apontar a imagem nova, esperar o rollout terminar e ler o histórico.

Troque a imagem do container web para cardapio:2.4.0, espere o rollout e mostre o histórico. O painel tem de trazer image updated, successfully rolled out e a tabela REVISION.

kubectl set image deployment/cardapio web=cardapio:latest
kubectl rollout status deployment/cardapio
ana@notebook:~$ kubectl set image deployment/cardapio web=cardapio:latest
deployment.apps/cardapio image updated

ana@notebook:~$ kubectl rollout status deployment/cardapio
deployment "cardapio" successfully rolled out

kubectl set image deployment/cardapio web=cardapio:2.4.0
kubectl rollout status deployment/cardapio
kubectl rollout history deployment/cardapio

A resposta tem três blocos: deployment.apps/cardapio image updated, a linha deployment "cardapio" successfully rolled out e a tabela do histórico. O rollout status é o passo que falta em quase todo pipeline caseiro: sem ele, o job termina “verde” no instante em que aplicou, mesmo que os pods novos nunca fiquem prontos. Com ele, o job falha junto com o deploy — que é o que você quer, para receber o aviso na hora.

O histórico, num cluster de verdade, mostra a causa de cada revisão. Nosso painel é econômico e registra o comando:

REVISION   CHANGE-CAUSE
1          <none>
2          set image

O <none> é a revisão de criação, feita sem anotação de causa. Para o histórico ficar legível, o pipeline anota o Deployment com kubernetes.io/change-cause antes de aplicar — algo como “build 481: cardapio 2.4.0”. Num cluster real, essa anotação aparece na coluna CHANGE-CAUSE; o painel deste guia mostra o comando, não a anotação, e é bom saber a diferença.

8. Antes do deploy: o Job que prepara o terreno

Algumas mudanças precisam acontecer antes de a versão nova subir: migrar a tabela do banco, gerar um arquivo de configuração, rodar um script de dados. Isso não é Deployment (não fica rodando para sempre) nem pod solto (ninguém recria se falhar): é Job, que roda até terminar e tem contagem de tentativas.

O campo que importa aqui é o backoffLimit: quantas vezes o Job tenta de novo depois de falhar. O padrão é 6, o que para uma migração é perigoso — seis tentativas de alterar o banco podem significar seis vezes o mesmo erro pela metade. Numa migração, use 0 e deixe o pipeline decidir: falhou, para tudo e avisa.

Ajuste o Job: nenhuma nova tentativa (backoffLimit: 0) e a imagem de destino na versão 2.4.0. Rode e veja o Job terminar.

apiVersion: batch/v1
kind: Job
metadata:
  name: migra-cardapio
spec:
  backoffLimit: 6
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migra
          image: kaniko:v1.23.2
          args:
            - --context=git://git.loja.test/padaria/site.git
            - --destination=registry.loja.test/padaria/cardapio:2.3.0

Quando a migração e a imagem precisam estar juntas, o padrão é outro: um initContainer dentro do próprio pod, que roda antes do container principal e trava o start até terminar. A diferença é de escopo — o Job é único para o deploy inteiro; o initContainer repete em cada pod novo. A aula de init containers entra nesse detalhe.

9. Cenários do dia a dia

Cenário 1: o deploy “verde” que não mudou nada

O pipeline terminou com sucesso e o site continuou velho. A causa mais comum é a tag repetida: latest publicada de novo, manifesto igual, apply respondendo unchanged. A segunda causa é o pipeline aplicar num contexto (namespace ou cluster) diferente do que você está olhando. Antes de investigar o cluster, confira a imagem que está rodando: kubectl get deployment cardapio -o yaml mostra a tag que o cluster realmente usa.

Cenário 2: a imagem existe, o pod não baixa

ImagePullBackOff com unauthorized quase sempre é pull secret faltando, ausente no namespace certo ou com credencial vencida. Vale lembrar que o pod usa o Secret do namespace dele, não do namespace onde o Secret foi criado por engano. E se a imagem acabou de ser publicada, espere alguns segundos: registro tem cache.

Cenário 3: o pipeline que virou gargalo

Com o time crescendo, cada push dispara build de tudo, e a fila do CI passa de vinte minutos. O remédio é o mesmo do Kubernetes: separar o que é independente. Build com cache de camadas, testes em paralelo, e deploy só do que mudou. Pipeline que demora mais que o intervalo entre commits deixa de ser contínuo — e vira um segundo problema.

10. Fixando o que ficou

1. Por que latest atrapalha o deploy?

2. Para que serve imagePullSecrets?

3. Por que um Job de migração costuma usar backoffLimit: 0?

Exercício: a tag do build 481

O build número 481 gerou a imagem registry.loja.test/padaria/cardapio:2.4.0. Escreva o trecho do Deployment que usa essa imagem e o Secret registry para baixá-la. Depois responda: qual campo do spec do pod recebe a referência ao Secret?

spec::
  - name: registry

Dica: imagePullSecrets fica no spec do pod (dentro de template.spec), não no spec do Deployment.

11. Resumo

CI/CD é o caminho automático entre o commit e o cluster: build, teste, imagem publicada, manifesto atualizado e deploy. Cada estação só começa se a anterior passou, e cada uma deixa um artefato com número — a imagem com tag imutável é o mais importante deles, porque é o que o cluster baixa.

latest é a armadilha da aula: com tag que se repete, o manifesto não muda, o rollout não acontece e dois nós podem rodar versões diferentes. Use versão, data ou hash do commit. E lembre que imagem privada exige imagePullSecrets — o kubelet não conhece o cofre do CI.

O kubectl pode estar no fim do pipeline ou fora dele, com um controlador aplicando (o GitOps da aula anterior). Em qualquer desenho, o passo que não pode faltar é o rollout status: sem ele, o pipeline diz “sucesso” antes de o site estar no ar. E quando a mudança exige preparar o banco, o Job com backoffLimit: 0 roda uma vez, para tudo se falhar e deixa o deploy seguir só depois.

Para lembrar
  • Tag imutável ou digest: é o que faz o rollout acontecer de verdade.
  • Pipeline verde não é site no ar — kubectl rollout status é o juiz.
  • Imagem privada + imagePullSecrets = pod que sobe.
  • Migração é Job, com backoffLimit: 0.
  • Se o CI tem a credencial do cluster, ele é o dono do deploy — saiba disso.
