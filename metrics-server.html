Metrics Server

A Ana criou um cluster novo, rodou kubectl top pods e recebeu um erro. O comando existe, o cluster está de pé, os pods estão rodando — falta uma peça que ninguém instala por padrão: o metrics-server. Nesta aula ela entende o que é esse componente, de onde ele tira os números de CPU e memória, por que ele se registra como uma API à parte, o que ele não mede e por que o HPA fica cego quando ele falta. É a aula que separa “o cluster não tem métricas” de “o cluster tem métricas e eu não sei ler”.

Você vai aprender
  • O que é o metrics-server e por que ele não vem no cluster.
  • De onde vêm os números: kubelet, cgroups e o endpoint de resumo de cada nó.
  • As quatro peças da instalação: Deployment, Service, APIService e RBAC.
  • O que ele guarda — e por que não serve para histórico.
  • O que ele mede e o que não mede, comparado com o Prometheus.
  • Os erros clássicos: Metrics API not available, certificado do kubelet e <unknown>.
  • Quem consome esses números: kubectl top, o HPA e o agendador.

1. A cena: o comando que não existe

O cluster de teste da Ana foi criado com kind create cluster, e o site subiu. Curiosa, ela digitou kubectl top pods para ver quanto de CPU o pod estava usando e recebeu:

$ kubectl top pods
error: Metrics API not available

A primeira interpretação foi “o Kubernetes não tem métricas”. Não é isso. O kubectl top é só um cliente: ele pergunta a uma API chamada metrics.k8s.io, e essa API não faz parte do núcleo do Kubernetes. Ela é servida por um componente instalado à parte, o metrics-server. Sem ele, a API não existe, e o kubectl responde exatamente isso — de forma honesta e pouco amigável.

No cluster gerenciado de nuvem, o metrics-server normalmente já vem instalado. No cluster que você cria para estudar, não. É por isso que a mesma pessoa tem experiências opostas em dois clusters: o comando é o mesmo, o que muda é a peça que responde.

E não é só o top que sofre. O HPA, aquele objeto que aumenta e diminui réplicas conforme a carga, lê a mesma API. Num cluster sem metrics-server, o HPA não tem número, não decide nada e mostra <unknown> na coluna de alvo. Duas funcionalidades importantes do dia a dia dependem de um componente que quase ninguém lembra de instalar.

2. O que é o metrics-server

É um programa pequeno, escrito em Go, que roda como um pod do próprio cluster — um Deployment no namespace kube-system, com um Service na frente. A cada ciclo ele visita o kubelet de cada nó, pega os números de CPU e memória de todos os containers e guarda o resultado em memória. Quando alguém pergunta, ele responde no formato de uma API do Kubernetes.

A parte esperta é como ele se encaixa. O Kubernetes tem um mecanismo chamado agregação de API: o servidor principal pode delegar um caminho de URL para outro serviço. O metrics-server se registra como um objeto APIService chamado v1beta1.metrics.k8s.io, e a partir daí todo pedido a /apis/metrics.k8s.io/v1beta1 é encaminhado para ele. Para o kubectl, é como se as métricas fossem parte do cluster.

metrics-server
O componente que coleta e serve CPU e memória. Roda como Deployment, quase sempre em kube-system, com uma réplica (duas para alta disponibilidade).
APIService
O objeto que diz ao servidor principal “esse caminho de API é servido por aquele Service”. É o que faz o kubectl top encontrar a resposta.
resumo do kubelet
O endpoint de cada nó que devolve o uso de CPU e memória de todos os containers daquele nó. É a fonte primária do metrics-server.
metric-resolution
De quanto em quanto tempo o metrics-server visita os kubelets. Padrão de 60 segundos; baixar aumenta a precisão e o custo.
utilization
Uso dividido pelo request do container, em porcentagem. É a unidade que o HPA usa para decidir escalar.

Vale conhecer o manifesto do componente, porque ele é um Deployment comum com argumentos próprios. O primeiro deles é a resolução da coleta: com 60 segundos, o número que você vê pode ter até um minuto; com 15, acompanha melhor um pico curto.

O Deployment do metrics-server coleta a cada 60 segundos. Troque a resolução para 15s e rode. (No painel ele fica no namespace default; num cluster real mora em kube-system.)

O argumento --kubelet-insecure-tls aparece em quase todo tutorial de cluster local, e por um motivo específico: o kubelet se apresenta com um certificado autoassinado, e o metrics-server, sendo rigoroso, recusa. Em produção, a resposta certa é configurar o certificado do kubelet, não desligar a verificação. Em cluster de estudo, o argumento economiza uma tarde.

3. De onde vêm os números

O metrics-server não inventa nada e não tem agente próprio. Ele pergunta ao kubelet, que já sabe. Cada nó roda um kubelet, e cada kubelet tem acesso ao cgroup de cada container — o mecanismo do Linux que contabiliza CPU e memória por grupo de processos. O kubelet expõe isso num endpoint de resumo, e o metrics-server só organiza.

O caminho completo é: o container queima CPU, o cgroup conta, o kubelet resume, o metrics-server visita cada nó e soma, a API responde, o kubectl top desenha a tabela. Quando alguém pergunta “de onde vem esse número?”, a resposta é cgroup — e é por isso que ele é confiável para consumo e não para faturamento: é uma leitura instantânea, não uma média acumulada.

Duas consequências práticas. A primeira: o número é do último ciclo. Se o pico aconteceu entre duas visitas, ele pode não aparecer. A segunda: a memória reportada é a memória de trabalho do processo naquele instante — não inclui cache de disco do nó e não é “quanto o pod já consumiu no total”.

O metrics-server também não guarda série histórica: ele mantém os últimos valores em memória para responder, e pronto. Reiniciou o componente, começa do zero. Quem precisa de gráfico, de média de uma hora ou de comparação entre semanas não usa ele — usa Prometheus, que é o assunto de uma aula adiante.

4. As peças da instalação

Instalar o metrics-server não é aplicar um Deployment e pronto. São quatro peças, e cada uma resolve um problema diferente. O Deployment roda o programa. O Service dá a ele um endereço estável dentro do cluster. O APIService diz ao servidor principal para encaminhar as requisições para esse Service. E o RBAC dá ao componente permissão para ler os nós e os pods.

A peça que mais quebra silenciosamente é o Service. O metrics-server usa um Service seletor para achar o pod, exatamente como qualquer aplicação. Se o seletor não casa com as etiquetas do Deployment, o Service existe e não tem endpoint — e o APIService, que aponta para ele, responde 503. O sintoma para você é error: Metrics API not available, mesmo com o pod do metrics-server rodando e saudável.

O Service procura app: metrics e o Deployment do metrics-server tem a etiqueta app: metrics-server. Faça o seletor casar e rode.

apiVersion: v1
kind: Service
metadata:
  name: metrics-server
spec:
  selector:
    app: metrics
  ports:
    - port: 443
      targetPort: 10250
service/metrics-server created

  selector:
    app: metrics-server

Repare nas portas: o Service escuta em 443 e manda para 10250, que é a porta segura em que o metrics-server responde. Trocar uma das duas produz o mesmo 503 e a mesma mensagem no kubectl — por isso, quando o top falha, a ordem de conferência é Service, endpoints, pod, APIService.

A quarta peça é o RBAC. O componente precisa listar nós e pods e ler as estatísticas de cada um; sem permissão, ele autentica, recebe Forbidden e não monta nada. O manifesto de referência do projeto traz uma ClusterRole system:metrics-server e um ClusterRoleBinding ligando essa role ao ServiceAccount do componente. Se o binding falta, o pod fica em Running e a API não responde.

O ClusterRoleBinding aponta para a role system:metrics, que não é a certa. Corrija para system:metrics-server e rode.

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: metrics-server
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:metrics
subjects:
  - kind: ServiceAccount
    name: metrics-server
    namespace: kube-system

Com as quatro peças no lugar, o teste é sempre o mesmo: kubectl top nodes. Se os nós aparecem, a coleta funciona; se o comando responde erro de API, o problema está na instalação, não nos pods. E vale lembrar que o painel deste guia não roda container nem tem a camada de agregação: ele guarda os objetos e mostra a resposta do kubectl para eles, mas o top continua indisponível aqui — como num cluster sem o componente.

5. O que ele guarda (e por quanto tempo)

Quase nada. O metrics-server mantém em memória o último valor de cada pod e de cada nó, e responde a partir disso. Não há banco, não há arquivo, não há série temporal. Se você perguntar “quanto este pod usou ontem às três da tarde?”, a resposta honesta é que ninguém sabe — aquele número existiu por um instante e foi substituído.

É por isso que ele é barato e é por isso que ele é limitado. Um componente que guarda tudo precisaria de disco, de compactação e de política de retenção; o metrics-server escolheu não ter nada disso e servir uma necessidade específica: decisão rápida com o número de agora. O HPA precisa exatamente disso, a cada quinze segundos.

A resolução é o único ajuste de retenção que existe. Com 60 segundos, você tem 60 números por hora, mas só o último disponível. Com 15, o número é mais fresco e a coleta custa quatro vezes mais chamadas aos kubelets. Em cluster grande, baixar a resolução demais vira carga nos kubelets e no próprio componente.

Existe ainda um detalhe de agregação: o metrics-server soma os containers do pod para dar o total do pod, e mantém o detalhe por container. É por isso que kubectl top pod cardapio mostra o total e kubectl top pod cardapio --containers mostra linha por container. Em pod com sidecar, a diferença importa: o total inclui o proxies e os agentes ao lado.

6. O que ele mede e o que não mede

CPU e memória. Só. Ele não sabe quantas requisições o site recebeu, quanto tempo cada uma levou, quantas falharam, quantas conexões estão abertas, quanto de disco foi lido. Essas perguntas são de outra família de ferramenta, e é aí que entra o Prometheus.

Perguntametrics-serverPrometheus
quanta CPU e memória agora?simsim
quantas requisições por segundo?nãosim, se a aplicação expõe
qual a latência do 95%?nãosim, com histograma
como estava há três dias?não guardasim, até a retenção configurada
alimenta o HPA?sim, métricas de recursosim, via adaptador
custo de operaçãoum podservidor, banco, coleta e regras

Há uma confusão comum que vale desfazer: kubectl describe node mostra uma seção de recursos alocados, com porcentagens. Aquele número não vem do metrics-server: vem dos requests declarados nos pods, somados pelo próprio agendador. É a reserva, não o consumo. Um nó pode estar com 90% de CPU alocada e 10% de uso real — ou o contrário.

O top mostra consumo; o describe node mostra reserva; o HPA compara um com o outro. Entender os três evita a conclusão errada de que “o cluster está cheio” quando só está reservado.

7. Quando não funciona

Os erros do metrics-server são poucos e cada um aponta para uma peça diferente. O mais comum é o do começo desta aula: error: Metrics API not available, que significa APIService ausente ou sem resposta. Logo depois vem error: metrics not available yet, que aparece nos primeiros minutos após instalar — o componente ainda não completou o primeiro ciclo de coleta.

Num cluster local, o campeão é o certificado do kubelet. A mensagem aparece nos logs do pod do metrics-server, não no kubectl: x509: cannot validate certificate for 192.0.2.10 because it doesn't contain any IP SANs. É o kubelet se apresentando com um certificado que não cobre o endereço, e a solução de estudo é o --kubelet-insecure-tls.

O terceiro grupo é o HPA reclamando. Com métricas de recurso, o HPA precisa do request de CPU do container para transformar consumo em porcentagem. Sem request, não há divisão, e o alvo fica <unknown>. A transcrição abaixo é de um cluster real com esse problema:

$ kubectl get hpa cardapio
NAME       REFERENCE             TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
cardapio   Deployment/cardapio   <unknown>/60%   1         4         1          5m

$ kubectl describe hpa cardapio
Events:
  Type     Reason                        Age   Message
  Warning  FailedGetResourceMetric       30s   failed to get cpu utilization: missing request for cpu

“missing request for cpu” é literal: falta o pedido de CPU. Não adianta reinstalar o metrics-server nem aumentar a resolução; o problema está no manifesto da aplicação. A outra metade dos casos de <unknown> é a aplicação sem metrics-server — mesma tela, causa oposta, e o caminho de diagnóstico é sempre começar pelo kubectl top: se ele funciona, o componente está bem e o problema é o request.

Um detalhe de leitura: kubectl top pod mostra <unknown> quando o pod é novo demais para ter sido coletado. Não é erro de instalação; é o ciclo ainda não ter passado por ele. Esperar um minuto resolve — e é mais um lembrete de que os números são amostras, não fluxo contínuo.

8. Quem consome esses números

Três consumidores importam. O primeiro é você, no terminal, com kubectl top: a tabela mostra CPU em milicores e memória em mebibytes, e aceita --sort-by=cpu, --sort-by=memory, -l para filtrar por etiqueta e --containers para abrir por container.

$ kubectl top pods
NAME                        CPU(cores)   MEMORY(bytes)
cardapio-6d8f89b786-88dn9   12m          48Mi
cardapio-6d8f89b786-4jjxx   9m           51Mi
forno-7b9c4f5d8-2xkqp       3m           22Mi

O segundo é o HPA, que fala com a mesma API a cada quinze segundos e transforma consumo em porcentagem do request. O terceiro é o agendador, mas de forma indireta: ele não usa o metrics-server, e sim os requests, para decidir onde cabe cada pod. Os três olham para números diferentes do mesmo container — consumo, consumo sobre reserva e reserva.

Por isso a frase “o nó está com 95%” precisa de contexto. Se for top nodes, é consumo real agora; se for describe node, é reserva comprometida. Um cluster com reserva alta e consumo baixo está superdimensionado; um com consumo alto e reserva baixa está a um pico de distância do OOMKilled.

9. Cenários do dia a dia

Cenário 1: o cluster novo sem top

A Ana recriou o cluster de estudo e perdeu o top. O metrics-server era um add-on instalado à mão na primeira vez e ninguém versionou o manifesto. O conserto foi guardar os quatro objetos num arquivo no repositório e aplicá-los junto com o resto do ambiente. Add-on sem manifesto versionado é add-on que some no próximo cluster.

Cenário 2: o HPA que nunca escalou

O HPA existia, o metrics-server também, e mesmo assim a coluna de alvo ficava em <unknown>. O evento dizia missing request for cpu: o Deployment não declarava requests. O time passou a tratar requests como parte do contrato de deploy, e o HPA passou a funcionar. Sem request não há porcentagem, por mais precisa que seja a medição.

Cenário 3: o número que sumia

O time queria provar que o pod usava pouca CPU ao longo do dia, e o top só mostrava o instantâneo. Tentaram baixar a resolução para 5 segundos, o que só deixou a amostra mais fresca — não criou histórico. A conclusão foi instalar Prometheus para as séries e manter o metrics-server só para o HPA e para a olhada rápida. Cada ferramenta no seu papel.

Exercício: a resolução da coleta

Você quer que o metrics-server colete a cada 15 segundos. Complete o argumento do container:

args: - --metric-resolution=

Dica: duração em segundos com sufixo s. O padrão é 60s; baixar deixa o número mais fresco e aumenta a carga nos kubelets.

11. Resumo

O metrics-server é um add-on, não parte do núcleo: sem ele, kubectl top responde Metrics API not available e o HPA fica sem número. Ele roda como Deployment em kube-system, com Service, APIService e RBAC, e se registra na API agregada como v1beta1.metrics.k8s.io.

Os números vêm do resumo que cada kubelet expõe, alimentado pelos cgroups: CPU e memória, por container e por nó, amostrados a cada metric-resolution (60 segundos por padrão). Ele guarda só o último valor — para histórico, Prometheus. O HPA transforma consumo em porcentagem dividindo pelo request, e sem request a conta não existe.

Quando o top falha, a ordem de conferência é Service, endpoints, pod, APIService, RBAC. Quando o <unknown> aparece só no HPA, o problema é o manifesto da aplicação. A próxima aula sai do número e vai para o texto: os logs, que começam por pod e terminam num sistema de agregação.

Para lembrar
  • Sem metrics-server não há kubectl top nem métrica de recurso para o HPA.
  • Quatro peças: Deployment, Service, APIService e RBAC.
  • Fonte dos números: resumo do kubelet, alimentado pelos cgroups de cada container.
  • --metric-resolution padrão de 60s; baixar custa mais coleta.
  • Ele guarda só o último valor: não é ferramenta de histórico.
  • Mede CPU e memória; não mede latência, erros nem requisições.
  • <unknown> no HPA costuma ser falta de requests.cpu.
  • describe node mostra reserva (requests), não consumo.
