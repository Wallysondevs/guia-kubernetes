Pods

O pod é a menor coisa que o Kubernetes liga, e o spec dele é o manifesto que a Ana mais escreveu até aqui. Só que o pod tem mais campos do que os três que ela usa no dia a dia: initContainers, volumes, securityContext, tolerations, probes. Esta página é a consulta: o que existe, onde fica e o que muda quando você mexe. Ela não substitui as aulas — serve para o momento em que você já sabe o que quer e só esqueceu o nome do campo.

Como usar esta página
  • A tabela 1 lista os campos do pod; a tabela 2, os do container. A confusão entre os dois níveis é o erro mais comum.
  • A seção 5 é a das armadilhas: leia antes de culpar o cluster.
  • Os dois campos que você vai usar em 90% dos manifestos: containers e resources.

1. Para que serve esta página (e o que ela não cobre)

Esta é a folha de consulta do spec do Pod. Ela responde “qual é o nome do campo?”, “ele fica no pod ou no container?” e “o que acontece se eu omitir?”. Também traduz as mensagens de validação que citam caminhos como spec.containers[0].env — as mais fáceis de resolver quando você sabe ler o caminho.

Ela não ensina o ciclo de vida do pod (isso é Cluster, node e pod), nem requests e limits a fundo (Requests e limits), nem probes (Readiness probe) nem volumes (emptyDir). O que está aqui é o mapa dos campos, com o ponteiro para a aula de cada assunto.

E há um motivo prático para conhecer bem este spec: ele é copiado inteiro para dentro do template de todo controlador. Quando você escreve um Deployment, o spec.template.spec é exatamente o spec do pod; no Job, é spec.template.spec; no DaemonSet, idem. Aprender um é aprender os quatro — e o erro de indentação também se copia.

Uma coisa que vale dizer de saída: o pod é o único objeto que o Kubernetes realmente executa. Deployment, Job, DaemonSet e StatefulSet não rodam nada — eles criam pods. Por isso o spec do pod aparece dentro do template de todos eles, e por isso vale conhecer este manifesto melhor do que qualquer outro.

2. O essencial em 10 linhas

  • spec.containers é obrigatório e é uma lista — mesmo com um container só, tem hífen.
  • Cada container precisa de name e image; o resto é opcional.
  • spec.initContainers roda antes, em ordem, e precisa terminar para o pod começar.
  • spec.restartPolicy é do pod: Always (padrão), OnFailure ou Never.
  • spec.volumes declara o volume; volumeMounts, no container, diz onde ele aparece.
  • resources é por container, com requests (reserva) e limits (teto).
  • securityContext existe nos dois níveis: no pod vale para todos, no container sobrescreve.
  • ports é informativo: não abre porta nem roteia tráfego.
  • command substitui o entrypoint da imagem; args, o comando padrão.
  • O pod nasce, vive e morre; quem o recria é um controlador, não ele mesmo.

A última linha é a que separa o pod de tudo o mais. Um pod solto não tem dono: se ele morre, ninguém o recria; se o nó reinicia, ele não volta. Quem garante a reposição é o controlador — Deployment, Job, DaemonSet. É por isso que o guia insiste tanto em não usar pod solto em produção, e é por isso que o restartPolicy do pod é diferente do comportamento do Deployment: o pod reinicia containers, o Deployment cria pods.

Se você chegou aqui procurando um campo que não está nas tabelas, tente o nome em inglês no kubectl explain pod.spec: a lista de campos do pod é longa e cresce a cada versão. O que está aqui é o que se usa de verdade num cluster de padaria.

Vale saber também o que o pod não tem: campo replicas, seletor, estratégia de atualização. Isso tudo é do controlador. O pod é a unidade; a política de quantas unidades existem e como são trocadas fica um nível acima — e é por isso que editar um pod criado por Deployment não adianta: o controlador compara com o template e desfaz.

Outra linha que vale decorar: lista é hífen. containers, env, ports, volumeMounts, volumes e initContainers são listas; resources, securityContext, nodeSelector e lifecycle são mapas. Trocar os dois é o erro de YAML que mais aparece — e a mensagem de validação sempre diz “must be a list” quando é esse o caso.

3. Anatomia do spec do Pod

containers
A lista de containers que rodam juntos, no mesmo IP e no mesmo ciclo de vida. Obrigatória; cada item precisa de name e image.
initContainers
Containers que rodam antes dos principais, um de cada vez, e precisam terminar com sucesso. Servem para esperar o banco, baixar um arquivo, ajustar permissão.
restartPolicy
O que fazer quando um container sai: Always (padrão), OnFailure ou Never. Fica no pod, não no container — e o Deployment só aceita Always.
volumes
Os volumes do pod, com nome e tipo (emptyDir, configMap, secret, persistentVolumeClaim). O container só os vê se montar com volumeMounts.
nodeSelector e tolerations
Onde o pod pode ser agendado: etiquetas obrigatórias do nó e permissões para taints. Vazio, o pod vai para onde houver espaço.
securityContext
Usuário, grupo e permissões. No nível do pod vale para todos os containers; no nível do container, sobrescreve o do pod.

Os initContainers merecem uma nota porque o nome engana: eles não são “containers menores”, são containers que rodam antes e precisam terminar com sucesso. O kubelet executa um de cada vez, na ordem da lista, e só depois de o último sair com zero é que os containers principais começam. Se um init falhar, o pod reinicia conforme o restartPolicy e os principais nunca sobem — o que costuma aparecer no get pods como Init:CrashLoopBackOff.

Fora dessa lista, mas ainda dentro do spec: serviceAccountName (a identidade que o pod usa para falar com a API), terminationGracePeriodSeconds (quanto tempo o kubelet espera antes de matar), hostNetwork (usa a rede do nó), dnsPolicy e priorityClassName. São campos de quem opera o cluster; no começo você não precisa deles, mas precisa saber que existem para não estranhar quando aparecerem num manifesto alheio.

Dois campos dessa tabela de container têm padrão que surpreende. O imagePullPolicy é IfNotPresent na maioria dos casos, mas vira Always quando a imagem usa a etiqueta :latest — e é por isso que :latest em produção é uma má ideia: o pod tenta baixar de novo a cada início. E o command/args segue a lógica do Docker: o command substitui o entrypoint da imagem, e o args substitui o comando padrão; se você só quer mudar o argumento, mexa no args e deixe o command em branco.

Uma leitura que ajuda a memorizar: o pod declara o que existe (volumes, containers, política de reinício); o container declara o que usa (mounts, env, recursos). Quando você se pegar escrevendo volumes dentro de um container, pare: é volumeMounts. E quando for resources, lembre que é sempre por container — o pod não tem resources.

5. Os campos que mais confundem

Cinco confusões respondem por quase todos os manifestos de pod que dão errado depois de aceitos. Elas não são de sintaxe: são de expectativa.

ConfusãoComo é de verdadeO que acontece
ports abre a portaé documentação; a porta já está aberta no containernada muda se você tirar — e o Service usa targetPort
resources no podé por container; o pod soma para o agendadoro campo no lugar errado é ignorado
securityContext só num nívelexiste no pod (vale para todos) e no container (sobrescreve)o do container ganha naquele container
env como mapaenv é lista de name/valueInvalid value: must be a list
restartPolicy no containeré campo do pod, ao lado de containerso container reinicia sozinho e o campo é ignorado
volumeMounts sem volumeso mount aponta para um volume que precisa existir no podnot found no kubelet — pod preso em ContainerCreating

Duas dessas merecem um parágrafo. A primeira é a do ports: quem nunca programou tende a achar que declarar containerPort: 8080 é o que faz o site responder na 8080. Não é. O programa escuta na porta que ele quiser; o campo só documenta, e é o Service que decide para onde mandar tráfego (targetPort). Se o seu pod responde na 3000 e o ports diz 8080, ninguém reclama — e o Service, se apontar para 8080, não acha nada.

A segunda é a do env. O formato de lista vem do desenho da API: uma variável pode ter valor fixo (value) ou vir de outro objeto (valueFrom, com configMapKeyRef, secretKeyRef ou fieldRef). Um mapa não conseguiria expressar as duas coisas, então o campo é lista. E como toda lista no YAML, cada item começa com hífen e tem as chaves indentadas abaixo.

Sobre as duas probes, a diferença em uma frase: a readiness decide se o pod recebe tráfego agora (e pode oscilar), a liveness decide se o container deve ser reiniciado (e só piora). Trocar as duas é um clássico: um pod que ainda está carregando, com liveness agressiva, é morto antes de terminar de subir. Para o “ainda estou subindo”, o campo certo é startupProbe.

Vale ainda um alerta sobre volumeMounts: o volume é declarado no pod com um nome, e montado no container por esse nome. Se o nome não casar, o pod fica em ContainerCreating e o evento diz que o volume não existe. É um dos poucos erros que o apply aceita e o kubelet recusa — ou seja, o manifesto passa, o pod não sobe, e o motivo está no describe, não no apply.

7. Duas coisas para praticar agora

A primeira caixa monta o mínimo que funciona — e o inicial esquece o campo que todo container precisa além da imagem, que é o nome. A segunda é o conserto do env escrito como mapa, o erro de YAML que mais aparece em pod.

O pod da vitrine tem imagem, mas o container está sem nome. Rode e leia a mensagem; depois acrescente name: web ao container e rode de novo.

apiVersion: v1
kind: Pod
metadata:
  name: vitrine
spec:
  containers:
    - image: vitrine:1.0
      ports:
        - containerPort: 8080
The Pod "vitrine" is invalid: spec.containers[0].name: Required value

apiVersion: v1
kind: Pod
metadata:
  name: vitrine
spec:
  containers:
    - name: web
      image: vitrine:1.0
      ports:
        - containerPort: 8080

A variável PORTA foi escrita como mapa e o servidor recusou. Passe para o formato de lista e rode: o pod tem de subir com PORTA no primeiro item de env.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
      env:
        PORTA: "8080"
The Pod "cardapio" is invalid: spec.containers[0].env: Invalid value: must be a list

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  containers:
    - name: web
      image: cardapio:1.0
      env:
        - name: PORTA
          value: "8080"

As duas caixas também ensinam onde o erro aparece. Falta de name e env em mapa são erros de validação: o objeto é recusado antes de existir, e o get pods continua vazio. Já um volumeMounts que aponta para um volume inexistente é erro de execução: o objeto é aceito, o pod fica em ContainerCreating, e o motivo só aparece no describe. Saber em qual das duas famílias o seu problema cai economiza metade do diagnóstico.

Repare que, nos dois casos, o painel mostra a mensagem de validação antes de criar qualquer coisa: o objeto é recusado inteiro, não “pela metade”. É assim que o Kubernetes trabalha — o manifesto é validado antes de virar objeto, e o erro aponta o caminho exato do campo.

Resumo

O spec do pod tem dois níveis: o do pod (containers, initContainers, restartPolicy, volumes, nodeSelector, securityContext) e o do container (name, image, command, args, env, ports, resources, volumeMounts, probes). Declarar é no pod, usar é no container — e trocar os dois é a origem da maioria dos erros.

containers é obrigatório e é lista; cada item precisa de name e image. restartPolicy vale para o pod inteiro e o padrão é Always; ports documenta e não roteia; resources é por container; env é lista, não mapa. As mensagens de validação citam o caminho completo, com índice — spec.containers[0].env —, e o describe mostra o que realmente entrou: Environment, Mounts, Requests, Limits e Events.
