Saída do kubectl

A Ana já sabe pedir as coisas ao cluster. O problema agora é o contrário: entender o que volta. Ela manda um print da tabela do get pods no ticket e o colega responde “e a imagem?”. Ela roda get deployment e não vê o status. Ela copia a tabela para uma planilha e descobre que a coluna AGE não é data. Nesta aula a Ana aprende que o kubectl tem várias formas de responder a mesma pergunta — e que escolher a forma é metade do trabalho.

Você vai aprender
  • O que a tabela padrão mostra e o que ela esconde.
  • As colunas de cada tipo — pod, Deployment, Service, namespace.
  • -o name e o formato tipo/nome que serve de alvo para o próximo comando.
  • -o wide, -o yaml e -o json: quando cada um resolve.
  • A diferença entre a resposta do cluster, o erro e o código de saída.
  • Por que No resources found não é erro — e quando o é.

1. A cena: o print que não respondia

O site da padaria começou a mostrar o cardápio antigo. A Ana abriu o terminal, rodou kubectl get pods, tirou print e colou no ticket:

ana@notebook:~$ kubectl get pods
NAME                        READY   STATUS    RESTARTS   AGE
cardapio-wj4jsx2tcw-q65ng   1/1     Running   0          3d

O colega respondeu com uma pergunta simples: “qual imagem está rodando nesse pod?”. A Ana olhou o print e não havia resposta ali. Não é falha do kubectl: a tabela é um resumo, feita para você bater o olho e saber se está tudo de pé. Para saber o que está rodando, é preciso pedir outra forma de saída. E é aí que a aula começa.

Pense na diferença entre o extrato do banco e o comprovante da transferência. O extrato tem data, valor e saldo — o suficiente para conferir se algo saiu. O comprovante tem o número da operação, a conta de destino, o horário exato. Os dois falam da mesma coisa; a pergunta é que decide qual você precisa. No kubectl, o extrato é a tabela e o comprovante é o -o yaml.

2. A tabela: o que ela mostra e o que ela cala

A saída padrão do kubectl get é uma tabela com cabeçalho em maiúsculas, alinhada por coluna. As colunas mudam conforme o tipo pedido — e é por isso que metade das dúvidas de iniciante é sobre uma coluna que não existe naquele tipo. O vocabulário que aparece em toda saída:

tabela
A saída padrão do get: cabeçalho, uma linha por objeto, colunas fixas por tipo. Feita para leitura humana, não para programa.
-o
A opção que escolhe a forma da resposta (output). Ela não muda o cluster nem a consulta: muda só como o resultado é impresso.
objeto
Um recurso do cluster (um pod, um Deployment). Em -o yaml, aparece com apiVersion, kind, metadata, spec e status.
lista
O que o get devolve quando você não informa nome: um objeto de kind: List com items dentro. Em tabela, a lista vira linhas.
código de saída
O número que o comando devolve ao shell: 0 quando deu certo (mesmo com lista vazia), diferente de zero quando houve erro.

As colunas do pod merecem ser lidas em ordem, porque cada uma responde a uma pergunta diferente. A tabela abaixo é a legenda que vale colar ao lado do terminal:

ColunaPergunta que respondeOnde engana
NAMEcomo o objeto se chamaem pod de Deployment o nome é comprido e muda a cada troca; o estável é a label
READYquantos containers estão prontos (prontos/total)0/1 com Running não é erro de imagem: é falta de prontidão
STATUSa fase do podRunning não quer dizer que o programa responde; quem diz é o READY
RESTARTSquantas vezes o container reiniciounúmero subindo é sintoma, não causa: a causa está nos eventos e nos logs
AGEhá quanto tempo o objeto existeé idade, não data; pod com AGE de segundos acabou de nascer ou de renascer

Nos outros tipos, as colunas mudam. O Deployment mostra READY, UP-TO-DATE (quantos pods já estão na versão nova), AVAILABLE (quantos estão disponíveis para atender) e AGE. O Service mostra TYPE, CLUSTER-IP, EXTERNAL-IP, PORT(S) e AGE. O namespace mostra NAME, STATUS e AGE. A regra é sempre a mesma: a tabela responde “existe, está de pé, há quanto tempo”, e nada além disso.

3. -o name: a lista que serve de alvo

Quando o objetivo é usar o resultado no comando seguinte, a tabela atrapalha: ela tem espaços, cabeçalho e colunas. O -o name imprime uma linha por objeto, no formato tipo/nome, que é exatamente o que describe, logs e delete aceitam. O cluster da padaria já está de pé na caixa abaixo, com o Deployment e seus dois pods.

A caixa lista os pods em tabela. Peça a mesma lista no formato tipo/nome (-o name) e veja cada pod virar um alvo pronto para o próximo comando.

kubectl get pods
ana@notebook:~$ kubectl get pods
NAME                        READY   STATUS    RESTARTS   AGE
cardapio-wj4jsx2tcw-q65ng   1/1     Running   0          1m
cardapio-wj4jsx2tcw-t4jwn   1/1     Running   0          10m

kubectl get pods -o name

A diferença parece pequena e não é. Na tabela, o nome está no meio de cinco colunas; em -o name, a linha inteira é o alvo: pod/cardapio-wj4jsx2tcw-q65ng. Copiar daqui elimina o erro de digitação que gera o famoso not found, e encadear comandos fica trivial no shell de verdade: kubectl logs $(kubectl get pods -o name | head -1) faz o logs receber o primeiro pod da lista sem ninguém digitar nada.

4. O prefixo do -o name muda com o tipo

O formato tipo/nome não é sempre igual, e isso pega muita gente. Pods vêm do grupo v1 (o grupo central da API) e aparecem como pod/nome. Objetos de outros grupos carregam o grupo no prefixo: deployment.apps/cardapio, replicaset.apps/cardapio-abc — o .apps é o grupo da API. Não é enfeite: é o que permite que dois tipos com nomes parecidos não se confundam na hora de colar o alvo num comando.

O Deployment do cardápio existe no cluster. Peça a lista de Deployments com -o name e repare no prefixo deployment.apps/, diferente do pod/ da caixa anterior.

kubectl get deployments
ana@notebook:~$ kubectl get deployments
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   2/2     2            2           2m

kubectl get deployments -o name

Na tabela, esse mesmo Deployment mostra READY, UP-TO-DATE, AVAILABLE e AGE — informação que o -o name joga fora de propósito. Quem precisa do alvo usa o nome; quem precisa saber quantas réplicas estão prontas usa a tabela ou o -o yaml. As duas perguntas são legítimas; só não cabem na mesma linha de comando.

O mesmo raciocínio vale para qualquer tipo com grupo próprio. Um Service do grupo central aparece como service/cardapio; um Ingress, do grupo networking.k8s.io, aparece como ingress.networking.k8s.io/cardapio. Por isso copiar o alvo do -o name é melhor que digitar: o prefixo certo vem de graça, e o delete aceita exatamente aquela string.

5. -o wide: a mesma tabela, mais colunas

Entre a tabela econômica e o YAML gigante existe um meio-termo: a saída larga. Ela mantém as colunas de sempre e acrescenta IP, NODE, NOMINATED NODE e READINESS GATES. É a resposta para “onde esse pod caiu?” e “dois pods foram para o mesmo nó?”, sem precisar abrir o objeto inteiro. Em Service, a saída larga acrescenta a coluna SELECTOR — o seletor que o Service usa para achar os pods, que é a primeira coisa a conferir quando não há endpoint.

Vale saber o que NOMINATED NODE e READINESS GATES significam, mesmo que apareçam como <none> em quase toda linha. O primeiro só tem valor quando o agendador já escolheu um nó mas o pod ainda não foi aceito por ele; o segundo existe para pods que usam condições extras de prontidão. Ver <none> ali é normal — não é campo faltando.

O que a saída larga não resolve é a pergunta da Ana no começo da aula: a imagem. Nenhuma coluna de tabela mostra imagem, porque imagem é spec, e tabela mostra estado resumido. Para isso existe a próxima seção.

6. -o yaml: o objeto como o cluster guarda

O -o yaml imprime o objeto inteiro — o mesmo que o cluster guarda, com apiVersion, kind, metadata, spec e status. É a resposta definitiva para “como isso está configurado?”, e é onde a imagem aparece. A caixa abaixo cria o Deployment e pede o objeto:

Crie o Deployment cardapio com a imagem cardapio:1.0 e peça o objeto inteiro com -o yaml, para encontrar a imagem e o número de réplicas.

kubectl create deployment cardapio --image=cardapio:1.0
kubectl get deployment cardapio
ana@notebook:~$ kubectl create deployment cardapio --image=cardapio:1.0
deployment.apps/cardapio created

ana@notebook:~$ kubectl get deployment cardapio
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
cardapio   1/1     1            1           2m

kubectl create deployment cardapio --image=cardapio:1.0
kubectl get deployment cardapio -o yaml

O arquivo que aparece tem quatro blocos, e cada um responde a uma coisa. apiVersion e kind dizem o que o objeto é. metadata traz nome, namespace, labels e annotations. spec é o que você pediu — réplicas, seletor, molde do pod e a imagem dentro dele. status é o que o cluster conta de volta: quantas réplicas estão prontas, quais condições estão verdadeiras. O status você nunca escreve: ele é calculado.

Uma observação que evita confusão: quando o comando não tem nome (kubectl get pods -o yaml), a resposta é uma lista — kind: List com items: e cada objeto indentado embaixo. Com nome (kubectl get deployment cardapio -o yaml), a resposta é o objeto sozinho. As duas formas são válidas; a lista é o que um programa costuma consumir, e o objeto é o que você lê.

7. -o json: a mesma informação para programa

O -o json entrega o mesmo conteúdo do YAML em JSON — chaves entre aspas, chaves separadas por vírgula, sem indentação significativa. Para quem lê com os olhos, YAML ganha: menos pontuação, mais silêncio. Para quem lê com um programa, JSON ganha: é o formato nativo de quase toda linguagem e de quase toda ferramenta de automação.

Falta um formato na tabela, e ele é o preferido de quem automatiza: o -o jsonpath, que recebe um caminho dentro do objeto e imprime só aquele pedaço. kubectl get pod cardapio -o jsonpath='{.status.phase}' devolve uma palavra, sem tabela nem YAML em volta. É a ferramenta certa para um script que precisa de um valor só, e o painel deste guia não a implementa — lá, o caminho é pedir o YAML e procurar o campo com os olhos. No cluster do trabalho, vale decorar a sintaxe: ela resolve em uma linha o que antes exigia grep e boa vontade.

Repare que nenhuma linha da tabela diz “melhor”. Cada formato é a resposta de uma pergunta diferente, e o erro clássico é usar o mais completo para tudo: quem faz get pods -o yaml para ver se o pod subiu perde trinta segundos por comando e não vê nada de errado na tela. O caminho normal é começar na tabela, desconfiar de uma linha e aprofundar no objeto — não o contrário.

8. O que é resposta, o que é erro e o que é código de saída

O kubectl escreve em dois canais diferentes, e o shell os trata de forma diferente. A resposta — tabela, YAML, No resources found — vai para a saída padrão (stdout). A mensagem de erro vai para a saída de erro (stderr). Por isso um script pode guardar a resposta num arquivo e ainda ver o erro na tela. Além disso, o comando deixa um código de saída: 0 quando deu certo, diferente de zero quando não.

ana@notebook:~$ kubectl get pod cardapio
Error from server (NotFound): pods "cardapio" not found

ana@notebook:~$ echo $?
1

A primeira lição dessa transcrição: “não achei” é erro, não lista vazia — o código de saída é 1. É por isso que um script com set -e para na primeira linha quando o pod não existe, e é bom que pare: quase sempre a próxima linha assumiria que ele existe.

ana@notebook:~$ kubectl get pods -n teste
No resources found in teste namespace.

ana@notebook:~$ echo $?
0

A segunda lição é a que mais confunde: No resources found é sucesso. A consulta foi feita, o cluster respondeu, e a resposta é “não há nada aqui”. Código de saída 0. Um script que trata isso como falha vai parar em cluster vazio sem motivo; e um script que trata NotFound como vazio vai seguir adiante quando o objeto está simplesmente em outro namespace. São duas situações diferentes com mensagens parecidas, e a diferença está no tipo do erro, não no texto.

Uma nota sobre o painel deste guia: ele mostra a sessão como se fosse um terminal, mas não é um shell — não há echo $? nem redirecionamento ali. O que você vê no painel é o texto que o kubectl imprimiria; os códigos de saída e a separação entre os dois canais são do terminal de verdade, e é por isso que eles aparecem nas transcrições acima e não numa caixa.

9. Cenários do dia a dia

Cenário 1: a imagem que ninguém sabia

O site servia o cardápio antigo e a tabela dizia Running, 1/1, zero reinícios. O problema não era saúde, era versão. Um kubectl get deployment cardapio -o yaml mostrou image: cardapio:1.0 onde deveria estar 1.1. Tabela diz se está de pé; só o objeto diz o que está vestindo.

Cenário 2: o script que parava no cluster vazio

Um script de conferência rodava kubectl get pods -n teste e abortava quando a saída não tinha linhas. Em cluster novo, com o namespace recém-criado, ele “falhava” sempre — porque No resources found não é erro e o código de saída é zero. A correção foi olhar o código de saída e o tipo da mensagem, em vez de contar linhas.

Cenário 3: o nome copiado com o prefixo errado

Alguém copiou deployment.apps/cardapio e tentou usar como nome de pod no logs. O kubectl respondeu NotFound, porque o prefixo era de outro tipo e de outro grupo. O -o name salva quando o copiar/colar vem da linha certa — e engana quando vem da linha errada. Conferir o prefixo antes de colar economiza a rodada.

11. Resumo

A tabela do get é um resumo para bater o olho: diz se existe, se está pronto e há quanto tempo. Ela não mostra imagem, seletor nem status — e não é falha, é escolha. Quando a pergunta muda, muda a forma da resposta: -o wide para IP e nó, --show-labels para etiqueta, -o name para o alvo, -o yaml para ler o objeto inteiro e -o json para entregar a um programa.

O formato tipo/nome do -o name carrega o grupo da API quando existe: pod/cardapio mas deployment.apps/cardapio. Copiar dali evita erro de digitação; usar a linha errada gera NotFound na hora seguinte.

E as duas frases que todo mundo confunde: Error from server (NotFound) é erro, sai na saída de erro e devolve código diferente de zero; No resources found é sucesso, sai na saída padrão e devolve zero. Na próxima aula a Ana aprende a mudar o objeto sem reaplicar o manifesto inteiro — com edit e patch, e com as alternativas que sempre funcionam.

Para lembrar
  • Tabela = resumo. Imagem, seletor e status só no objeto.
  • -o name imprime tipo/nome: pod/x, deployment.apps/x, service/x.
  • -o wide acrescenta IP e NODE (e SELECTOR em Service).
  • -o yaml e -o json mostram o objeto inteiro: spec é o pedido, status é a resposta.
  • NotFound é erro (código 1); No resources found é lista vazia (código 0).
  • Erro vai para a saída de erro, resposta vai para a saída padrão.
