Tracing

O cliente reclamou que o pedido demorou “uma eternidade”. A Ana abriu os logs do site e encontrou uma linha de sucesso, 812 milissegundos, sem erro nenhum. Abriu o log do banco e também estava limpo. Abriu o do serviço de pagamento: limpo. Três programas, todos bem comportados, e um pedido lento — o log responde “o que aconteceu aqui”, mas não responde “onde o tempo foi gasto”. Quem responde isso é o trace: a história de uma requisição contada por todos os programas que ela atravessou, com o relógio de cada trecho.

Você vai aprender
  • O que log, métrica e trace respondem — e por que os três convivem.
  • O que são trace, span, trace_id e span_id.
  • Como o contexto viaja entre serviços, no cabeçalho traceparent.
  • O que é OpenTelemetry e por que existe um “coletor” no meio.
  • Rodar o coletor no cluster e apontar a aplicação para ele.
  • Ligar o trace ao log pela identificação e ver a história do pedido lento.

1. A cena: três logs limpos e um pedido lento

O pedido 1042 levou 812 ms. O normal é 120. Nenhum erro apareceu em lugar nenhum: o site respondeu 200, o banco respondeu 200, o pagamento aprovou. Só que, em algum lugar do caminho, oito décimos de segundo passaram sem que ninguém registrasse.

A Ana tem três ferramentas de observação, e cada uma responde a uma pergunta diferente. A métrica diz “a média subiu de 120 para 400 ms na última hora” — ótima para saber que existe um problema, péssima para saber onde. O log diz “o pedido 1042 foi gravado às 15h52” — ótimo para saber o que um programa fez, e cego para o que aconteceu entre programas. O trace diz “este pedido passou por quatro programas; 12 ms no site, 640 ms esperando o banco, 150 ms no pagamento, 10 ms de volta” — e é exatamente a pergunta em aberto.

A diferença está na unidade de medida. Métrica conta eventos por minuto; log escreve frases de um processo; trace segue uma requisição do começo ao fim, cruzando processos. Sem trace, o seu diagnóstico de lentidão é tentativa e erro entre logs de sistemas diferentes — e você acaba culpando o banco por um tempo que foi gasto na fila do próprio site.

2. Log, métrica e trace: três perguntas

Vale fixar o papel de cada uma antes das definições, porque muita equipe tenta resolver tudo com uma só. As três se complementam, e todas custam dinheiro: guardar log é caro pelo volume, métrica é cara pela quantidade de séries, trace é caro pela amostragem e pelo armazenamento.

SinalPergunta que respondeExemplo da padaria
métricaquantos, com que frequência, com que tendência“pedidos por minuto caíram 30% às 15h”
logo que este programa fez neste momento“pedido 1042 gravado, total 42,00”
tracepor onde esta requisição passou e onde gastou tempo“640 ms esperando o banco”

Repare que a métrica avisa, o trace localiza e o log explica. O ciclo de investigação que funciona é esse: a métrica (ou o alerta) diz que há problema; o trace mostra qual trecho está lento ou falhando; o log daquele trecho conta o detalhe. Começar pelo log é o caminho mais lento, porque você não sabe em qual dos cinco programas olhar.

3. A anatomia de um trace

Um trace é o registro de uma requisição. Ele é feito de spans: cada span é um pedaço de trabalho com começo, fim e um nome. “Receber o pedido HTTP”, “consultar o banco”, “chamar o pagamento”, “gravar o arquivo” — cada um é um span, e todos carregam o mesmo trace_id, a etiqueta que amarra a história.

Os spans têm hierarquia: cada um aponta para o span que o originou (o pai). É isso que permite desenhar a árvore em vez de uma lista solta, e é isso que responde “o tempo foi gasto dentro de qual chamada”.

trace
A história completa de uma requisição, identificada por um trace_id de 32 caracteres hexadecimais.
span
Um trecho dessa história: nome, início, duração, atributos e o resultado (sucesso ou erro).
span_id
O identificador do span, de 16 caracteres. O span pai é referenciado no parent_span_id.
contexto
O conjunto trace_id + span_id que viaja junto com a requisição entre serviços.
atributos
Pares chave-valor que dão sentido ao span: http.status_code, db.system, usuario.id.
amostragem
A decisão de guardar ou descartar um trace. Guardar 100% custa caro; guardar 5% costuma bastar.

Um aviso para quem está começando: trace não é log com mais campos. Ele é estruturado em árvore e pensado para ser consultado por tempo e por serviço, não lido de cima a baixo. Um trace com oitenta spans é normal e é para ser explorado na interface, não impresso.

4. A propagação de contexto

Se cada programa criasse o seu próprio trace_id, você teria três traces separados e nenhuma história. Para virar um trace só, a identificação viaja junto com a requisição, num cabeçalho HTTP. O padrão atual chama-se W3C Trace Context e o cabeçalho é o traceparent:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

Lendo da esquerda para a direita: a versão do formato (00), o trace_id, o span_id de quem está chamando e os flags (01 quer dizer “amostrado, guarde este trace”). O serviço que recebe lê esse cabeçalho, cria o seu span como filho daquele span_id e repassa adiante na próxima chamada.

O ponto de falha clássico é aqui. Basta uma biblioteca HTTP que não repassa o cabeçalho para a história quebrar: você vê o span do site, o span do pagamento, mas eles não se ligam, e o trace aparece partido em dois. É por isso que “instrumentar” não é só instalar uma biblioteca — é garantir que todo cliente HTTP e todo consumidor de fila saiba propagar o contexto.

Do lado de dentro do processo, o contexto também precisa estar disponível para quem escreve o log. É o que permite carimbar o trace_id em cada linha e, depois, pular do log para o trace na interface com um clique.

5. OpenTelemetry: um padrão, não um produto

OpenTelemetry (OTel, na conversa) é o projeto que padronizou as três coisas necessárias para instrumentar: a API (as chamadas que o seu código faz para criar spans), o SDK (a implementação que faz o trabalho dentro do processo) e o protocolo de envio (OTLP). Antes dele, cada fornecedor tinha a sua biblioteca, e trocar de fornecedor significava reescrever o código.

O terceiro pedaço é o coletor (OpenTelemetry Collector): um programa que recebe os dados, processa e exporta para onde você quiser. Ele existe porque ninguém quer que cada aplicação saiba falar com três fornecedores, aplicar regras de amostragem e lidar com retentativa. A aplicação manda para um endereço só; o coletor decide o resto — e, quando o fornecedor muda, muda a configuração dele, não o código.

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318
processors:
  batch: {}
exporters:
  otlp:
    endpoint: jaeger:4317
    tls:
      insecure: true
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp]

Essa configuração tem três blocos, e a leitura é sempre a mesma: receivers é por onde entra, exporters é para onde vai, processors é o que acontece no meio (o batch junta spans em lotes para não fazer uma chamada por span). O bloco service.pipelines liga as pontas.

6. O coletor no cluster

No Kubernetes, o coletor é um Deployment como outro qualquer, com a configuração num ConfigMap e as portas declaradas. A caixa abaixo tem as duas peças: o ConfigMap com a configuração e o Deployment que o monta.

Crie o ConfigMap otel-collector-config, aponte o volume para ele montado em /etc/otelcol e declare a porta 4317 no container.

As portas do coletor são poucas e vale conhecê-las, porque é nelas que os erros de conexão aparecem: a 4317 é o OTLP em gRPC (a mais usada), a 4318 é o OTLP em HTTP, e algumas imagens expõem ainda uma porta de métricas internas e uma de saúde.

Uma escolha de desenho aparece aqui: o coletor pode ser um Deployment (uma instância que serve todos os pods) ou um DaemonSet (uma instância por nó). O Deployment é mais simples e concentra a configuração num lugar; o DaemonSet evita que todos os pods de todos os nós mandem tráfego para uma única instância, o que ajuda quando o volume é grande. Para a padaria, um Deployment resolve.

7. Instrumentar a aplicação

Com o coletor no ar, a aplicação precisa saber três coisas: para onde mandar, como se chamar e quanto amostrar. Em muitas linguagens isso é feito só com variáveis de ambiente, sem mudar uma linha de código — o SDK lê as variáveis e se configura.

A caixa abaixo tem o Deployment do site. As variáveis estão com o nome errado (o SDK ignora o que não conhece, e o resultado é silêncio: nenhum span aparece e nenhum erro é registrado). Conserte os dois nomes e os valores.

Troque OTEL_ENDPOINT por OTEL_EXPORTER_OTLP_ENDPOINT e aponte para http://otel-collector:4317.

O valor http://otel-collector:4317 usa o nome do Service do coletor — e aqui aparece uma ligação direta com a aula de DNS interno: dentro do cluster, o nome curto resolve porque existe um Service com esse nome no mesmo namespace. Se o coletor estiver em outro namespace, o endereço precisa do sufixo (otel-collector.observabilidade.svc.cluster.local) ou você configura OTEL_EXPORTER_OTLP_ENDPOINT com o nome completo.

Outra variável que muda o jogo é OTEL_TRACES_SAMPLER. O padrão costuma ser amostrar tudo, e amostrar tudo em produção é uma conta alta no fim do mês. Valores comuns são parentbased_traceidratio com OTEL_TRACES_SAMPLER_ARG=0.05, que guarda 5% dos traces e mantém a decisão coerente na cadeia inteira — se o pai foi amostrado, os filhos também são.

Esse formato é o que o exporter debug imprime: um resumo por lote e, em seguida, os detalhes de cada span. Serve para provar que a instrumentação funciona antes de apontar para o armazenamento de verdade — é o equivalente a um echo no lugar de um envio real.

Do lado da aplicação, o ganho é carimbar o trace_id em cada linha de log. Aí o log deixa de ser uma frase solta e vira um endereço para a história completa (transcrição):

15:52:02 GET /pedido/1042 200 812ms trace_id=4bf92f3577b34da6a3ce929d0e0e4736 span_id=00f067aa0ba902b7
15:52:02 consulta de precos: 640ms db=postgres tabela=precos
15:52:03 cobranca aprovada: 150ms gateway=pix

Com o trace_id na mão, você abre a interface do armazenamento (Jaeger, Tempo, o que for), cola o identificador e vê a árvore. É nesse momento que o “812 ms sem explicação” vira “640 ms esperando o banco”: o span da consulta tem 640 ms e o span do site tem 812 — o resto é o site esperando.

Para abrir a interface de um Jaeger que está rodando no cluster, o caminho é o mesmo da aula de portas: um túnel do seu notebook até o pod. A caixa abaixo erra a porta — aponta para a 16685, que é o gRPC do Jaeger, e não a interface.

A interface do Jaeger escuta na 16686. Conserte a porta de destino e abra o túnel.

kubectl run jaeger --image=jaegertracing/all-in-one:1.62
kubectl port-forward pod/jaeger 16686 16685
ana@notebook:~$ kubectl run jaeger --image=jaegertracing/all-in-one:1.62

Depois disso, http://localhost:16686 no navegador é a busca de traces. Escolha o serviço cardapio, o período e clique: a lista mostra os traces mais lentos primeiro. O túnel morre quando você fecha o terminal — e é bom que morra, porque a interface do Jaeger em produção aberta para a internet é um vazamento de dados internos.

9. O que o Kubernetes tem a ver com isso

Uma confusão comum: achar que o Kubernetes “faz tracing”. Ele não faz. O cluster cuida de rodar os pods, dar endereço e reiniciar o que cai. Tracing é decisão da aplicação (instrumentar) somada a um lugar para guardar (o armazenamento). O que o Kubernetes oferece é a infraestrutura onde as três peças vivem.

O que ele facilita é bastante, porém. O coletor sobe como Deployment com a configuração num ConfigMap, escala com réplicas e tem probe apontando para a porta de saúde. O endereço dele é um Service, e por isso a aplicação não precisa saber em qual nó ele está. E o trace_id no log casa com o kubectl logs que você já usa: você acha a linha estranha no log do pod, copia o identificador e abre o trace.

O que ele atrapalha, se você não pensar: pod que reinicia perde o que estava em memória antes de o coletor receber; coletor com uma réplica só vira ponto único de falha; e a decisão de amostragem precisa estar na aplicação, porque o coletor já recebeu o que sobrou. Nada disso é específico de Kubernetes, mas tudo aparece junto com ele.

10. Cenários do dia a dia

Cenário 1: o trace partido em dois

A Ana instrumentou o site e o pagamento, mas os traces apareciam separados. O cliente HTTP usado pelo site não repassava o cabeçalho traceparent — a biblioteca de instrumentação automática dependia de uma configuração que ninguém tinha ligado. Depois de ligar, os dois spans viraram uma árvore e o tempo apareceu onde devia.

Cenário 2: a conta do tracing

O time deixou a amostragem em 100% e, em três semanas, o armazenamento de traces ficou maior que o banco de produção. A correção foi amostrar 5% das requisições, mantendo 100% dos erros — a combinação que dá informação útil sem gastar o orçamento: erro é raro e precisa de trace completo; sucesso é comum e uma amostra basta.

Cenário 3: o coletor que virou gargalo

Uma única réplica do coletor recebia os spans de trinta pods. Quando o tráfego subia, ele atrasava e os spans chegavam fora de ordem ou eram descartados. O conserto foi escalar o coletor para duas réplicas atrás de um Service e reduzir o envio com batch — o processador que junta spans em lotes antes de exportar.

Complete a variável de ambiente que diz ao SDK para onde enviar os spans, apontando para o Service do coletor na porta gRPC.

env: - name: OTEL_SERVICE_NAME value: cardapio - name: value: http://otel-collector:4317

Dica: o nome segue o padrão OTEL_ + EXPORTER + protocolo. Um nome inventado não gera erro: o SDK simplesmente ignora e você não vê span nenhum.

12. Resumo

Trace é a história de uma requisição; span é cada trecho dessa história. Todos os spans de um pedido carregam o mesmo trace_id e apontam para o span pai, formando uma árvore com tempos. O contexto viaja entre serviços no cabeçalho traceparent, e é aí que a instrumentação quebra quando uma biblioteca não repassa o cabeçalho.

OpenTelemetry padroniza API, SDK e protocolo; o coletor recebe, processa e exporta, o que permite trocar o destino sem tocar no código. No cluster, o coletor é um Deployment com a config num ConfigMap, portas 4317 (gRPC) e 4318 (HTTP), endereço atrás de um Service. A aplicação se configura por variáveis de ambiente, e a amostragem é o botão que decide a conta no fim do mês.

Use métrica para saber que existe problema, trace para localizar e log para entender o detalhe — com o trace_id carimbado no log, os três se conversam. Na aula de Helm a Ana sai da observação e entra na entrega: como parar de copiar manifesto para três ambientes, começando pelo Helm.

Para lembrar
  • Trace = requisição inteira; span = um pedaço, com início, fim e resultado.
  • trace_id amarra; parent_span_id dá a hierarquia.
  • O contexto viaja no traceparent (W3C): versão, trace, span, flags.
  • Coletor: recebe (4317/4318), processa (batch), exporta.
  • A aplicação aponta para o Service do coletor via OTEL_EXPORTER_OTLP_ENDPOINT.
  • Amostragem é decisão de custo: guarde menos sucesso e mais erro.
