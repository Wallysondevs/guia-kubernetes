ServiceAccounts

Toda vez que a Ana usa o kubectl, o cluster sabe quem ela é: a identidade vem do arquivo de acesso. Mas e o pod? Quando o gerador de relatórios precisa listar os pods por conta própria, quem ele diz ser? Pod não tem carteira de identidade no bolso — tem uma ServiceAccount, um objeto que o cluster cria, nomeia e entrega dentro do pod como um token. Nesta aula a Ana cria a conta de serviço do gerador, vê o token que aparece montado no sistema de arquivos, descobre como desligar essa montagem quando não é necessária e aprende a dar permissão para o pod sem dar permissão para gente.

Você vai aprender
  • O que é uma ServiceAccount e por que ela não é um usuário.
  • Que todo namespace já tem a conta default, e o que isso significa.
  • Criar uma conta e apontá-la no pod com serviceAccountName.
  • Onde o token aparece dentro do container e para que serve cada arquivo.
  • Desligar a montagem com automountServiceAccountToken: false.
  • Dar permissão para a conta com um binding e testar com auth can-i.

1. A cena: o pod que precisava perguntar

O gerador de relatórios da padaria é um programa pequeno que roda de madrugada. Ele soma os pedidos do dia e publica o resultado. Até aí, nada de especial: um pod comum, uma imagem, um horário. O problema apareceu quando a Ana quis que ele mesmo verificasse se o cardápio estava no ar antes de gerar o relatório — ou seja, que ele chamasse o API server e perguntasse “quantos pods do cardápio estão rodando?”.

Um programa dentro de um pod não tem usuário, não digita senha e não faz login. Ele precisa de uma identidade que o cluster reconheça e que possa ser limitada. Essa identidade é a ServiceAccount — conta de serviço, no português possible. É um objeto como outro qualquer: tem nome, namespace e pode receber permissões por binding. A diferença é que ninguém “entra” com ela: o pod já nasce com ela.

E há um detalhe que surpreende: mesmo quando você não pede, o pod recebe uma. Todo namespace tem uma conta chamada default, criada automaticamente pelo cluster, e todo pod que não especifica outra usa essa. É por isso que o describe de um pod sempre mostra uma linha Service Account: default, mesmo nos manifestos mais simples do guia.

2. Usuário não é conta de serviço

A confusão é natural, porque as duas coisas aparecem no mesmo lugar do RBAC: no campo subjects de um binding. Mas elas vivem em mundos diferentes. Um usuário não existe como objeto no cluster — o nome dele vem do certificado ou do provedor de identidade, e o Kubernetes apenas compara textos. Uma ServiceAccount existe: você cria, lista, descreve e apaga, e o cluster guarda o objeto no namespace.

Guarde a última linha: ServiceAccount é para pod. Um erro comum é criar uma conta de serviço por pessoa, para “organizar” o acesso de gente. Isso não funciona bem por dois motivos. Primeiro, o token de uma conta de serviço pode ser lido por qualquer um que tenha acesso ao pod — não é segredo de pessoa. Segundo, o RBAC não distingue quem usou a conta: se três pessoas compartilham a mesma ServiceAccount, a auditoria mostra sempre o mesmo nome.

serviceAccountName
O campo do spec do pod que escolhe a conta. Sem ele, vale a default do namespace.
default
A conta que todo namespace ganha ao nascer. Não tem permissão além do básico de leitura pública da API.
token projetado
Um JWT temporário, ligado ao pod e à conta, que o kubelet escreve em /var/run/secrets/kubernetes.io/serviceaccount/token e renova antes de vencer.
automountServiceAccountToken
Campo booleano que liga ou desliga a montagem do token. Pode ficar no pod ou na própria conta; o do pod vence.
system:serviceaccount
O prefixo do nome que a conta recebe dentro da API: system:serviceaccount:NAMESPACE:NOME.

3. A conta default de todo namespace

Antes de criar qualquer coisa, vale ver o que já existe. A caixa abaixo é um terminal. O comando descreve um pod que ainda não existe — rode primeiro para ver o erro e depois crie o pod e descreva-o. Repare que o pod “ganha” uma identidade sem que ninguém tenha pedido.

O primeiro comando sozinho não funciona: ainda não existe pod para descrever. Crie o pod cardapio com a imagem cardapio:1.0 e depois descreva-o para ver qual conta ele usa.

kubectl describe pod cardapio
ana@notebook:~$ kubectl describe pod cardapio
Error from server (NotFound): pods "cardapio" not found

kubectl run cardapio --image=cardapio:1.0
kubectl describe pod cardapio

O describe traz Service Account: default na terceira linha, ao lado de Priority. Nada disso foi escrito por você: é o preenchimento automático do cluster, do mesmo tipo que já apareceu em outras aulas com restartPolicy: Always. A listagem das contas, que no cluster real mostra a default, aqui no painel responde No resources found — o motor não semeia essa conta, e essa é mais uma diferença dele com o servidor de verdade:

ana@notebook:~$ kubectl get serviceaccounts
NAME      SECRETS   AGE
default   0         12d

A coluna SECRETS em zero confunde quem estudou Kubernetes em material antigo. Até a versão 1.24, criar uma conta gerava também um Secret com um token permanente, e o pod lia dali. Hoje o token é projetado e temporário, criado na hora em que o pod sobe — por isso a conta não tem Secret nenhum e o 0 está correto.

Essa conta default é inofensiva por um motivo específico: ela não tem permissão para nada além do que todo mundo tem (listar informações públicas da API). Se o seu pod precisa fazer alguma coisa, ele vai precisar de outra conta e de um binding — e é aí que a história fica interessante.

4. Criando a conta do gerador

Uma ServiceAccount tem o manifesto mais curto do guia: apiVersion, kind, metadata.name e, quando você quer garantir, metadata.namespace. Só isso. Não há spec, não há senha, não há e-mail. O “conteúdo” dela é o nome e o namespace — o resto é o cluster.

O pod já pede a conta relatorio, mas ela não foi criada — e o painel não reclama disso. Acrescente o documento do ServiceAccount no começo do arquivo e rode.

apiVersion: v1
kind: Pod
metadata:
  name: gerador
spec:
  serviceAccountName: relatorio
  containers:
    - name: gerador
      image: cardapio:1.0
pod/gerador created

No resources found in default namespace.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: relatorio
---
apiVersion: v1
kind: Pod
metadata:
  name: gerador
spec:
  serviceAccountName: relatorio
  containers:
    - name: gerador
      image: cardapio:1.0

A resposta traz serviceaccount/relatorio created, pod/gerador created e a tabela das contas. Note o campo do pod: serviceAccountName, no spec, nível de cima — não dentro do container, porque a identidade é do pod inteiro. Todos os containers do pod compartilham a mesma conta.

Agora, a parte honesta: no painel, o pod é criado mesmo com a conta faltando, porque o motor não roda o plugin de admissão que faz essa checagem. Num cluster de verdade, a criação é recusada na hora:

ana@notebook:~$ kubectl apply -f gerador.yaml
Error from server (Forbidden): error when creating "gerador.yaml": pods "gerador" is forbidden: error looking up service account default/relatorio: serviceaccount "relatorio" not found

Essa é uma transcrição de cluster real, e a frase diz tudo o que você precisa: o namespace (default), o nome que faltou (relatorio) e o objeto que não foi encontrado (serviceaccount). O conserto é criar a conta antes do pod — a mesma lógica de ordem que já apareceu com namespaces. No painel, use a meta como bússola: ela confere os dois objetos, e é assim que você sabe que a conta foi criada de verdade.

5. O token que aparece dentro do pod

Aqui está o mecanismo. O cluster monta no pod um volume projetado chamado kube-api-access- mais um sufixo, em /var/run/secrets/kubernetes.io/serviceaccount/. O kubelet mantém esse diretório atualizado enquanto o pod vive. Dentro dele há três arquivos, e cada um resolve um problema:

ArquivoO que éPara que o programa usa
tokenum JWT curto, ligado àquele podmandar em Authorization: Bearer
ca.crto certificado da autoridade do clusterconfiar no API server sem “pular” a verificação
namespaceo namespace do pod, em texto purosaber onde procurar os objetos

Duas características desse token merecem atenção. A primeira: ele expira (por padrão em torno de uma hora) e o kubelet renova sozinho, reescrevendo o arquivo. Um programa que lê o token uma vez e guarda em memória por horas vai falhar com Unauthorized depois de um tempo — o certo é ler do arquivo a cada chamada, ou usar uma biblioteca cliente que já faz isso. A segunda: o token é bound, isto é, amarrado àquele pod e àquela conta. Se você copiar o arquivo para fora e tentar usar em outro lugar, ele não vale como identidade eterna — e isso é proposital.

No painel, o describe mostra Mounts: <none> e um volume projetado genérico, porque o motor não injeta esse volume: ele só guarda o que você escreveu. No cluster real, a mesma linha traz /var/run/secrets/kubernetes.io/serviceaccount from kube-api-access-7k2m9 (ro). A diferença é do simulador, não do seu manifesto.

6. Desligando a montagem quando ela não serve

Nem todo pod conversa com a API. O site da padaria só responde páginas; ele nunca lista pods nem lê Secrets. Para esses pods, o token é peso morto: um arquivo com credencial dentro de um container que não precisa dele. Se alguém conseguir executar código ali, o token vai junto. Desligar é uma linha, no spec do pod:

Este pod monta o token sem precisar. Troque o valor de automountServiceAccountToken para false e rode: o -o yaml do painel tem de mostrar o campo desligado.

apiVersion: v1
kind: Pod
metadata:
  name: cardapio
spec:
  automountServiceAccountToken: true
  containers:
    - name: web
      image: cardapio:1.0
      ports:
        - containerPort: 8080
pod/cardapio created

O campo existe em dois níveis, e o do pod vence: se a ServiceAccount diz true e o pod diz false, não há token. O nível da conta serve para o caso oposto — uma conta usada por muitos pods, em que você quer desligar por padrão e ligar só nos poucos que precisam. E sim: desligar não impede o pod de rodar, nem muda o Service Account que aparece no describe. A conta continua sendo a identidade do pod; só o token deixa de ser montado.

Se o seu programa fala com a API, aí é o contrário: mantenha a montagem e dê permissão à conta. Um pod com token e sem binding é um pod que se autentica e leva Forbidden em tudo — o que, aliás, é um bom estado de partida: identidade sim, poder não.

7. Dando permissão para a conta

A ServiceAccount entra no RBAC como qualquer subject, com uma diferença: ela precisa do campo namespace, porque o nome dela só é único dentro de um namespace. Um binding para a conta relatorio do namespace default fica assim — kind: ServiceAccount, name: relatorio, namespace: default.

Do lado de dentro, a identidade que aparece na API tem um formato comprido: system:serviceaccount:default:relatorio. É esse texto que você usa quando quer perguntar em nome da conta. A transcrição abaixo é de um cluster real, com um Role de leitura de pods ligado à conta:

ana@notebook:~$ kubectl auth can-i list pods --as=system:serviceaccount:default:relatorio
yes
ana@notebook:~$ kubectl auth can-i delete pods --as=system:serviceaccount:default:relatorio
no
ana@notebook:~$ kubectl auth can-i list pods --as=system:serviceaccount:default:cardapio
no

As duas primeiras linhas são a conta com binding: lê, não apaga. A terceira é outra conta do mesmo namespace, sem binding nenhum — e a resposta é no. Repare que não existe “herança” entre contas: cada uma começa do zero e só tem o que os bindings dela dão.

O mesmo efeito que o token provoca no programa (um Forbidden no meio da madrugada) aparece para você assim:

ana@notebook:~$ kubectl logs gerador
Servindo o cardapio na porta 8080
erro ao listar pods: pods is forbidden: User "system:serviceaccount:default:relatorio" cannot list resource "pods" in API group "" in the namespace "default"

Essa linha de erro é a mais útil do assunto: ela mostra o nome completo da identidade e o que faltou. Se aparecer system:serviceaccount:default:relatorio onde você esperava outra conta, o pod está com o serviceAccountName errado. Se o nome estiver certo e o verbo faltando, é o binding. E se aparecer Unauthorized em vez de Forbidden, o token não foi montado ou venceu — volte ao automountServiceAccountToken.

8. O que muda no pod (e o que não muda)

Vale separar o que a conta de serviço é do que ela faz, porque a expectativa errada aqui custa tempo. Ela muda três coisas no pod: a identidade que o programa usa ao falar com a API, o conteúdo do volume projetado, e o que aparece no Service Account do describe e nos eventos de auditoria do cluster.

O que ela não muda é igualmente importante. Não é usuário do sistema operacional: o processo continua rodando com o UID que a imagem define (isso é assunto de securityContext, na aula seguinte). Não dá acesso ao nó nem ao disco. Não substitui um Secret: se o programa precisa de uma senha de banco, ela vem de um Secret, não da conta. E não sobrevive ao pod: quando o pod morre, o token morre com ele.

Um uso legítimo e pouco conhecido: a ServiceAccount pode carregar imagePullSecrets, as credenciais para baixar imagens de um registro privado. Em vez de repetir o segredo em cada pod, você põe na conta e aponta o serviceAccountName. É a mesma ideia dos bindings: escrever uma vez, referenciar muitas.

Fechando o assunto com uma regra de bolso: a conta deve ter exatamente o que o programa precisa para funcionar, e nada mais. Um pod que só lê pods precisa de get e list em pods. Um pod que só escreve relatórios em outro serviço provavelmente não precisa de token nenhum — e aí o caminho é desligar a montagem, não criar um binding “por garantia”. Cada permissão a mais é uma linha a menos de surpresa quando alguém invade o container.

E vale lembrar do custo de esquecer: contas de serviço antigas, sem uso, com permissões largas, são um dos achados mais comuns em auditoria de cluster. Como elas não têm senha para vencer e ninguém “sai” delas, só desaparecem quando alguém apaga o objeto — e apagar é seguro justamente quando o binding some primeiro.

9. Cenários do dia a dia

Cenário 1: o pod que funcionava e parou de manhã

O gerador lia o token uma vez, na inicialização, e guardava. Funcionava à noite; a partir de certo horário, Unauthorized em tudo. O token tinha vencido, e o programa não relia o arquivo. O conserto foi mexer na biblioteca cliente para ler a cada chamada — não foi permissão, e por isso nenhum binding resolvia.

Cenário 2: a conta criada no namespace errado

A Ana criou relatorio em padaria, mas o pod rodava em default. O cluster recusou a criação do pod com serviceaccount "relatorio" not found — e o nome existia, só não ali. ServiceAccount é objeto de namespace: o mesmo nome em dois namespaces são duas contas diferentes.

Cenário 3: a conta com poder de admin

Para “destravar” um deploy, alguém ligou a conta default do namespace a um ClusterRole de admin. Todo pod daquele namespace passou a poder apagar qualquer coisa, inclusive os vizinhos. O problema não foi o binding — foi o escopo: uma conta usada por todo mundo deveria ter o mínimo, e o mínimo quase nunca é admin.

Exercício: o nome comprido da identidade

Um pod do namespace padaria usa a conta relatorio. Complete o nome que aparece na API e no auth can-i --as=:

--as=system:serviceaccount:padaria:

Dica: o formato é system:serviceaccount:NAMESPACE:NOME. Um erro de digitação aqui faz o can-i responder no para uma conta que existe.

11. Resumo

ServiceAccount é a identidade do pod: um objeto de namespace, sem senha, criado por você (ou pelo cluster, no caso da default) e apontado no spec.serviceAccountName. Todo pod tem uma; sem escolher, é a default, que não dá poder nenhum além do básico.

O cluster monta um volume projetado em /var/run/secrets/kubernetes.io/serviceaccount/ com token, ca.crt e namespace. O token expira e é renovado, então leia do arquivo a cada chamada. Pod que não fala com a API deve desligar a montagem com automountServiceAccountToken: false.

Permissão para conta de serviço é RBAC normal: binding com kind: ServiceAccount, mais o namespace dela, e teste com --as=system:serviceaccount:NAMESPACE:NOME. Criar a conta antes do pod é obrigatório no cluster de verdade. Na próxima aula a Ana conhece o ClusterRole, o objeto que existe justamente para o que não cabe dentro de um namespace.

Para lembrar
  • ServiceAccount = identidade de pod; User = gente. Não misture os dois.
  • Todo namespace tem a conta default, usada por quem não escolhe outra.
  • Token em /var/run/secrets/kubernetes.io/serviceaccount/token; expira e é renovado.
  • automountServiceAccountToken: false tira o token de quem não precisa dele.
  • Binding de ServiceAccount exige namespace no subject; o nome na API é system:serviceaccount:NS:NOME.
