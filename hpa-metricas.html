HPA e métricas

O HPA da Ana está escrito, apontando para o Deployment certo, com piso e teto razoáveis — e não faz nada. A tabela mostra TARGETS <unknown>/70% e o número de réplicas não sai do lugar. O problema não está no HPA: está no número que ele precisa ler. Nesta aula a Ana descobre de onde vem esse número, por que ele depende de um servidor de métricas que ninguém instalou por padrão, o que os requests têm a ver com a porcentagem e como pedir ao HPA que olhe mais de uma métrica ao mesmo tempo.

Você vai aprender
  • O caminho da métrica: kubelet, metrics-server, API e HPA.
  • O que kubectl top faz e o que significa Metrics API not available.
  • Por que requests é o denominador da porcentagem.
  • A lista metrics: CPU, memória e o critério de “a maior vence”.
  • averageUtilization e averageValue: quando usar cada um.
  • Métricas customizadas, adaptadores e o que investigar quando o número não bate.

1. A cena: o TARGETS que não sai do lugar

O HPA do cardápio foi copiado de um tutorial, com averageUtilization: 70 e maxReplicas: 6. No cluster de teste da Ana ele funciona; no cluster novo, não. O kubectl get hpa mostra TARGETS <unknown>/70% e REPLICAS 2 congelado. O kubectl describe hpa diz, nos eventos, FailedGetResourceMetric e uma frase sobre não conseguir ler a métrica de CPU dos pods.

O instinto é mexer no HPA: aumentar o maxReplicas, trocar o alvo para 50%, recriar o objeto. Nada disso resolve, porque o HPA não está quebrado: ele está pedindo um dado que ninguém está publicando. É como reclamar que a balança não marca o peso quando ninguém subiu nela. Antes de ajustar a conta, é preciso garantir que os dois números da conta existam.

Esta aula é sobre esses dois números. O de baixo, o request, é você quem escreve no manifesto. O de cima, o consumo, vem de um componente do cluster que precisa estar instalado e saudável. Quando os dois existem, o HPA funciona; quando um falta, o TARGETS vira <unknown> e o autoscaler, com razão, não chuta.

2. O caminho da métrica: do kubelet ao HPA

O consumo de CPU e memória de um container não é medido pelo HPA nem pelo API server. Quem mede é o kubelet, o agente que roda em cada nó e conversa com o runtime de containers. Ele lê os números do cgroup — o mecanismo do Linux que agrupa processos e contabiliza recursos — e os expõe num endpoint local do próprio nó. Nenhum outro componente do cluster enxerga esse endpoint diretamente.

No meio do caminho existe um componente chamado metrics-server. Ele roda como um Deployment no namespace kube-system, descobre os nós, vai até o kubelet de cada um, coleta os números de todos os pods e os publica numa API do próprio Kubernetes: metrics.k8s.io. É essa API que o kubectl top consulta, e é ela que o HPA consulta. Sem o metrics-server, a API não existe, e tanto o top quanto o HPA ficam sem resposta.

O fluxo completo, em ordem: kubelet mede → metrics-server coleta (a cada 15 segundos, por padrão) → API metrics.k8s.io serve → HPA lê a média dos pods do alvo → HPA calcula → HPA escreve spec.replicas. Se qualquer elo dessa corrente faltar, o resultado é o mesmo <unknown>. Por isso o diagnóstico começa pelo elo mais fácil de testar, que é o kubectl top.

Vale saber que o metrics-server não guarda histórico. Ele serve o retrato do momento, e o HPA é quem decide como usar esse retrato (para subir, usa o valor mais recente; para descer, olha a janela de estabilização). Quem quer histórico de verdade — gráficos, consultas, alertas — usa Prometheus, que é outro produto, com outro custo e outro assunto.

3. kubectl top: o teste de dez segundos

kubectl top pods mostra CPU e memória de cada pod agora; kubectl top nodes faz o mesmo por nó. É o comando mais rápido para responder “existe métrica neste cluster?”. Num cluster com metrics-server funcionando, a saída é uma tabela curta:

cardapio-6d9c8f7b5b-9p7wl    19m          35Mi

$ kubectl top nodes

guia-control-plane   182m         9%     1104Mi          26%
guia-worker          241m         12%    1650Mi          40%

Num cluster sem metrics-server, os dois comandos respondem a mesma frase: error: Metrics API not available. Essa mensagem é ouro, porque separa dois mundos: se ela aparece, o problema é de infraestrutura (falta instalar ou o servidor está quebrado); se o top funciona mas o HPA mostra <unknown>, o problema é de configuração do alvo — quase sempre falta de requests ou métrica customizada sem adaptador.

Suba o cardápio e complete o diagnóstico: rode o top dos pods e o dos nós. O painel se comporta como um cluster sem metrics-server — a mensagem de erro é a resposta que você procura.

O painel desta aula não roda um cluster com métricas: ele responde exatamente o que um cluster sem metrics-server responde. Isso é proposital — o erro é a lição. Num kind recém-criado, o metrics-server não vem instalado; num cluster gerenciado de nuvem, costuma vir. A instalação é um apply de um manifesto pronto, e no kind ela precisa de um ajuste por causa do certificado do kubelet:

$ kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
serviceaccount/metrics-server created
deployment.apps/metrics-server created
...

$ kubectl -n kube-system patch deployment metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
deployment.apps/metrics-server patched

$ kubectl top nodes
NAME                 CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
guia-control-plane   180m         9%     1098Mi          26%

Esse --kubelet-insecure-tls é um remédio para laboratório: os certificados que o kind gera para os kubelets não são assinados por uma autoridade que o metrics-server confie. Em produção, o caminho é configurar os certificados, não desligar a verificação. É um dos raros casos em que o tutorial da internet está certo para o seu laboratório e errado para o seu trabalho.

4. requests é o denominador

Aqui está a parte que quase ninguém entende na primeira leitura. Quando o HPA diz que a CPU está em 142%, isso não significa “142% de um núcleo”. Significa 142% do request de CPU daquele container. Se o pod pede 200m e está usando 284m, a conta é 284 ÷ 200 = 1,42, ou 142%. Sem requests, não há denominador — e sem denominador, não há porcentagem.

É por isso que o HPA de CPU exige requests em todos os containers do alvo. Um pod sem request aparece como <unknown> na média, e se todos estiverem sem, o HPA não tem o que calcular. O erro é silencioso: o manifesto é aceito, o pod roda, o site funciona — só o autoscaler fica parado. Num Deployment de várias réplicas, basta um container sem request para contaminar a média.

Há uma consequência prática que muda a escolha dos números: o request não é só a reserva que o agendador usa; é também a régua do autoscaler. Se a Ana pedir 200m e o programa normalmente usar 50m, o HPA vai ler 25% e nunca vai escalar, mesmo com o site cheio — porque 25% está muito abaixo de 70%. Se ela pedir 40m e o programa usar 50m, ele lê 125% e escala sem necessidade. Ajustar request é ajustar o humor do HPA.

O cardápio não tem requests de CPU — sem isso o HPA não calcula porcentagem. Coloque requests.cpu: 200m no container e mude o alvo para 60. Rode e leia o TARGETS.

5. Várias métricas: a lista e o “maior vence”

O campo metrics é uma lista, e quase todo manifesto de tutorial mostra um item só. Mas o HPA aceita vários, e o critério é simples: ele calcula a recomendação de réplicas para cada métrica e escolhe a maior. A lógica é de segurança: se a CPU pede 4 réplicas e a memória pede 6, seis é o número que satisfaz as duas; quatro deixaria a memória estourada.

Combinar CPU e memória é o caso mais comum, e ele resolve um problema real: um programa pode ter CPU tranquila e memória crescendo, ou o contrário. Com uma métrica só, o HPA fica cego para o outro recurso. Com duas, ele escala pelo que estiver pior. O preço é que o comportamento fica mais difícil de explicar — “por que subiu?” passa a ter duas respostas possíveis.

metrics[].type
A família da métrica: Resource (CPU e memória do pod), Pods (métrica customizada por pod), Object (métrica de outro objeto) ou External (fora do cluster).
resource.name
cpu ou memory. Só vale quando o tipo é Resource.
target.type
Utilization (porcentagem do request) ou AverageValue (valor absoluto por pod). Obrigatório: sem ele, a API de verdade recusa o objeto.
target.averageUtilization
A porcentagem alvo, como 60 para 60%. É o campo que o TARGETS mostra depois da barra.
target.averageValue
O alvo em valor absoluto, como 500Mi de memória por pod. Não depende de request.
metric.selector
Para Pods e Object: quais objetos entram na média, por etiqueta. Sem seletor, a métrica pode agregar pods que não interessam.

6. averageUtilization ou averageValue?

As duas formas de alvo respondem perguntas diferentes. averageUtilization pergunta “quanto do que eu pedi você está usando?” e depende do request. averageValue pergunta “quanto você está usando, em número absoluto?” e não depende de nada. Para CPU, a porcentagem é o padrão da indústria porque o custo de CPU é relativo ao que você reservou. Para memória, o valor absoluto costuma fazer mais sentido, porque memória de programa não escala com o request: um processo que usa 300 MB usa 300 MB, tenha ele pedido 256 MB ou 1 GB.

Há um efeito colateral de escolher porcentagem para memória: se o request está superdimensionado, a porcentagem fica baixa e o HPA não escala, mesmo com o pod perto do limite. Se está subdimensionado, a porcentagem fica alta e o HPA escala por um consumo que é normal para o programa. Com averageValue, o alvo é o número que você quer ver de verdade, e o request deixa de interferir.

Não existe escolha “certa” universal: existe a métrica que representa o que dói no seu serviço. Um site que fica lento quando a CPU aperta escala por CPU. Um serviço que estoura memória e morre com OOMKilled escala por memória. Um que processa fila escala pelo tamanho da fila — e aí estamos no território das métricas customizadas.

7. Métricas customizadas e adaptadores

CPU e memória são as únicas métricas que o Kubernetes serve sem ajuda. Todo o resto — tamanho de fila, latência, requisições por segundo, conexões abertas — precisa de um adaptador: um componente que lê a fonte (Prometheus, por exemplo) e publica o número numa API que o HPA entende. São três APIs diferentes, e o tipo da métrica no manifesto diz qual delas usar.

Tipo no manifestoAPI que serveO que medeExemplo da padaria
Resourcemetrics.k8s.ioCPU e memória do próprio poduso de CPU do cardápio
Podscustom.metrics.k8s.iométrica por pod, agregada pela médiapedidos por segundo atendidos por pod
Objectcustom.metrics.k8s.iométrica de outro objeto do clusterprofundidade da fila de um Service
Externalexternal.metrics.k8s.iométrica de fora do clustertamanho da fila no serviço de mensagens

Montar esse caminho é trabalho de algumas horas: instalar o Prometheus, instalar o prometheus-adapter, escrever as regras que traduzem a consulta em métrica e declarar o spec.metrics com o seletor certo. Quando o adaptador não está no lugar, o sintoma é o mesmo de sempre — TARGETS <unknown> —, mas a mensagem do describe hpa muda: em vez de reclamar da métrica de recurso, ela diz que não encontrou a métrica customizada.

Para casos em que a decisão de escalar é por evento (uma mensagem na fila, um job pendente), existe uma alternativa que embala tudo isso: KEDA. Ele cria HPAs por baixo dos panos a partir de gatilhos declarados, e é o caminho comum quando o time não quer escrever adaptador nem consulta. Não é objeto nativo do Kubernetes, então fica como ponte para o Nível 3 — mas vale saber que existe antes de sofrer montando um adaptador do zero.

8. Quando o número não bate: o roteiro

Com métrica no lugar, ainda aparece o clássico “o HPA não escala como eu esperava”. A ordem de investigação é sempre a mesma: primeiro o get hpa, depois o describe hpa, depois o top, depois os requests. Cada passo elimina uma camada, e o evento quase sempre entrega o motivo antes do último passo.

$ kubectl get hpa
NAME       REFERENCE             TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
cardapio   Deployment/cardapio   <unknown>/70%   2         6         2          14m

$ kubectl describe hpa cardapio | tail -n 8
Conditions:

  AbleToScale    True    SucceededGetScale        the HPA controller was able to get the target's current scale
  ScalingActive  False   FailedGetResourceMetric  the HPA was unable to compute the replica count:

$ kubectl get --raw /apis/metrics.k8s.io/v1beta1/nodes

Essa sequência conta uma história completa: o HPA conseguiu ler a escala do alvo (AbleToScale True), mas não conseguiu calcular (ScalingActive False), e o motivo é a API de métricas ausente — confirmado pelo get --raw respondendo NotFound. O conserto é instalar o metrics-server, não mexer no HPA. Quando o get --raw funciona e o top mostra números, o problema muda de lado: ou falta requests, ou o alvo está errado, ou o teto já foi atingido.

9. Cenários do dia a dia

Cenário 1: o cluster de nuvem que veio sem nada

A Ana subiu um cluster num provedor e o kubectl top funcionava no primeiro dia. Duas semanas depois, o HPA parou de reagir. O metrics-server tinha sido instalado por um colega, com duas réplicas, e as duas caíram em CrashLoopBackOff por falta de memória no nó do kube-system. O sintoma apareceu longe da causa: o site não escalava, e o time procurava o problema no HPA. O primeiro comando do diagnóstico deveria ter sido kubectl -n kube-system get pods.

Cenário 2: a memória que nunca chega a 80%

Ela configurou duas métricas, CPU a 70% e memória a 80%, e o HPA só escala pela CPU. O gráfico de memória mostra o pod usando 200 MB, mas o request é 1Gi — 20% de utilização, longe dos 80%. A régua está errada, não o alvo: com averageValue: 400Mi, o HPA passaria a olhar o consumo real em vez da fração de uma reserva que ela nunca usou. Ajustar o request para perto do real resolve tanto a conta do HPA quanto o desperdício de reserva no nó.

Cenário 3: a fila que cresce e o HPA não vê

A padaria passou a receber pedidos por uma fila, e o tempo de espera cresceu. A CPU do cardápio continuava baixa — o programa passa a maior parte do tempo esperando — então o HPA de CPU não tinha por que escalar. O conserto foi uma métrica customizada de profundidade da fila, com adaptador no meio. É o exemplo perfeito de que o HPA só é tão bom quanto a métrica que você escolhe: CPU mede trabalho, não mede espera.

10. Fixando o que ficou

Três perguntas sobre a origem e a régua do número.

1. O TARGETS mostra <unknown>/70% e o kubectl top pods responde Metrics API not available. Qual é o problema?

2. Se o request de CPU de um pod é 200m e o consumo é 284m, o que o HPA lê?

3. O HPA tem duas métricas: uma recomenda 4 réplicas e a outra recomenda 6. Quantas ele tenta deixar?

Exercício: a régua do cardápio

O cardápio pede 250m de CPU e 256Mi de memória. Escreva no HPA uma métrica de memória com alvo absoluto de 200Mi por pod. Depois responda: qual campo do alvo diz que o número é porcentagem em vez de valor absoluto?

target.: Utilization

Dica: averageUtilization anda junto com Utilization; averageValue anda com AverageValue. O target.type é obrigatório na API de verdade.

11. Resumo

O número que o HPA lê não nasce no HPA: o kubelet mede, o metrics-server coleta e publica em metrics.k8s.io, e o autoscaler consulta essa API. Sem metrics-server, kubectl top responde Metrics API not available e o TARGETS vira <unknown>/70%. A instalação é um apply de manifesto pronto; no kind, com o ajuste de certificado do kubelet.

A porcentagem é sempre relativa ao request: 142% significa 142% do que o container pediu, não 142% de um núcleo. Sem request, não há denominador — e é por isso que o HPA de CPU exige requests em todos os containers do alvo. O request, portanto, não é só reserva para o agendador: é a régua do autoscaler.

O campo metrics é uma lista: com várias métricas, o HPA calcula cada uma e escolhe a maior recomendação. Cada item tem um type (Resource, Pods, Object, External) e um target com averageUtilization ou averageValue. Métricas fora de CPU e memória exigem adaptador — Prometheus Adapter ou KEDA — e o diagnóstico segue sempre a mesma ordem: get hpa, describe hpa, top, requests.

Para lembrar
  • kubelet mede, metrics-server publica, HPA lê. Faltou um elo, faltou número.
  • Metrics API not available = infraestrutura; <unknown> com top funcionando = configuração.
  • A porcentagem é sobre o request: 284m ÷ 200m = 142%.
  • Várias métricas: o HPA escolhe a recomendação maior.
  • Memória costuma pedir averageValue; CPU, averageUtilization.
  • target.type é obrigatório; sem ele, a API de verdade recusa o objeto.
