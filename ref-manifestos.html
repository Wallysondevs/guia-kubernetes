Manifestos

Todo manifesto do Kubernetes tem o mesmo começo: quatro blocos, dois espaços de indentação e um kind que decide o resto. A Ana já sabe escrever o do pod; o que ela não lembra de cabeça é qual apiVersion vai com cada tipo — apps/v1? batch/v1? networking.k8s.io/v1? Esta página é a consulta: primeiro o esqueleto, depois o mapa, depois as mensagens de erro que aparecem quando um dos dois está errado.

Como usar esta página
  • A tabela 2 é o mapa que você vai consultar mais: kind → apiVersion.
  • As mensagens de erro estão no fim, com a tradução e o conserto de cada uma.
  • Para a sintaxe do YAML (hífen, indentação, dois-pontos), a aula é A anatomia do YAML.

1. Para que serve esta página (e o que ela não cobre)

Esta é a folha de consulta do formato. Ela responde a três perguntas: quais blocos todo manifesto tem, o que vai dentro de cada um e qual apiVersion acompanha cada kind. Também traduz as mensagens de validação — as que começam com The Deployment "x" is invalid: —, que são as mais fáceis de resolver e as mais assustadoras de ler.

Ela não cobre o significado de cada campo de cada recurso: para isso existem as páginas de consulta Pods, Deployments e Services e Ingress. Também não cobre a sintaxe do YAML em si, nem kubectl apply a fundo — isso fica em A anatomia do YAML e em apply e dry-run.

Vale distinguir duas ideias que costumam andar juntas na cabeça de quem começa. kubectl create é uma ordem pontual: cria e reclama se já existe. kubectl apply é uma convergência: compara o arquivo com o que está no cluster e ajusta a diferença. É por isso que apply pode ser rodado dez vezes com o mesmo arquivo e o resultado é o mesmo objeto — e é por isso que ele é o comando dos manifestos versionados, enquanto o create fica para o improviso.

Uma coisa que vale dizer de saída: o manifesto é a entrada. O cluster responde com um objeto maior, cheio de campos que você não escreveu. Quem entende essa separação nunca se pergunta “por que o meu arquivo não tem uid?” — porque uid é resposta, não pedido.

2. O essencial em 10 linhas

  • Quatro blocos: apiVersion, kind, metadata e spec.
  • apiVersion é texto: v1 para o núcleo, apps/v1 para Deployment.
  • kind é o tipo do objeto, com maiúscula: Pod, Service, Deployment.
  • metadata guarda identidade: name, namespace, labels, annotations.
  • spec guarda o que você quer que exista. O conteúdo muda com o kind.
  • status não se escreve: é o cluster respondendo ao que você pediu.
  • Indentação é estrutura: dois espaços, nunca Tab.
  • Lista é hífen; mapa é chave: valor com um espaço depois dos dois-pontos.
  • --- separa vários objetos no mesmo arquivo.
  • Antes de aplicar, kubectl apply -f arquivo.yaml --dry-run=client ensaia sem enviar.

A última linha é a que economiza mais tempo e a que quase ninguém usa no começo. O --dry-run=client monta o objeto no seu computador, valida o formato e mostra o que seria enviado; erros de digitação aparecem ali, não no cluster. É o equivalente a provar a massa antes de levar ao forno.

Não existe “o manifesto do Kubernetes” no singular: existe um formato comum e um conteúdo por tipo. O que você reaproveita de um Pod para um Deployment são os quatro blocos e a disciplina da indentação; o spec é sempre novo.

E há uma regra de ouro que resolve a maioria dos “não funcionou”: o manifesto descreve um estado desejado, não uma sequência de comandos. Você não diz “crie um pod e depois mexa na imagem”; você diz “quero este pod, com esta imagem”. Quem compara o desejo com a realidade é o controlador — e é por isso que aplicar o mesmo arquivo duas vezes não cria duas coisas.

3. Anatomia de um manifesto

apiVersion
A versão da API que entende aquele kind: v1 (núcleo), apps/v1 (Deployment), batch/v1 (Job). Vem sempre antes do kind.
kind
O tipo do objeto, com maiúscula inicial: Pod, Service, ConfigMap. É o campo que decide qual spec é válido.
metadata
Identidade e organização: name (obrigatório), namespace, labels (para selecionar) e annotations (para registrar).
spec
O que você quer que exista. Cada kind tem o seu: no Pod é a lista de containers; no Service são as portas; no Deployment são réplicas, seletor e template.
status
A resposta do cluster: fase, condições, IPs, contagens. Nunca se escreve no arquivo; aparece no kubectl get -o yaml.

Para treinar a leitura, vale soletrar um Deployment: apiVersion: apps/v1 diz qual API entende aquele tipo; kind: Deployment diz o que é; metadata.name dá o nome; spec.replicas, spec.selector e spec.template respondem “quantas cópias, de qual modelo, e quem são os pods desse modelo”. Dentro do template há um segundo metadata — o do pod que será criado — e um segundo spec, o do pod. É o mesmo esqueleto, um nível mais fundo: um manifesto que fabrica outro manifesto.

Repare que não existe data nem stringData nesta lista: são campos de ConfigMap e Secret, que ficam no nível do objeto, ao lado de spec — e não dentro dele. Isso não é exceção à regra: é o formato daquele tipo. A regra que vale sempre é “os quatro blocos de cima”; o resto é o conteúdo do tipo.

O sufixo /v1 não é decoração: ele faz parte do endereço da API. O kubectl traduz Deployment para apps/v1 por uma tabela interna, e essa tabela é exatamente a do kubectl api-resources — o comando que mostra a versão e o escopo de tudo o que o cluster conhece. Quando você esquecer um apiVersion, é lá que se consulta (a página Recursos da API detalha cada grupo).

Um mesmo kind pode ter mais de uma versão viva ao mesmo tempo, e a escolha muda o que você consegue escrever. O HorizontalPodAutoscaler é o exemplo da casa: autoscaling/v1 aceita só CPU e um alvo só; autoscaling/v2 aceita lista de métricas e o bloco behavior. O kind e o nome do objeto são os mesmos — o que muda é o vocabulário do spec. Quando um campo “não existe” na sua versão, o problema pode ser a versão, não o campo.

Se você estiver na dúvida sobre a versão de um tipo, há dois caminhos de consulta no próprio terminal. kubectl api-resources lista todos os tipos com a versão e o escopo (namespaced ou não), e kubectl explain deployment mostra a versão do tipo seguida dos campos aceitos. Os dois respondem com o que aquele cluster conhece — o que é mais confiável do que qualquer blog, porque inclui os recursos customizados que alguém instalou ali.

Outro detalhe do formato: um arquivo pode ter vários objetos, separados por uma linha com três hífens. O apply lê o arquivo inteiro e aplica na ordem em que os documentos aparecem — o que importa quando um objeto depende de outro, como um ConfigMap antes do Deployment que o monta. A ordem entre namespaces e objetos também conta: o namespace precisa existir antes do primeiro pod que mora nele.

Um cuidado especial com os tipos antigos. Tutoriais de 2019 usam extensions/v1beta1 para Ingress e batch/v1beta1 para CronJob; essas versões foram removidas do Kubernetes 1.22 e 1.25. Copiar o manifesto de um tutorial antigo dá um erro de “no matches for kind”, que assusta e tem conserto de uma linha.

5. Os campos que mais confundem

Quatro confusões respondem por quase todos os manifestos que dão errado na primeira tentativa. Elas não são de sintaxe: são de lugar.

ConfusãoComo é de verdadeO que quebra
labels × annotationslabels são para selecionar (app: cardapio); annotations são para registrar (dono: ana)seletor que não acha nada
metadata.name × metadata.namespaceo nome identifica o objeto dentro do namespace; o mesmo nome pode existir em dois namespacesdois apply que “não se veem”
spec × statusspec é o pedido; status é a resposta — e o servidor ignora status no seu arquivoesperar que o campo replicas do status obedeça ao arquivo
spec.selector × spec.template.metadata.labelso seletor do Deployment precisa casar com as etiquetas do templateselector does not match template labels
apiVersion: v1 × apps/v1só os objetos do núcleo usam v1; Deployment, StatefulSet e DaemonSet usam apps/v1no matches for kind

Um exemplo de cada lado esclarece a primeira linha da tabela. Etiqueta é o que o Service usa para achar pods: app: cardapio vira selector: app: cardapio, e o Service manda tráfego para quem tiver aquilo. Anotação é o que ninguém seleciona: o dono do objeto, o link do chamado, a versão do build. O próprio kubectl apply grava uma anotação com o último arquivo aplicado — útil para diff, invisível para seletores.

Vale decorar a segunda linha da tabela, porque ela explica um comportamento que parece mágica: o namespace faz parte da identidade. Um ConfigMap chamado cardapio em default e outro com o mesmo nome em padaria são objetos diferentes, com histórias diferentes, e um pod só enxerga os do próprio namespace. É por isso que -n muda o resultado de um get — e por isso que “funcionava ontem” costuma ser “ontem eu estava em outro namespace”.

Já a última linha é a que mais aparece em manifesto copiado. A regra prática: se o kind é Pod, Service, ConfigMap, Secret, Namespace, Node ou PersistentVolume, a apiVersion é v1. Todo o resto tem grupo, e o grupo aparece no nome da versão.

A transcrição abaixo é de um cluster de verdade e mostra quatro recusas diferentes. Repare que nenhuma delas diz “erro genérico”: todas apontam o campo.

$ kubectl apply -f sem-api.yaml
The Pod "cardapio" is invalid: apiVersion: Required value

$ kubectl apply -f maiusculo.yaml
The Pod "Cardapio" is invalid: metadata.name: Invalid value: "Cardapio": a lowercase RFC 1123
subdomain must consist of lower case alphanumeric characters, '-' or '.', and must start and end
with an alphanumeric character (e.g. 'example.com', regex used for validation is
'[a-z0-9]([-a-z0-9]*[a-z0-9])?(\.[a-z0-9]([-a-z0-9]*[a-z0-9])?)*')

$ kubectl apply -f vazio.yaml
error: no objects passed to apply

$ kubectl apply -f deployment-v1.yaml
error: resource mapping not found for name: "vitrine" namespace: "" from "STDIN": no matches for
kind "Deployment" in version "v1"
ensure CRDs are installed first

Duas lições saem daí. Required value é “faltou o campo”; Invalid value é “o campo veio, mas com formato errado” — e o texto entre parênteses costuma trazer o exemplo do formato aceito, como o example.com da mensagem do nome. E o caminho do campo, quando tem colchetes (spec.containers[0].image), aponta para o item da lista: o primeiro container, na posição zero.

Quando a mensagem não basta, o campo se descobre com kubectl explain. Ele aceita o caminho completo (kubectl explain deployment.spec.strategy) e imprime o tipo do campo, a descrição e os subcampos — sem internet e sem adivinhação. É o mesmo comando que responde “isto é lista ou mapa?” quando você está na dúvida entre hífen e dois-pontos.

Num cluster de verdade, uma sessão de conserto tem esta cara:

$ kubectl apply -f cardapio.yaml
pod/cardapio created
service/cardapio created

$ kubectl get pod cardapio -o yaml
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: "2026-11-27T15:50:21Z"
  labels:
    app: cardapio
  name: cardapio
  namespace: default
  resourceVersion: "48213"
  uid: 6f1c2a3e-9d4b-4a7e-8c1f-2b3d4e5f6a7b

  containers:

    name: web

Compare o que você escreveu com o que voltou: o spec é seu, e o status + uid + resourceVersion + creationTimestamp são do cluster. Os campos que você não escreveu e aparecem no spec são os padrões que o servidor preencheu — como restartPolicy: Always e a política de pull da imagem.

A primeira caixa monta o mínimo que funciona: um pod com os quatro blocos. A segunda conserta o erro de apiVersion mais comum de todos, o do Deployment escrito com v1.

  replicas: 2

    matchLabels:
      app: vitrine

      labels:
        app: vitrine
    spec:
      containers:
        - name: web
          image: vitrine:1.0

  name: vitrine
spec:
  replicas: 2
  selector:

      app: vitrine

      labels:
        app: vitrine
    spec:
      containers:
        - name: web

As duas caixas desta página rodam no painel do guia, que valida o manifesto com as mesmas regras do cluster: campos obrigatórios, formato de nome, combinação de apiVersion e kind. A mensagem que aparece é a mensagem de verdade, não um resumo — dá para comparar com a tabela de erros linha por linha.

Na primeira caixa, o erro é de validação: o objeto chegou ao servidor e foi recusado porque falta um campo obrigatório. Na segunda, o erro é de roteamento: o servidor nem chegou a validar o spec, porque não existe um tipo Deployment na versão v1. São famílias diferentes de problema, e a mensagem de cada uma diz isso com precisão.

No segundo caso, o erro que o painel mostra é o mesmo do cluster de verdade: error: resource mapping not found for name: "vitrine" ... no matches for kind "Deployment" in version "v1", com a linha ensure CRDs are installed first no fim. Essa última linha é um consolo para quem usa recurso customizado e uma pista falsa para quem só errou a versão: não há CRD nenhuma faltando, há um apiVersion trocado.

8. Para ir além

A leitura recomendada, na ordem em que o guia apresenta:

  • A anatomia do YAML — indentação, listas, --- e os erros de sintaxe.
  • O manifesto do Pod — os quatro blocos aplicados a um caso concreto.
  • apply e dry-run — o ensaio, o create e a diferença.
  • Recursos da API — os grupos, o escopo e o api-resources.
  • Pods — todos os campos do spec do pod.
  • Deployments — réplicas, seletor, estratégia e o mapa até o pod.
  • Services e Ingress — os campos de quem expõe o serviço.
  • kubectl — os verbos e as saídas do comando que aplica o manifesto.

Resumo

Todo manifesto tem apiVersion, kind, metadata e spec — e o status, que é resposta e não se escreve. O kind vem com maiúscula e decide qual spec é válido; o apiVersion vem com minúscula e segue o mapa: v1 para o núcleo, apps/v1 para Deployment, batch/v1 para Job, networking.k8s.io/v1 para Ingress, autoscaling/v2 para HPA, rbac.authorization.k8s.io/v1 para Role.

metadata guarda identidade (nome, namespace, etiquetas e anotações) e spec guarda o desejo. As mensagens de validação têm forma fixa — The TIPO "nome" is invalid: mais o caminho do campo — e as três mais comuns são Required value (faltou), Invalid value (formato errado) e no matches for kind (versão errada). Antes de aplicar, --dry-run=client; depois de aplicar, -o yaml para ver o que o cluster acrescentou.
