Tipos de Secret

A Ana colocou o certificado e a chave privada num Secret, apontou o Ingress para ele e o cadeado nunca apareceu no navegador. O problema era uma palavra: o type estava Opaque, e o controlador de Ingress procura um Secret do tipo kubernetes.io/tls. Nesta aula ela percorre os tipos que importam — o genérico, o do certificado, o do registro de imagens, o de usuário e senha e o do token de conta de serviço —, vê o que cada um exige, o que o cluster valida antes de aceitar e o que acontece quando o tipo não combina com o conteúdo.

Você vai aprender
  • O que o campo type muda — e o que ele não muda.
  • Opaque, data e stringData.
  • kubernetes.io/tls: as duas chaves obrigatórias e o erro quando falta uma.
  • kubernetes.io/dockerconfigjson: o JSON do Docker e o imagePullSecrets.
  • kubernetes.io/basic-auth, ssh-auth e service-account-token.
  • Por que o tipo certo faz uma integração funcionar sem configuração extra.

1. A cena: o cadeado que não apareceu

O site da padaria ia começar a vender com cartão, então precisava de HTTPS. A Ana gerou o certificado, colocou tudo num Secret com as chaves tls.crt e tls.key, apontou o Ingress para ele e esperou. O navegador continuou mostrando o aviso de site não seguro, e o log do controlador repetia uma mensagem seca sobre não encontrar um certificado.

Ela conferiu oito vezes: o nome do Secret estava certo, as chaves estavam certas, o namespace era o mesmo. Faltava uma única linha no manifesto — type: kubernetes.io/tls. Sem ela, o objeto é um mapa de bytes opaco, e é isso que a palavra significa: opaque, sem contrato. O controlador de Ingress não adivinha que aquelas duas chaves são um certificado; ele procura um Secret que declare ser um certificado.

É a diferença entre uma caixa escrita “documentos” e uma caixa escrita “passaporte”. O conteúdo pode ser o mesmo; quem procura passaporte só abre a segunda. O campo type é esse rótulo — e, ao contrário de um rótulo qualquer, ele é verificado pelo cluster na hora do apply.

2. O que o campo type é — e o que ele não é

Todo Secret é um mapa de nomes para valores em base64. O type não muda esse formato: continua sendo um mapa. O que ele faz é declarar um contrato — quais chaves devem existir, com que formato, e quem no cluster sabe ler aquele objeto. É um rótulo com consequências.

A consequência número um é validação: se o contrato exige tls.crt e você não colocou, o servidor recusa o objeto com Invalid ou Required value. A consequência número dois é descoberta: componentes do cluster procuram Secrets por tipo. O controlador de Ingress procura TLS; o kubelet procura dockerconfigjson quando vai baixar imagem de registro privado; o ServiceAccount procura o token. Um Secret com o tipo certo entra na conversa sem configuração extra; com o tipo errado, é invisível para quem precisa dele.

type
O contrato do Secret. Padrão: Opaque. Os tipos do Kubernetes usam o prefixo kubernetes.io/.
data
O mapa de chave para valor em base64. É o que o Secret guarda de verdade.
stringData
Açúcar de escrita: você põe texto puro e o servidor converte para base64 ao gravar.
tls.crt / tls.key
As duas chaves que o tipo kubernetes.io/tls exige.
.dockerconfigjson
A chave (com ponto no começo) que o tipo dockerconfigjson exige: o JSON do Docker.
imagePullSecrets
A lista, no pod, de Secrets que o kubelet usa para autenticar no registro de imagens.

Uma observação que economiza confusão: o tipo não criptografa nada. Um Secret Opaque e um Secret kubernetes.io/tls são igualmente legíveis por quem tem permissão de ler Secrets no namespace. O tipo é sobre forma, não sobre segurança. Segurança vem de RBAC, de não versionar o valor e de não deixar o segredo em log — assuntos que já apareceram e voltam na aula de boas práticas.

3. Opaque: o genérico

Opaque é o tipo padrão, e é o que você usa quando não existe um tipo melhor. Senha de banco, token de API, uma frase secreta de assinatura: tudo isso é Opaque. Ele não exige chave nenhuma — aceita desde um mapa vazio até vinte chaves com nomes inventados.

O detalhe prático do Opaque é a escolha entre data e stringData. Com data você escreve o valor já em base64 e o que está no arquivo é exatamente o que o cluster guarda. Com stringData você escreve texto puro, legível, e o servidor converte na gravação — o objeto salvo sai com data, e o stringData não fica no objeto. Para manifesto feito à mão, stringData é mais legível e menos sujeito a erro; para manifesto gerado por ferramenta, data é o normal.

Cuidado com uma armadilha de leitura: base64 não é criptografia. czNuaDQ= é “s3nh4” para qualquer pessoa com um comando de terminal. Quem trata base64 como proteção está escrevendo a senha em texto claro com um passo extra.

4. kubernetes.io/tls: o contrato do certificado

O tipo kubernetes.io/tls existe para uma coisa só: dizer “aqui dentro está um certificado e a chave privada dele”. Exige exatamente duas chaves, com nomes fixos — tls.crt (o certificado, em PEM) e tls.key (a chave privada, em PEM). Se faltar uma, o cluster recusa.

ana@notebook:~$ kubectl apply -f tls-padaria.yaml
The Secret "tls-padaria" is invalid: data[tls.crt]: Required value

ana@notebook:~$ kubectl get secrets
NAME          TYPE                DATA   AGE
banco         Opaque              1      3m
tls-padaria   kubernetes.io/tls   2      40s

A primeira linha é o cluster fazendo o trabalho dele: sem tls.crt, o objeto não entra. A segunda mostra o resultado depois do conserto — repare na coluna TYPE, que é onde se vê, de relance, se um Secret é TLS ou genérico. É essa coluna que você confere quando o cadeado não aparece no navegador.

Quem consome esse tipo: o controlador de Ingress (para terminar HTTPS), o próprio servidor de API (para servir TLS no endpoint do cluster) e qualquer programa que monte o Secret como volume esperando /etc/tls/tls.crt e /etc/tls/tls.key. A caixa abaixo pega um Secret genérico com as duas chaves e transforma no tipo certo — que é exatamente o conserto da cena de abertura.

O Secret tem as duas chaves, mas o tipo continua Opaque e o Ingress não declara TLS nenhum. Troque o tipo para kubernetes.io/tls e acrescente o bloco tls no Ingress, com secretName: tls-padaria.

apiVersion: v1
kind: Secret
metadata:
  name: tls-padaria
type: Opaque
data:
  tls.crt: Y2VydGlmaWNhZG8tZmFrZQ==
  tls.key: Y2hhdmUtZmFrZQ==
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: vitrine
spec:
  ingressClassName: nginx
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapio
                port:
                  number: 80
secret/tls-padaria created
ingress.networking.k8s.io/vitrine created

NAME      CLASS   HOSTS          ADDRESS      PORTS     AGE
vitrine   nginx   padaria.test   192.0.2.10   80, 443   10m

apiVersion: v1
kind: Secret
metadata:
  name: tls-padaria
type: kubernetes.io/tls
data:
  tls.crt: Y2VydGlmaWNhZG8tZmFrZQ==
  tls.key: Y2hhdmUtZmFrZQ==
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: vitrine
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - padaria.test
      secretName: tls-padaria
  rules:
    - host: padaria.test
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: cardapio
                port:
                  number: 80

A caixa devolve os dois objetos criados e a linha do Ingress com PORTS 80, 443. As metas conferem o tipo do Secret e o secretName do Ingress, que é o par que faz o cadeado aparecer num cluster de verdade. Uma honestidade necessária: o painel não valida o conteúdo do certificado — ele guarda o que você escreveu. Num cluster de verdade, o servidor valida a presença das chaves; validar se o PEM é um certificado legítimo, e se a chave combina com ele, é trabalho do consumidor (o Ingress, o servidor web) na hora de usar. Certificado vencido, por exemplo, é aceito pelo cluster e recusado pelo navegador.

5. O tipo do registro de imagens

Quando a imagem do site mora num registro privado, o kubelet precisa provar que tem direito de baixá-la. A prova é um Secret do tipo kubernetes.io/dockerconfigjson, com uma única chave obrigatória: .dockerconfigjson — com ponto no começo, porque é o nome que o Docker usa no arquivo ~/.docker/config.json.

ana@notebook:~$ kubectl create secret docker-registry regcred \
  --docker-server=loja.test --docker-username=ana --docker-password=s3nh4

ana@notebook:~$ kubectl get secret regcred -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d
{"auths":{"loja.test":{"auth":"YW5hOnMzbmg0","username":"ana"}}}

O comando create secret docker-registry monta esse JSON para você e grava o resultado em base64. Lendo de volta, aparece o conteúdo real: o servidor, o usuário e o campo auth com usuário e senha concatenados e codificados. É por isso que esse Secret é tão sensível quanto a senha: quem lê o objeto tem a credencial do registro.

Do lado do pod, a ponte é o campo imagePullSecrets, que lista os Secrets que o kubelet deve usar ao baixar imagens. Sem ele, o Secret existe mas ninguém o procura, e o pod fica em ImagePullBackOff com a mensagem de “não autorizado”. A caixa mostra a ligação completa.

O Secret está com o tipo errado e o pod não pede credencial nenhuma. Corrija o tipo para kubernetes.io/dockerconfigjson e faça o pod usar o Secret em imagePullSecrets.

apiVersion: v1
kind: Secret
metadata:
  name: regcred
type: Opaque
data:
  .dockerconfigjson: eyJhdXRocyI6eyJsb2phLnRlc3QiOnsiYXV0aCI6IllXNWhPbk16Ym1nMCIsInVzZXJuYW1lIjoiYW5hIn19fQ==
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: cardapio:2.0
secret/regcred created
pod/web created

NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          9m

apiVersion: v1
kind: Secret
metadata:
  name: regcred
type: kubernetes.io/dockerconfigjson
data:
  .dockerconfigjson: eyJhdXRocyI6eyJsb2phLnRlc3QiOnsiYXV0aCI6IllXNWhPbk16Ym1nMCIsInVzZXJuYW1lIjoiYW5hIn19fQ==
---
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  imagePullSecrets:
    - name: regcred
  containers:
    - name: web
      image: cardapio:2.0

Repare que o Secret e o pod estão no mesmo arquivo, separados por ---. A ordem importa: o Secret precisa existir quando o pod for criado, senão o kubelet não tem o que usar. O painel aplica na ordem do arquivo, então a ordem que você vê é a ordem que roda.

6. basic-auth e ssh-auth: os contratos pequenos

Dois tipos existem para credenciais que aparecem em todo lugar. kubernetes.io/basic-auth exige username e password — as duas chaves, sempre. E kubernetes.io/ssh-auth exige ssh-privatekey, a chave privada SSH em formato PEM.

Nenhum dos dois faz mágica: o programa que consome precisa ler as chaves certas. O valor está na padronização — em vez de cada time inventar user, usuario ou login, o tipo define o nome e o cluster valida a presença. Em ambiente com muitos serviços, isso é o que faz um manifesto de outro time fazer sentido no primeiro olhar.

O clássico da Ana foi o oposto: ela tinha um Secret Opaque com uma chave só, chamada senha, e um programa que esperava username e password. O manifesto estava válido, o pod subia, e a autenticação falhava em silêncio. A caixa mostra a correção: mudar o tipo e acrescentar a chave que faltava.

O Secret guarda só password e se declara Opaque. Transforme-o em kubernetes.io/basic-auth e acrescente username com o valor YW5h (que é “ana” em base64).

apiVersion: v1
kind: Secret
metadata:
  name: banco
type: Opaque
data:
  password: czNuaDQ=
secret/banco created

NAME    DATA   AGE
banco   1      5m

apiVersion: v1
kind: Secret
metadata:
  name: banco
type: kubernetes.io/basic-auth
data:
  password: czNuaDQ=
  username: YW5h

A escolha entre esse tipo e o Opaque é de disciplina, não de funcionamento. Um Secret Opaque com as chaves username e password funciona igual para quem lê secretKeyRef. A diferença aparece na revisão de código e na validação: com o tipo certo, um manifesto sem username é recusado antes de virar problema em produção.

7. service-account-token: o tipo que mudou de casa

O tipo kubernetes.io/service-account-token guarda o token de uma conta de serviço — a identidade que um pod usa para falar com o servidor de API. Historicamente, o Kubernetes criava um Secret desse tipo automaticamente para cada ServiceAccount, e o pod o montava em /var/run/secrets/kubernetes.io/serviceaccount.

Isso mudou. Desde a versão 1.24, o token não nasce mais como Secret: ele é projetado no pod, com prazo de validade e público definidos, e renovado sozinho. Criar um Secret desse tipo à mão ainda é possível e às vezes necessário (para tokens de longa duração, usados por sistemas fora do cluster), mas exige uma anotação que amarra o Secret à conta:

ana@notebook:~$ kubectl apply -f token.yaml
The Secret "token-relatorio" is invalid: metadata.annotations[kubernetes.io/service-account.name]: Required value

ana@notebook:~$ kubectl get secrets
NAME              TYPE                                  DATA   AGE
token-relatorio   kubernetes.io/service-account-token   0      12s
banco             kubernetes.io/basic-auth              2      4m

A primeira linha é a validação do tipo cobrando a anotação kubernetes.io/service-account.name. A segunda é o estado depois do conserto — e o DATA zero é normal nesse tipo: quem preenche o token é o controlador, não você. Você declara o “quero um token para esta conta”; o cluster fabrica o conteúdo.

Um cuidado de leitura: essa anotação tem pontos e barra no nome, então ela não é endereçável por caminho simples em meta de caixa. Por isso, no guia, esse tipo aparece em transcrição e em manifesto de leitura, não como exercício de meta. E há uma limitação honesta do painel: ele não fabrica token nenhum — registra o objeto como você escreveu. A projeção automática de token, com prazo e renovação, é assunto de cluster real.

Duas linhas dessa segunda tabela merecem destaque. A do ImagePullBackOff é a mais comum em empresa: o time cria o Secret com o JSON do Docker mas esquece o imagePullSecrets no pod, e o kubelet nunca olha para o objeto. E a da chave com nome errado é a mais traiçoeira, porque não gera erro nenhum: o manifesto é aceito, o pod sobe, o programa não encontra a variável e falha. O cluster só valida o contrato do tipo; o contrato entre o Secret e o seu código é você quem garante.

9. Cenários do dia a dia

Cenário 1: o certificado que veio de fora

A Ana recebeu do provedor um fullchain.pem e uma private.key. Em vez de renomear os arquivos, usou kubectl create secret tls tls-padaria --cert=fullchain.pem --key=private.key: o comando copia o conteúdo para tls.crt e tls.key, que são os nomes que o tipo exige. O Ingress funcionou de primeira e os arquivos originais ficaram intactos na pasta.

Cenário 2: o registro que funcionava com o Docker e falhava no cluster

O time testava o login com docker login loja.test e tudo funcionava. No cluster, o pod não baixava a imagem. O motivo: o config.json gerado pelo Docker tinha mais de um registro, e o comando create secret docker-registry usado só com um servidor gerou um JSON com um registro. A correção foi passar --from-file=.dockerconfigjson=config.json, reaproveitando o arquivo inteiro.

Cenário 3: o basic-auth que economizou uma reunião

Dois times consumiam a mesma API com nomes de chave diferentes — user num serviço, login no outro. A padronização em kubernetes.io/basic-auth forçou os dois a usar username e password, e o cluster passou a recusar manifesto incompleto. Nenhum código mudou de lógica; mudou o nome das chaves e a validação passou a ser automática.

11. Resumo

type é contrato, não formato: o Secret continua sendo um mapa de base64, mas o tipo declara quais chaves precisam existir e quem sabe ler o objeto. Opaque aceita qualquer chave; kubernetes.io/tls exige tls.crt e tls.key; kubernetes.io/dockerconfigjson exige .dockerconfigjson e depende de imagePullSecrets no pod para funcionar; kubernetes.io/basic-auth exige username e password; ssh-auth exige ssh-privatekey; e service-account-token cobra a anotação da conta.

O cluster valida presença de chave, não a qualidade do conteúdo: certificado vencido, senha errada e JSON malformado passam pelo apply e falham no consumidor. E base64 não é criptografia — quem lê o objeto tem o valor.

Com o tipo certo escolhido, a pergunta seguinte é como o segredo chega ao programa: variável de ambiente é fácil e não atualiza; arquivo montado atualiza e permite permissão restrita. É o assunto da próxima aula — o Secret montado como volume.

Para lembrar
  • Opaque é o padrão e aceita qualquer chave; stringData evita base64 manual.
  • TLS exige tls.crt + tls.key; sem uma delas o apply é recusado.
  • dockerconfigjson exige .dockerconfigjson e imagePullSecrets no pod.
  • basic-auth: username + password; ssh-auth: ssh-privatekey.
  • Token de ServiceAccount não nasce mais como Secret: é projetado no pod.
  • Tipo certo = integração sem configuração extra. Tipo errado = silêncio.
