kubectl

A Ana usa o kubectl todo dia e mesmo assim esquece, de vez em quando, se o nome do pod vem antes ou depois do -o wide. Para isso existe esta página: não é aula, é consulta. Ela foi escrita para ser aberta no meio de uma tarefa, lida em trinta segundos e fechada — procure o comando, copie o exemplo, siga. Quando você precisar do porquê, o fim da página aponta a aula certa.

Como usar esta página
  • Procure com Ctrl + F pelo comando ou pela mensagem de erro.
  • As tabelas vêm antes da prosa de propósito: primeiro o que fazer, depois a explicação.
  • Uma coluna de cada vez: “no painel” diz o que a caixa deste guia consegue mostrar.
  • As duas caixas do fim são exercícios de dez segundos: uma monta o mínimo, a outra conserta.

1. Para que serve esta página (e o que ela não cobre)

Esta é a folha de consulta do comando. Ela cobre a gramática — verbo, tipo, nome e flags —, as saídas mais úteis, as flags que economizam digitação e as mensagens de erro que aparecem quando algo está escrito errado. Cada linha tem um exemplo que funciona se você copiar.

Ela não cobre três coisas, e é bom saber onde achá-las. A instalação e a configuração do kubectl ficam em Instalar kubectl e kind. A sintaxe do YAML fica em A anatomia do YAML. E cada recurso tem a sua própria página de consulta: Pods, Deployments e Services e Ingress. Aqui o assunto é o comando.

Uma convenção que vale para o guia inteiro: nomes em MAIÚSCULA são lugares onde você troca o texto. kubectl get pod NOME quer dizer “escreva o nome do seu pod ali”. Tudo o mais é literal.

Há um detalhe que explica metade dos “não achei” deste guia: o kubectl sempre fala com um cluster e um namespace por vez. O cluster vem do arquivo de configuração (o ~/.kube/config) e o namespace vem do que estiver gravado no contexto atual — quase sempre default. Quando a Ana cria um objeto com -n padaria e depois lista sem -n, ela está olhando para outro lugar. Não é falha do comando: é o comando fazendo exatamente o que foi pedido.

E há duas fontes de ajuda que dispensam esta página no dia a dia: kubectl VERBO --help mostra todas as flags daquele verbo, e kubectl explain CAMPO descreve um campo de manifesto. As duas respondem na hora e não dependem de internet — são a resposta oficial quando você esquece um nome que não está aqui.

2. O essencial em 10 linhas

  • A forma é kubectl VERBO TIPO [NOME] [flags] — nesta ordem.
  • Sem nome, o comando lista; com nome, mostra um objeto.
  • Os tipos têm apelidos: po, deploy, svc, ns, no, cm, pvc.
  • -n NAMESPACE escolhe o namespace; -A olha todos de uma vez.
  • -o wide mostra mais colunas; -o yaml mostra o objeto inteiro; -o name mostra só tipo/nome.
  • -l app=cardapio filtra por etiqueta; --show-labels mostra as etiquetas.
  • describe conta a história (configuração + eventos); logs mostra a saída do programa.
  • apply -f arquivo.yaml cria ou atualiza; delete apaga por nome ou por arquivo.
  • Toda saída é texto puro: dá para colar num script, num e-mail, num chamado.
  • Erro do kubectl quase sempre é erro de digitação no tipo ou no nome — leia a mensagem até o fim.

A ordem é rígida, mas as flags não: kubectl get pods -n padaria -o wide e kubectl get -n padaria pods -o wide fazem a mesma coisa. O que não pode mudar de lugar é o verbo, que vem sempre logo depois de kubectl. Se você digitar as palavras na ordem “de frase” — kubectl pods get — o comando entende pods como verbo e reclama.

Duas flags desta lista merecem virar reflexo: -n quando o objeto não está em default, e -o wide quando você precisa saber onde o pod caiu. Sem elas, a tabela responde “o quê”, mas não responde “onde” — e “onde” é a pergunta de metade dos problemas de agendamento.

3. Anatomia de um comando

Cinco peças, sempre na mesma ordem. A maioria dos comandos usa três delas; as outras duas entram quando você precisa de outro namespace ou de outra saída.

verbo
O que você quer fazer: get (ver), describe (entender), apply (entregar), delete (apagar). Vem sempre em primeiro lugar, depois de kubectl.
tipo
O recurso: pod, deployment, service. Aceita singular, plural e apelido — pod, pods e po valem o mesmo. Errar aqui é o tropeço número um.
nome
Opcional. Com nome, o comando age sobre um objeto só: kubectl get pod cardapio. Sem nome, age sobre a lista inteira do namespace.
-n / -A
Onde procurar. -n padaria olha um namespace; -A olha todos. Sem os dois, o comando usa o namespace do seu contexto — normalmente default.
-o
Como imprimir: -o wide, -o yaml, -o name. Sem -o, a tabela padrão.
-l
Filtro por etiqueta, para ver só um grupo: -l app=cardapio. Pode repetir com vírgula: -l app=cardapio,tier=web.

Lendo em voz alta: kubectl get pods -n padaria -o wide é “kubectl, pegue os pods do namespace padaria e mostre com IP e nó”. Já kubectl logs cardapio -c web é “kubectl, mostre os logs do pod cardapio, do container chamado web” — o -c só faz sentido quando o pod tem mais de um container, e é o motivo de o comando reclamar de ambiguidade quando você esquece dele.

Duas observações que economizam tentativa e erro. Primeiro: kubectl delete aceita tipo/nome colado (kubectl delete pod/cardapio) ou separado (kubectl delete pod cardapio); os dois funcionam e o colado é o formato que o -o name imprime. Segundo: kubectl apply -f - lê o manifesto da entrada padrão, o que permite colar um YAML direto no terminal — útil para testar um objeto de três linhas antes de salvar o arquivo.

A transcrição abaixo é de um cluster de verdade e mostra as três saídas que mais economizam tempo:

$ kubectl get pods -o wide
NAME                        READY   STATUS    RESTARTS   AGE   IP           NODE
cardapio-6d9c8f7b5b-4xj2q   1/1     Running   0          3m    10.244.1.9   guia-worker
cardapio-6d9c8f7b5b-9p7wl   1/1     Running   0          3m    10.244.2.7   guia-worker2

$ kubectl get pods -o name
pod/cardapio-6d9c8f7b5b-4xj2q
pod/cardapio-6d9c8f7b5b-9p7wl

$ kubectl get pods --show-labels
NAME                        READY   STATUS    RESTARTS   AGE   LABELS
cardapio-6d9c8f7b5b-4xj2q   1/1     Running   0          3m    app=cardapio,pod-template-hash=6d9c8f7b5b

Antes de decorar qualquer flag, vale aprender a ler as quatro colunas da tabela padrão, porque é nelas que o problema aparece primeiro. READY compara containers prontos com containers existentes: 1/1 é saudável, 0/1 é “subiu, mas não está pronto”. STATUS é a fase: Running, Pending, Succeeded, Failed. RESTARTS conta quantas vezes o container reiniciou — um número que sobe é programa morrendo. AGE é o tempo de vida; idade pequena demais toda vez que você olha quer dizer que algo está recriando o pod.

Quando a tabela não basta, a ordem é sempre a mesma: get para ver, describe para entender, logs para ouvir o programa. O describe traz os eventos no fim — é lá que está o motivo de um Pending —, e o logs traz a saída do processo, que é onde está o motivo de um CrashLoopBackOff. Trocar a ordem (começar pelo log de um pod que nem subiu) só faz perder tempo.

Repare no -o name: ele imprime pod/nome, e esse formato serve de alvo para o próximo comando — kubectl describe $(kubectl get pods -o name | head -1) é um jeito comum de descrever o primeiro pod da lista sem digitar o nome. E repare no --show-labels: é ele que revela o pod-template-hash, a etiqueta que o Deployment usa para saber de qual versão cada pod veio.

5. As flags que salvam

Estas são as flags que aparecem em quase toda sessão. A última coluna é a mais importante desta página: ela diz o que a caixa deste guia consegue reproduzir e o que você só vê num cluster de verdade.

-nescolhe o namespacekubectl get pods -n kube-systemfunciona

-o widemais colunas (IP, nó, seletor)kubectl get nodes -o widefunciona
-o yamlo objeto inteirokubectl get svc cardapio -o yamlfunciona
-o namesó tipo/nomekubectl get deploy -o namefunciona

--field-selectorfiltra por campo do objetokubectl get pods --field-selector status.phase=Runningnão: transcrição
--sort-byordena por um campokubectl get pods --sort-by=.metadata.namenão: transcrição
--no-headersesconde o cabeçalho da tabelakubectl get pods --no-headersnão: transcrição

As flags aceitam três grafias e as três funcionam: -o wide, -o=wide e --output wide. A forma curta é para o dia a dia; a longa é para script, porque ela diz o que faz sem consulta. O mesmo vale para -n (--namespace) e -l (--selector).

Três dessas flags merecem uma frase a mais, porque o nome não entrega o que elas fazem. --dry-run=client monta o objeto no seu computador e valida o formato sem mandar nada ao cluster: é o jeito de conferir um manifesto antes de aplicar. --field-selector filtra por campo do objeto (status, nome), enquanto -l filtra por etiqueta — os dois parecem iguais e não são. E --no-headers existe para o dia em que a saída vai alimentar um script: sem a primeira linha, sobra só dado.

6. Erros e mensagens

As mensagens do kubectl são curtas e literais. Quase todas dizem exatamente qual palavra está errada; o trabalho é ler até o fim em vez de olhar só a primeira linha.

MensagemO que significaO que fazer
Error from server (NotFound): pods "x" not foundo tipo existe, mas não há objeto com esse nomeconfira o nome e o namespace (-n)
error: the server doesn't have a resource type "podss"o tipo está escrito erradouse kubectl api-resources para ver a lista
error: You must specify the type of resource to get.faltou o tipokubectl get pods, não kubectl get

error: must specify one of -f and -ko apply precisa de um arquivokubectl apply -f arquivo.yaml

error: Metrics API not availablenão há servidor de métricas no clusteré o assunto de HPA e métricas

Num cluster de verdade, uma sessão de erros de digitação tem esta cara — e note que o kubectl nunca se confunde sobre o que está errado:

$ kubectl get pod cardapio
Error from server (NotFound): pods "cardapio" not found

$ kubectl get podss
error: the server doesn't have a resource type "podss"

$ kubectl get
error: You must specify the type of resource to get. Use "kubectl api-resources" for a complete list of supported resources.

$ kubectl gt pods
error: unknown command "gt" for "kubectl"

$ kubectl apply
error: must specify one of -f and -k

As mensagens caem em três famílias, e reconhecer a família economiza diagnóstico. A primeira é nome: NotFound e No resources found dizem que o comando funcionou e não achou o objeto — o problema está no nome ou no namespace. A segunda é tipo: doesn't have a resource type e unknown command dizem que você escreveu uma palavra que o kubectl não conhece — o problema está na digitação. A terceira é conteúdo: The Pod "x" is invalid: … diz que o objeto chegou ao servidor e foi recusado por um campo — o problema está no manifesto, e o campo está citado na mensagem com o caminho completo (spec.containers[0].image, por exemplo).

Há ainda uma quarta família que não aparece nas caixas deste guia: Error from server (Forbidden). Ela não fala de nome, tipo nem conteúdo — fala de permissão, e é assunto de RBAC. Se você vir essa palavra, o manifesto está certo e o seu usuário é que não pode fazer aquilo.

A última linha é a que mais aparece em tutorial copiado: kubectl apply sem -f não faz nada, porque o comando precisa saber qual arquivo. E o NotFound da primeira é o erro mais mal interpretado do Kubernetes: ele não quer dizer que o cluster está quebrado, quer dizer que aquele nome não existe naquele namespace.

7. Duas coisas para praticar agora

A primeira caixa monta o mínimo que funciona: um pod e a tabela com IP e nó. A segunda é o conserto rápido mais comum — o filtro de etiqueta que não acha nada porque a etiqueta tem outro nome.

Crie o pod cardapio com a imagem cardapio:1.0 e mostre a tabela com IP e nó. O painel tem de trazer o endereço 10.244… na saída.

kubectl run cardapio --image=nginx:1.29
kubectl get pods
ana@notebook:~$ kubectl run cardapio --image=nginx:1.29
pod/cardapio created

ana@notebook:~$ kubectl get pods
NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          2m

kubectl run cardapio --image=cardapio:1.0
kubectl get pods -o wide

O filtro -l app=cardapio não acha o pod criado com kubectl run. Descubra a etiqueta de verdade com --show-labels e filtre por ela.

kubectl run cardapio --image=cardapio:1.0
kubectl get pods -l app=cardapio
ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0
pod/cardapio created

ana@notebook:~$ kubectl get pods -l app=cardapio
No resources found in default namespace.

kubectl run cardapio --image=cardapio:1.0
kubectl get pods --show-labels
kubectl get pods -l run=cardapio

Se a caixa mostrar uma saída diferente da que você esperava, compare com a tabela de erros antes de mexer no comando: No resources found quase sempre é etiqueta errada no filtro, e NotFound quase sempre é nome trocado. As duas mensagens são o painel sendo honesto, não o painel quebrado.

Nas duas caixas, o painel responde como o kubectl de um cluster de três nós. O que ele não faz está na coluna “no painel” da tabela de flags: --dry-run, --field-selector, --sort-by e --no-headers aparecem aqui só como transcrição, para você reconhecer a saída quando encontrar num tutorial.

8. Para ir além

Cada verbo tem uma aula própria, com o contexto e os tropeços de quem está começando:

  • O básico do kubectl — a primeira sessão, do zero.
  • kubectl get — listar, filtrar e ler a tabela.
  • kubectl describe — o detalhe e os eventos.
  • kubectl logs — a saída do programa, com -f e --previous.
  • Saída do kubectl — -o name, -o wide, -o yaml e o código de saída.
  • kubectl delete — apagar sem levar o cluster junto.
  • apply e dry-run — o ensaio antes do apply.
  • kubectl exec — entrar no container.
  • Namespaces — por que -n muda tudo.

Resumo

kubectl VERBO TIPO [NOME] [flags]. Sem nome, lista; com nome, um objeto. Os apelidos (po, deploy, svc) economizam dedo e são aceitos em qualquer verbo. -n escolhe o namespace e -A olha todos; -o wide acrescenta IP e nó; -o yaml mostra o objeto inteiro; -o name imprime tipo/nome, que serve de alvo para o próximo comando.

-l filtra por etiqueta e --show-labels revela as etiquetas — juntos, resolvem o clássico “o filtro não acha nada”. --dry-run=client ensaia sem enviar e --field-selector filtra por campo do objeto, não por etiqueta. E quando o comando reclama, leia a mensagem até o fim: ela diz se o problema é o tipo (doesn't have a resource type), o nome (NotFound), o arquivo (must specify one of -f and -k) ou só uma lista vazia (No resources found).
