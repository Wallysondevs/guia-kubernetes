Namespaces

A Ana tem dois cardápios: o de verdade, que o cliente vê, e um de teste, onde ela experimenta preço novo e imagem nova antes de publicar. Os dois se chamam cardapio. No cluster, isso seria briga — dois objetos com o mesmo nome no mesmo lugar não cabem. A solução não é inventar cardapio-teste-v2: é separar os dois em pastas. Essas pastas existem, têm nome, e a Ana já usou uma delas em quase toda aula sem perceber. São os namespaces.

Você vai aprender
  • O que é um namespace e o que ele realmente separa.
  • Quais namespaces já existem em todo cluster e para que serve cada um.
  • Como criar um namespace, por comando e por manifesto.
  • Por que criar um objeto em namespace inexistente dá erro.
  • O mesmo nome em dois namespaces: o que muda e o que não muda.
  • O que é do namespace e o que é do cluster inteiro.
  • Quando vale criar namespace e quando ele só atrapalha.

1. A cena: dois cardápios, um nome só

A Ana aplicou o manifesto do cardápio de teste no cluster e o site saiu do ar por alguns minutos. O Deployment de teste tinha o mesmo nome do de produção, e o apply não criou um segundo: ele atualizou o que já existia. A imagem de teste entrou no lugar da imagem boa, as réplicas foram trocadas e o cliente viu a versão que ela estava experimentando.

O susto tem três lições embutidas. A primeira: nome é único dentro de um namespace, e o apply procura por nome. A segunda: “atualizar” é o comportamento correto do apply — ele existe para isso. A terceira: o cluster tem uma forma de separar dois mundos que não depende de inventar nomes, e é ela que a Ana vai usar dali em diante. Em vez de cardapio e cardapio-teste, ela passa a ter cardapio em producao e cardapio em teste.

Se o cluster é uma pasta cheia de arquivos, como dizia a aula de get, o namespace é uma subpasta. Você continua com um cluster só, um kubectl só, um nó só — e cada grupo de objetos mora na sua subpasta, com nomes independentes.

2. O que um namespace separa

A separação mais visível é de nomes: dois pods chamados cardapio convivem sem problema desde que estejam em namespaces diferentes, exatamente como dois arquivos index.html em pastas diferentes. Comandos como get, describe, logs, exec e delete obedecem a esse recorte: sem -n, olham o default.

A segunda separação é de permissão e de cota. Em cluster de time, cada namespace pode ter suas próprias regras de quem pode fazer o quê, e um limite de quanta CPU e memória o conjunto pode pedir. É isso que impede o ambiente de teste de derrubar produção: mesmo com regras separadas, o nó é o mesmo, e a cota é o que garante a fatia de cada um.

O que o namespace não separa é rede. Por padrão, um pod do namespace teste alcança um pod do producao pelo nome do serviço, sem pedir licença. Isolar tráfego é trabalho de NetworkPolicy, assunto mais adiante. Confundir as duas coisas é o erro conceitual mais comum do tema: namespace organiza e limita, mas não é firewall.

namespace
Divisão lógica de nomes dentro do cluster. Todo objeto de namespace precisa morar em um.
default
O namespace usado quando você não diz nada. É onde a maioria dos testes acaba morando.
kube-system
Onde o próprio Kubernetes roda: DNS, controladores, proxies. Não é lugar para o seu site.
escopo
Se o objeto vive dentro de um namespace (namespaced) ou é do cluster inteiro, como nó e namespace.
quota
O limite de recursos somados que um namespace pode pedir. Separar por namespace é o que torna a cota possível.

3. Os namespaces que já existem

Todo cluster nasce com pelo menos dois. O primeiro é o default, onde tudo cai quando você não escolhe nada — é onde os pods das aulas anteriores moraram. O segundo é o kube-system, onde o próprio Kubernetes vive: o DNS que resolve nomes de serviço, os controladores, o proxy de rede. Mexer nele é mexer no encanamento do prédio.

A caixa só lista pods. Liste os namespaces para ver o default e o kube-system — o comando é kubectl get namespaces.

kubectl get pods
ana@notebook:~$ kubectl get pods
No resources found in default namespace.

kubectl get namespaces

A tabela tem duas colunas: NAME e AGE. O AGE maior costuma ser do default e do kube-system, porque nasceram com o cluster. Os outros, criados depois, mostram a idade da criação — e essa é uma informação útil: namespace com idade de três minutos é alguém testando alguma coisa agora.

Em clusters de nuvem aparecem também kube-public e kube-node-lease. O primeiro guarda informação que pode ser lida por qualquer um, o segundo guarda os batimentos dos nós. Nos dois casos, a regra prática é a mesma do kube-system: olhe, entenda, não mexa. O lugar do site da padaria é um namespace seu, com nome que diga o que é.

4. Criar um namespace

Criar é uma linha: kubectl create namespace padaria. A resposta é namespace/padaria created, no mesmo formato de sempre. Se já existir, o cluster recusa com AlreadyExists — e isso é bom, porque o comando não sobrescreve nada por acidente.

O erro que aparece logo depois é o mais instrutivo do tema: criar um objeto num namespace que não existe. O cluster não cria o namespace por você; ele recusa o objeto inteiro.

O comando tenta criar um pod no namespace teste, que ainda não existe. Primeiro crie o namespace e depois rode o pod de novo, terminando com a listagem no namespace certo.

kubectl run cardapio --image=cardapio:1.0 -n teste
ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0 -n teste
Error from server (NotFound): error when creating "STDIN": namespaces "teste" not found

kubectl create namespace teste
kubectl run cardapio --image=cardapio:1.0 -n teste
kubectl get pods -n teste

A mensagem do erro merece ser lida devagar: error when creating "STDIN": namespaces "teste" not found. O STDIN aparece porque o objeto veio de um comando, não de um arquivo — no dia em que você usar apply -f, ali vai estar o nome do arquivo. O resto é direto: o namespace teste não foi encontrado, e nada foi criado. Nenhum pod ficou pela metade.

O mesmo namespace também pode nascer de um manifesto, e é o que você faz quando quer guardar tudo no repositório:

apiVersion: v1
kind: Namespace
metadata:
  name: padaria

Vale conhecer a validação, porque ela aparece em qualquer objeto: nome de namespace segue a mesma regra de nome de pod — minúsculas, números e hífen, começando e terminando por letra ou número. Um manifesto com name: Padaria é recusado com a frase comprida que você já viu na aula de erro de nome: “a lowercase RFC 1123 label must consist of lower case alphanumeric characters or '-'…”. O conserto é trocar uma letra.

5. O mesmo nome em dois namespaces

Aqui está o motivo de o tema existir. Dois pods com o mesmo nome, em namespaces diferentes, convivem sem conflito — e cada comando enxerga só o seu. A transcrição abaixo é de uma sessão real no cluster de teste, com os dois “cardápios” lado a lado:

ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0 -n padaria
pod/cardapio created
ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0 -n teste
pod/cardapio created
ana@notebook:~$ kubectl get pods -n padaria
NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          3m
ana@notebook:~$ kubectl get pods -n teste
NAME       READY   STATUS    RESTARTS   AGE
cardapio   1/1     Running   0          1m

Repare que o pod/cardapio created apareceu duas vezes, sem erro de duplicidade. Se os dois estivessem no mesmo namespace, o segundo seria recusado com AlreadyExists. E repare também na consequência para o delete: apagar cardapio em teste não toca no cardapio de padaria. O nome é o mesmo; o objeto não.

Para o Service, o namespace muda até o endereço. Um serviço chamado cardapio no namespace padaria tem o nome completo cardapio.padaria.svc.cluster.local, e é assim que ele é achado de fora do namespace. De dentro do mesmo namespace, basta cardapio. Essa diferença é a origem de metade dos “funciona local e não funciona entre serviços”: a URL estava com o nome curto e o chamador morava em outro namespace.

6. O namespace corrente

Todo comando que fala de objeto por namespace aceita -n nome ou --namespace=nome. Existe ainda um terceiro caminho, que é mudar o padrão do contexto: kubectl config set-context --current --namespace=padaria. A partir daí, todo comando sem -n olha o padaria. É prático e traiçoeiro: o mesmo comando passa a significar outra coisa, e quem lê o histórico não sabe em qual pasta você estava.

A caixa abaixo percorre o caminho inteiro com a flag explícita: dois namespaces, um cardapio em cada, e uma listagem por vez. Repare que o -n aparece em todas as linhas — é ele que escolhe a pasta, e é por isso que o comando funciona igual para quem lê e para quem escreveu.

A caixa começa listando o namespace teste, que ainda não existe. Crie os dois namespaces, suba um cardapio em cada um e liste os dois para ver o mesmo nome convivendo sem conflito.

kubectl get pods -n teste
ana@notebook:~$ kubectl get pods -n teste
No resources found in teste namespace.

kubectl create namespace teste
kubectl create namespace padaria
kubectl run cardapio --image=cardapio:1.0 -n teste
kubectl run cardapio --image=cardapio:1.0 -n padaria
kubectl get pods -n teste
kubectl get pods -n padaria

7. Quando criar um namespace

A divisão mais comum é por ambiente: producao, homolog, teste. Ela resolve o problema da Ana da seção 1 e é o que permite aplicar o mesmo manifesto em lugares diferentes sem editar nome. A segunda é por time ou por projeto, num cluster compartilhado: cada time com sua cota, suas permissões, seu espaço para experimentar sem pisar no vizinho.

Existe também a divisão por cliente, comum em produto que atende várias empresas com a mesma aplicação. Funciona, e tem custo: cada namespace novo é mais um lugar para configurar, monitorar e limpar. Namespace é uma ferramenta de organização, não um botão de “isolar tudo”. Se a separação for de rede, o caminho é NetworkPolicy; se for de máquina, é nó separado; se for de cluster, é outro cluster.

Uma regra prática que evita o exagero: crie namespace quando existir uma fronteira de responsabilidade — quem pode mexer, quanto pode gastar, o que pode apagar sem levar outra coisa junto. Se a única diferença for o nome do objeto, talvez baste uma etiqueta. Etiqueta separa listas; namespace separa mundos.

O teste mais rápido é fazer a pergunta ao contrário: “se eu apagar este namespace inteiro agora, quem chora?”. Se a resposta for “ninguém, é tudo descartável”, ele é um bom namespace de teste. Se a resposta incluir o banco de dados de outra pessoa, o desenho está errado — ou o namespace é grande demais, ou objetos de gente diferente moraram juntos. A tabela abaixo resume as fronteiras que costumam valer a pena e as que costumam virar bagunça.

FronteiraCriar namespace?Por quê

Repare na linha do microsserviço. É tentador dar um namespace a cada serviço — cardapio, precos, pedidos — porque parece organizado. Na prática, os três falam entre si o tempo todo, compartilham o mesmo ConfigMap de ambiente e sobem juntos numa versão. Você ganha nomes curtos e perde a visão de conjunto: um kubectl get pods sem -n passa a mostrar um terço do sistema, e cada investigação começa com uma caçada ao namespace certo.

8. As armadilhas do dia a dia

Quatro coisas mordem quem começa com namespaces. A primeira é esquecer o -n na metade dos comandos: cria num, lista em outro, apaga num terceiro. A cura é colar a flag nos três e, em script, guardar o namespace numa variável. A segunda é criar objeto em namespace inexistente e ler o erro como se fosse do objeto — namespaces "teste" not found é sobre o namespace, não sobre o pod.

A terceira é apagar um namespace sem olhar o que tem dentro. Ele leva tudo: pods, deployments, services, configmaps, secrets, e o disco dos PersistentVolumeClaim que estiverem lá. Não há confirmação nem lista de filhos — o comando responde namespace/teste deleted e o estrago já aconteceu. A quarta é usar o kube-system como se fosse o default: qualquer coisa que você quebrar ali pode levar o DNS do cluster junto, e aí nada resolve nada.

ana@notebook:~$ kubectl run cardapio --image=cardapio:1.0 -n teste
Error from server (NotFound): error when creating "STDIN": namespaces "teste" not found

Essa frase é a companheira de quem trabalha com namespace. Ela diz três coisas ao mesmo tempo: o objeto não foi criado, o motivo é o namespace, e o nome exato que faltou está entre aspas no fim. Na dúvida, o comando seguinte é kubectl get namespaces — se o nome não estiver na lista, é isso.

Em script, a defesa é não repetir o nome em cada linha. Guarde o namespace numa variável e passe sempre ela: NS=padaria e depois kubectl get pods -n "$NS", kubectl logs cardapio -n "$NS", kubectl delete pod cardapio -n "$NS". Quando o script roda em outro ambiente, muda uma linha e o resto acompanha. A variável também serve de aviso para quem lê: aquele comando tem um alvo explícito, não está à mercê do contexto de quem o executou. É a diferença entre “apaguei o pod errado” e “apaguei o pod do namespace que o script mandou”.

9. Cenários do dia a dia

Cenário 1: o site que caiu com um apply de teste

O Deployment de teste tinha o mesmo nome do de produção, e o apply atualizou o objeto existente. O conserto foi criar o namespace teste, mudar o metadata.namespace do manifesto de teste e aplicar de novo. Desde então existe um cardapio em producao e um cardapio em teste, e o pior que um teste pode fazer é derrubar o próprio namespace.

Cenário 2: o serviço que não achava o outro

O site chamava http://precos/api e recebia erro de nome não resolvido. O serviço precos existia — em outro namespace. De dentro do mesmo namespace, o nome curto funciona; de fora, é preciso o nome completo precos.producao.svc.cluster.local. O erro não era de rede nem de Service: era de endereço relativo, como um arquivo que você procura na pasta errada.

Cenário 3: a limpeza que levou o banco

Num cluster de homologação, alguém apagou o namespace teste para começar do zero. Levou junto o banco de dados que o time usava para ensaiar migração — porque o banco estava lá dentro. A regra que ficou escrita no README: antes de apagar um namespace, listar o que existe nele, tipo por tipo, e conferir se alguma coisa dali não é descartável.

11. Resumo

Namespace é a divisão lógica do cluster: um lugar com nome onde objetos de mesmo nome convivem sem conflito. Todo cluster nasce com default e kube-system; o primeiro é onde os testes caem quando você não escolhe, o segundo é onde o próprio Kubernetes mora. Criar é kubectl create namespace nome, e criar objeto em namespace inexistente dá namespaces "x" not found.

Comandos de objeto aceitam -n; o default vale quando você não diz nada. O nome do serviço muda conforme quem pergunta: curto dentro do namespace, completo (servico.namespace.svc.cluster.local) fora dele. E nem tudo vive em namespace: nó, volume persistente e o próprio namespace são do cluster inteiro. Namespace organiza nomes, permissões e cotas — não isola rede, e não substitui pensar antes de apagar.

Para lembrar
  • Namespace = subpasta do cluster; nomes iguais convivem em namespaces diferentes.
  • default é o padrão; kube-system é do Kubernetes — não mexa.
  • kubectl create namespace padaria cria; repetir dá AlreadyExists.
  • Objeto em namespace inexistente: namespaces "teste" not found, nada é criado.
  • -n escolhe o namespace; sem ele, é sempre default.
  • Nó, volume persistente e namespace são do cluster, não do namespace.
  • Apagar namespace leva tudo o que está dentro — sem confirmação.
